# V1d24b（Issue #380）: リースの答えのない要求の一覧が満ちたときに、効く `jti` を残す

## Grill の記録

Issue #380 のコメント「V1d24b の Grill」（2026-11-22）と「決定（持ち主、2026-11-27、すべて推奨案）: 24b-1 の測りのあとの聞き直し」と、この行の作業のあとの問 24b-5 への答えのコメント（2026-11-27）に、持ち主の答えがある。2026-11-22 の 24b-1 は、測る前の仮の答えだった。測った結果で前提が変わったので、2026-11-27 に聞き直し、24b-3 と 24b-4 が加わった。設計の本文（`../design.ja.md`）で変えたのは、§10.4 の手順 2、§8.6 の表の `retry` の行、§12.6.2（送る前に失敗した要求の見分けに、プロキシのトンネルを足した）、§12.7.3、§12.7.7 と、§20.7 と §22 の V1d24b の行である。

### 測った事実

- Grill の事実調べ（Issue #380 の 2026-11-27 のコメント。実の `elm-server` をテストのプロセスの中で立て、偽の時計を使った。SDK 10.0.404）: 答えを受け取れない更新が 17 回続くと、効いている `jti` が一覧から押し出され、18 回目の更新が `ELM_CLONE_DETECTED` で `Lost` になった（`deny`。`flag` では偽の複製の記録が残る）。16 回までは起きなかった。再試行は 15 秒、30 秒、そのあとは 60 秒おきなので、17 回の再試行には約 16 分（15 + 30 + 60 × 15 = 945 秒）かかる。更新はリースの期間の 3 分の 1 で始まり、残りの 3 分の 2 のうちに 17 回目に届くのは、期間がおよそ 24 分を超えるリースだけである。
- コードから読んだこと（`origin/main` の 5a23241）: リースのクライアントは、`HttpRequestException` なら何でも答えのない要求にしていた（`LicenseClient.SendAsync`）。端末から出なかった要求（名前の解決、接続、TLS、プロキシのトンネルの失敗）の `jti` も一覧に入り、取得と借り出しでは返却を送っていた。例外はピンの不一致だけだった。有効化（`ActivationClient.SendAsync`）は、その 4 つを答えのない要求にしていなかった。
- この行で読んだ .NET の源（dotnet/runtime の release/10.0、`src/libraries/System.Net.Http/src/System/Net/Http/SocketsHttpHandler/`）:
  - `ConnectHelper.cs`: `CreateWrappedException` は、接続の失敗を `ConnectionError` に、`SocketError.HostNotFound` と `TryAgain` を `NameResolutionError` に、`AuthenticationException` を `SecureConnectionError` にする。`EstablishSslConnectionAsync` は、TLS の失敗を `SecureConnectionError` で包む。ピンを確かめる `RemoteCertificateValidationCallback` が `false` を返したときも、ここを通る。
  - `ConnectionPool/HttpConnectionPool.cs` の `EstablishProxyTunnelAsync`（HTTP のプロキシ）と `EstablishSocksTunnel`（SOCKS のプロキシ）は `ProxyTunnelError` を付け、`ConnectionPool/HttpConnectionPool.Http3.cs` は接続のときの ALPN の失敗に `ConnectionError` を付ける。
  - `HttpConnection.cs`: つながったあとの `IOException` は `Unknown` か、`HttpIOException` の値（`ResponseEnded`、`InvalidResponse` など）になる。別の接続で送り直してよい印（`_canRetry`）は、本文がないときか、`Expect: 100-continue` で本文を送る前にだけ付く（`request.Content is null || allowExpect100ToContinue is not null`）。このクライアントは `ExpectContinue` を設定せず、要求の版は既定の HTTP/1.1（`HttpVersionPolicy.RequestVersionOrLower`）のままなので、`HttpConnectionPool.cs` の HTTP/2 を選ぶ条件に当たらず、いつも HTTP/1.1 で送る。本文のある要求が一度出たあとで、送り直しの接続の失敗によって「出なかった」の値になることはない。

- 24b-2: 上限は 16 のまま（§8.6 と、両方のサーバーの約束）。
- 24b-3（2026-11-27）: 端末から出なかった要求（`HttpRequestError` が `NameResolutionError`、`ConnectionError`、`SecureConnectionError`、`ProxyTunnelError`）は、答えのない要求にしない。同じ見分けを使う取得と借り出しの返却（§12.7.7）も、出なかったものには送らない。有効化と §10.4 の手順 2 にそろえる。クライアントが送り直す返却の一覧（`_owedReleases`）の、16 件で古いものを落とす扱いは、V1d5b の問 5b-2 で受け入れたもので、変えない。

### こちらが決めたこと

- 見分けは `BoundedAnswer.NeverSent` の 1 か所にし、`LicenseClient` と `ActivationClient` が同じものを使う。
- ピンの不一致の項（`!_pinFailed`）は、答えのない要求の判定から外した。ピンの確かめは TLS のハンドシェイクの中で失敗し、`SecureConnectionError` になるので、`NeverSent` が同じ要求をすでに除く。重ねて確かめると、変異が生き残る形になる（`testing.mdc`）。
- 誤りの文（「The server cannot be reached: …」）は変えない。有効化は出なかった要求と出た要求で文を分けているが、リースの文を変えると、アプリと利用者の文書が読む文が変わるので、この行では分けない。

### 同じ種類を探した範囲と、行の外で見つけたこと

- 答えのない要求を見分ける所を、`src/` で `Unanswered` と `HttpRequestError` で探した。`LicenseClient.SendAsync`（更新、取得、借り出し、返却、回収が通る）と `ActivationClient.SendAsync` の 2 つだけで、どちらも `NeverSent` を使う。`elm` の `OidcHttp` と管理の要求は、答えのない要求の一覧を持たない。
- 行の外で見つけたこと: サーバーに届かなかったのに、答えのない要求として数える要求がある。つなぐあいだに 30 秒（§12.1）が切れた要求（Linux の tcp(7) の `tcp_syn_retries` は既定で 6 で、「retrying for up to approximately 127 seconds」とある。答えのない宛先への接続は、30 秒より長く待つ）と、出たかどうかわからない切断である。これが先に 16 件たまり、そのあとサーバーに届いた要求の答えを受け取れなかったときは、効く `jti` が一覧に入らず、次の再試行は複製と判定される。古いものを落とす形なら、この順では効く `jti` が残っていた。持ち主の答えは上の 24b-5（行 V1d24e が直す）。

## 退けた案

- **決定:** 一覧が 16 件になったら古いものを残し、17 件目からは足さずに再試行を続ける（24b-1）。
- **理由:** 効く `jti` は、サーバーに届いた最初の要求のもので、一覧の古いほうにある。測ると、古いものを落とす形では、答えを 17 回続けて受け取れないと 18 回目が複製になった。
- **却下した案:** 送るのをやめてリースを `Lost` にする（戻れたリースを失う）。今のまま古いものを落とす（効く `jti` を押し出す）。

- **決定:** 上限は 16 のまま（24b-2）。
- **理由:** §8.6 と、`elm-server` と `elm-service` の約束の数で、変えると両方のサーバーと古いクライアントの組み合わせが変わる。
- **却下した案:** 上限を増やす。

- **決定:** 端末から出なかった要求は、答えのない要求にせず、取得と借り出しの返却も送らない（24b-3）。
- **理由:** サーバーはその要求を受け取っていない。一覧に入れると、効く `jti` の入る場所を使い、16 件の上限を早く埋める。有効化と §10.4 の手順 2 は、もとからこの見分けである。
- **却下した案:** 今のまま、`HttpRequestException` をすべて答えのない要求にする。

- **決定:** 接続ができる前に打ち切りで終わった要求を、出なかった要求として見分けるかは、新しい行 V1d24e（Issue #498）で決めて直す（24b-5 の案 A）。
- **理由:** 攻撃者のいない、宛先が答えない不通が 16 回続いたあとに答えをなくすと、リースが複製と判定される。見分けを広げれば、この道を閉じられる。
- **却下した案:** B: §5.4 に受け入れとして書く（起きればリースを複製として失う）。C: 何もしない（設計は起きることを書くが、受け入れたかが決まらない）。
