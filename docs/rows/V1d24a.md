# V1d24a（Issue #364）: 残る一時ファイルと、Windows で読み手が開いているファイルの削除と移動

## Grill の記録

Issue #364 のコメント「V1d24a の Grill」（2026-11-22、問 24a-1〜24a-5）と「V1d24a の追加の答え」（同じ日、実装の前の事実調べのあと）に、持ち主の答えがある。どれも推奨案である。設計の本文（`../design.ja.md`）で変えたのは、§12.6.2（読み手の共有、一時ファイルの作り方、残った一時ファイルの掃除、待ちの時計）、§12.7.4（返した借り出し）、§13.5（ピン）、§13.7（サーバーライセンスのファイル）、§16（`elm` のログインのファイル）、§5.4 の 2 つの行と、§20.7 と §22 の V1d24a の行である。

### 測った事実

Grill の事実調べ（`origin/main` の c31f7a5、Windows 11 の pwsh、.NET 11.0.0）のあと、同じ head から切ったこの行のブランチで、.NET 10 でもう一度測った。測ったのは、スクラッチパッドの小さなコンソールのプログラムで、測ったあと消した。

- Windows 11 build 26300、.NET 10.0.14。読み手が開いているあいだの、そのファイルの操作:

| 読み手の共有 | `File.Delete` | `File.Move`（そのファイルを別の名前へ） | `File.Move(<一時ファイル>, <そのファイル>, overwrite: true)` |
| --- | --- | --- | --- |
| `Read`（`File.ReadAllBytes` の形） | `IOException` 0x80070020 | `IOException` 0x80070020 | `UnauthorizedAccessException` 0x80070005 |
| `ReadWrite` | `IOException` 0x80070020 | `IOException` 0x80070020 | `UnauthorizedAccessException` 0x80070005 |
| `ReadWrite \| Delete` | 通る | 通る | `UnauthorizedAccessException` 0x80070005 |
| `Read \| Delete` | 通る | 通る | `UnauthorizedAccessException` 0x80070005 |

  削除が通ったとき、名前は、読み手が開いたままでも、すぐになくなった（`File.Exists` が `false`）。開いているファイルの上への置き換えは、読み手の共有によらず断られる。これは V1d2a の測定と同じで、§12.6.2 の「置き換えのやり直し」が扱う。
- 書き手が一時ファイルを `FileMode.CreateNew`、`FileAccess.Write`、`FileShare.Read | FileShare.Delete` で開いたまま持つとき（Windows は上と同じ。Linux は wslc のコンテナーの `mcr.microsoft.com/dotnet/sdk:10.0`、Ubuntu 24.04、.NET 10.0.14）:
  - 掃除の側が `FileShare.None` で開くと、Windows は `IOException` 0x80070020、Linux は `IOException` 0x0B（`EWOULDBLOCK`）で断られる。`FileAccess.Read` でも `ReadWrite` でも同じ。
  - 書き手は、持ったまま一時ファイルを本番のパスへ移せる（どちらの OS も）。
  - 移したあと、書き手が閉じるまで: `FileShare.ReadWrite | FileShare.Delete` の読み手は開ける。`File.ReadAllBytes`（`FileShare.Read`）は、Windows では `IOException` 0x80070020 で断られ、Linux では開ける。書き手が `FileShare.Delete` だけを許すと、Windows では `ReadWrite | Delete` の読み手も断られた（書き手の共有に `Read` がないため）。
  - だれも開いていない一時ファイル（書き手が閉じたもの、残ったもの）は、`FileShare.None` で開けて、消せる。
- Linux と macOS の、.NET のファイルのロック: dotnet/runtime の release/10.0 の `src/libraries/System.Private.CoreLib/src/Microsoft/Win32/SafeHandles/SafeFileHandle.Unix.cs` を読んだ。`Init` は、`FileShare.None` なら `flock(LOCK_EX | LOCK_NB)`、ほかの共有なら `flock(LOCK_SH | LOCK_NB)` を取り、`EWOULDBLOCK` だけを共有の違反の `IOException` にする。`CanLockTheFile` は、`DOTNET_SYSTEM_IO_DISABLEFILELOCKING` のときロックを取らず、書くために開く `LOCK_SH` は、ファイルシステムが NFS、SMB、SMB2、CIFS のとき、または種類が分からないとき取らない。ロックは `open` のあとに取るので、作ってからロックを取るまでのあいだは、ロックがない（同じファイルの注記「not atomic with file opening」）。
- コードから読んだこと（c31f7a5）:
  - 返した借り出しの削除（`LicenseClient.DeleteBorrow`）が断られると、ファイルは期限まで `GetBorrowedLeases` に出続けた。消すのは期限の切れたファイルだけで、`DeleteBorrow` の注記「deleted by the next GetBorrowedLeases」は誤りだった。
  - 自分の読み手のうち `FileShare.Delete` を許していたのは、`activation.json`（`ActivationStore.Read`）と `elm-service` の利用ログの取り出しだけだった。借り出し、ピン、インストール鍵、秘密のファイル、サーバーライセンスのファイルは `File.ReadAllBytes`（`FileShare.Read`）、署名つきのログの読み手（`LogVerifier` と `SignedLog`）は `FileShare.ReadWrite` で開いていた。
  - サーバーライセンスのファイルには、`elm-server` の自動の更新（`ActivationClient` の中、端末のロックを持つあいだ）と、`elm server activate`、`refresh`、`import`（どれも `ServerLicenseCommands.Kept` から、`ActivationClient` を閉じたあと）の書き手があり、共通のロックがない。ピンと借り出しにも、プロセスをまたぐロックはない。`activation.json` は端末のロック、`elm` のログインのファイルはログインのロックの中で書く。

### 持ち主が決めたこと

- 24a-1: 自分のコードの読み手を `FileShare.ReadWrite | FileShare.Delete` で開く。返した借り出しの ID はメモリーにも覚え、削除が残っても表示しない。範囲は、追加の答えで、サーバーライセンスの読み手（`ElmServer.TryReadLicense` と `elm server deactivate` の `RemoveIfKept`）と秘密の読み手（`ProtectedFiles.TryReadSecret`）に広げた。
- 返した借り出し（追加の答え）: 覚えた ID は、次の `GetBorrowedLeases` と `SaveBorrow` で削除をやり直す。再起動でメモリーは消えるので、残ったファイルは期限まで有効な借り出しとして出る。これを §5.4 に書く。
- 24a-2: 書く前か一覧を読むときに、同じフォルダーで自分の名前の形に合う古い一時ファイルを消す。
  - 24a-2a（追加の答え）: 古いかの見分け。書き手は一時ファイルを作ってから置き終えるまで、`FileShare.Read | FileShare.Delete` で開いたまま持つ。掃除は、名前の形に合うファイルのうち `FileShare.None` で開けたものだけを消す。`flock` が効かない所と、Unix で作ってからロックを取るまでの短いあいだは、書いている最中の一時ファイルを消しうる。そのとき書き手は「書けない」で終わり、書きかけのファイルは置かれない。これを §5.4 に受け入れとして書く。
  - 24a-2b（追加の答え）: 掃除の対象は、`activation.json`、サーバーライセンスのファイル、借り出し（一覧のときと保存の前）、ピン、`elm` のログインのファイルの 5 つ。`elm` の `--force` の出力と `elm-service backup` の一時ファイルは掃除しない。
- 24a-3: 決まった名前の一時ファイル（`ActivationStore`、`LicenseFiles`）を乱数の名前にし、残ったものは 24a-2 の掃除で消す。
- 24a-4: 置き換えの待ちは渡された時計で数えることを、`ActivationClientOptions.TimeProvider` と `LicenseClientOptions.TimeProvider` の XML ドキュメントと、利用者の文書の `reference/dotnet-api.md`（英語と日本語）に書く。
- 24a-5: `src/` のファイルの削除と移動をすべて 1 つずつ判断し、直すか直さない理由をここに書く（下の「削除と移動の判断」）。`FileClockGuard` は V1d24d（Issue #444）に回す。
- `InstallationKeyStore.Delete()`（追加の答え。行の外で見つけた点）: XML ドキュメントの「as after a deactivation」を、設計（§12.6、0.89: 解除しても鍵は残す）に合わせて直す。メソッドは残す。

### こちらが決めたこと

- 一時ファイルの名前: `<ファイル>.<16 進の小文字 16 文字>.tmp`（8 バイトの乱数、`RandomNumberGenerator`）を、`activation.json`、サーバーライセンスのファイル、ピン、`elm` のログインのファイルの 4 つで同じ形にした（前は、ピンが小文字、ログインが大文字の 16 進）。借り出しは、前のとおり `<リース ID>.json.tmp`（リース ID は借り出しごとに新しい）。
- 利用者の文書: `reference/formats.md`（サーバーライセンスのファイルの一時ファイルの名前と掃除）と `reference/dotnet-api.md`（2 つの `TimeProvider` の、置き換えの待ち。`GetBorrowedLeases` の、返した借り出し）を、英語と日本語で直す。
- 掃除の手順: フォルダーの中で、名前の形に合うものを探し、それぞれを `FileShare.None` で開く。開けなければ（書き手が持っている、読めない、フォルダーである）残す。開けたら閉じて、`File.Delete` で消す。消せなくても誤りにしない。リンクは開かず、リンクそのものを消す（自分の書き手はリンクを作らない）。ピンと借り出しは、そのフォルダーのすべてのピンと借り出しの一時ファイルが対象で、ほかの 3 つは、そのファイルの一時ファイルだけが対象である。

- 書き手の一時ファイルは、`FileStreamOptions.BufferSize = 0`（バッファーなし）で開く（`FileReplacement.OpenNew` と `ProtectedFiles.TryCreateSecret`）。持ったまま置き換えるので、書き込みの失敗（ディスクがいっぱい）が `Dispose` の書き出しでもう一度投げられると、失敗のあとの削除に届かない。最初の Linux の走らせ（下の「テスト」）で `Writers_DiskFullAfterCreating_DeleteTheNewFile` の `create-new` と `secret` が、バッファーありの形で落ちたので、そうした。
- 自分の読み手の共有は `FileReplacement.ReadShared(path, maxLength)`（`FileReplacement.ShareWithWriters` = `ReadWrite | Delete`）にまとめた。上限を超えれば `null` を返し、呼び出し側は、前の「大きすぎる」と同じに扱う（`RemoveIfKept` は、保存したファイルより長いものを自分のファイルとみなさない）。`ElasticLM.Issuing` の `LogVerifier` と `SignedLog` は、`ElasticLM.Client` を参照しないので、同じ共有をそれぞれに書いた。

### コードの独立レビュー（bb104a7 に対して）と、その直し

扱いは Issue #364 のコメント「PR #475（bb104a7）のコードの独立レビューと、その扱い」にある。

- FIFO の受け入れを取り下げた。持ち主は、同じ種類のすきを Issue #444 の 24d-6a（2026-11-22）で閉じると決めたので、`.cursor/rules/similar-findings.mdc` に従い、ここも閉じた。Linux と macOS の掃除は `FileStream` で開かず、`ElasticLM.Client` の `UnixLeftover`（libc の `open(O_RDONLY | O_NONBLOCK | O_NOFOLLOW | O_CLOEXEC)`、Linux は `statx`、macOS は `fstat`（x64 は `fstat$INODE64`）、`flock(LOCK_EX | LOCK_NB)`、`unlink`、`close`）を呼ぶ。ふつうのファイルでなければ閉じて残し、リンクは開かずにリンクそのものを消す。Windows は前のとおり `FileShare.None` で開く。§5.4 の行と §12.6.2 の「ファイルでないもの」を消した。
- 2 か所: V1d24d（PR #474、ブランチ `fix/444-clock-guard-file`）の `src/ElasticLM.Licensing/UnixLeftover.cs` を、名前空間と冒頭の注記だけ変えて写した（定数、形、ライブラリの名前は同じ）。`ElasticLM.Client` は `ElasticLM.Licensing` を参照するが、`ElasticLM.Licensing` は `InternalsVisibleTo` に `ElasticLM.Client` を持たないので、内部の型を共有できない。共有するには `ElasticLM.Licensing.csproj` に `InternalsVisibleTo` を足すか、型を公開にする必要があり、どちらも V1d24d の PR と、公開の面に触れるので、写した。設計 §12.6.2 に、2 か所を同じに保つと書いた。
- 定数は、Linux の `asm-generic/fcntl.h`（`O_NONBLOCK` 04000、`O_NOFOLLOW` 0400000、`O_CLOEXEC` 02000000）、arm64 の `arch/arm64/include/uapi/asm/fcntl.h`（`O_NOFOLLOW` 0100000）、macOS の `sys/fcntl.h`（0x4、0x100、0x1000000）、`sys/file.h`（`LOCK_EX` 2、`LOCK_NB` 4）、`sys/stat.h`（`S_IFMT` 0xF000、`S_IFREG` 0x8000）、Linux の `struct statx` の `stx_mode`（28 バイト目）、macOS の 64 ビットの i-node の `struct stat` の `st_mode`（4 バイト目）である。V1d24d の値と同じであることを、行ごとに比べた。

## 退けた案

- **決定:** 自分のコードの読み手を `FileShare.ReadWrite | FileShare.Delete` で開く（問 24a-1）。
- **理由:** Windows で、読み手が `Read` か `ReadWrite` で開いているあいだ、削除と移動が `IOException` で断られ、`ReadWrite | Delete` なら通る（測った）。断られる原因を、読み手の側でなくす。
- **却下した案:** 削除にもやり直しを広げる（待つだけで原因が残り、待つあいだスレッドか端末のロックを持つ）。今のまま文書に書く。

- **決定:** 書く前か一覧を読むときに、自分の名前の形に合う古い一時ファイルを消す（問 24a-2）。
- **理由:** 消すことも断られた一時ファイルは、乱数とリース ID の名前では、次の書き込みが同じ名前を作らないので、だれも消さない（V1d24 のレビューの K4）。
- **却下した案:** 名前を固定にする（2 つの書き手が同じ一時ファイルを奪い合う。K7）。受け入れて §12.6.2 に書く。

- **決定:** 古いかは、書き手が置き終えるまで一時ファイルを開いたまま持ち、掃除が `FileShare.None` で開けるかで見分ける（追加の答えの 24a-2a）。
- **理由:** 時計を読まない。書いている最中のほかのプロセスの一時ファイルを消さないので、プロセスをまたぐロックのない書き手（サーバーライセンスのファイル、ピン、借り出し）でも、掃除がほかの書き手を失敗させない。
- **却下した案:** ファイルの更新時刻で判断する（ファイルシステムの時計と `TimeProvider` が混ざり、偽の時計のテストで決まらず、遅い書き手や時計の戻りで書いている最中のものを消しうる）。すべての書き手が取るロックの中でだけ掃除する（サーバーライセンスのファイル、ピン、借り出しにはそのロックがなく、足すと 24a-3 で退けたロックと同じ形になる）。

- **決定:** 掃除するのは、`activation.json`、サーバーライセンスのファイル、借り出し、ピン、`elm` のログインのファイルの一時ファイルである（追加の答えの 24a-2b）。
- **理由:** `--force` の出力と `elm-service backup` の一時ファイルは、利用者か運用者のフォルダーにあり、次の書き込みは別の名前を狙うので、名前の形の掃除が届かない。どちらも失敗のときに一時ファイルを消す。
- **却下した案:** その 2 つも掃除する。

- **決定:** 決まった名前の一時ファイル（`ActivationStore`、`LicenseFiles`）を乱数の名前にする（問 24a-3）。
- **理由:** Unix で 2 つの書き手が同じファイルに同時に書くと、決まった名前では、あとの書き手が先に消して作り直した一時ファイルを、先の書き手の移動が本番のパスに置きうる（K7）。乱数の名前なら、それぞれが自分の書き終えたファイルを置く。
- **却下した案:** `LicenseFiles` にプロセスをまたぐロックを足す。§5.4 に受け入れる。
- **前の決定との違い:** V1d24 の問 24-1（[V1d24.md](./V1d24.md)）は、名前を変えずに先に消して作る形を選び、乱数の名前を「残った一時ファイルを誰も消さなくなる」ことで退けた。V1d24a では、24a-2 の掃除が残った一時ファイルを消すので、その理由はなくなった。V1d24 が直した、先に置かれたリンクやファイルを開かないこと（`CreateNew`）は、乱数の名前でも同じに保つ。

- **決定:** 置き換えの待ちは渡された時計で数えると、2 つの設定の XML ドキュメントと `reference/dotnet-api.md` に書く（問 24a-4）。
- **理由:** 時刻はすべて渡された時計で読む（`.cursor/rules/security.mdc`）。
- **却下した案:** 実時間の 2 秒の上限を足す。

- **決定:** `InstallationKeyStore.Delete()` の XML ドキュメントを設計に合わせて直し、メソッドは残す（追加の答え）。
- **理由:** 解除は鍵を消さない（§12.6、0.89）。
- **却下した案:** メソッドが要るかを別の Issue にする。
