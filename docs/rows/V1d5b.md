# V1d5b（Issue #420）: 取得と借り出しの答えが届かないとき、席がリースの期限まで埋まることを確かめて直す

## Grill の記録

- 測った事実（Issue #420 のコメント「V1d5b の Grill」。`origin/main` 5ce2174、本物の `LicenseClient` と、プロセスの中の `elm-server` と `elm-service`）:
  - 取得の答えが大きすぎるときも、届かないときも、サーバーにはリースが残り、次の取得は新しい席を取った。2 席の機能では、3 回目の取得が `ELM_NO_SEATS` になった。
  - 席はリースの期限まで埋まった。借り出しなら借り出しの期間で、`elm-server` の管理者は借り出しを返せない（§12.7.4）。
  - 取得の本文の `retry` は、どちらのサーバーも読まない。
  - コード: `LicenseClient.AcquireCoreAsync` は、取得の `Reply.Unanswered` を捨てていた（更新は `Lease.AddUnanswered` で一覧に入れる）。`elm-server` の取得は `ElmServer.AcquireAsync` と `LeaseEngine.AcquireCore`、`elm-service` の取得は `ElmService.AcquireInScopeAsync`（`issued_by` は証明の `jti`）。
  - 設計は、中継による喪失だけを T17 で受け入れていて、正当な利用での喪失（通信の切れ、30 秒の打ち切り、大きすぎる答え）は書いていなかった。
- 持ち主が決めたこと（2026-11-14。どれも推奨案 A）:
  - 問 5b-1: クライアントは、答えの届かなかった取得（借り出しを含む）の返却を、その要求の証明の `jti` で名指して送る。サーバーは、その `jti` で出した、同じ鍵のリースだけを消す（記録から戻した借り出しはトークンの `areq`）。知らなければ `204`。
  - 問 5b-2: 送るのは、送ったのに答えがない（通信の失敗、30 秒の打ち切り、アプリの取り消し）、大きすぎる `2xx`、読めないか §12.7.5 の手順 1〜7 を通らない `2xx`、借り出しを保存できないとき。届かなければメモリーに 16 件まで残し（古いものから落とす）、そのサーバーへの次の要求の前と `DisposeAsync` で送り直す。ファイルには書かない。
  - 問 5b-3: 借り出しの返却は早期返却として `BorrowReturnLimit` に数え、同じ規則で断る（§12.7.4、0.40、0.57）。
  - 問 5b-4: `DELETE /v1/leases/requests/{jti}` に証明（`jwk` を持つ）。止めたリースは `409` と `ELM_CLONE_DETECTED`。両方のサーバーで同じで、§12.7.6 の返却の検査の順に合わせる。`jti` は、探す前に要求の ID の形で確かめる。
- こちらが決めたこと（設計 §12.7.7）:
  - 消すのは、一度も更新していない（`seq` が 1）リースだけにした。更新したリースは答えを受け取ったクライアントが持っているので、正しいクライアントがそれを名指すことはない。同じ鍵のほかの持ち手が名指しても、持たれているリースは消えない。
  - `{jti}` の形が外れたら、証明を確かめずに `204` にした（リース ID での返却の、形でない ID と同じ）。
  - 「届いた」の見分け: 256 KiB までの応答が `2xx` か、`429` と `5xx` 以外の状態で返ったとき。`409` の 2 つのコード（`ELM_CLONE_DETECTED`、`ELM_RETURN_NOT_ALLOWED`）はサーバーが決めて断ったので、送り直さない。`429` と `5xx` は、待てば変わりうるので送り直す。本文のない `404` も届いたとみなすのは、このパスを知らないサーバーに送り続けないためである。
  - 送り直しは、1 つが届かなければそこでやめる。つながらないサーバーに、一覧の数だけ 30 秒を待たないためである。
  - アプリが取り消した呼び出しの中では送らない（取り消された `CancellationToken` で送ろうとするので、送られずに一覧に入る）。送れば、取り消したアプリを待たせる。
  - 利用ログは、リース ID での返却と同じ行（`lease.released`、`borrow.returned`。`elm-service` の `by` は `device`）にした。新しい値は足さない。
  - `elm-server` は、メモリーに（拇印、`jti`）からリースを引く表を持つ。リースをすべてなめる形は、取得と更新に何も足さないが、証明を作れる誰もが、リースの数に比例する仕事をサーバーにさせられる。`elm-service` は、`leases` の `key_id` に索引を足した（移行 `0009`）。`issued_by` を索引に入れないのは、更新のたびに変わるからである（§12.7.6）。

## 退けた案

- **決定:** 答えの届かなかった取得と借り出しは、クライアントが、その要求の証明の `jti` を名指す返却（`DELETE /v1/leases/requests/{jti}`）を送り、サーバーは、その要求で出した同じ鍵のリースだけを消す。届かなければメモリーに 16 件まで残して送り直す。借り出しは早期返却として数える（問 5b-1〜5b-4。設計 §12.7.7）。
- **理由:** 正当な利用（通信の切れ、30 秒の打ち切り、大きすぎる答え、アプリの取り消し）でも、席がリースの期限まで埋まり、2 席の機能では 3 回目の取得が断られた。借り出しは管理者も返せない。答えの届かなかったクライアントはリース ID を知らないので、要求の `jti` で名指す。`jti` で出したリースだけを消すので、中継がほかの持ち手の答えを運んでも、そのリースは消えない（V1d5 の問 5-4 と両立する）。
- **却下した案:** Issue #420 が挙げた、サーバーが取得の `retry` の `jti` で同じリースを返す案（取得し直すアプリにしか効かず、取得し直さないアプリでは席が期限まで埋まる）。設計 §5.4 に受け入れる案（測った害は正当な利用で起きる）。送り直しの一覧をファイルに書く案（問 5b-2 で持ち主が退けた）。
