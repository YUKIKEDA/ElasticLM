### 測った事実（`origin/main` の 4ebee8e。Windows 11、SDK 10.0.404、.NET 10.0.15）

- 文字として読めない JSON（スクラッチのプログラムで、4 つの形をそれぞれ読ませた）: 設計 §8.3 の「測った事実」のとおり。Grill の前に知られていたことに、次が加わった。
  - `TryGetProperty` は後ろのメンバーから探す。読めない名前が探す名前より前にあると例外にならず、後ろにあるか探す名前がないと出る。名前の長さによっては、比べずに飛ばし、例外にならない（`\ud800` の名前は、`type` を探すと例外になり、`abcdefgh` を探すと例外にならない。どの長さで飛ばすかの規則は調べていないので、テストは探す名前より長い読めない名前を使う）。
  - UTF-8 でないバイトは、`GetRawText` でも `InvalidOperationException` になる（`LicenseClient.TryReadBorrowFile` と `TryReadServerLicense`、`ActivationClient.ReadIssued` は、ライセンスの部分を `GetRawText` で取る）。
  - UTF-8 でないバイトの名前は、`AllowDuplicateProperties = false` の `JsonDocument.Parse` を通り、`TryGetProperty` でも出ないが、`JsonProperty.Name` で出る。`elm-service` の `Licenses.Meta`（`meta` の名前を `entry.Name` で読む）が、この形で `500` を返す道だった。
  - `JsonSerializer` で `JsonElement` を書くと、4 つの形のどれでも出る。`elm license inspect` は、読めたあとの書き出し（`GetRawText`、`Pretty`）で、処理されない例外になった。
- F19: 設計 §12.2 の期限の比べ方のとおり（Issue #342 の本文の再現: +300.5 秒で 2 つ目のリース）。
- F36: `LeaseVerifier.cs:148` と `LeaseEngine.cs:930` は `(expires + license.GracePeriod).ToUnixTimeSeconds()` で、`expires` が 9999-12-31T23:59:59Z で `GracePeriod` が 1 秒以上なら `ArgumentOutOfRangeException` になる。

### こちらが決めたこと

- `AdminAnswer.Of` と `OidcHttp.Send` は、読み手ごとに受けず、本文を読む 1 か所で、すべての名前と文字列を読めるか確かめる（設計 §8.3 の表の下）。理由: どちらも 1 つの答えを多くの所が読む（`OidcHttp` の文書は、`AdminCommands` のログインの手続きの中で、関数を通さずに `TryGetProperty` と `GetString` で 10 ほどの所が読む）。読み手ごとに受けると受け忘れが残り、`AdminAnswer.WriteIndented` では、16 KiB を書き出したあとに例外になって、途中まで書いた出力が残る。持ち主の決定（問 23-3）の「読み手ごとに受けて誤りを返す」と結果は同じで、受ける所が 1 つになる。
- `RequestBody.Parse` は、解析の前に本文全体が UTF-8 として正しいかを確かめる（`Utf8.IsValid`）。`meta` の名前の UTF-8 でないバイトが、解析を通り `JsonProperty.Name` で `500` になったためである（上の測った事実）。名前のサロゲートは、問 23-3 のとおり、解析の例外を受けて `ELM_MALFORMED` にする。
- `elm license inspect`（`LicenseCommands.Decode`）も、同じ種類として直した。トークンの部分を読むときに、すべての名前と文字列を読めるか確かめ、読めなければ、前からの誤り（`The file is not an ElasticLM license file.`）にする。
- `LicenseClient.TryReadServerLicense` も、同じ種類として直した（Grill の一覧になかった。`GetRawText` と `TryGetProperty` が出す）。
- `ActivationStore.Parse` の `seq` と、オフラインの要求の数（`TryReadNumber`）は、`TryGetInt64` の前に `ValueKind` を確かめる（`.cursor/rules/security.mdc`）。結果は変わらない（前から `InvalidOperationException` を受けていた）。
- `LogKeyMaterial.Certificates` の `node` を省けなくした。問 23-10 で、検証が `node` のない最初の行を誤りにするので、`node` を書かない書き手は、検証を通らないログを書くことになるためである。
- `LogReport` は、出来事の行の一覧（`Entries`）の代わりに、その数（`EntryCount`）を持つ。`ElasticLM.Issuing` は配らないパッケージなので、API を変えてよい（Grill の前提）。
- F37 で、秘密を表す値のうち、コードで `==` で比べていたのは、`ActivationClient` のライセンスキーのハッシュ（オフラインの要求を使い回すかの判定と、答えのない要求の `aim`）だった。規則に合わせて `FixedTimeEquals` にした。どちらも端末の中の値どうしで、時間の差を測れる者はすでに端末を持つので、守りは変わらない。

### 持ち主が決めたこと（PR #441 のあと、2026-11-14。Issue #342 のコメント）

- 問 23-3 を `elm` について変えた: `elm` の読み手は、本文を読む 1 か所（`AdminAnswer.Of`、`OidcHttp.Send`）で名前と文字列をすべて確かめる。`elm admin login` には関数を通さずに文書を読む所が 10 ほどあり、読み手ごとでは受け忘れが残るためである。`WriteIndented` が 16 KiB を書いたあとで例外になり、途中の出力が残ることも避けられる。引き換えに、`WriteIndented` の誤りの文は「not the answer」から、JSON でない答えと同じ文になる。クライアントとサービスの読み手は、読み手ごとに受ける形のまま。
- 問 23-8 を強めた（独立レビューの K1）: `chain.reset` の `prev` に、前のファイルの最初の `auth` 行の SHA-256（`prev.first`）を足し、検証で照らす。書き込みの失敗のときはメモリから、起動のときはファイルの頭から取り、ファイルを開けないときだけ省く。名前だけでは、前のファイルを消し、その前のファイルをその名前に変えるとすり抜けられたため（Z、A、B、C で C が `chain.reset` のとき、B を消して A を B にすると、Z、B（中身は A）、C が通った）。

### 独立レビューの指摘で直したこと（5b18e98 に対して）

- K2: `ProofVerifier` は、ノンスの期限と `jti` の記録で時刻を別々に読むので、期限の瞬間に、2 つの読み取りのあいだ（数マイクロ秒と錠の待ち）だけ、同じ証明がもう一度通るすきがあった。`MemoryReplayStore` が記録を期限の 60 秒あとまで残すようにした（`KeptAfterExpiry`。`elm-service` の +60 秒と同じ幅。§12.2、§13.2）。時刻を 1 度だけ読んで両方に渡す形は採らなかった。`IReplayStore` の公開の形を変えることになり、60 秒の幅で同じすきが閉じるためである。
- K3: §20.7 の V1d14 の記録の、`FileClockGuard` が 64 バイトを確かめるという文に、外したことを足した。
- K4: テストの数に、成功しなかったもの（スキップ）の数と理由を足した（下の「テスト」）。
- 利用者の文書（R1〜R7、J1〜J9）: `logs.md` の `chain.reset` の `prev`（`first` と、`reason` が名指すファイルと違う 2 つの場合）、検証の誤りを箇条書きにして、`chain.reset` の直前のファイルを含むことと誤りの文を書いた。途中で切れた最後の行の警告が出る条件。`verify-the-usage-log.md` に欠けたファイルの文。`administration-api.md` と `device-protocol.md` に、名前のサロゲートと UTF-8 でないバイト。`device-protocol.md` と `devices-and-proofs.md` に、`elm-server` の記録の 60 秒（K2）。

### 設計を書いたあとに直したこと（実装のとき）

- `chain.reset` の `prev.file` は、はじめ「起動のときは読めなかったファイル、書き込みに失敗したあとは失敗したファイル」と書いた。失敗したファイルを作れなかったとき（ディスクが一杯で `CreateNew` が失敗したとき）、その名前のファイルはフォルダーになく、検証が欠けたファイルの誤りを出してしまう。そのため、新しいファイルを作る前にフォルダーを読んで見つけた、名前で最新のログのファイルを書くことにした（§18.1）。検証が前のファイルとして渡されるのは、そのファイルである。
- `LogVerifier.IsReadableText` を、`elm` も使えるように `ElasticLM.Issuing` の公開の `JsonText.IsReadable` に移した（`elm license inspect` と `OidcHttp.Send`）。

## 退けた案

- **決定:** `chain.reset` の行に、前のファイルの名前（`prev.file`）と、その最初の `auth` 行の SHA-256（`prev.first`）を足す（問 23-8 と、PR #441 のあとの持ち主の決定）。
- **理由:** `chain.reset` で始まるファイルの前のファイルを消しても、検証が分からなかった（T15-1）。名前だけでは、前のファイルを消して、その前のファイルをその名前に変えるとすり抜けられた（K1）。最初の `auth` 行は `jti` を持つのでファイルごとに違い、行は最初の署名が覆うので、書き換えれば分かる。
- **却下した案:** 名前だけを足す（Grill の問 23-8 の最初の形。上の名前を変えるすり抜けが通る）。最後の署名の行のハッシュを持たせる（最後の署名を読めないか書けないから `chain.reset` になるので、持たせる値がない）。何もしないで §5.4 に書く（ファイルの削除という、検証が見つけると約束していることを、1 行で見つけられる）。

- **決定:** `LogVerifier` は 1 行ずつ読み、出来事はコールバックに渡す（問 23-5）。
- **理由:** 検証が、すべてのファイルの行と出来事を記憶に持ち、上限がなかった（F28）。
- **却下した案:** ファイルの数と大きさに上限を置く（利用ログは日ごとにファイルを替え、何年分も検証するのが正しい使い方で、上限は正しいログを断る）。

- **決定:** ノンスの期限を、秒より細かい時刻で比べる（問 23-4）。
- **理由:** 受け付けの最後の時刻と、`jti` の記録が切れる時刻をそろえ、最後の 1 秒に同じ証明が通らないようにする（F19）。
- **却下した案:** `jti` の記録を 1 秒長く持つ（2 つの期限がずれたままで、ずれの分を数で合わせることになる）。

- **決定:** F37 は、`security.mdc` の文を絞る（問 23-7）。
- **理由:** 約 30 か所が比べている鍵の ID、拇印、トークンの ID は、トークンに載る公開の値で、時間の差が知らせるのは、トークンがすでに見せている値だけである。
- **却下した案:** すべての所を `FixedTimeEquals` にする（守るものがなく、読みにくくなる）。
