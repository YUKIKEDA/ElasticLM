# V1d3a（Issue #356）: `TlsChainTests` のテストが、ときどき「中間証明書が送られていない」で落ちる原因を調べて直す

## Grill の記録

- V1d3a の Grill（Issue #356 に記録した。持ち主の決定は 2 回で、どちらも推奨案 A。2026-11-13）: `TlsChainTests` のテストが、Windows のローカルのゲートで、ときどき「中間証明書が送られていない」で落ちる原因を調べて直す。原因は製品の側にあり、`elm-server` と `elm-service` の起動を変えた（§13.5 の「起動のときの送信の確かめ」）。Issue は `test` の型で立てたが、製品の動きを変えたので、持ち主が `type:bug` に改めた（2026-11-13）。退けた案は design-decisions.md にある。
  - 測った事実（1 回目。`main` の 2919c9c、Windows 11、SDK 10.0.404、.NET 10.0.15、Debug、管理者でない利用者で、.NET は `CurrentUser\CA` に書いた）:
    - 本物のテストでは、この形（サーバー自身の証明書は出ているが、中間証明書が送られていない）は再現しなかった（クラスだけを 30 回、プロジェクトの全部を 10 回、全部を 3 つ並べて 75 回、中間証明書を期待する接続は合わせて約 1,000 回で、失敗は 0）。クラスを 3 つ並べて 120 回流すと 10 回が落ちたが、別の形（起動のときの `CryptographicException`「An unknown chain building error occurred.」。`CurrentUser\CA` に同じ名前のテストの証明書が 21 個たまっていた）だった。
    - テストと Kestrel のすることをなぞる試しのプログラムでは、ほかの TLS のハンドシェイクが同じプロセスで並んで走っているときだけ、最初のハンドシェイクの 0.2〜0.5 % がリーフだけになった。
    - Windows では、.NET は SChannel にリーフだけを渡し、中間証明書は `SslStreamCertificateContext.Create` がストア（`LocalMachine\CA`、だめなら `CurrentUser\CA`）に書き、SChannel がハンドシェイクのときにストアから連なりを組む（dotnet/runtime の `SslStreamPal.Windows.cs`、`SslStreamCertificateContext.Windows.cs`）。テストの「送られたか」の決め方（コールバックの `ExtraStore`）は正しかった。
    - どの鎖も同じ主体の名前を使い、並べたテストのプロセスが消したあとも、同じ名前の証明書がストアに残った。
  - 1 回目の問いと答え（問 3a-1、問 3a-2。推奨案 A）: 製品は、中間証明書を Windows のストアに書き、聞き始める前に待ち、起動のあとに自分で確かめて、だめなら理由を言って止まる。待つ長さと、再起動で直るかは、設計を書く前に測る。テストは、鎖ごとに別の主体の名前を使い、あとで片づけ、確かめは残す。
  - 測った事実（2 回目、設計の前の測定。Release、ほかは 1 回目と同じ。試しのプログラムは鎖ごとに別の名前で、`Create(leaf, [intermediate, root], offline: true)` のあとループバックでハンドシェイクした）:
    - ストアをほかに書く者がいなければ、待ちなしの最初のハンドシェイクで、鎖が全部送られた（`SslStream` で 1,800 本、Kestrel で 40 本、リーフだけは 0 回）。
    - ほかに書く者がいると、どの待ちでもリーフだけの最初のハンドシェイクが出た: 8 つの並行の作り手と関係のない TLS のループ 2 つの下で、待ち 0 ms・5 ms・20 ms の 12,000 本ずつのうち 1 回・3 回・3 回。作り手 1 つと、同じプロセスで関係のない CA の証明書を `CurrentUser\CA` に足して消すループ 4 つの下で、0 ms・50 ms の 2,500 本ずつのうち 24 回・11 回。別のプロセスのループ 4 つの下で 1,200 本のうち 8 回。Kestrel（`UseHttps`）と別のプロセスのループで 1,500 本のうち 8 回。1 回目に書いた「20 ミリ秒待つと 1,000 回で 0 回」は確かめ直せなかった。効くのは、自分がストアに書いてからの時間ではなく、最初のハンドシェイクのときに、だれかが同じストアを書き換えているかである。
    - 新しいプロセスでは直る（決まった手順で作ったリーフだけの状態で、同じ PKCS#12 のファイルを別のプロセスで読むと、2 本のうち 2 本で鎖が全部送られた）。同じプロセスでは直らない（同じリーフの新しい `SslStreamCertificateContext` は、0 ms から 30 秒までのどの間でもリーフだけだった。決まった手順で 2 本のうち 2 本、競り合いで 43 回のうち 29 回）。理由は dotnet/runtime v10.0.15 の `SslSessionsCache.cs` の 17〜98 行（プロセス全体の資格情報のキャッシュを、リーフの拇印と設定で引く）と `SslStream.Protocol.cs` の 746〜764 行。
    - `SslStreamCertificateContext.Windows.cs` の 22〜109 行は、`Create` の中で同期に、中間証明書をストアに足す（足すときの失敗は握りつぶし、消すことはない）。`Create(leaf, [intermediate, root])` は 5〜7 ミリ秒で、2 件を `CurrentUser\CA` に書いた。
    - 自分のプロセスの中での確かめはできる。`app.StartAsync()` のあと自分のポートに `SslStream` でつなぎ（再開は切る）、`ExtraStore` を読む。かかる時間は、静かなとき中央 10.4 ms・最大 29.2 ms（40 回）、別のプロセスがストアを書き換えているとき中央 19.5 ms・最大 75.6 ms（1,500 回）。1,500 回の起動のうち最初の確かめがリーフだけだった 8 回は、2 回目もリーフだけで、最初が全部で 2 回目がリーフだけの起動はなかった。
    - 本物のテスト（`TlsChainTests` の 7 つ）を、別のプロセスが関係のない CA の証明書を足して消している間に 58 回流すと、3 回落ちた。名前を鎖ごとに別にしても、リーフだけの割合は下がらなかった（同じ名前の 2,000 本で 0 回、別の名前の 4,000 本で 1 回）。拇印で消す片づけは、ストアが並行に書かれていると消し残した（約 464 件のうち 3 件）。
  - 2 回目の問いと答え（問 3a-1'、問 3a-2'。推奨案 A。1 回目の答えは、測定で前提が崩れたので、これに替わった。待ちは守りにならず、ストアへの書き込みは .NET がすでにしているため）:
    - 3a-1'（製品）: ストアへの書き込みと、聞き始める前の待ちは入れない。Windows では、起動のたびに、聞き始めた直後に、自分のポートへのハンドシェイクで中間証明書が送られているかを確かめ、送られていなければ、足りない証明書と「起動し直すと直る」を言って止まる。聞き始めてから確かめが終わるまでの数十ミリ秒は、リーフだけを送ることがある。
    - 3a-2'（テスト）: 確かめは残す。ストアに書くテストを、2 つのテストのプロジェクトをまたぐ名前つきの排他で同時に走らせない。主体の名前は鎖ごとに別にし、片づけは名前の接頭辞で掃く。サーバーが確かめに落ちて止まったときだけ、テストは立て直す。
  - 独立レビューのあとの問いと答え（問 3a-3。指摘 M2 から。持ち主の決定は推奨案 A。2026-11-13）: 確かめが答えを得られないとき（ループバックの TLS のハンドシェイクが失敗するか、10 秒以内に終わらない）も、起動を止める（作ったとおり）。利用者の文書に、起動のたびにそうなるときに確かめることを書く。退けた案: (B) 運用の記録に警告を書いて起動を続ける。(C) 確かめを切る設定を足す。
  - こちらが決めたこと（実装。持ち主の決定の外のもの）:
    - 確かめは `ElasticLM.Issuing` の `TlsChainSelfCheck` に置き、2 つの製品が使う（`TlsCertificateFiles` と同じ置き場所）。待ち受けの端点は、Kestrel が `ListenOptions.IPEndPoint` に書く、選んだポートを読む。
    - ワイルドカードの `listen` はループバックへつなぐ（`0.0.0.0` は `127.0.0.1`、`[::]` は `[::1]`）。https の待ち受けは `listen` の 1 つだけなので、いくつもの端点はない。
    - 時間の上限は 10 秒（Kestrel の `HandshakeTimeout` の既定）を、呼び出す側の `TimeProvider` で数える。答えが得られないとき（接続の失敗、ハンドシェイクの失敗、上限）も、送られたかが分からないので、起動しない。
    - 期待するのは、ファイルの証明書でサーバーの証明書から組んだ連なりに入る中間 CA だけ（ルートと、連なりに入らない CA の証明書は期待しない）。送られたかは、主体の名前と公開鍵で比べる（拇印では比べない。ストアにある、更新した同じ CA の証明書を Windows が送ることがある）。
    - 止まるときの文は 1 つにした。はじめは、ストアを読んで「ストアにない（どちらのストアにも書けないアカウント）」と「ストアにあるのに送られなかった」を別の文にしたが、ストアがほかに書き換えられている間は、ストアを読んでもあるはずの中間 CA を見落とし、リーフだけの最初のハンドシェイクを作った 2 つのテストの、別のプロセスの書き込みの下での 206 回の起動のうち 3 回で、誤った文になった。文は、起動し直すことと、起動のたびにそうなるならマシンのストアに入れることの両方を言う。
    - 確かめに落ちた起動は、待ち受けの失敗と同じく、起動の失敗の破棄でホストを破棄して待ち受けを閉じる（`elm-server` は `admin.sock` も消える）。開始の記録は書かない。`elm-service` は利用ログに `service.stopped` を書く（§14.8）。
    - テストの立て直しは、確かめの「Windows left …」の文で止まったときだけで、鎖は 3 つまで（`TestCertificateChain.StartAttempts`）。立て直すたびに新しい鎖（新しいリーフ）を作る。同じプロセスでは、同じリーフの起動は同じ結果になるためである。3 つにした理由: 書き換えの続く下でも起動の約 0.5 %（1,500 回のうち 8 回）なので、3 回続くのは (8/1500)^3 ≒ 1.5 × 10^-7、約 659 万回に 1 回。
    - 排他は `Global\ElasticLM.Tests.TlsChainStore` の名前つきの `Mutex` で、中間 CA を送るサーバーを立てる前から、ストアを掃き終わるまで持つ（鎖の `Dispose`）。`Mutex` はそれを取ったスレッドのものなので、専用のスレッドで取って放す。待つ上限は 5 分（持つのは 1 回の起動と数回のハンドシェイクと掃除で、約 1 秒）。持ち主が死んで放されなかった排他（`AbandonedMutexException`）は取ったものとする。`./build.ps1` は、テストのプロジェクトを 1 つずつ順に流す（`foreach ($project in $testProjects)` の中の `dotnet test`）ので、ゲートでは 2 つのプロジェクトは並ばない。並ぶのは、2 つの `dotnet test` を同時に流したときと、プロジェクトの中で xUnit がテストのクラスを並べて流すときで、排他はどちらも防ぐ。
    - 鎖の主体の名前は `CN=ElasticLM test chain <16 桁の 16 進数> root` と `… intermediate`。片づけは、排他を持った鎖だけが、2 つのストアから `CN=ElasticLM test chain ` で始まる証明書を掃く（前の実行の残りも消える）。ストアがほかに書き換えられている間は、削除が効かないことがあった（50 回の実行のうち 1 回）ので、読み直して 3 回まで掃く。
    - リーフだけの最初のハンドシェイクは、決まった手順で作る（実際のもので、差し込みの口は作らない）: 中間 CA がどのストアにもない間に、Kestrel と同じ設定の `SslStream` の待ち受けをリーフだけで作り、1 回ハンドシェイクする。そのあと同じプロセスで同じリーフのサーバーを立てると、確かめが送られていないことを見つける。
  - 測った事実（実装。Windows 11、SDK 10.0.404、.NET 10.0.15。管理者でない利用者）:
    - 起動の時間（発行した NativeAOT の win-x64、Release。起動の記録の `in N ms`。中間 CA のある PEM で https。確かめのある版とない版を交互に 32 回ずつ。確かめのない版は、2 つの製品から確かめの呼び出しを除いた同じ木）: `elm-server` は、ある版が中央 100 ms（最小 92、最大 144）、ない版が中央 90 ms（最小 79、最大 131）で、中央の差は 10 ms。`elm-service` は、ある版が中央 230.5 ms（最小 203、最大 677）、ない版が中央 215 ms（最小 198、最大 417）で、中央の差は 15.5 ms。
    - 確かめにかかる時間（テストの中で、確かめの中に一時的に時刻を書く行を足して測り、外した）: 別のプロセスがストアを書き換えている間、368 回で中央 20 ms、90 % 点 110 ms、最大 1,706 ms。書き換えるプロセスが、自分の消し残しを掃かずに CA のストアを約 300 件に増やした下では、121 回で中央 39 ms、90 % 点 2,660 ms、最大 49,850 ms で、ハンドシェイクが待ち受けの側から切られて失敗した回もあった（テストは偽の時計を使うので、10 秒の上限は効かない）。製品では、この場合は答えが得られないとして起動しない。
    - 1 つの待ち受けへの 20 回のハンドシェイクを、鎖を 400 個作って、別のプロセスがストアを書き換えている間に流すと、393 個は 20 回とも中間 CA が送られ、7 個は 20 回とも送られなかった。食い違った鎖はなかった。
    - 2 つのテストのプロジェクトの鎖のテスト（`ElasticLM.Server.Tests` の `TlsChainTests` と `TlsChainSelfCheckTests`、`ElasticLM.Service.Tests` の名前に `Intermediate` のあるテスト）を、2 つの `dotnet test` で同時に、別のプロセスが `CurrentUser\CA` に関係のない CA の証明書（主体の名前は `elm-v1d3a-impl-` で始まる）を 4 つのループで足して消している間に 50 回流した（最後の版）: 1,100 のテストのうち 1 つが落ちた（`Dispose_ChainAServerSent_LeavesNoneOfItsCertificatesInTheStores`。掃除の削除が効かずに 1 枚残った）。これを受けて掃除を 3 回まで読み直すようにした。その前の版の 55 回では、1,100 のうち 1 つ（`Run_RenewedIntermediateSent_Passes`。テストの待ち受け自身の最初のハンドシェイクが更新した中間 CA を落とした）が落ち、テストを直した。直す前の `TlsChainTests` の 7 つは、測定で 58 回のうち 3 回落ちた。サーバーが確かめで止まったテストは、立て直しで通った。ストアの数は、測る前と後で `CurrentUser\CA` が 38 件、`LocalMachine\CA` が 9 件だった。
  - テスト（`ElasticLM.Server.Tests`、`ElasticLM.Service.Tests`）: 中間 CA の送信の確かめ（どの既存のテストも、確かめに通ったうえで中間 CA が届くことを確かめる）。リーフだけの最初のハンドシェイクのあとの起動が、両方の製品で、その証明書の名前と拇印を示す文で止まり、待ち受けを残さない（`elm-server` は `admin.sock` も `server.started` も残さない）。`TlsChainSelfCheck` の、送られないときの文（`127.0.0.1`、`0.0.0.0`、`[::]`）、同じ待ち受けへの続けての確かめ（毎回、再開しないハンドシェイクで読む）、更新した中間 CA、連なりに中間 CA のないファイル（つながない）、答えのない待ち受け（10 秒の手前と 10 秒）、閉じられた接続と断られた接続、Windows でない OS（つながない。Windows では理由つきで飛ばす）。テストの補助の、立て直しの条件と回数、掃除。
  - 変異の確かめ（Windows、Release。`ElasticLM.Server.Tests` の鎖のテストと、`ElasticLM.Service.Tests` の名前に `Intermediate` のあるテストを流した）:

    | 変異 | 結果 | 落ちたテスト |
    | --- | --- | --- |
    | 製品が確かめの答えで止まらない（2 つの製品） | 落ちた | 両方の `Start_FirstHandshakeWithoutTheIntermediate_Throws` |
    | 送られていない中間 CA も、送られたとする | 落ちた | 両方の `Start_FirstHandshakeWithoutTheIntermediate_Throws`、`Run_IntermediateNotSent_NamesIt` |
    | 送られた証明書を読まない（`ExtraStore` を使わない） | 落ちた | 鎖を送るすべての起動のテスト（2 つのプロジェクト）、`Run_RenewedIntermediateSent_Passes` |
    | ファイルのルートも期待する | 落ちた | `Start_PemWithRoot_SendsTheIntermediate` |
    | 連なりに入らない CA の証明書も期待する | 落ちた（時間の上限で止まった） | `Start_PemWithAnUnrelatedAuthority_StartsAndSendsItsOwnIntermediate`、`Start_PemWithRoot_SendsTheIntermediate` |
    | 上限を 20 秒にする | 落ちた | `Run_ListenerNeverAnswers_EndsAtTheLimit` |
    | ワイルドカードのアドレスをそのまま使う | 落ちた | `Run_IntermediateNotSent_NamesIt`（`0.0.0.0` と `::`） |
    | テストの立て直しを、どの失敗のあとでもする | 落ちた | `StartAsync_OnlyAfterTheCheckSentence_TriesAnotherChain` |
    | テストの掃除が何も消さない | 落ちた | `Dispose_ChainAServerSent_LeavesNoneOfItsCertificatesInTheStores` |
    | テストが排他を取らない | 1 回の実行で落ちた（決まって落ちるテストはない） | `Dispose_ChainAServerSent_LeavesNoneOfItsCertificatesInTheStores`（並んだテストの証明書が残った） |
    | 送られたかを拇印で比べる | 生き残った | — |
    | TLS の再開を許す | 生き残った | — |
    | Windows でない OS でも確かめる | Windows では生き残った | `Run_NotWindows_MakesNoConnection`（Linux と macOS の CI で流れる） |

    - 拇印の変異が生き残る理由: 同じ比べを、期待する中間 CA を選ぶ所（`ExpectedIntermediates`）でも使う。Windows が連なりを組むとき、ストアにある更新した証明書を選ぶと、拇印で比べる変異では期待する中間 CA がなくなり、確かめをしない。2 つの所を別々に変えるテストは足していない。
    - 再開の変異が生き残る理由: 同じ待ち受けに 3 回続けて確かめても（`Run_SameListenerAgain_MakesAFullHandshake`）、変異のある版でも、どの回も中間 CA が読めた。このテストでは、再開は起きなかった。再開を起こすテストは足していない。
    - 排他は、決まって示すテストを作れなかった。2 つのプロセスの起動の時刻を、テストから重ねられないためである。
  - 独立レビューのあとに直したこと（PR #401 のレビュー、指摘 M1〜M4、L1〜L8）:
    - M1 確かめの間の要求: Kestrel は `app.StartAsync` から要求を受けるので、確かめに落ちる起動でも、確かめの間（中央 20 ms、上限 10 秒）に来た要求を処理し、借り出しの記録に書いたあとで、もう破棄した利用ログに書けずに終わることがありえた（破棄の順は、`elm-server` が規則の仕組み → 利用ログ → ホスト、`elm-service` が利用ログ → ホスト）。2 つの製品の最初のミドルウェア `StartGateAsync` が、起動が終わる（`AfterStart` のあと）までに来た要求を、答えずに切る（`HttpContext.Abort()`）。答えずに切るのは、まだ待ち受けていないときと同じ形だからで、`503` の誤りのコードには当たるものがない（§13.5）。`app.StopAsync()` で止めてから破棄する案は、受けた要求を最後まで処理するので退けた。
    - M2: 答えのない確かめは、問 3a-3 のとおり起動を止める。利用者の文書（`server-configuration.md`、`service-configuration.md`、How-to の「Use your own TLS certificate」。英語と日本語）に、起動のたびに止まるときに確かめることを書いた。「Windows left …」なら、どちらのストアにも書けないアカウントがいちばん考えられ、管理者がコンピューターの中間証明機関のストアに中間 CA を入れる。答えのないときは、クライアントの側の TLS のバージョンが Windows の設定で切られていることと、ループバックの TLS に割り込むプログラムを、考えられる原因として挙げた。管理者が証明書をストアに入れる手順（`certutil -addstore CA <file>` などのコマンド）は、この端末に管理者の権限がないので試しておらず、コマンドは書かず、ストアの名前と管理者が要ることだけを書いた（`.cursor/rules/user-docs.mdc` の、試していない OS の手順の扱い）。

## 退けた案

- **決定:** Windows では、`elm-server` と `elm-service` は、起動のたびに、待ち受けを始めた直後に、自分の待ち受けへのハンドシェイクで、運用者の証明書のファイルの中間 CA が送られているかを確かめ、送られていなければ、足りない証明書と「起動し直すと直る」を言って止まる。ストアへの自前の書き込みと、待ち受けの前の待ちは入れない（持ち主の決定 3a-1'、推奨案 A。2026-11-13）。テストは、送られたことの確かめを残し、ストアに書くテストを、2 つのテストのプロジェクトをまたぐ名前つきの排他で同時に走らせず、主体の名前を鎖ごとに別にして、名前の接頭辞で片づけ、サーバーが確かめに落ちて止まったときだけ立て直す（持ち主の決定 3a-2'、推奨案 A。同じ日）。先の答え 3a-1 と 3a-2（どちらも推奨案 A）は、そのあとの測定で前提が崩れたので、これに替わった（設計 §13.5 の「起動のときの送信の確かめ」、§20.7 の「V1d3a の Grill」）。
- **理由:** 中間 CA が送られないのは、資格情報の最初のハンドシェイクのときに、ほかのプログラムが同じストアを書き換えているときで、その状態はプロセスが終わるまで続き、新しいプロセスでは直る。待ちは、0 ms、5 ms、20 ms、50 ms のどれでもサーバーの証明書だけのハンドシェイクを止めなかった。自分のハンドシェイクで読めば、そのプロセスで送るものが分かる（最初の確かめと 2 回目が食い違った起動はなかった）。テストの名前を別にするだけでは、測定で落ちた。
- **却下した案:** 3a-1' の (B) 止まる前に、自分で新しいプロセスとして起動し直す（運用者は手を動かさずに済むが、サービスの管理の仕組みの外でプロセスを作り、起動し直しても同じ結果になる場合（どちらのストアにも書けないアカウント）にくり返す）。(C) 先の答え 3a-1 のまま（ストアへの書き込みと、待ち受けの前の待ちも入れる。測定では、待ちは守りにならず、書き込みは .NET がすでにしている）。3a-2' の (B) 名前と片づけだけにする（測定では、名前を別にしても落ちた）。(C) 確かめを何回かやり直す（製品の不具合を、テストが隠す）。実装で選んだもので退けたもの: 送られていない理由をストアを読んで 2 つの文に分ける（ストアが書き換えられている間は、読んでもあるはずの証明書を見落とし、206 回の起動のうち 3 回で誤った文になった）。拇印が同じときだけ送られたとする（更新した同じ CA の証明書を Windows が送ると、クライアントは同じ連なりを組めるのに止まる）。時間の上限を設けない、または実時間で数える（`.cursor/rules/security.mdc` の `TimeProvider` に反し、テストで上限を確かめられない）。
- **独立レビューのあとの決定（2026-11-13）:** 問 3a-3（指摘 M2）で、持ち主は推奨案 A を選んだ: 確かめが答えを得られないとき（ループバックの TLS のハンドシェイクが失敗するか、10 秒以内に終わらない）も、起動を止める（作ったとおり）。利用者の文書に、起動のたびにそうなるときに確かめることを書く。退けた案: (B) 運用の記録に警告を書いて起動を続ける（送られているかが分からないまま、中間 CA を送らないサーバーが動きうる）。(C) 確かめを切る設定を足す（設定が増え、切ったサーバーは問題を言わずに動く）。指摘 M1 の直し方では、起動が終わるまで要求に答えずに切る形（最初のミドルウェア）を選んだ。退けた案: 確かめに落ちたとき `app.StopAsync()` で止めてから破棄する（この間に受けた要求は最後まで処理され、借り出しや利用ログに記録が残ったまま起動が失敗する）。この間の要求に `503` の誤りで答える（`ELM_SERVER_RECOVERING` と `ELM_SERVER_BUSY` は別の意味を持ち、`elm-service` の経路と管理 API には当たるコードがない。新しいコードは公開の番号を増やす）。指摘 L1 の、更新した同じ CA の証明書を送られたとみなす決め方には、そのときの時刻がその証明書の期間に入ることを足した。退けた案: 拇印だけで比べる（ストアにある更新した証明書を Windows が送ったときに、正しいサーバーを止める）。
