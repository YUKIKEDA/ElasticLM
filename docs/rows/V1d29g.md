# V1d29g（Issue #494）: Windows と macOS のマシン ID の読み手から、OS の値を解く部分を分けてテストする

## Grill の記録

Grill は、問 1〜6 の 6 つを持ち主に出した。持ち主は 2026-11-28 にすべて推奨案を選び、Issue #494 のコメント「決定」に書いた。

### 測った事実（`origin/main` の 8c35a87）

- 3 つの読み手（`MachineIdSources.cs` の `ReadWindowsMachineGuid`、`ReadWindowsSmbiosUuid`、`ReadMacPlatformUuid`）は `private` だった。中の規則のどれを外しても、落ちるテストはなかった。3 つを通るのは `Compute_ThisMachine_ReturnsStableFingerprints` だけで、このテストは指紋が 1 つ以上あることしか見ない。Windows には指紋が 2 つあるので、片方の読み手が壊れても通る。
- 32 ビットのビューには MachineGuid がない。Windows 11（この機械）で `reg query "HKLM\SOFTWARE\Microsoft\Cryptography" /v MachineGuid /reg:32` は「The system was unable to find the specified registry key or value」を返し、`/reg:64` は REG_SZ の値を返した。64 ビットのプロセスでは `Registry64` と `Default` が同じビューを開くので、`Default` にした変異は x64 のテストでは落ちない。§4.1 の RID の一覧は、実行ファイルと `libelasticlm` についてのものである。NuGet の `ElasticLM.Licensing` は x86 のプロセスでも動く。
- `Guid.TryParse(text, CultureInfo.InvariantCulture, out _)` が受け入れる形を、.NET 10 で測った（`dotnet run` で 1 つのファイルを流した）。受け入れたのは、たとえば、大文字の D 形式、N（32 桁）、B（`{}`）、P（`()`）、X（`{0x…}`）、前後に空白と `\n` がある D 形式で、どれも同じ 16 バイトになった。35 文字、空の文字列、先頭が U+0660 の文字列は false だった。PR #516 の独立レビューのあとに、ほかにも受け入れる形を測った（使い捨てのコンソールのプロジェクト）。D の形のフィールドの先頭の `+` と `0x`（`+0112233-…`、`0x112233-…`、`00112233-+455-…`）、X の形の中の空白と短い桁（`{0x1,0x2,0x3,{0x4,…}}`）、前後の U+00A0 と U+3000 も、どれも受け入れた。そのため §10.3 は、形を「たとえば」で挙げ、これらも書いた。`ToByteArray(bigEndian: true)` は文字列の順のバイトになり、`bigEndian: false` では先頭 8 バイトの並びが変わった（`33221100 5544 7766 …`）。
- 本当の入力では結果を変えない境界が 2 つあった。大きさが 8 バイトちょうどなら、`Length` は 0 以下か残りの 0 バイトを超えるので、どちらの書き方でも null になる（`size <= 8` と `< 8`）。`Length` が 0 なら、空の表を `ParseSmbiosSystemUuid` が null にする（`tableLength <= 0` と `< 0`）。

### 持ち主が決めたこと（2026-11-28、Issue #494、問 1〜6 はすべて案 A）

- 問 1（分ける形）: Windows と macOS が共有する `internal static byte[]? ParseGuid(string? text)` と、`internal delegate uint FirmwareTableReader(Span<byte> buffer)` を引数に取る `internal static byte[]? ReadSmbiosUuid(FirmwareTableReader read)` に分ける。`libelasticlm` と `samples/VerifyLicense` の NativeAOT の大きさを、前と後で測る。
- 問 2（64 ビットのビュー）: `ReadWindowsMachineGuid` を `internal` にし、Windows で MachineGuid が読めることをテストする。`Registry64` を `Default` にした変異は、x86 の .NET で 1 回流して落とし、ここに記録する。
- 問 3（届きにくい確かめ）: 1 MiB の上限、2 回目の大きさの違い、`Length` の範囲は残し、偽の読み手でテストする。`<= 8` と `< 8`、`<= 0` と `< 0` は書き換えず、同値な変異として PR に書く。
- 問 4（§10.3）: MachineGuid の値の型、Windows と macOS の UUID の文字列の形とバイト順、SMBIOS の UUID は格納されたとおりに読むこと、RSMB のバッファの規則、macOS の 63 バイトを足し、設計の独立レビューを通す。
- 問 5: `Guid.TryParse` の広い受け入れは変えずに、§10.3 に書く。
- 問 6: テストは `MachineFingerprintTests` に置く。名前は `ParseGuid_Text_AcceptsGuidFormsInTextByteOrder`、`ReadSmbiosUuid_FirmwareTableSize_ReadsOnlyFrom9BytesTo1MiB`、`ReadSmbiosUuid_SecondCallOrTableLength_RefusesMismatch`、`ReadWindowsMachineGuid_ThisMachine_ReadsTheValue`。

### こちらが決めたこと

- Windows は `ParseGuid(key?.GetValue("MachineGuid") as string)` と書く。`is string` の確かめは型の変換になり、外す変異は作れない。`RegistryKey.GetValue` は REG_EXPAND_SZ の値も展開した文字列で返すので、§10.3 は「文字列の値（REG_SZ と、展開した REG_EXPAND_SZ）」と書いた（問 4 の言葉は「REG_SZ」だった）。
- macOS は `ParseGuid(Marshal.PtrToStringUTF8((nint)text))` と書く。`stackalloc` のポインターは 0 にならないので、前の `?? string.Empty` には届かなかった。`ParseGuid` が `null` を受け取るので、その式は要らなくなった。
- `ReadRawSmbiosData` は `fixed` で `GetSystemFirmwareTable` を包む。空の Span を `fixed` すると null のポインターになるので、1 回目の呼び出しは前と同じく `(null, 0)` になる。
- 大きさが 8 バイト以下のときは、2 回目を呼ばない。テストは、結果に加えて呼び出しの回数も見る。そのため、`size <= 8` を `< 8` にした変異 F1 は、8 バイトのときに 2 回目を呼ぶので落ちる。同値な変異として残るのは、`<= 0` を `< 0` にした F5 だけである。§10.3 には「このときは 2 回目を呼ばない」と書いた。
- `BitConverter.ToInt32` はそのままにした。Windows はいつもリトルエンディアンで動くので、§10.3 の「リトルエンディアンの `Length`」と同じになる。
- 読む ID が変わらないことを確かめた。この機械（Windows 11）で、分岐点（8c35a87）とこのブランチの `MachineFingerprint.Compute("acme-cad")` を流した。どちらも同じ 2 つの指紋を返した（比べたのは、指紋の SHA-256 の先頭 12 桁）。

### 設計の文とテスト

| §10.3 の文 | テスト |
| --- | --- |
| MachineGuid と IOPlatformUUID は UUID の文字列として読み、`Guid.TryParse` が受け入れる形をすべて受け入れ、文字列の順の 16 バイトにする | `ParseGuid_Text_AcceptsGuidFormsInTextByteOrder`（D の小文字と大文字、N、B、P、X、前後の空白と改行は読む。35 文字、37 文字、`uninitialized`、空、`null` は読まない。バイトを逆に並べると変わる ID で、バイト順を見る） |

| 1 回目の大きさが 8 バイト以下か 1 MiB を超えれば読まず、2 回目を呼ばない | `ReadSmbiosUuid_FirmwareTableSize_ReadsOnlyFrom9BytesTo1MiB`（0 と 8 は 1 回だけ呼んで null。9 は 2 回呼んで null。1 MiB は UUID。1 MiB + 1 は 1 回だけ呼んで null） |

macOS の 63 バイトの上限（`CFStringGetCString`）は、OS の API の側に残した。テストはない。

### 変異の確かめ

Windows 11 で、`MachineIdSources.cs` を 1 つずつ変え、`ElasticLM.Licensing.Tests` を作り直して `MachineFingerprintTests` を流した。ファイルは、変異のたびに中身を書き戻した。

| 変異 | 結果 |
| --- | --- |
| G1 `ToByteArray(bigEndian: true)` → `false` | `ParseGuid_…` で落ちた |
| G2 `Guid.TryParse` → `Guid.TryParseExact(text, "D", …)` | `ParseGuid_…` で落ちた |
| F1 `size is <= HeaderLength` → `< HeaderLength` | `ReadSmbiosUuid_FirmwareTableSize_…` で落ちた（8 バイトで 2 回目を呼ぶ） |
| F2 `> 1024 * 1024` → `>= 1024 * 1024` | `ReadSmbiosUuid_FirmwareTableSize_…` で落ちた |
| F3 `> 1024 * 1024` → `> (1024 * 1024) + 1` | `ReadSmbiosUuid_FirmwareTableSize_…` で落ちた |
| F4 2 回目の大きさの確かめを外す（`&& buffer.Length < 0`） | `ReadSmbiosUuid_SecondCallOrTableLength_…` で落ちた |
| F5 `tableLength <= 0` → `< 0` | 生き残った（同値。`Length` 0 は空の表になり null） |
| F6 `tableLength <= 0` を外す | `ReadSmbiosUuid_SecondCallOrTableLength_…` で落ちた（負の `Length` で例外） |
| F7 `tableLength > …` → `>=` | 2 つの `ReadSmbiosUuid_…` で落ちた |

| W1 `RegistryView.Registry64` → `RegistryView.Default` | x86 で `ReadWindowsMachineGuid_ThisMachine_ReadsTheValue` が落ちた（60 件のうち 1 件）。x64 では 60 件すべてが通った（このビルドでは区別できない） |
| W2 値の名前 `"MachineGuid"` → `"MachineGuid2"` | `ReadWindowsMachineGuid_…` で落ちた |
| W3 キーのパスを `…\Cryptography2` にする | `ReadWindowsMachineGuid_…` で落ちた |

x86 は、`dotnet build tests/ElasticLM.Licensing.Tests -c Debug -r win-x86 --no-self-contained`（SDK 10.0.404）で作った。それを、x86 の .NET ランタイム 10.0.15（`DOTNET_ROOT_X86` に `C:\Program Files (x86)\dotnet` を指定）の上で `ElasticLM.Licensing.Tests.exe -class ElasticLM.Licensing.Tests.MachineFingerprintTests` として流した。変異のない木では 60 件すべてが通った。CI は x64 だけで流すので、W1 を確かめたのはこの 1 回である（問 2）。

macOS の読み手の中は、この機械では変異を流せない。`ParseGuid` を Windows と共有するので、G1 と G2 は macOS の規則も確かめる。

### NativeAOT の大きさ

Measure と同じ形で測った（linux-x64、バイト）。WSL のコンテナー（`wslc` 3.0.5、`almalinux:8@sha256:2d0f2eb2…`）に `dnf install clang zlib-devel binutils libicu` と、`dotnet-install.sh --version 10.0.404` で SDK 10.0.404 を入れた。`git archive` で取り出した木ごとに、`dotnet publish src/ElasticLM.Native -c Release -r linux-x64` と `dotnet publish samples/VerifyLicense -c Release -r linux-x64` を流した。どの publish も警告は 0 件だった。

| 木 | `libelasticlm.so` | `VerifyLicense` |
| --- | --- | --- |
| ブランチの分かれ目（8c35a87、`origin/main` と同じ） | 7,295,896 | 4,060,048 |
| このブランチ（0e9d91b） | 7,295,896（±0） | 4,060,048（±0） |

測ったとき `origin/main` は分かれ目のままだったので、`main` にこのブランチをマージした木は、このブランチの木と同じだった（`git merge-tree --write-tree origin/main HEAD` と `HEAD^{tree}` は、どちらも 23361ed）。

linux-x64 では、この変更は大きさに出ない。変えたコードは Windows と macOS の読み手だけで、NativeAOT のコンパイラー（ILC）は、linux-x64 では `OperatingSystem.IsWindows()` と `IsMacOS()` の枝を外すからである（PR #516 の独立レビュー）。そこで win-x64 でも、2 つの木を同じ形で出した。この機械（Windows 11、SDK 10.0.404、Visual Studio の MSVC のリンカー）で、`git archive` で取り出した木ごとに `dotnet publish … -c Release -r win-x64` を流した。警告は 0 件だった。

| 木 | `elasticlm.dll` | `VerifyLicense.exe` |
| --- | --- | --- |
| ブランチの分かれ目（8c35a87） | 6,767,616 | 4,201,472 |
| このブランチ（0e9d91b） | 6,768,640（+1,024） | 4,203,008（+1,536） |

増えた分の内訳を、`VerifyLicense` を `-p:IlcGenerateMapFile=true` で出し直して、2 つの木の map ファイルで比べた。節点の大きさの差は合わせて +611 バイトで、どれも `MachineIdSources` から来ている。

- 新しいメソッドのコード: `ReadSmbiosUuid` 205、`ReadRawSmbiosData` 127、`ParseGuid` 120。
- 外へ移したコードの分だけ減ったもの: `ReadWindowsSmbiosUuid` −307、`ReadWindowsMachineGuid` −85。
- デリゲートの型 `FirmwareTableReader` とその呼び出しの道具: 型 96、`DynamicInvoke` の stub 88、`InvokeOpenStaticThunk` 22、`Invoke` 11、デリゲートを作る helper 19。
- メタデータ 180 と、GC の情報や表の小さな差。

ほかに、正規表現のソース生成のクラスが、名前のハッシュを変えて 92 の節点に現れたが、合わせると ±0 だった。ファイルの大きさの差（+1,536）が節点の差（+611）より大きいのは、PE の節が 512 バイトの単位で揃えられるからである。`elasticlm.dll` の +1,024 も同じコードの差で、map ファイルでは比べていない。

### 同じ種類を探した範囲

`MachineIdSources.cs` のすべての読み手と解析を読んだ。テストのない規則で、残したのは macOS の OS の API の側（`IOServiceMatching` から `CFStringGetCString` まで、63 バイトの上限を含む）と、Windows のレジストリの例外の `catch` である。どちらも、OS の API を偽にしなければ起こせない。

## 退けた案

- **決定:** Windows と macOS は `ParseGuid(string?)` を共有する。
- **理由:** 同じ規則（`Guid.TryParse` と、文字列の順のバイト）が 1 か所になる。Windows の値の型の確かめは `as string` になり、外せなくなる。
- **却下した案:** 読み手ごとに Parse を作る（`ParseMachineGuid(object?)` と `ParsePlatformUuid(string)`）。同じ規則が 2 か所に分かれる（問 1 の案 C）。

- **決定:** SMBIOS は、OS の呼び出しを `FirmwareTableReader` として渡す。
- **理由:** 大きさの上限と下限、2 回目の違い、`Length` の範囲を、すべて OS なしで確かめられる。
- **却下した案:** `RawSMBIOSData` の頭と `Length` だけを解く関数に分ける。大きさの規則と 2 回目の違いが、テストのないまま残る（問 1 の案 B）。

- **決定:** 64 ビットのビューは、x86 で 1 回流して確かめ、CI には足さない。
- **理由:** 32 ビットのビューに値がないことは測ってある。CI と workflow を変えずに、変異が落ちることを確かめられる。
- **却下した案:** CI に x86 のジョブを足す（問 2 の案 B）。CI の時間と workflow の変更が増える。ビューを引数にして両方を読む（問 2 の案 C）。確かめるのが OS の事実になり、コードが選んだビューではない。

- **決定:** 届きにくい確かめを残し、境界の書き方も変えない。
- **理由:** OS から得る値は信頼しない（`security.mdc`）。負の `Length` と超える `Length` は、確かめがなければ例外になる。動きは変えない。
- **却下した案:** 本当の入力で届かない確かめを外す（問 3 の案 B）。外すと例外が外へ漏れるか、上限のない読み方になる。
