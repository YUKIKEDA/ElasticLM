# V1d27（Issue #346、#404、#406）: `elm` の、V1d の低の指摘を片付ける

## Grill の記録

Issue #346 のコメント「V1d27 の Grill」に、持ち主の答え（2026-11-14、問 27-1〜27-7 のすべてが推奨案）がある。#404 と #406 の点は、持ち主の決定（2026-11-13）で、この行の Grill で決める点に足した。設計の本文（`../design.ja.md`）は、§16 の「遠くの答えと、検証していないファイルの文字」、`elm admin` の応答の読み方と `elm admin request` の本文の無通信の上限、§18.1 の「ファイルを署名したライセンス」と「日時として読めない名前」、§5.3 の T15 を持つ。

### 持ち主が決めたこと（2026-11-14、すべて推奨案）

- 問 27-2 F30: `CliFiles.ReadBytes` は、ファイルのバイトを上限を確かめながらそのまま読む。同じ関数を直す V1d24c（Issue #386）の PR に入れる。この PR は、V1d24c の行の文（§20.7 の表、§22 の表、roadmap）に F30 を足した。
- 問 27-3 F31: 遠くの答えと、検証していないファイルから来た文字を出すときは、どこでも C0 と C1 の制御文字を `\uXXXX` に置き換える（`OfflineCommands`、`ServerAdminApi.Unexpected`、`AdminCommands` の `verification_uri`、`LicenseCommands` の `inspect` と、同じ種類のすべて）。
- 問 27-4 T15-3: `elm log verify` が、ファイルごとのサーバーライセンスの ID を文の出力と `--json` に出し、`--license <ID>` を足して、違えば NOT INTACT（終了コード 1）にする。

### 測った事実（`origin/main` の 5e026d0。行の番号は、そのときのもの）

- 遠くの文字を文の出力に書く所（読んで数えた）: `OfflineCommands.cs` の 113 行（問題の `code` と `detail`）と 128 行（発行の答えから、検証せずに読む有効化の ID とライセンスの ID）。`ServerAdminApi.cs` の 86 行（`Unexpected`）。`ServerCommands.cs` の 170〜205 行（`status`、`leases`、`reload` の表示）。`ServerLicenseCommands.cs` の 407 行（読み直しの断りの `detail`）と 514 行（`Refused`。`ActivationClient` の誤りの文は、サービスの `detail` を 1〜512 文字で持つ。`LicenseClient.ProblemOf` の `keepDetail`）。`AdminCommands.cs` の 95 行（発行者）、126〜130 行（`verification_uri`、`user_code`、`verification_uri_complete`）、303 行（誤りの本文）、278〜282 行（成功の本文）。`OidcHttp` と `AdminCredentials` の `CliException` の文（ID プロバイダーの `error` と、発見の文書から読んだ URL を持つ）。`LicenseCommands.cs` の 213 行と 218 行（`inspect` のヘッダーの `GetRawText`）と 336 行（`verify` の断りの文）。`LogCommands.cs` の 105 行（指摘のファイルの名前と文。`LogVerifier` の文は、行の中の `prev.file` と `node` を持つ。`LogVerifier.cs` の 396、416、436 行）。
- `JsonSerializer`（ソースで生成した文脈でない既定の設定）と `Utf8JsonWriter`（既定の `JsonWriterOptions`）は、`"a\u0001\u001b\u007f\u0080\u0085\u009f z"` を `"a\u0001\u001B\u007F\u0080\u0085\u009F z"` と書いた。`JsonDocument` に読んだ `{"a":"x<0x7F><U+0085>y\u001b"}` の `RootElement` を `JsonSerializer` で書くと `{"a":"x\u007F\u0085y\u001B"}` になり、`GetRawText` は 0x7F と 0xC2 0x85 をそのまま返した（.NET 10.0.14、Windows 11、scratch のコンソールのプログラム。`elm` の `CliJsonContext` と `AdminAnswer.WriteIndented` も、エンコーダーを指定しない）。そのため `--json` の出力は C0、DEL、C1 をすでに逃がしていて、`inspect` の文の出力のヘッダーだけが逃がしていなかった。`src/` に `Encoder =` と `JavaScriptEncoder` の指定はない（`rg` で探した）ので、サービスが書く JSON も同じエンコーダーで書く。
- `AdminCommands.Request`（5e026d0 の 258〜305 行）は `HttpClient.Timeout` の 100 秒と `ResponseHeadersRead` で送り、本文を同期の `Stream.Read` と `StreamReader.Read` で読んでいた。`OidcHttp.Create`（`AdminCredentials.cs` の 19〜20 行）は `MaxResponseContentBufferSize = 64 KiB` と既定の `ResponseContentRead` で送り、自前の 64 KiB の数え（52 行）は、`HttpClient` が 64 KiB を超える本文を先に断るので届かなかった。
- `LogCommands.ExpandFiles`（127〜159 行）は、フォルダーのファイルが 0 個のとき `CliException` を投げ、`notLogFiles` の警告は、その後（78〜82 行）でしか書かれなかった。
- `LogReport.Files` は、最初の行が通ったファイルごとに、ファイルの終わりの `LogFileKey(File, LicenseId, KeyId)` を持つ（`LogVerifier.cs` の 337 行）。ファイルの途中の `key.changed` は、別のライセンス ID の鍵にも替えられる（`LogVerifier.cs` の 272〜296 行は、新しい鍵がサービスの鍵でないことだけを確かめる。`ElmServer.ReloadLicense` は、検査を通る別のライセンス ID のファイルも読み込む。§5.4 の「手で入れた古いサーバーライセンス」の行）。
- 確かめていないこと: 無通信の上限の前例（curl の `--speed-time`、wget の `--read-timeout`）。wget の手引きの頁は 2 回とも 429 で読めず、curl の頁は要約しか得られなかった。100 秒は持ち主の決定で、前例には頼らない。

### こちらが決めたこと

- 置き換える範囲は `char.IsControl`（C0、DEL、C1）にした。問 27-3 は C0 と C1 と言うが、§14.5 の「管理 API の本文の文字」（V1d26）が同じ 3 つを制御文字として断るので、範囲をそろえた。16 進は、`JsonSerializer` と同じ大文字の 4 桁にした。
- 誤りの 1 行は、`CommonOptions.Run` で、`CliException` の文をまとめて置き換える。投げる所ごとに置き換えると、置き忘れが残るためである（V1d23 の `Readable` と同じ考え）。`ArgumentException` の文も同じにした。
- `elm admin request` の本文は、LF と TAB を残す。JSON と NDJSON の行を行のまま出すためで、サービスの答えは、その 2 つのほかに制御文字を持たない（上の測ったこと）。CR は置き換える（行の頭に戻して前の文字を上書きできるため。サービスの JSON は CR を書かない）。
- `elm log verify` の文の出力のライセンスの行は、`file: <名前>: server license <ID>`（`elm-service` は `file: <名前>: elm-service`）にし、指摘の行のあと、まとめの行の前に置いた。`--json` の名前は、すでに数を持つ `files` と重ならない `licenses` にした。比べる誤りは、行 0 の、ファイルごとの指摘にした（ほかのファイルの誤りと同じ形で、どのファイルが違うかが分かる）。
- #404 の警告は、標準エラーに、誤りの行の前に書く。結果（標準出力）を書かずに止まるので、`--json` でも標準出力を空にしておくためである。
- 無通信の 100 秒は、読み取りのたびに `CancellationTokenSource(100 秒, CliHost.Time)` を作って数える。ヘッダーまでの 100 秒は、今のとおり `HttpClient.Timeout` に任せた（問 27-6 が決めたのは本文の読み取りである）。
- `OidcHttp` の 30 秒は、`BoundedAnswer.Deadline`（30 秒、`elm` の時計）にした。デバイス認可の問い合わせの繰り返しでは、256 KiB を超えた答えも、ほかの終了コード 3 と同じく通信の失敗として続ける（§16 の手順 5 の「通信の失敗では間隔を 2 倍にし、続ける」）。

### 持ち主に聞くこと

- **ファイルの途中でライセンス ID が替わったログ。** `LogReport.Files` はファイルの終わりのライセンスだけを持つので、ファイルの途中の `key.changed` で A から B に替わったログは、`B` とだけ出て、`--license B` で通る。その前の行は A の鍵の署名である。
  - 案 A（推奨）: `LogReport` に、ファイルごとの、署名したすべてのライセンス ID を持たせ（`ElasticLM.Issuing` の公開の型を変える）、`elm` はすべてを出し、`--license` はすべてと比べる。T15-3 の「どのサーバーライセンスが署名したログか」を、ファイルの中の行の分まで言える。検証と発行の組（`ElasticLM.Issuing`）を触るので、その組の行と並ばないときに入れる。
  - 案 B: 今の形のまま、§5.4 に受け入れる脅威として書く。ライセンス ID を替えるには、そのサーバーのインストール鍵に結びついた別のサーバーライセンスが要り、ベンダーがそれを発行している。行ごとの `lic` は出来事の行に残る。
  - この PR は案 B の形で動き、設計の §18.1 は「持ち主に聞いている」と書く。答えを受けて、案 A なら行を足すか、この PR に入れる。

## 退けた案

- **決定:** 遠くの文字は、出力の所で `\uXXXX` に置き換える（問 27-3）。
- **理由:** 置き換えた文字は、何が来たかを残し、端末を動かさない。
- **却下した案 1:** 制御文字を落とす。何が来たかが消え、調べられない。
- **却下した案 2:** 制御文字を持つ答えを、形の誤りとして断る。サービスと ID プロバイダーの答えの多くは、`elm` が中身を読まない文で、断る理由にならない。

- **決定:** `--json` の出力は置き換えない。
- **理由:** 既定のエンコーダーが、C0、DEL、C1 を逃がす（測った）。

- **決定:** `elm admin request` の本文に、全体の時間の上限を置かない（問 27-6）。
- **理由:** 利用ログのファイルは大きく、遅い回線でも読み終えたい。止まった相手は、無通信の上限で分かる。
- **却下した案:** 全体に時間の上限を置く。大きな本文を読み終えられないことがある。

- **決定:** `OidcHttp` の上限を 256 KiB にする（問 27-7）。
- **理由:** サービスが同じ ID プロバイダーから読む大きさ（§14.6）と同じにする。
- **却下した案:** 64 KiB のまま `BoundedAnswer` にする。サービスが読める答えを、`elm` が読めない。

- **決定:** `elm log verify --license` の違いは誤り（NOT INTACT、終了コード 1）にする（問 27-4）。
- **却下した案:** 警告にする。別のサーバーのログを渡したことが、終了コード 0 で通る。

- **決定:** `CommonOptions.Run` に何でも受ける `catch` を置かない（問 27-1）。
- **却下した案:** すべての例外を終了コード 3 にする。プログラムの誤りが、通信の失敗と区別できなくなる。
