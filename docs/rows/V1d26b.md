# V1d26b（Issue #503）: `elm-service` の PostgreSQL への接続で TLS が使えない（`SSL Mode=Require` 以上は扱われない例外で終わり、`Prefer` と既定は平文でつなぐ）ことを直す

## Grill の記録

- 測った事実:
  - Issue #503 の再現（`origin/main` 9661ee7、Windows 11、.NET SDK 10.0.404、JIT と NativeAOT の `elm-service`、PostgreSQL 18.6 を WSL のコンテナー `wslc` 3.0.5 で、`ssl=on`）: `SSL Mode` を書かないときと `Prefer` は平文でつなぎ、`Require`、`VerifyCA`、`VerifyFull` は `setup` が扱われない `NotSupportedException` で異常終了した。表は Issue #503 の Reproduction にある。
  - Grill の事実調べ（Npgsql 10.0.3 の slim のビルダーに `EnableTransportSecurity()` を付けた小さなコンソール、JIT、同じ環境。サーバーはイメージの snakeoil の証明書で `ssl=on`）:
    - `Prefer` と書かないときは TLSv1.3 でつながる。`Allow` は平文でつながる。
    - `Require` に別の CA の `Root Certificate` を渡しても TLSv1.3 でつながる（証明書を確かめない）。
    - `VerifyCA` は、ルートがないと OS のストアで確かめて断られ、正しいルートでは `Host=127.0.0.1`（名前の違う証明書）でもつながる。`VerifyFull` は、正しいルートと `Host=localhost` でつながり、`Host=127.0.0.1` では名前の違いで断られる。
    - ルートのファイルがないと `NpgsqlException`「Exception while performing SSL handshake」の内側に `FileNotFoundException` が入る。TLS の失敗は、どれも外側の文が同じだった。
    - `PGSSLROOTCERT` でルートを渡すと `VerifyFull` がつながる。`Require` と `Channel Binding=Require` はつながり、`Disable` と `Channel Binding=Require` は断られる。
  - Npgsql 10.0.3 の源（読んだだけ）: `Prefer` は、SSLRequest に `N` が返ると平文に下り、TLS のあとの失敗でも `Disable` でやり直す（`src/Npgsql/Internal/NpgsqlConnector.cs` の `SetupEncryption` と `OpenCore`）。`Prefer` と `Require` は `SslTrustServerValidation`（何でも受け付ける）で、失効の確認も切る。ルートは、コールバック、`Root Certificate`、`PGSSLROOTCERT`、既定の `root.crt` の順に探し、なければ OS のストア。Npgsql は `PGSSLMODE` を読まない（`src/Npgsql/PostgresEnvironment.cs`）。`EnableTransportSecurity()` は AOT の注釈を持たない。
  - libpq は、ルートの CA のファイルがあれば `sslmode=require` を `verify-ca` と同じに扱う（https://www.postgresql.org/docs/18/libpq-ssl.html ）。Npgsql は違う。
  - CI の `postgres:18@sha256:edb0c08…` には `/etc/ssl/certs/ssl-cert-snakeoil.pem`（CN と SAN が `localhost`）と `openssl` があり、`postgres` は `ssl-cert` の組にいる。
- 持ち主が決めたこと（2026-11-28、すべて推奨案。Issue #503 の最後のコメント）:
  - 問 26b-1: `Database.cs` の `NpgsqlSlimDataSourceBuilder` に `.EnableTransportSecurity()` を足す。
  - 問 26b-2: 接続先がループバックでも Unix ソケットでもないときは、`SSL Mode` が `VerifyCA`、`VerifyFull`、明示の `Disable` のどれかでなければ、`setup` と起動で設定の誤り（終了コード 2）にする。複数ホストと、名前がループバックに引けるかの読み方は、この行で決める。
  - 問 26b-3: `elm-service` の NativeAOT の警告と大きさ（CI の 3 つの OS）を変える前と後で PR に書き、`libelasticlm` が変わらないことも示す。数字が動いたら持ち主に戻す。
  - 問 26b-4: (1) `DbException` の内側の例外の文も「The database cannot be used: …」に足す。(2) `Root Certificate`、`SSL Certificate`、`SSL Key` のファイルがないことを設定の誤り（終了コード 2）にする。(3) 広い `catch (Exception)` は足さず、扱われない例外の道がなくなったことをテストで確かめる。

  - 問 26b-6: PostgreSQL の頁（英語と日本語）の案内を `SSL Mode=VerifyFull` と `Root Certificate` に変え、`Prefer` と `Require` の弱さ、ルートを探す順、断るものを書く。設定の参照の頁にも要点を書く。頁の試しのコンテナーは、ループバックで TLS なしのまま。

## 退けた案

- **決定:** 確かめを `ServiceSettings.Load` に置く。
- **理由:** 問 26b-2 は `setup` と起動の両方で終了コード 2 を求める。`Program.cs` は `Load` の誤りだけを 2 にする。
- **却下した案:** `Database.Create` で確かめる。起動では `ElmService.StartAsync` の誤りになり、終了コードが 1 になる。

- **決定:** ループバックは IP アドレスと `localhost` だけで、ほかの名前は名前解決をしない。
- **理由:** 起動のときの DNS や `hosts` の答えで判断が変わらない。ループバックに引ける名前を許すと、名前解決を変えられる者が、確かめない接続を通させられる。
- **却下した案:** 名前を解決して、すべてのアドレスがループバックなら通す。起動のたびに答えが変わりうり、接続のときの解決とも同じとは限らない。

- **決定:** 複数のホストは、1 つでもネットワークの先なら規則を当てる。
- **理由:** Npgsql は、どのホストにつなぐかを接続のたびに選ぶので、ネットワークの先のホストにも確かめない接続が流れうる。
- **却下した案:** 先頭のホストだけで判断する。2 つ目からのホストへの接続が守られない。

- **決定:** CI の証明書を、その実行のたびに PowerShell と .NET で作る。
- **理由:** テストの鍵は実行のときに作る（`.cursor/rules/security.mdc`）。PowerShell と .NET はランナーと手元の両方にあり、`openssl` の版に頼らない。
- **却下した案:** イメージの snakeoil の証明書を `-c ssl=on …` で使う（鍵がイメージの中で公開されている）。ランナーの `openssl` で作る（手元の Windows では Git for Windows の `openssl` に頼ることになる）。
