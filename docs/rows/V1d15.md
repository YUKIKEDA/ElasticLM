### 持ち主が決めたこと（2026-11-14、すべて推奨案 A）

- 問 15-1: 設計をコードに合わせる。§5.1 のライセンスキーの行を「知れば、そのライセンスの上限（有効化の数、席）まで有効化でき、クラウドのフローティングの席も取れる」にする。§5.4 の中継の行は、理由を「中継を動かす者はキーを読め、ライセンシーと同じことを上限まで行える。害はそのライセンスの上限の中にとどまる。止めるには、ライセンスを失効し、新しいキーで発行し直す」に書き換えて、受け入れ直す。
- 問 15-2: 設計の 3 か所（§5.1 のキーの行、§5.4 のサーバーの鍵の行の席数はリース 1 つの席数でリースの数は限らないこと、§5.4 の解除の行の `DeactivationLimit` の既定は上限なしであること）と利用者の文書を、1 つの PR で直す。PR を出す前に、設計の差分の独立レビューを受ける（`.cursor/rules/design-docs.mdc`）。
- 問 15-3: 6 つの指摘（R8-D1、D2、D3、D6、D7、D8）の文は、その場で条件を 1 文足し、`docs/guide/explanation/security-model.md` の受け入れる脅威の一覧へリンクする。
- 問 15-4: `docs/guide/` と `docs/guide.ja/` のすべての頁、`README.md`、`README.ja.md`、`SECURITY.md`、`docs/container.md` を、§5.4 のすべての行と照らし、同じ種類の文も直す。弱いもの（条件が同じ頁にあるか、リンクの先にあるもの）は、限界を言わずにリンクだけを持つ文にだけ 1 文を足し、ほかは直さない理由をこの記録に書く。
- 問 15-5: §5.4 の 3 つの行（`jti` の記録を埋める相手、`github-pages` の artifact の置き換え、`build` の 1 つの RID のジョブによる書き換え）を、`security-model.md` の受け入れる脅威の一覧に足す。1 つ目は顧客のライセンスサーバーの項に置き、同じ頁の「Floods are limited」の文を条件付きにする。2 つ目と 3 つ目は、リリースとサイトの項に 1 つの項目として置く。
- 問 15-6: 利用ログの文は、§5.4 の今の 2 つの例外（サーバーの鍵を持つ者による書き直し、いちばん新しいファイルの削除と切り詰め）で直し、受け入れる脅威の一覧へリンクする。V1d30（Issue #349、T15-2）がもう一度触る文は、持ち主が #349 に書く。
- 問 15-7: レビュー（出す前の設計、正しさ、初めて読む人、日本語、読み直し）は、持ち主の側が別のエージェントで行う。

### こちらが決めたこと

- 設計の §5.4 のサーバーの鍵の行は、範囲の列挙の「席数」を「リース 1 つの席数」にし、それが `n` と機能の `seats` の比べであること、リースの数は限らないことを足した。「席数を無視したリースの署名」は、リース 1 つの席数は範囲に限られるので、「席の数え上げを通らないリースをいくつでも署名でき」にした。
- §5.4 の解除の行は、既定が上限なしであることを、§9.3 と §14.5 の値を挙げて書いた。
- §5.4 の中継の行は、M4d2 の設計のレビュー R4 のときの理由が誤っていたこと、V1d15 で受け入れ直したことを、行の中に書いた（決定 0.94 の「中継が偽る問題の応答とキーの読み取りを §5.4 で受け入れた」は、受け入れたことは変わらないので、そのままにした）。
- 設計の中で同じことを言う文を探した（「キーだけ」「席数を無視」「で絞る」「知れば有効化」「席もトークンも」と、`DeactivationLimit`、中継の語）。ほかに直すものはなかった。§12.7.5 の「これで、…鍵を取り出したサーバーの管理者（§5.4）が出すリースを、サーバーライセンスの範囲に限る」は、1 つずつのリースについての文で、§5.4 の行が数を言うので、そのままにした。

## 退けた案

- **決定:** 設計をコードに合わせ、§5.1 のライセンスキーの行を「知れば、そのライセンスの上限（有効化の数、席）まで有効化でき、クラウドのフローティングの席も取れる」にし、§5.4 の中継の行を、新しい理由で受け入れ直す（問 15-1 の A）。
- **理由:** サービスはキーのハッシュだけでライセンスを探し（`ElmService.Client.cs:117`、`ElmService.Leases.cs:68`）、新しいインストール鍵の証明で足りる。中継を動かす者が得るのは、ライセンシーと同じ権利で、そのライセンスの上限の中にとどまり、失効と発行し直しで止められる。
- **却下した案:** 問 15-1 から問 15-7 の B 以降の案。Issue #333 のコメントには持ち主の答えだけがあり、問の文と退けた案の文はない。問を書いた側から受け取って、ここに書き足す（下書きの段階で未記入）。

- **決定:** 設計の 3 か所と利用者の文書を 1 つの PR で直し、出す前に設計の独立レビューを受ける（問 15-2 の A）。6 つの指摘の文は、その場に条件を 1 文足し、受け入れる脅威の一覧へリンクする（問 15-3 の A）。
- **理由:** 利用者の文書は設計から書き、設計とコードが違えば設計を直す（`.cursor/rules/user-docs.mdc`）。安全だと言う文は、相手と、止めないものを、その場で言う（同じ規則の「Name the threat」）。くわしくは一覧が持ち、同じ注意を頁ごとに書き直さない（同じ規則の、いくつもの頁が共有する注意は 1 か所で説明する）。
- **却下した案:** 上と同じく、問の文から書き足す。
