# V1d18（Issue #337）: リースの検証で、サーバーライセンスの機能そのものの有効期限を確かめる

## Grill の記録

Issue #337 のコメント「V1d18 の Grill」に、持ち主の答え（2026-11-14、問 18-1〜18-5 のすべてが推奨案 A）がある。設計の本文（`../design.ja.md`）は §12.7.1（切り詰め）、§12.7.5 の手順 5 と手順 7（版）と SaaS 型の段落、§13.4（回収の範囲と借り出しの記録）、§19（`ELM_EXPIRED`、`ELM_FEATURE_VERSION_NOT_LICENSED`、`ELM_LEASE_OUT_OF_BOUNDS` の行）を持つ。

### 測った事実（`origin/main` の c408111。行の番号は、そのときのもの）

- リーストークンは機能の版を持たない。`LeasePayload` の `ver` はトークンの形の版である（`LeaseAndProofPayloads.cs` の 12〜14 行）。
- `LeaseVerifier` の手順 3 は `lic`、`feat`、`n ≤ seats` を確かめ（134〜138 行）、手順 5 はサーバーライセンスの `exp + grace` を確かめる（148 行。V1d23 のあとは秒の `long`）。機能の `exp` と `ver` は、どこでも確かめていなかった。`VerifyHosted` は手順 1、2、6 を行う。`ServerIdentity.TryVerify` は、機能を名指さずにサーバーライセンスを検証する。
- `LicenseVerifier` は、機能がない → 版 → `now > feat.exp`（猶予なし）の順に確かめる（295〜318 行）。
- `elm-server` の `LeaseEngine` は、期限の切れた機能の取得と更新を断る（`LeaseRules.CheckFeature`）が、リースと借り出しの `exp` は、サーバーライセンスの `exp + grace` だけで切っていた（`LicenseLimit`、930 行付近。`LeaseRules.Expiry`）。回収（`ReclaimOne`）は `VerifyOwnLease` を通る。
- `elm-service` は `min(ライセンスの exp, 機能の exp)` で切る（`ElmService.Leases.cs` の `LeaseLimit`、613〜620 行付近。§12.7.6 の取得の 9）。
- 再現: 機能の期限の 1 分前に取った 7 日の借り出しは、機能の期限を約 7 日超え、クライアントはそれを受け取った。

### 持ち主が決めたこと（2026-11-14、すべて推奨案 A）

- 問 18-1: 検証器で、リースの `exp` が、サーバーライセンスのその機能の `exp`（猶予は足さない）を超えないことを確かめる。`elm-server` もリースと借り出しの `exp` を `min(ライセンスの exp + grace, 機能の exp)` で切る（`elm-service` の `LeaseLimit` と同じ形）。
- 問 18-2: §12.7.5 の手順 5 に足す（手順の番号は変えない）。§13.4 の範囲と、§12.7.1 の切り詰めの行にも、機能の期限を足す。
- 問 18-3: 誤りは `ELM_LEASE_OUT_OF_BOUNDS`（「The lease outlives the feature of the server license.」）。サーバーで切った結果が 1 秒未満なら `ELM_EXPIRED`。
- 問 18-4: オンプレミスの取得と借り出しの答えで、アプリが版を渡し、サーバーライセンスの機能が `ver` を持つとき、版が範囲になければ、クライアントが `ELM_FEATURE_VERSION_NOT_LICENSED` で断る（§12.7.5 の手順 7 の側。`LicenseClient` の `AcquireMismatch` の近く）。
- 問 18-5: SaaS 型のリースは、クライアントに確かめを足さない。サービスが機能の期限で断り、切ることを §12.7.5 に書く。
- 書く帰結: 機能の期限が短くなったあとの回収は `ELM_LEASE_OUT_OF_BOUNDS`（クライアントは `Lost`）。記録から戻す借り出しのうち、機能の期限を過ぎたものは、期限切れとして読み飛ばす。前のトークンのための移行は設けない（まだリリースしていない）。

### こちらが決めたこと

- 手順 5 の中の順: サーバーライセンスの `exp + grace` を先に、機能の `exp` をあとに確かめる。両方を超えるリースは、前からの文（「The lease outlives the server license.」）のままになる。
- `elm-server` の切り詰めの値は、機能ごとの値として、サーバーライセンスを読むときに 1 度だけ計算する（`LeaseEngine` の `FeaturePool.Limit`）。取得と更新の道に、計算を足さないためである。
- 切り詰めて 1 秒未満のときの `ELM_EXPIRED` の文は「The feature of the server license has expired.」にした。サーバーライセンスの `exp + grace` に達した取得と更新は、`IssueNext` の前に、同じ時刻で `LicenseExpired` が断るので、切り詰めで 1 秒未満になるのは、機能の `exp` のちょうどの秒だけである。V1d18 より前、`IssueNext` の「The server license has expired.」の分かれは、どの状態からも届かなかった（前の確かめが先に断る）。この行で、その文を機能の文に替えた。
- `elm-service` の、切り詰めで 1 秒未満になるときの文も、「The license has expired.」から「The feature of the license has expired.」に替えた（再レビューの K3）。`elm-service` でも、ライセンスの期限は `Licenses.State`（`expires <= now`）が同じ時刻で先に断るので、1 秒未満になるのは機能の期限のちょうどの秒だけである。機能の期限を両方のサーバーで同じに伝えるため、この行で直した（§12.7.6 の取得の 9）。
- 問 18-4 の版の確かめは、`ELM_REQUEST_MISMATCH` の 5 つの比べ（手順 7 の 1〜5）を通ったあとに行う。別の要求への答えや、別の機能のリースは、先に `ELM_REQUEST_MISMATCH` になる。比べ方は、下の「持ち主が決めたこと（PR #446 のあと）」のとおり、公開の `LicensedFeature.CoversVersion` による。はじめは、`ElasticLM.Licensing` の `InternalsVisibleTo` に `ElasticLM.Client` を足し、内部の型（`FeatureVersion`、`FeatureVersionRange`）を直接使っていた。
- `major.minor[.patch]` の形でない版は、範囲の外とする（正しいサーバーは、そういう版を `ELM_INVALID_ARGUMENT` で断り、リースを出さない）。サーバーライセンスの `ver` は、検証のとき（`LicensePayloadRules`）に範囲として読めたものだけが通るので、読み直しが失敗することはない（`LeaseRules.CheckFeature` と同じく、失敗すれば範囲の外として扱う形にしてあるが、その状態には届かない）。
- 版で断ったときの扱いは、`ELM_REQUEST_MISMATCH` と同じにした: リースを持たず、借り出しを保存せず、その要求の証明の `jti` を名指す返却を送る（§12.7.7）。サーバーが出したリースは、その要求で出したものなので、この返却で消える。

### 持ち主が決めたこと（PR #446 の独立レビューの K1 のあと、2026-11-14。Issue #337 の最後のコメント）

- 版の確かめは、`ElasticLM.Licensing` の内部の型を `ElasticLM.Client` に開く（`InternalsVisibleTo`）のではなく、公開の型 `LicensedFeature` に公開のメソッド `CoversVersion(string version)` を 1 つ足し、それで確かめる（推奨案）。理由: `ElasticLM.Client` と `ElasticLM.Licensing` は別々に配るパッケージで、`ElasticLM.Client` の依存は版の下限だけである。内部の型でつなぐと、`ElasticLM.Licensing` だけを上げた組み合わせで、内部の型が変わっていれば実行時の例外になりうる。
- `CoversVersion` は、検証と同じ内部の型で読み、`major.minor[.patch]` の形でない版には `false` を返し、範囲のない機能にはそれ以外の版で `true` を返す。`null` は `ArgumentNullException`。クライアントは、機能が範囲を持つときだけ呼ぶ（範囲のない機能は確かめない、§12.7.5 の手順 7）。

### 持ち主が決めたこと（PR #446 の再レビューの K4 のあと、2026-11-14。Issue #337 の最後のコメント）

- 取得と更新の答えは、クライアントが今使っているサーバーライセンスだけで確かめる。手元に残した前のサーバーライセンスは、それに結びついた既存のリースの返却と回収にだけ使う（推奨案）。理由: 前のサーバーライセンス（機能の期限が長い、または版の範囲が広い）を名指す答えで、入れ替えたあとの機能の期限と版の範囲を越えるリースが、手順 5 と 7 を通っていた（`ELM-Server-License` のヘッダーで写しを選んでいた）。
- 実装（`LicenseClient.ReadLeaseAsync`）: 今の写しで確かめる。ヘッダーが手元にない `jti` を名指すときだけ、サーバーライセンスを取り直す。前の写しを名指す答えは、トークンの `slic` が今の写しと違うので、§12.7.5 の手順 1 の `slic` の比べで `ELM_LEASE_OUT_OF_BOUNDS`（「The lease was issued under another server license; fetch the server license again.」）になる。新しい誤りの文は作らなかった。前の写しを名指す答えで取り直さないのは、取り直すとサーバーが前のサーバーライセンスを返しうるためである（鍵を持つ者も、前のファイルに戻したサーバーも）。
- 帰結: サーバーが、クライアントの手元にある前のサーバーライセンスのファイルに戻ると、そのクライアントは `ResetServerPin` を呼ぶか作り直すまで、そのサーバーからリースを取れない（§13.5）。

### 持ち主が決めたこと（K4 の帰結、2026-11-14。Issue #337 の最後のコメント）

- 上の帰結を受け入れ（推奨案 A）、設計 §13.5 と利用者の文書（セキュリティモデルの頁の古いサーバーライセンスのファイルの項、サーバーライセンスの更新の How-to、`elm server reload` の項）に書く。運用者が前のファイルに戻したら、新しい方を知っているクライアントは `ResetServerPin`（C では `elm_client_reset_server_pin`）を呼ぶか、作り直す。

### 同じ種類を探した範囲

- `src/` の `VerifyOnPremises`、`VerifyOwnLease`、`LeaseRules.Expiry` を呼ぶ所のすべて: クライアントの取得と更新の答え（`ReadLeaseAsync`）、保存した借り出しを読む所（`LicenseClient` の借り出しのファイル。手順 5 を通るので直った）、`elm-server` の回収（直った）、`elm-service` の取得と更新（前から機能の期限で切る）。
- `elm-server` の記録から借り出しを戻す所（`LeaseEngine.Restore`、`TryReadOwnLease`）は、§13.4 のとおり今のサーバーライセンスの範囲を問わない。V1d18 からの借り出しは機能の期限を超えないので、期限切れとして読み飛ばされる（`Borrow_BeforeTheFeatureExpiry_EndsAtIt`）。

### 退けた案

- **決定:** 取得と更新の答えは今のサーバーライセンスだけで確かめる（持ち主の決定、PR #446 の再レビューの K4 のあと）。
- **理由:** 前のサーバーライセンスを名指す答えで、入れ替えたあとの機能の期限と版の範囲を越えるリースを通さないため。
- **却下した案:**
  - 鍵を取り出したサーバーの脅威として受け入れ、設計に書くだけにする。この行が足す手順 5 と 7 の確かめが、前のサーバーライセンスを名指すだけで外れる。
  - 別の行にする。この行の確かめが、この行のうちに穴を持つことになる。

- **決定:** K4 の帰結（前のファイルに戻したサーバーから、新しい方を知っているクライアントがリースを取れない）を受け入れる（持ち主の決定）。
- **理由:** 前のファイルに戻すのは、受け入れた脅威（§5.4、§13.1 の「手で入れたファイルの限界」）の手での操作で、ふつうの更新では起きない。
- **却下した案:** (B) どのリースも指さなくなった前の写しを捨て、次にその `jti` を名指されたら取り直す。リースを持たないクライアントに対して、前のサーバーライセンスの機能の期限と版の範囲で借りる道が開き直る。

- **決定:** 問 18-4 の版の確かめに、公開の `LicensedFeature.CoversVersion` を足して使う（持ち主の決定、PR #446 の K1 のあと）。
- **理由:** 別々に配るパッケージを内部の型でつながず、公開の API で 1 つの読み方を共有するため。
- **却下した案:**
  - (A) `ElasticLM.Licensing` の `InternalsVisibleTo` に `ElasticLM.Client` を足し、内部の型を直接使う（この PR のはじめの形）。`ElasticLM.Client` の依存は下限だけなので、`ElasticLM.Licensing` だけを上げた組み合わせで実行時の例外になりうる。
  - (B) (A) のうえで、`ElasticLM.Client` の `ElasticLM.Licensing` への依存を、ちょうどの版（`[x.y.z]`）に固定する。利用者が `ElasticLM.Licensing` だけの直しを取れなくなり、ほかのパッケージとの版の解決も狭まる。
  - (C) 版と範囲を読むコードを `ElasticLM.Client` に写す。検証とクライアントで読み方が分かれうる（2 つの実装）。
