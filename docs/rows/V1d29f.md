# V1d29f（Issue #481）: Kestrel の上限が HTTP/2 でも効くことを、`elm-service` と `elm-server` の両方のテストで確かめる

## Grill の記録

V1d29 の作業（PR #476）が見つけ、持ち主の決定（2026-11-22、Issue #348 の最後のコメントの 5、[V1d29.md](V1d29.md) の持ち主への問い 5 の案 A）で足した行。この行の Grill で決める点（設計 §20.7 の表）は、超えたときの答え（ストリームのリセットか 431 か）と、`elm-service` を TLS で待ち受けるテストの形の 2 つだった。答えはソースと実行で決まる事実で、製品も上限の値も変えないので、持ち主への問いは立てていない。

### 読んだソース

aspnetcore v10.0.14 の次のファイル。手元の実行に使った ASP.NET Core のランタイムは 10.0.15 で、v10.0.15 の同じファイルは v10.0.14 とバイトまで同じだった（GitHub の API で両方の版を取り、`cmp` で比べた）。

- `src/Servers/Kestrel/Core/src/Http2Limits.cs`: 既定は `MaxStreamsPerConnection` 100、`HeaderTableSize` 4,096、`MaxFrameSize` 16,384、`MaxRequestHeaderFieldSize` 32 KiB、`InitialConnectionWindowSize` 1 MiB、`InitialStreamWindowSize` 768 KiB。
- `src/Servers/Kestrel/Core/src/KestrelServerLimits.cs`: `MaxRequestLineSize` 8 KiB、`MaxRequestHeaderCount` 100、`MaxRequestHeadersTotalSize` 32 KiB。HTTP/2 も、この 3 つを使う（下）。
- `src/Servers/Kestrel/Core/src/Internal/Http2/Http2Connection.cs`: コンストラクターが、HPACK の復号を `HeaderTableSize` と `MaxRequestHeaderFieldSize` で作り、SETTINGS の `MAX_HEADER_LIST_SIZE` に `MaxRequestHeadersTotalSize` を出す。`OnHeaderCore` は、擬似ヘッダーを含むすべての項目の名前と値のバイトを足し（RFC 9113 の 1 項目 32 オクテットは足さない）、和が `MaxRequestHeadersTotalSize` の 2 倍を超えると `PROTOCOL_ERROR` の接続のエラーにする。ヘッダーの数が `MaxRequestHeaderCount` の 2 倍（`Http2Stream.cs` の `_eagerRequestHeadersParsedLimit`）を超えたときの `TooManyHeaders` も、ここで `PROTOCOL_ERROR` の接続のエラーにする。`StartStream` は、同時に開いたストリームが `MaxStreamsPerConnection` を超えると、そのストリームを `REFUSED_STREAM` でリセットする。
- `src/Servers/Kestrel/Core/src/Internal/Http2/Http2Stream.cs`: `TryValidatePseudoHeaders` は、要求の行の代わりに `:method`、`:scheme`、`:authority`（または Host）、`:path` の値の長さの和を `MaxRequestLineSize` と比べ、超えるとストリームを `PROTOCOL_ERROR` でリセットする（`ResetAndAbort`）。`TryParseRequest` は、その後で、和が `MaxRequestHeadersTotalSize` を、数が `MaxRequestHeaderCount` を超えると、431 で答える。
- `src/Servers/Kestrel/Core/src/Internal/Http/HttpProtocol.cs`: `OnHeader` が、擬似ヘッダーを含むすべての項目を数える（`IncrementRequestHeadersCount`）。
- `src/Shared/runtime/Http2/Hpack/HPackDecoder.cs`: `OnStringLength` は、HPACK の文字列（名前か値。Huffman で符号化されていれば符号化されたままの長さ）が `MaxRequestHeaderFieldSize` を超えると `HPackDecodingException` を投げ、`Http2Connection` はそれを `COMPRESSION_ERROR` の接続のエラーにする。

`MaxRequestHeaderFieldSize` と `MaxRequestHeadersTotalSize` は同じ 32 KiB なので、32 KiB ちょうどの値は復号を通っても、名前と擬似ヘッダーを足した和が上限を超え、200 にはならず 431 になる。1 つの値の上限のちょうどの側で見えるのは、接続が切れずに 431 で答えることである。

### 測った事実

測ったのは、`origin/main` の 9661ee7 から切ったこの行のブランチ、Windows 11（build 26300）、SDK 10.0.404、ASP.NET Core 10.0.15、Debug。同じプロセスのサーバーに、テストが HTTP/2 のフレームを組んで送った（TLS の ALPN で h2 を選ぶ。プリフェイスと空の SETTINGS のあとに、HEADERS と CONTINUATION。どの項目も、索引を使わず、Huffman で符号化しない HPACK のリテラル）。ヘッダーの数は、4 つの擬似ヘッダー（`:method`、`:scheme`、`:authority`、`:path`）を含めて数え、和は擬似ヘッダーを含む名前と値のバイトで数えた。答えは、最初の HEADERS の `:status`、そのストリームの RST_STREAM、GOAWAY のどれかで読み、答えか RST_STREAM のあとは、同じ接続で飾りのない要求を送って 200 を確かめた。

| 上限 | 送ったもの | `elm-service`（`GET /health`） | `elm-server`（`GET /v1/nonce`） |
| --- | --- | --- | --- |
| 要求の行（擬似ヘッダーの値の長さの和） | 8,192 | 200 | 200 |
| | 8,193 | RST_STREAM、`PROTOCOL_ERROR`（接続は残る） | 同じ |
| ヘッダーの数 | 100 | 200 | 200 |
| | 101 | 431 | 431 |
| | 200 | 431 | 431 |
| | 201 | GOAWAY、`PROTOCOL_ERROR` | 同じ |
| 名前と値の和 | 32,768 | 200 | 200 |
| | 32,769 | 431 | 431 |
| | 65,536 | 431 | 431 |
| | 65,537 | GOAWAY、`PROTOCOL_ERROR` | 同じ |
| 1 つの値の長さ | 32,768 | 431（和の上限を超える） | 431 |
| | 32,769 | GOAWAY、`COMPRESSION_ERROR` | 同じ |

431 のあとも、接続は残った。どれも、ソースから先に書いた期待のとおりだった。

### `HttpClient` をやめた理由と、接続のリセット

最初は、`HttpClient`（`SocketsHttpHandler`、`RequestVersionExact`）で送るテストを書いた。期待の値は同じだったが、繰り返すと次の 2 つで落ちた。

- 和が 32 KiB を超える要求を、`HttpClient` が送らずに断ることがある（「The HTTP request headers length exceeded the server limit of 32768 bytes.」）。`elm-service` のテストを 30 回流して、6 回で `size` の 32,769 がこれで落ちた。dotnet/runtime v10.0.15 の `SocketsHttpHandler/Http2Connection.cs` は、サーバーの SETTINGS の `MAX_HEADER_LIST_SIZE` を受け取ったあとは、項目ごとに 32 オクテットを足した大きさがそれを超えるヘッダーを、送る前に断る。SETTINGS が要求を書く前に届くかは競争なので、超える要求がサーバーに届くかが決まらない。Kestrel が 431 で答える大きさ（和が 32 KiB を超える）は、`HttpClient` の数え方でも 32 KiB を超えるので、SETTINGS が届いたあとは、`HttpClient` では 431 のテストができない。
- 接続を切る場合に、GOAWAY の代わりに、リセットされた接続を読むことがある。`HttpClient` の形で 8 回流して、1 回で `field` の 32,769 が「Unable to read data from the transport connection」（`SocketException`、接続の中止）で落ちた。フレームを組む形の最初の版は、サーバーの SETTINGS に ACK を返していて、`elm-server` のテストを 30 回流して、1 回で `size` の 65,537 が、同じく接続のリセットで落ちた（`elm-service` は 30 回とも通った）。どちらも、Kestrel が接続を切ると決めたときに、クライアントがそのあとに書いたバイト（`HttpClient` では値の残りのフレーム、最初の版では ACK）があった。
- 直した形: リクエストのあとには何も書かない。Kestrel は SETTINGS の ACK を待たない（`Http2Connection.cs` の `ProcessSettingsFrameAsync` は、ACK を受けても何もしない。このファイルに、ACK を待つ時間の決まりはない）。1 つの値の上限を超える要求は、その値の長さ（HPACK の文字列の長さ）までを送り、END_HEADERS を付けない。Kestrel は長さを読んだところで断る（`HPackDecoder.cs` の `OnStringLength`）。ヘッダーの数と和が 2 倍を超える要求は、超える項目が最後の項目になるので、Kestrel が断るまでに、送ったバイトをすべて読む。直した形で、両方のテストを 50 回ずつ流して（12 件の 50 回で 600 件ずつ）、どちらも 1 回も落ちなかった。

### 同じ種類を探した範囲

- `Protocols` を設定する場所: `src/` に `Protocols` と `HttpProtocols` はない（`rg`）。どちらのサーバーも、TLS の待ち受けでは既定の `Http1AndHttp2` で、http の待ち受け（`elm-service` の `http://` の設定）は HTTP/1.1 だけになる（既定は `ListenOptions.cs` の `DefaultHttpProtocols`。TLS のない接続で HTTP/1 と HTTP/2 の両方を受ける設定なら、ALPN がなく見分けられないので HTTP/1 にする。aspnetcore v10.0.14 の `Internal/HttpConnection.cs` の `SelectProtocol`）。
- Kestrel の上限を変える場所: `src/` で `kestrel.Limits` を変えるのは、2 つのサーバーの `MaxRequestBodySize` だけだった（`rg "kestrel\.Limits"`）。

### 行の外で見つけたこと

- `Http2Limits.cs` のほかの既定（同時に開けるストリーム 100 を超えたストリームの `REFUSED_STREAM`、フレーム 16 KiB、HPACK の表 4 KiB、受信の窓）には、テストがない。Issue #481 の Cases は、ヘッダーの 3 つの上限だった。テストを足すかは、持ち主に聞く（この行の PR の問い）。

## 退けた案

- **決定:** HTTP/2 のテストは、テストが組んだフレームを送り、RST_STREAM と GOAWAY を読む。
- **理由:** `HttpClient` は、サーバーの SETTINGS が届いたあとは、和の上限を超えるヘッダーを自分で断るので、431 の要求がサーバーに届くかが競争で決まる（上の「`HttpClient` をやめた理由」）。また、RST_STREAM と GOAWAY に同じ `HttpProtocolException` を投げるので、ストリームのリセットと接続のエラーを、エラーコードだけでは見分けられない。
- **却下した案:** `HttpClient` で、超える要求の前に SETTINGS を受け取らせない。`SocketsHttpHandler` に、その順序を決める手段はない。
- **却下した案:** `HttpClient` で、接続が切れたかを、次の要求が新しい接続を要したか（`ConnectCallback` の数）で見る。見分けはつくが、上の競争は残る。
