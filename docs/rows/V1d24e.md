# V1d24e（Issue #498）: 要求のバイトを書く前に終わった打ち切りと取り消しを、端末から出なかった要求として扱う

## Grill の記録

Issue #498 のコメント「決定（持ち主、2026-11-28、V1d24e の Grill、すべて推奨案）」に、持ち主の答えがある。設計の本文（`../design.ja.md`）で変えたのは、§10.4 の手順 2、§12.1 の「応答の読み方」の時間の項、§12.6.2、§12.7.3、§12.7.7 と、§20.7 と §22 の V1d24e の行である。

### 測った事実

- 測り方: `origin/main` の 0f3e24e のとき、使い捨てのコンソールプロジェクト（net10.0、Release）で測った。SDK 10.0.404、Windows 11（10.0.26300）である。本文のある HTTP/1.1 の `POST` を、`SocketsHttpHandler`（`AllowAutoRedirect = false`、`HttpClient.Timeout` は無限）で送り、要求のトークンを 2 秒か 3 秒で取り消した。届かない宛先には `10.255.255.1:81` を使った。それ以外の相手はループバックで待ち受けた。
  - 平文で待つだけの相手。
  - TCP は受けるが TLS を話さない相手。
  - TLS を済ませて答えない相手（自己署名の証明書）。
  - 1 回目に答え、2 回目を持つ相手（プールの接続）。
  - 平文の HTTP プロキシ。
  - CONNECT に答えないプロキシ。
  - CONNECT に 200 を返して先へつなぐプロキシ。
  - `Accept` しない待ち受け。
  - 終わらない `ConnectCallback`。
- 例外の形:
  - 30 秒の打ち切り（製品ではトークン）と取り消しは、どの段階でも `HttpRequestError` を持たない `TaskCanceledException` になった。
  - 接続や TLS の前に止まったとき（届かない宛先、TLS を話さない相手、CONNECT に答えないプロキシ）は、中に `TaskCanceledException` だけが入る。要求を書いたあとに止まったときは、中に `IOException` と `SocketException`（`OperationAborted`）が入る。段階は中身の形で分かれるが、これは文書にない実装の細部で、約束された値はない。
  - Windows で届かない宛先につなぐと、21.4 秒で `HttpRequestException`（`ConnectionError`、中は `SocketException` の `TimedOut`）になった。30 秒より前なので、もとから出なかった要求だった。Linux では tcp(7) の `tcp_syn_retries` の既定 6 で約 127 秒待つ（測っていない）。macOS は確かめていない。
- `ConnectCallback`:
  - 接続ごとに呼ばれ、要求ごとではない。要求を取り消して 300 ミリ秒たっても、コールバックのトークンは取り消されていなかった。プールの接続を使い回す 2 回目の要求では、呼ばれなかった。
  - プロキシを使うときは、プロキシへの接続にだけ呼ばれ、終点はプロキシの番地だった。CONNECT のトンネルの先の接続には呼ばれなかった。
  - 要求の `AsyncLocal` の値は、`ConnectCallback` の中からも見えた。接続を始めた要求の実行コンテキストが流れるためだが、その要求がその接続で送られるとは限らない。
- `ConnectTimeout`: 中に `TimeoutException`（「A connection could not be established within the configured ConnectTimeout.」）を入れた `TaskCanceledException` になり、`ConnectionError` にはならなかった。実の時計で数える。
- `PlaintextStreamFilter` で包んだストリームへの書き込みで、その要求の `AsyncLocal` の印を立てる形を、14 の場合で試した。
  - 印が立たなかった場合: 届かない宛先、TLS を話さない相手、終わらない `ConnectCallback`。CONNECT の接続を包まないようにすると、CONNECT に答えないプロキシと、トンネルの先で TLS が進まない場合も立たなかった。
  - 印が立った場合: 平文で待つだけの相手、TLS を済ませて答えない相手、プールの接続での 2 回目の要求、平文の HTTP プロキシ、`Accept` しない待ち受け（カーネルが接続を受ける）、トンネルの先の TLS の上の要求。
  - フィルターに渡る `InitialRequestMessage` は、CONNECT の接続では `CONNECT`、トンネルの先の接続ではもとの要求だった。
- 読んだ .NET の源（dotnet/runtime の release/10.0、`src/libraries/System.Net.Http/src/System/Net/Http/SocketsHttpHandler/`）:
  - `ConnectionPool/HttpConnectionPool.cs`:
    - `ConnectAsync`: `ProxyTunnel` は `EstablishProxyTunnelAsync` を通り、`ConnectToTcpHostAsync`（`ConnectCallback` を呼ぶ所）を通らない。
    - `ConnectToTcpHostAsync`: 取り消しでない例外を `ConnectHelper.CreateWrappedException` で包む。
    - `ApplyPlaintextFilterAsync`: フィルターを接続ごとに、TLS のあとで呼ぶ。
    - `GetConnectTimeoutCancellationTokenSource` と `CreateConnectTimeoutException`: `ConnectTimeout` は `new CancellationTokenSource(Settings._connectTimeout)` で、OCE の中に `TimeoutException` を入れる。
  - `ConnectHelper.cs` の `CreateWrappedException`: `AuthenticationException` を `SecureConnectionError` に、`SocketError.HostNotFound` と `TryAgain` を `NameResolutionError` に、それ以外を `ConnectionError` にする。
  - `ConnectionPool/HttpConnectionPool.Http1.cs` の `InjectNewHttp11ConnectionAsync`: 接続を作る処理は要求から切り離されていて、接続ごとの `ConnectTimeout` のトークンを渡す。
  - `ConnectionPool/HttpConnectionWaiter.cs` の `SetTimeoutToPendingConnectionAttempt`: 要求が終わったあとの、作りかけの接続の打ち切り。遅らせる時間の既定値は確かめていない。
  - `HttpConnection.cs`: `NetworkStream` の `Socket.Poll` を使うのは同期の要求（`!async`）だけである。包んだストリームでは `NetworkStream` に見えなくなるが、このクライアントは非同期でしか送らないので、変わらない。

### 持ち主が決めたこと（2026-11-28、すべて推奨案）

- Q1: `PlaintextStreamFilter` で平文のストリームを包み、要求のバイトを書いたら、その要求の `AsyncLocal` に印を付ける。
- Q2: 印で「出なかった」とするのは、打ち切りと取り消しのうち、要求のバイトを書かなかったものだけにする。`HttpRequestException` は今の 4 つの値のまま見分ける。
- Q3: 有効化、リースの更新、取得と借り出しの返却の 3 つすべてに当てる。有効化の文は「The service cannot be reached」に分ける。
- Q4: CONNECT のトンネルを作る接続には印を付けない。
- Q5: 印の仕組みを付けた handler（`BoundedAnswer.CreateHandler`）を通った要求にだけ、この見分けを使う。
- Q6: テストは (a)〜(f) のとおりにする。(b) は、決定の文の「`elm-server` を相手に」と違い、ループバックの相手に対して確かめる形を、持ち主があとで受け入れた（下の「テスト」）。

### こちらが決めたこと

- 印は `BoundedAnswer` の中に閉じる。
  - `CreateHandler` が `PlaintextStreamFilter` を付ける。
  - `CreateClient` は、`HttpClient` を継いだ公開しない型（`MarkingClient`）を返す。間の `DelegatingHandler` をたどった先が、そのフィルターを持つ `SocketsHttpHandler` かどうかを覚える。フィルターは 1 つのフィールドに持ち、参照で比べる（Q5）。
  - `SendAsync` は、印のある client のときだけ、要求ごとに新しい印を `AsyncLocal` に置く。
- 書く前に終わったことは、公開しない例外の型で `NeverSent` に渡す。打ち切りは `TimeoutException` を継ぐ型、取り消しは `OperationCanceledException` を継ぐ型で、文は変えない（打ち切りは「No whole answer came within 30 seconds.」、取り消しはもとの例外の文）。どちらも継いだ型なので、`TimeoutException` と `OperationCanceledException` を捕まえる `elm` の呼び出し（`OfflineCommands`、`AdminCredentials`、`ServerAdminApi`）の振る舞いと文は変わらない。
- リースの誤りの文（「The server cannot be reached: …」）は、24b のときと同じく変えない。
- `elm` の `BoundedAnswer.CreateHandler` も同じフィルターを持つ（`ServerAdminApi` の Unix ドメインソケットも）。`NeverSent` を使わないので、振る舞いは変わらない。

### テスト

- (a) `LeaseAnswerTests.Renewal_SixteenEndedBeforeTheyWereWrittenThenAnswerLost_RetryNamesOnlyTheLostRenewal`: 期間 1 時間のリースで、中継（`Recorder.HoldNextRenewals`）が、16 回の更新をクライアントの handler の手前で持ち、30 秒の打ち切りで終わらせる。そのあと答えをなくし、`Held`、`seq` 2、効く `jti` がなくした要求のものになる。
- (b) `BoundedAnswerTests`（本物のソケットと TLS、偽の時計）:
  - `NeverSent_EndedBeforeAnyByteWasWritten_IsTrue`: TCP は受けるが TLS を話さない相手（打ち切り、取り消し、`DelegatingHandler` を挟んだ打ち切り）と、CONNECT に答えないプロキシ（打ち切り、取り消し）。
  - `NeverSent_EndedAfterTheRequestWasWritten_IsFalse`: TLS を済ませて要求を読み、答えない相手（打ち切り、取り消し）、平文の HTTP プロキシ（打ち切り、取り消し）、プールの接続での 2 回目の要求（打ち切り）。
  - `NeverSent_HandlerWithoutTheMark_IsFalseForATimeLimit`: 自前の `SocketsHttpHandler` と、`PlaintextStreamFilter` を差し替えた handler（Q5）。
  - Q6 の (b) は「`elm-server` を相手に」だったが、本物の TLS の 3 つの形は、ループバックの相手に対して、この 3 つのテストで確かめた。決定の文と違うこの形は、PR #524 で持ち主に聞き、持ち主が受け入れた（2026-11-28、Issue #498 のコメント）。`elm-server` の前に TCP の中継を置く形は作っていない。リースの要求はサーバーのピンで TLS を確かめるので、中継は TLS を終えられず、「書いたあとに答えない」形を `elm-server` の前では作れない。`elm-server` と `elm-service` を相手にした形は、(a)、(c)、(d)、(e) が、クライアントの handler の手前で持つ中継（`Recorder`）で確かめる。
- (c) `LeaseAnswerTests.Renewal_EndedByTheTimeLimit_IsNamedByTheRetry` を `Renewal_EndedByTheTimeLimitBeforeItWasWritten_IsNotNamedByTheRetry` にした。再試行の本文は `{"seq":1}` で、持った更新の `jti` を名指さない。
- (d) `LostAcquisitionTests.Acquire_EndedBeforeItWasWritten_IsNotReleased`: 中継（`Recorder.HoldNextAcquisition`、この行で足した）が取得を手前で持つ。取り消しでも打ち切りでも、返却を送らず、借りも作らない。次の取得は `POST` だけを送る。書いたあとの取り消しは、前からある `Acquire_Canceled_OwesTheReleaseWithoutWaiting` が、返却を借りにすることを確かめる。
- (e) `HostedLeaseAnswerTests.Hosted_SixteenEndedBeforeTheyWereWrittenThenAnswerLost_RetryGetsTheLostRenewalsToken`: `elm-service` で (a) と同じ。
- 有効化: `ActivationClientTests.Refresh_EndedBeforeOrAfterItWasWritten_IsUnreachableOrUnanswered`。書く前の打ち切りは「The service cannot be reached: No whole answer came within 30 seconds.」、書く前の取り消しは「The service cannot be reached: 」で始まる文で、どちらも `jti` を残さない。書いたあとの打ち切りは「The service did not answer: …」で `jti` を残す。
- 前からある `AnswerLimitTests.Request_AnswerThatStops_IsANetworkErrorAfterThirtySeconds` は、要求を読んだあとに止まる相手なので、有効化の文は「The service did not answer: 」のまま通る。

### 同じ種類を探した範囲と、行の外で見つけたこと

- 答えのない要求を見分ける所を、`src/` で `NeverSent`、`Unanswered`、`OperationCanceledException`、`TimeoutException` で探した。`NeverSent` を使うのは、`LicenseClient.SendAsync`（更新、取得、借り出し、返却、回収が通る）と `ActivationClient.SendAsync` の 2 つだけで、どちらにも当たる。`BoundedAnswer.SendAsync` を使うほかの所（`LicenseClient` の最初の接続の `GET /v1/server/license`、`elm` の `OfflineCommands`、`AdminCredentials`、`ServerAdminApi`）は、答えのない要求の一覧を持たない。
- 利用者の文書で、前の振る舞いを書いていたのは、`explanation/floating-licenses.md` の英語と日本語の 2 か所（`retry` に入れない要求と、返却を送らない取得）で、この PR で直した。`docs/guide/` と `docs/guide.ja/` を「never left」「did not answer」「デバイスから出な」で探し、ほかにはなかった。
- 行の外で見つけたことはない。

## 退けた案

- **決定:** 要求のバイトを書いたかを、`PlaintextStreamFilter` で包んだストリームの書き込みで、要求ごとの `AsyncLocal` の印として見る（Q1）。
- **理由:** HTTP/1.1 の要求は、その要求の非同期の流れの中で書かれるので、プールの接続でも印が要求に結びつく。名前の解決、ソケット、プロキシは .NET のままで、偽の時計で試せる。測った 14 の場合で期待どおりだった。
- **却下した案:** B: `ConnectCallback` で接続ができたことを覚える（接続ごとで要求に結びつかない。プロキシのときはプロキシへの接続にしか呼ばれない。TLS の前に止まったときを「つながった」と見る。名前の解決とソケットを製品が持つ）。C: `ConnectTimeout` を 30 秒より短くする（`ConnectionError` ではなく OCE になり、実の時計で数えるので `testing.mdc` に反し、取り消しを覆わない）。D: 例外の中に `IOException` があるかで見分ける（文書にない実装の細部）。

- **決定:** 印で見分けるのは、打ち切りと取り消しだけにする（Q2）。
- **理由:** release/10.0 では、書く前の `HttpRequestException` は 4 つの値のどれかになるので、動きはどちらでも同じである。すべての失敗に当てると、内側を呼ばずに例外を投げるテストの中継の模型が変わり、V1d24b のテストを広く作り直すことになる。
- **却下した案:** 書いていない要求の失敗をすべて出なかったとする。

- **決定:** 有効化、リースの更新、取得と借り出しの返却の 3 つすべてに当て、有効化の文を「The service cannot be reached」に分ける（Q3）。
- **理由:** 見分けは `BoundedAnswer.NeverSent` の 1 か所で、有効化では、つなぐあいだに切れる要求が 16 回続くと `ELM_INVALID_STATE` になって送れなくなっていた。
- **却下した案:** リースだけに当てる。

- **決定:** CONNECT のトンネルを作る接続は包まない（Q4）。
- **理由:** その接続に書くのは CONNECT の要求と、トンネルの上の TLS のバイトで、もとの要求ではない。
- **却下した案:** CONNECT の接続も包む（CONNECT に答えないプロキシと、トンネルの先で TLS が進まない要求を、届いたかもしれない要求と数える）。

- **決定:** 印の仕組みのない handler では、印がないことを出なかったと読まない（Q5）。
- **理由:** そう読むと、届いた要求まで一覧から外し、次の再試行を複製と判定させる側に誤る。
- **却下した案:** どの handler でも印で見分ける。
