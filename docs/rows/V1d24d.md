# V1d24d（Issue #444）: 時計の守りの状態のファイルを、`CreateNew` で作る一時ファイルから書く

## Grill の記録

Issue #444 のコメント「V1d24d の Grill」（2026-11-22、問 24d-1、24d-2）と「V1d24d の追加の答え」（2026-11-22、PR #474 の独立レビューのあと。問 24d-3〜24d-5）に、持ち主の答えがある。問 24d-5 の答えは、そのあとの測定で改めた（下の「持ち主が決めたこと」）。設計の本文（`../design.ja.md`）で変えたのは、§11.4 の手順 7〜9（一時ファイルの作り方、残った一時ファイルの掃除、状態の読み手）、§5.4 の 2 行（掃除が書いている最中の一時ファイルを消しうること。Windows で、置き換えてから閉じるまでのあいだの読み手）、§12.6.2 の「一時ファイルの作り方」の終わりの文、§20.7 の表の V1d24d の行、§22 の表の V1d24d の行（節に §5.4 を足した）である。

### 測った事実（`origin/main` の c31f7a5）

- `FileClockGuard.WriteState`（`src/ElasticLM.Licensing/FileClockGuard.cs`）は、状態のファイルと同じフォルダーに、乱数の名前（`<状態のファイル>.<16 進の大文字 16 文字>.tmp`）の一時ファイルを `File.WriteAllBytes` で書き、`File.Move(…, overwrite: true)` で置き換えていた。`IOException` か `UnauthorizedAccessException` なら、`_lastFailedWrite` を置き、`TryDelete` で一時ファイルを消していた。
- Linux（WSL のコンテナー、Debian、umask 022）で、そのコードが書いた状態のファイルのモードは 0644 だった（下のテスト `Observe_WritesTheStateForThisUserOnlyOnUnix` が、直しの前のコードで `OtherRead | GroupRead | UserWrite | UserRead` を見て落ちた）。
- `ElasticLM.Licensing` でファイルを書くのは `FileClockGuard` だけである（`src/ElasticLM.Licensing` の `File.Write`、`File.Move`、`File.Delete`、`File.Create`、`File.Open`、`FileStream`、`FileMode`、`Directory.Create`、`Directory.Delete`、`Directory.Move` を `rg` で探した。当たったのは `FileClockGuard.cs` の 3 行だけ）。
- `FileReplacement`（V1d24、PR #447）は `ElasticLM.Client` の `internal` で、`ElasticLM.Licensing` は `ElasticLM.Client` を参照しない（参照の向きは逆）。

### 測った事実（独立レビューの M4 と問 24d-5。Windows 11 ビルド 26300、.NET 10.0.14、SDK 10.0.403、scratch の `dotnet run` で）

- 置き換える先を読み手が開いているあいだの `File.Move(temp, target, overwrite: true)` は、読み手の共有が `FileShare.Read`、`ReadWrite`、`Read | Delete`、`ReadWrite | Delete` のどれでも `UnauthorizedAccessException`（HResult 0x80070005、「Access to the path is denied.」）で断られた。`IOException` ではない。前の記録の「`IOException` で断られる」（Issue #364 のコメント「V1d24a の Grill」の事実。.NET 11.0.0 で測ったもの）は、このリポジトリの .NET 10 では違った。`FileReplacement.cs` のコメント（V1d2 と V1d2a、.NET 10.0.14 と 10.0.15）とは合う。
- 同じ読み手のもとで、開いているファイルの削除（`File.Delete`）と、別の名前への移動（`File.Move(target, away)`）は、`Read` と `ReadWrite` では `IOException`、`Read | Delete` と `ReadWrite | Delete` では通った。
- 書き手が `FileAccess.Write`、`FileShare.Read | FileShare.Delete` で開いたままのファイルは、`FileShare.None` で開くと `IOException`（「being used by another process」）、`File.ReadAllBytes` でも `IOException` で断られ、書き手自身の `File.Move` は通った。
- Debian のコンテナー（.NET 10.0.14）で、`mkfifo` の FIFO の `FileInfo.Attributes` は `Normal` で、ふつうのファイルと同じだった（24d-6 のために測った）。
- Linux では、書き手が同じ形で開いたままの一時ファイルを `FileShare.None` で開けないこと（.NET の `flock`）を、テスト `Observe_TemporaryFileHeldByAnotherWriter_IsLeft` が WSL のコンテナーで確かめた。リンクの先の FIFO を開くと、開くところで待ち続けること（変異 L11 で、テストが 300 秒の上限に届いた）も、そのコンテナーで見た。

### 持ち主が決めたこと

2026-11-22、「V1d24d の Grill」（すべて推奨案）:

- 24d-2: V1d24 のピンと同じものを確かめる（作ったあとに書けないときの削除を Linux の 4 KiB の tmpfs で、置き換えに失敗したときの削除、Unix のモード 0600、§11.4 の「例外にせず、メモリで続け、60 秒は書かない」が保たれること）。それぞれに変異の確かめ。
- `FileClockGuard.TryDelete` もこの行で扱う（V1d24a の Grill の問 24a-5。Issue #364）。

2026-11-22、「V1d24d の追加の答え」（PR #474 の独立レビューのあと、すべて推奨案）:

- 24d-3: 乱数の名前では、先に消さない。名前は 64 ビットの乱数で、先にファイルが置かれることはなく、先の削除を外す変異はどのテストでも落とせない（はじめの実装の変異 L6 は生き残った。`.cursor/rules/testing.mdc` の、届かない確かめは消して理由を設計に書く）。`CreateNew` は他人が置いたファイルを開かずに断るので、守りは変わらない。
- 24d-4: 残った一時ファイルは、V1d24a（Issue #364）の Grill の問 24a-2a がクライアントの一時ファイルに決めた形と同じに掃除する。書き手は置き終えるまで一時ファイルを `FileShare.Read | FileShare.Delete` で開いたまま持ち、書く前に `<状態のファイル>.*.tmp` のうち `FileShare.None` で開けるものを消す。
- 24d-5（はじめの答え）: 状態の読み手を `FileShare.ReadWrite | FileShare.Delete` で開き、Windows で読み手を開いたまま置き換えるテストと変異を足す。
- 24d-5（改めた答え、案 B）: 上の測定で、読み手の共有を広げても .NET 10 の Windows では置き換えが通らないと分かり、持ち主に聞き直した。読み手は `FileShare.Read` のままにし、断られた置き換えは §11.4 の手順 6 の書き込めないとき（60 秒後に書き直す）になることを、測った結果とともに §11.4 の手順 9 と、この記録に書く。

2026-11-22、「決定（PR #474 の受け入れ 3 点）」（4918f67 のあと）:

- 24d-6（FIFO）: 受け入れずに直す。掃除は、名前の形に合うものでも、開く前にファイルの種類を確かめ、ふつうのファイルでなければ開かない。リンクは今のとおり、開かずにリンクそのものを消す。
- 24d-6a（FIFO の、確かめてから開くまでのすき。案 B）: Unix の掃除は .NET の `FileStream` で開かず、libc の `open`（`O_RDONLY | O_NONBLOCK | O_NOFOLLOW | O_CLOEXEC`）、`fstat`（ふつうのファイルでなければ閉じて残す）、`flock(LOCK_EX | LOCK_NB)`、`unlink`、`close` を呼ぶ。定数は Linux と macOS のそれぞれで確かめ、macOS の CI を通す。「残るすき」は §11.4 から外し、§5.4 には書かない。
- 24d-7: 残る 2 つの限界（`flock` が効かない場所と、作ってからロックを取るまでのあいだ。Windows で、置き換えてから閉じるまでのあいだの読み手）は受け入れ、§11.4 に加えて §5.4 にも書く。どちらも守りを破らず、安全な側に倒れる。

### こちらが決めたこと

- 一時ファイルの名前は乱数のままにする。§11.4 の手順 6 のとおり、複数のプロセスが同時に同じ状態のファイルを書く（同じアプリの `ActivationClient` と `LicenseClient`、`elm-server`、C の検証）。乱数の 16 進は、前のとおり大文字（`Convert.ToHexString`）で、掃除は大文字だけを形に合うとみなす。
- 置き換えのやり直し（§12.6.2）は使わない（PR #367 の問いの持ち主の決定のとおり）。
- 一時ファイルを書くストリームは、バッファーを持たない（`BufferSize = 0`）。書けないときは `Write` がその場で投げ、閉じるときに書き直すものがない。
- 掃除は 1 回の書き込みで 1,000 個まで見る。書き込みの手間に上限を置くためで、それより多いものは次の書き込みに残る。
- 掃除は、書き込みのたびに、書く前に行う（状態を読むときには行わない）。書き込みは、§11.4 の手順 6 のとおり時刻が 60 秒進んだときと、`AcceptServerTime` のときだけなので、掃除も同じ回数である。
- `TryDelete` の `catch` は、`FileReplacement.DeleteQuietly` と同じ形（`catch (Exception e) when (e is IOException or UnauthorizedAccessException)`）にした。
- 4918f67 では、持ち主の答えから出る結果として、3 つを受け入れとして §11.4 に書いた。持ち主は 24d-6 と 24d-7 で、FIFO を直し、残る 2 つを §5.4 にも書くと決めた。
- Unix の掃除（24d-6、24d-6a）: `UnixLeftover.TryRemove`（`src/ElasticLM.Licensing/UnixLeftover.cs`）。開いた記述子の種類は、Linux では `statx` の `AT_EMPTY_PATH`（glibc の `fstat` は 2.33 からで、リリースが支える glibc 2.28 にはない）、macOS では `fstat`（x64 は `fstat$INODE64`、`st_mode` は 4 バイト目）で読む。`O_NOFOLLOW` が断ったパスがリンクなら、リンクそのものを消す。ライブラリの名前と、`statx` のない C のライブラリの扱い（消さずに残す）は、`ElasticLM.Client` の `UnixOwner` と同じにした。Windows には FIFO がなく、前のとおり `FileShare.None` で開いて確かめる。はじめは、パスの種類を `lstat` で確かめてから `FileStream` で開いた（`UnixFileType`。変異 L14〜L17 はそれに対して走らせた）。確かめてから開くまでに FIFO に置き換えられるすきがあり、持ち主に聞いて、24d-6a で記述子で確かめる形にした。
- 1 か所にまとめる（調整役の指示、PR #475 のマージのあと）: PR #475（V1d24a）は、この `UnixLeftover` を `ElasticLM.Client` に写した（`IsSupported` を足した形。973adbf でこちらも同じ形にした）。#475 のマージのあとに `origin/main` を取り込み、`ElasticLM.Licensing` の `InternalsVisibleTo` に `ElasticLM.Client` を足して（`ElasticLM.Leasing`、`ElasticLM.Issuing`、実行ファイルと同じ形）、`FileReplacement` がこの型を呼ぶようにし、`src/ElasticLM.Client/UnixLeftover.cs` を消した。設計 §12.6.2 の「2 か所を同じに保つ」の文は、1 か所の文にした。`ElasticLM.Client.Tests` には、`UnixLeftover` を直接呼ぶテストはなく、`FileReplacementTests` の FIFO とパイプのテストは `FileReplacement` の掃除の道を確かめるので残した。
- アーキテクチャ（独立レビューの C1）: `O_NOFOLLOW` の値は、Linux の x64 が `0x20000`、arm64 が `0x8000` で、32 ビットの ARM と ppc64le は `0x8000` を使い、`0x20000` は別のフラグ（`O_LARGEFILE`、`O_DIRECT`）である。値を読んだアーキテクチャ（Linux の x64 と arm64、macOS の x64 と arm64）でだけ Unix の掃除をし、ほかでは残す。

### テスト

足したテスト（`tests/ElasticLM.Licensing.Tests/FileClockGuardTests.cs`）:

- `Observe_WritesTheStateForThisUserOnlyOnUnix`: モード 0666 の状態のファイル（中身は `{}`）があるところで書くと、モードが 0600 になり、`.tmp` が残らない。Windows では飛ばす。
- `Observe_ReplacementFails_DeletesTheTemporaryFileAndKeepsGoing`: 状態のパスに、中にファイルを持つフォルダーを置いて、置き換えを失敗させる。例外にならず、`.tmp` が残らず、フォルダーはそのまま。メモリの値で 301 秒前を断り、フォルダーを消したあと、59 秒後には書かず、60 秒後に書く。
- `Observe_DiskFullAfterCreating_DeletesTheTemporaryFileAndKeepsGoing`: Linux の 4 KiB の tmpfs を 4096 バイトのファイルで埋め、一時ファイルを作れても書けない状態にする（V1d24 の `FileReplacementTests.Writers_DiskFullAfterCreating_DeleteTheNewFile` と同じ形。`sudo -n mount`）。例外にならず、フォルダーには埋めたファイルしか残らない。メモリの値で 301 秒前を断り、埋めたファイルを消したあと、59 秒後には書かず、60 秒後に書く。Linux だけで、root では飛ばす。GitHub Actions で `sudo` が使えなければ失敗にする。
- `Observe_LeftoverTemporaryFiles_AreDeletedBeforeWriting`: `clock.json.<16 進の大文字>.tmp` の 2 つを消し、形の違う 4 つ（小文字、15 文字、16 進でない文字、ほかのファイルの名前）を残す。小文字の名前は、Windows で大文字と小文字だけが違う名前が同じファイルになるので、ほかの名前と文字そのものが違うもの（`aaaaaaaaaaaaaaaa`）にした。
- `Observe_ManyLeftovers_DeletesAtMostAThousand`（1,000 と 1,001）: 1,000 個なら残らず、1,001 個なら 1 つ残る。
- `Observe_TemporaryFileHeldByAnotherWriter_IsLeft`: 書き手と同じ形（`FileAccess.Write`、`FileShare.Read | FileShare.Delete`）で開いたままの一時ファイルは消さない。
- `Observe_LinkAtALeftoverName_DeletesTheLinkOnly`: 形に合う名前のシンボリックリンクの先に `mkfifo` の FIFO を置く。待たずに書き、リンクだけを消し、FIFO は残る。Windows では飛ばす。
- `Observe_FifoAtALeftoverName_IsLeftAlone`（24d-6）: 形に合う名前そのものに `mkfifo` の FIFO を置く。待たずに書き、FIFO は残る。Windows では飛ばす。
- `Observe_DanglingLinkAtALeftoverName_IsDeleted`（独立レビューの C2）: 形に合う名前に、先のないシンボリックリンクを置く。リンクは消える。Windows でも走る（リンクを作れない利用者では飛ばす。この開発機では走った）。
- `Observe_UnopenableFileAtALeftoverName_IsLeft`（独立レビューの C3）: 形に合う名前の、モード 0000 のファイルは、開けないので残る。Linux と macOS で、root でなければ走る。

落ちることを先に確かめたもの: 直しの前のコードで、`Observe_WritesTheStateForThisUserOnlyOnUnix` が Linux のコンテナーで落ちた。置き換えと書き込みの失敗の 2 つは、直しの前のコードでも通った（前のコードも、失敗のあとに一時ファイルを消し、`_lastFailedWrite` を置いていた）。問 24d-2 のとおり、直したあとの形を変異でピンする。掃除の 4 つは、掃除のないはじめの実装（28e0f5b）にない振る舞いを確かめる。

- Linux の arm64 の `O_NOFOLLOW`（`0x8000`）と、macOS の x64 の `fstat$INODE64`。CI のテストのランナーは Linux の x64 と macOS の arm64 で、どちらも走らない。macOS の arm64 の定数と `fstat` の位置は、CI の macOS の `build.ps1` がこのテストで確かめる。
- アーキテクチャの分かれ目（x64 と arm64 のほかでは掃除しない）は、ほかのアーキテクチャで走らせられず、変異で確かめていない。
- `statx` の `stx_mask` に `STATX_TYPE` がないときに残す確かめは、ローカルのファイルシステムがいつも型を返すので、それを落とす入力を作れず、変異で確かめていない。

はじめの実装（28e0f5b）の変異のうち、L3（置き換えの失敗のあとの削除）は、削除が 1 か所になったので L2 にまとめた。L6（先の `File.Delete` を外す）は、問 24d-3 で先の削除をなくしたので、もうない。L4 と L5 は、同じ 1 か所の `catch` の変異になった。書き手が置き換えるまで一時ファイルを開いたままにすること（閉じてから置き換える変異）は、ほかのプロセスの掃除が、閉じてから置き換えるまでのあいだに来たときだけ違いが出るので、変異を走らせていない。

### 同じ種類を探した範囲

- `ElasticLM.Licensing` のファイルの書き手: 上の「測った事実」のとおり、`FileClockGuard` だけ。

## 退けた案

- **決定:** `FileClockGuard` の一時ファイルの作り方を、`ElasticLM.Licensing` の中に private で持つ（問 24d-1）。
- **理由:** `ElasticLM.Licensing` だけを使うアプリと libelasticlm にも効き、パッケージの境界と公開の API を変えない。
- **却下した案:** `FileReplacement` を `ElasticLM.Licensing` に移し、`InternalsVisibleTo` で `ElasticLM.Client` から使う（パッケージのあいだに内部の依存ができる）。公開の API にする（設計が挙げない公開の面が増える）。

- **決定:** テストは、作ったあとに書けないときの削除（Linux の 4 KiB の tmpfs）、置き換えに失敗したときの削除、Unix のモード 0600、§11.4 の「例外にせず、メモリで続け、60 秒は書かない」を確かめる（問 24d-2）。
- **理由:** V1d24 のピンと同じものを確かめる。名前が乱数なので、先にリンクやファイルを置く場合は作れない。
- **却下した案:** 乱数の名前を差し替える `internal` の入口を作り、リンクのテストもする（V1d24 の `ServerPins` の判断と違い、テストのためだけの入口が要る）。

- **決定:** 乱数の名前の一時ファイルは、先に消さない（問 24d-3）。
- **理由:** 名前を前もって知れず、`CreateNew` は先に置かれたものを開かずに断る。先の削除を外す変異は、どのテストでも落とせない。
- **却下した案:** V1d24 と形をそろえて残し、落とせない理由を記録に書く。

- **決定:** 残った一時ファイルは、書く前に、`FileShare.None` で開けるものだけを消す。書き手は置き終えるまで一時ファイルを開いたまま持つ（問 24d-4。V1d24a（Issue #364）の Grill の問 24a-2a がクライアントに決めた形と同じ）。
- **理由:** 一時ファイルは、消すことも断られたときと、作ってから置き換えるまでにプロセスが終わったときに残り、終わった回数だけ増える。開いたまま持つので、ほかのプロセスが書いている最中のものは消さない。
- **却下した案:** 掃除しない（クラッシュのたびに一時ファイルが増える）。はじめの実装の「掃除しない」の判断（28e0f5b の記録。理由は、同時に書くほかのプロセスの一時ファイルを消しうること）は、開いたまま持つことで、その理由がなくなった。

- **決定:** Unix の掃除は、libc の `open`（`O_NONBLOCK`、`O_NOFOLLOW`）、開いた記述子の種類の確かめ、`flock(LOCK_EX | LOCK_NB)`、`unlink` で消す（問 24d-6 と 24d-6a）。
- **理由:** 名前の形に合う FIFO で検証を止める道をなくす。.NET の `FileStream` は FIFO を開くと待ち、待たずに開く方法がない。パスの種類を確かめてから開く形は、そのあいだに FIFO に置き換えられる。
- **却下した案:** FIFO で止められることを受け入れ、§5.4 に書く（4918f67 の形）。パスの種類を `lstat` で確かめてから `FileStream` で開き、置き換えのすきを受け入れる（24d-6a の案 A）。Unix では開かず、最終更新から決まった時間がたったものだけ消す（24d-6a の案 C。V1d24a（Issue #364）の Grill の問 24a-2a が、ファイルの時刻と `TimeProvider` が混ざるとして退けた形と同じ）。

- **決定:** 状態の読み手は `FileShare.Read` のままにする（問 24d-5 の改めた答え、案 B）。
- **理由:** .NET 10.0.14 の Windows では、読み手の共有が何でも、置き換えは `UnauthorizedAccessException` で断られた。共有を広げても置き換えは通らず、その変更を落とせるテストもない。
- **却下した案:** 読み手を `FileShare.ReadWrite | FileShare.Delete` で開き、テストも変異もなしにする（案 A。今は届かない変更になる）。案 B に加えて、置き換えが断られることを固定するテストを足す（案 C。OS とランタイムの振る舞いが変われば落ちる）。V1d24a の対象に足す（はじめの答えで退けた。並べて進めている行どうしで同じファイルに触れる）。
