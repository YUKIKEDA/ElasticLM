# V1d24d（Issue #444）: 時計の守りの状態のファイルを、`CreateNew` で作る一時ファイルから書く

## Grill の記録

Issue #444 のコメント「V1d24d の Grill」（2026-11-22）に、持ち主の答え（24d-1、24d-2 のどちらも推奨案）がある。設計の本文（`../design.ja.md`）で変えたのは、§11.4 の手順 7（一時ファイルの作り方）、§12.6.2 の「一時ファイルの作り方」の終わりの文、§20.7 の表の V1d24d の行である。

### 測った事実（`origin/main` の c31f7a5）

- `FileClockGuard.WriteState`（`src/ElasticLM.Licensing/FileClockGuard.cs`）は、状態のファイルと同じフォルダーに、乱数の名前（`<状態のファイル>.<16 進 16 文字>.tmp`）の一時ファイルを `File.WriteAllBytes` で書き、`File.Move(…, overwrite: true)` で置き換えていた。`IOException` か `UnauthorizedAccessException` なら、`_lastFailedWrite` を置き、`TryDelete` で一時ファイルを消していた。
- `ElasticLM.Licensing` でファイルを書くのは `FileClockGuard` だけである（`src/ElasticLM.Licensing` の `File.Write`、`File.Move`、`File.Delete`、`File.Create`、`File.Open`、`FileStream`、`FileMode`、`Directory.Create`、`Directory.Delete`、`Directory.Move` を `rg` で探した。当たったのは `FileClockGuard.cs` の 3 行だけ）。
- `FileReplacement`（V1d24、PR #447）は `ElasticLM.Client` の `internal` で、`ElasticLM.Licensing` は `ElasticLM.Client` を参照しない（参照の向きは逆）。

### 持ち主が決めたこと（2026-11-22、すべて推奨案）

- 24d-1: `ElasticLM.Licensing` の中に、V1d24 と同じ書き方（先に消す、`CreateNew`、Unix は 0600、書けなければ消す）を private で持つ。Licensing だけを使うアプリと libelasticlm にも効き、パッケージの境界を変えない。
- 24d-2: V1d24 のピンと同じものを確かめる（作ったあとに書けないときの削除を Linux の 4 KiB の tmpfs で、置き換えに失敗したときの削除、Unix のモード 0600、§11.4 の「例外にせず、メモリーで続け、60 秒は書かない」が保たれること）。それぞれに変異の確かめ。
- `FileClockGuard.TryDelete` もこの行で扱う（V1d24a の Grill の問 24a-5。Issue #364）。

### こちらが決めたこと

- 一時ファイルの名前は乱数のままにする。§11.4 の手順 6 のとおり、複数のプロセスが同時に同じ状態のファイルを書く（同じアプリの `ActivationClient` と `LicenseClient`、`elm-server`、C の検証）。名前を固定にすると、ほかのプロセスが作った一時ファイルを、先に消す手順で消してしまう。
- 置き換えのやり直し（§12.6.2）は使わない（PR #367 の問いの持ち主の決定のとおり）。
- `TryDelete`（V1d24a の問 24a-5）: 直さない。消すことも断られた一時ファイルは残り、誰も消さない。一時ファイルを開くのはこのプロセスだけで、消す前に閉じる。残るのは、ほかのプログラムがその一時ファイルを開いているとき（Windows）や、作ってから消すまでのあいだにフォルダーの権利が変わったときで、失敗のあとの書き込みは 60 秒に 1 回までなので、残るファイルも 60 秒に 1 つまでである。状態を読む手順は `<状態のファイル>` だけを読み、残ったファイルは守りに効かない。V1d24a の問 24a-2 の掃除（自分の名前の形に合う古い `*.tmp` を消す）は、`ElasticLM.Client` の書き手のためのもので、ここには入れない。入れると、同時に書いているほかのプロセスの一時ファイルを消しうる（名前の形が同じため）。
- `TryDelete` の `catch` は、`FileReplacement.DeleteQuietly` と同じ形（`catch (Exception e) when (e is IOException or UnauthorizedAccessException)`）にした。

### テスト

足したテスト（`tests/ElasticLM.Licensing.Tests/FileClockGuardTests.cs`）:

- `Observe_WritesTheStateForThisUserOnlyOnUnix`: モード 0666 の状態のファイル（中身は `{}`）があるところで書くと、モードが 0600 になり、`.tmp` が残らない。Windows では飛ばす。
- `Observe_ReplacementFails_DeletesTheTemporaryFileAndKeepsGoing`: 状態のパスに、中にファイルを持つフォルダーを置いて、置き換えを失敗させる。例外にならず、`.tmp` が残らず、フォルダーはそのまま。メモリーの値で 301 秒前を断り、フォルダーを消したあと、59 秒後には書かず、60 秒後に書く。
- `Observe_DiskFullAfterCreating_DeletesTheTemporaryFileAndKeepsGoing`: Linux の 4 KiB の tmpfs を 4096 バイトのファイルで埋め、一時ファイルを作れても書けない状態にする（V1d24 の `FileReplacementTests.Writers_DiskFullAfterCreating_DeleteTheNewFile` と同じ形。`sudo -n mount`）。例外にならず、フォルダーには埋めたファイルしか残らない。メモリーの値で 301 秒前を断り、埋めたファイルを消したあと、59 秒後には書かず、60 秒後に書く。Linux だけで、root では飛ばす。GitHub Actions で `sudo` が使えなければ失敗にする。

落ちることを先に確かめたもの: 直しの前のコードで、`Observe_WritesTheStateForThisUserOnlyOnUnix` が Linux のコンテナーで落ちた（`Actual: OtherRead | GroupRead | UserWrite | UserRead`。umask 022 で 0644）。ほかの 2 つは、直しの前のコードでも通った（前のコードも、失敗のあとに一時ファイルを消し、`_lastFailedWrite` を置いていた）。2 つは、問 24d-2 のとおり、直したあとの形を変異でピンする。

走らせた場所: Windows 11（SDK 10.0.403）と、WSL のコンテナー（`mcr.microsoft.com/dotnet/sdk:10.0` の Debian、root でない利用者、パスワードなしの `sudo`、tmpfs のために `--cap-add SYS_ADMIN`）。

### 同じ種類を探した範囲

- `ElasticLM.Licensing` のファイルの書き手: 上の「測った事実」のとおり、`FileClockGuard` だけ。
- `FileClockGuard` を作る所（`ActivationClient`、`LicenseClient`、`InstallationClockGuard`、`ElmServer`、`Exports.cs`）は、パスを渡すだけで、自分では状態のファイルを書かない。
- 状態の読み手（`ReadState`）は `File.ReadAllBytes`（`FileShare.Read`）で読む。V1d24a の Grill の事実（Issue #364）のとおりなら、Windows で、ほかのプロセスが読んでいるあいだの置き換えは `IOException` で断られる。そのときは §11.4 の手順 6 の書き込めないときになり、一時ファイルを消して 60 秒後に書き直す（`Observe_ReplacementFails_DeletesTheTemporaryFileAndKeepsGoing` と同じ道）。読み手の共有の指定は、この行では変えていない（V1d24a の問 24a-1 は、`ElasticLM.Client` の読み手を挙げる）。

## 退けた案

- **決定:** `FileClockGuard` の一時ファイルの作り方を、`ElasticLM.Licensing` の中に private で持つ（問 24d-1）。
- **理由:** `ElasticLM.Licensing` だけを使うアプリと libelasticlm にも効き、パッケージの境界と公開の API を変えない。
- **却下した案:** `FileReplacement` を `ElasticLM.Licensing` に移し、`InternalsVisibleTo` で `ElasticLM.Client` から使う（パッケージのあいだに内部の依存ができる）。公開の API にする（設計が挙げない公開の面が増える）。

- **決定:** テストは、作ったあとに書けないときの削除（Linux の 4 KiB の tmpfs）、置き換えに失敗したときの削除、Unix のモード 0600、§11.4 の「例外にせず、メモリーで続け、60 秒は書かない」を確かめる（問 24d-2）。
- **理由:** V1d24 のピンと同じものを確かめる。名前が乱数なので、先にリンクやファイルを置く場合は作れない。
- **却下した案:** 乱数の名前を差し替える `internal` の入口を作り、リンクのテストもする（V1d24 の `ServerPins` の判断と違い、テストのためだけの入口が要る）。

- **決定:** 消すことも断られた一時ファイル（`TryDelete`）は残し、掃除しない（V1d24a の問 24a-5 でこの行に回した判断）。
- **理由:** 残るのは外のプログラムが開いているときなどで、60 秒に 1 つまでであり、守りに効かない。掃除は、同時に書いているほかのプロセスの一時ファイルを消しうる。
- **却下した案:** 書く前に、同じフォルダーの `<状態のファイル>.*.tmp` を消す（V1d24a の問 24a-2 の形）。
