# V1d29h（Issue #506）: Kestrel の HTTP/2 のほかの既定の上限を、`elm-service` と `elm-server` の両方のテストで確かめる

## Grill の記録

V1d29f の作業（PR #505、問 29f-1）が見つけ、持ち主の決定（2026-11-28、Issue #481 のコメント、案 A）で足した行。Grill は Issue #506 のコメント（2026-11-28）で、問 29h-1〜29h-8 は、持ち主がどれも推奨のとおりに決めた。

### Grill で測った事実

- 環境: Windows 11、SDK 10.0.404、ASP.NET Core 10.0.15。
- 測り方: PR #505 の head（5914fe6）を scratch に `git archive` で書き出し、両方のテストのプロジェクトに、生の HTTP/2 のフレームを組む probe を足した（TLS と ALPN の h2、経路は `/v1/nonce`）。15 の場合を、両方のサーバーで 20 回ずつ流し、20 回とも同じ結果だった。
- ソース: aspnetcore v10.0.14 を読んだ。使った 9 ファイルは、v10.0.15 と blob SHA が同じ。
- 両方のサーバーとも、変えている Kestrel の上限は `MaxRequestBodySize` だけで、HTTP/2 で話すのは、TLS の待ち受けで ALPN が h2 を選んだときだけ。
- 同時のストリーム: 101 本目は RST_STREAM `REFUSED_STREAM` を受け、接続は残る。1 本を閉じると、次のストリームは 200 を受ける。
- フレームの大きさ: 16,384 バイトは通り、16,385 バイトは GOAWAY `FRAME_SIZE_ERROR`。
- HPACK の表: 大きさの更新 4,096 は通り、4,097 は GOAWAY `COMPRESSION_ERROR`。
- 受信の窓: ストリームの窓は 786,432、接続の窓は 1,048,576。どちらも 1 バイト超えると GOAWAY `FLOW_CONTROL_ERROR` で、ストリームの窓を超えたときも接続のエラー。
- SETTINGS: サーバーの SETTINGS は `MAX_CONCURRENT_STREAMS=100`、`INITIAL_WINDOW_SIZE=786432`、`MAX_HEADER_LIST_SIZE=32768`。`HEADER_TABLE_SIZE` と `MAX_FRAME_SIZE` は既定の値なので送られない。接続の WINDOW_UPDATE は +983,041。
- 変異: `elm-server` で、上限を全部 1 つ上げたビルドと 1 つ下げたビルドを流し、どちらでも結果は期待のとおりに入れ替わった。
- 採らない形: 本文を送らない POST（405 で終わる）。`/health`（答えがすぐ終わり、結果が速さの競争になる）。

### 持ち主の決定（問 29h-1〜29h-8）

- 29h-1: 5 つの上限を、ちょうどの値と 1 つ超えた値で確かめる。ENHANCE_YOUR_CALM は対象にしない（heartbeat の時間に頼るため）。
- 29h-2: クライアントの `SETTINGS_INITIAL_WINDOW_SIZE` を 0 にした `GET /v1/nonce`（END_STREAM 付き）で、ストリームを開いたままにする。
- 29h-3: 受信の窓は、窓を 0 にした `GET /v1/nonce`（END_STREAM なし）に、200 を見てから DATA を送り、続けて PING を送る。結果は PING ACK か GOAWAY `FLOW_CONTROL_ERROR` で読む。ストリームの窓は 786,432 と +1、接続の窓は 2 本で 1,048,576 と +1。
- 29h-4: `elm-service`（TLS）と `elm-server` で、同じ場合と同じ期待を確かめる。
- 29h-5: 製品のコードは変えず、既定に頼る。既定が変われば、テストが落ちて知らせる。
- 29h-6: サーバーの SETTINGS の、上限に関わる値も確かめる（ENABLE_CONNECT_PROTOCOL は確かめない）。
- 29h-7: PR #505 のブランチ（`test/481-http2-limits`）の上に積み、`--base test/481-http2-limits` で開く。`KestrelLimits.cs` に共通の部品を足し、`Http2OutcomeAsync` はその部品の上に載せ直す。
- 29h-8: 設計 §5.3 T16 に、既定値と、超えたときの答えの種類（ストリームのエラーか、GOAWAY による接続のエラーか）を書く。テストの形と測った事実は、このファイルに書く。

### 読んだソース

この行の実装で、テストの文が名前を挙げる aspnetcore v10.0.14 の次のファイルを、GitHub の API でタグ v10.0.14 から取って読んだ。

- `src/Servers/Kestrel/Core/src/Http2Limits.cs`: 既定は `MaxStreamsPerConnection` 100、`HeaderTableSize` 4,096、`MaxFrameSize` 16,384、`InitialConnectionWindowSize` 1 MiB、`InitialStreamWindowSize` 768 KiB。`MaxFrameSize` の設定は 16,384 未満を `ArgumentOutOfRangeException` で断り、2 つの窓の設定は 65,535 未満を断る。
- `src/Servers/Kestrel/Core/src/Internal/Http2/Http2Connection.cs`: `ProcessRequestsAsync` は、プリフェイスを読んだあと、まず SETTINGS（`GetNonProtocolDefaults` の値）を書き、`InitialConnectionWindowSize` が 65,535 より大きければ、差の分の接続の WINDOW_UPDATE を書く。`StartStream` は、数えたストリームが `MaxStreamsPerConnection` を超えると、そのストリームを `REFUSED_STREAM` でリセットする（ストリームのエラー）。`ProcessRstStreamFrameAsync` は、クライアントの RST_STREAM を読んだその場で、ストリームの数を減らす（`Http2Stream.cs` の `AbortRstStreamReceived`）。
- `src/Shared/ServerInfrastructure/Http2/Http2FrameReader.cs`: `TryReadFrame` は、フレームのヘッダーの 9 バイトを読んだところで長さを `MaxFrameSize` と比べ、超えると `FRAME_SIZE_ERROR` の接続のエラーにする。本体が届くのを待つのは、その後。
- `src/Shared/ServerInfrastructure/Http2/Http2PeerSettings.cs`: `GetNonProtocolDefaults` は、HTTP/2 の既定（表 4,096、同時のストリームは無制限、窓 65,535、フレーム 16,384、ヘッダーの一覧の大きさは無制限）と違う値だけを返す。ヘッダーの一覧の大きさは既定が無制限なので、`MaxRequestHeadersTotalSize` の 32,768 が送られる。そのあとに、値によらず、いつも `SETTINGS_ENABLE_CONNECT_PROTOCOL` を 1 で足す。テストがこの設定（8）を比べないのは、上限ではなく、問 29h-6 で確かめないと決めたからである。
- `src/Shared/runtime/Http2/Hpack/HPackDecoder.cs`: `SetDynamicHeaderTableSize` は、表の大きさの更新が `HeaderTableSize` を超えると `HPackDecodingException` を投げ、`Http2Connection` はそれを `COMPRESSION_ERROR` の接続のエラーにする。
- `src/Shared/Hpack/DynamicHPackEncoder.cs`: 答えを符号化する表は 4,096 で始まり、`Http2Connection.cs` がクライアントの SETTINGS を受けたときに `HeaderTableSize` との小さいほうへ変える。値が変わると、次の HEADERS の先頭に表の大きさの更新を書く（`UpdateMaxHeaderTableSize`）。
- `src/Servers/Kestrel/Core/src/Internal/Http2/FlowControl/InputFlowControl.cs`: `TryAdvance` は、窓を超える DATA を `FLOW_CONTROL_ERROR` の接続のエラー（`Http2ConnectionErrorException`）にする。ストリームの窓（`StreamInputFlowControl.cs`）も、接続の窓も、この型で数える。
- `src/Servers/Kestrel/Core/src/Internal/Http2/Http2Stream.cs` と `FlowControl/StreamInputFlowControl.cs`: 窓を返す道は 2 つある。1 つは `OnDataRead` で、ハンドラーが本文を読んだ分を返す。`GET /v1/nonce` のハンドラーは本文を読まない。もう 1 つは `CompleteStream` の `_inputFlowControl.Abort()` で、ストリームが終わるときに、読まれていない分を接続の窓へ返す（`StreamInputFlowControl.Abort` から `UpdateConnectionWindow`）。
- `src/Servers/Kestrel/Core/src/Internal/Http2/Http2OutputProducer.cs` と `Http2FrameWriter.cs`: `CompleteStream` を呼ぶのは、`OnRequestProcessingEnded`（ハンドラーが終わったとき）と `CompleteResponseAsync` の、遅いほうである。`CompleteResponseAsync` は、`Http2FrameWriter.cs` が答えを END_STREAM まで書き終えたときに呼ぶ。クライアントの窓が 0 では、答えの DATA も END_STREAM も書けないので、ストリームは終わらず、テストが DATA を送るあいだに窓は戻らない。受信の窓のテストの結果が決まるのは、このためである。

### テストの形（この行で決めたこと）

- `KestrelLimits.Http2Connection`（`tests/ElasticLM.Service.Tests/KestrelLimits.cs`。`ElasticLM.Server.Tests` は、このファイルを結び付けて使う）: TLS の接続を ALPN の h2 で開き、プリフェイスと、テストが渡す値の SETTINGS を書く（`OpenAsync`）。テストが組んだ複数のフレームを 1 回で書く（`WriteAsync`）。読み手（`ReadAsync`）は、HEADERS の `:status`、RST_STREAM、PING ACK、GOAWAY を、届いた順に集め、決めた数の答えが集まるか、GOAWAY が届くか、実時間の 10 秒（`AnswerLimit`）が過ぎると止まる。サーバーの最初の SETTINGS と接続の WINDOW_UPDATE は、読み手が通り過ぎるときに値を残す。読み手は何も書かない（V1d29f と同じ理由）。
- `Http2OutcomeAsync`（V1d29f）は、この部品の上に載せ直した。送るバイト、読む順、返す値は変わらない。V1d29f のテストは変えずに、12 件が両方のサーバーで通った。
- `:status` の読み手は、ヘッダーのブロックの先頭にある動的な表の大きさの更新を読み飛ばす。表の大きさを 4,095 に下げた変異では、Kestrel の符号化の側も、次の答えの先頭に更新を書くので（下の `DynamicHPackEncoder.cs`）、読み飛ばさないと、期待の違いではなく読み手のアサートで落ちる。
- `Http2OtherOutcomeAsync` と `KestrelLimits.Http2AtAndPastOtherLimits` の 10 件、両方のサーバーで同じ表:

| 場合 | 送ったもの | 期待 |
| --- | --- | --- |
| streams 100 | 窓を 0 にした接続で、END_STREAM 付きの GET を 100 本 | 100 本とも 200。そのあと 1 本目を RST_STREAM（CANCEL）で閉じると、次の 1 本も 200 |
| streams 101 | 同じく 101 本。102 本目まで送るので、テストの設定が 1 つの送信元の頻度の上限を 1,000 に上げていることに頼る（`Deployment` の `RateLimitPerIp`、`TestService` の `RateLimitPerIp` と `RateLimitClientPerIp`） | 100 本は 200、101 本目は RST_STREAM `REFUSED_STREAM`。そのあと 1 本目を閉じると、次の 1 本は 200 |
| frame 16,384 | 本体が 16,384 バイトの HEADERS 1 つ（詰め物のヘッダーで長さを合わせる） | 200。同じ接続の次の GET も 200 |

- `Http2ServerSettingsAsync` と `Kestrel_Http2Settings_StateTheLimits`（両方のサーバー）: 空の SETTINGS と PING を送り、PING ACK までに読んだ SETTINGS を、ENABLE_CONNECT_PROTOCOL を除いて `3=100, 4=786432, 6=32768` と比べ、接続の WINDOW_UPDATE の和を 983,041 と比べる。表とフレームの大きさ（1 と 5）が送られないことも、この比較に入る。
- フレームの大きさを超える場合は、フレームのヘッダーだけを送る。Kestrel は長さを見たところで断るので（上の `TryReadFrame`）、Kestrel が読まない本体が残らない。V1d29f で、Kestrel が接続を切ると決めたあとにクライアントが書いたバイトがあると、GOAWAY の代わりにリセットされた接続を読むことがあった（[V1d29f.md](V1d29f.md)）。受信の窓の場合は、問 29h-3 のとおり DATA のあとに PING を書くが、DATA と PING を 1 回の書き込みにした。窓を超えた DATA のあとに PING の 17 バイトが続いても、接続のリセットにならないことは、パケットでは確かめていない。推論は次のとおり。`SslStream` は 1 回の書き込みを約 16 KiB ずつのレコードに分けるので、最後の DATA フレームの終わりと PING は最後のレコードに入る。Kestrel はそのレコードを丸ごと復号してからフレームを読むので、窓を超えたフレームを読んだ時点で、読まれていないバイトは残らない。実際に、超えた 2 つの場合は、両方のサーバーで 20 回とも GOAWAY を受けた（下の「測った事実」）。
- `elm-service` の https の起動は、V1d29f のテストと同じ手順を `ElmServiceTests.StartOnHttpsAsync` に分けて、両方の HTTP/2 のテストで使う。
- テストの名前: `Kestrel_Http2StreamsFramesTableAndWindows_KeepTheirLimits`（`ElmServiceTests` と `ServerProtocolTests`）、`Kestrel_Http2Settings_StateTheLimits`（同じ 2 つ）。

### 同じ種類を探した範囲

- Kestrel の上限を変える場所: `src/` で `kestrel.Limits` を変えるのは、2 つのサーバーの `MaxRequestBodySize` だけ（`rg "kestrel\.Limits" src`）。`Http2` の設定は、どちらのサーバーにもない（`rg "Http2" src`）。
- 利用者の文書（`docs/guide/`、`docs/guide.ja/`）に、HTTP/2 の上限を述べる文はない（`rg "HTTP/2|Http2Limits|REFUSED_STREAM" docs/guide docs/guide.ja`）。

## 退けた案

- **決定:** ストリームを開いたままにするのは、クライアントの `SETTINGS_INITIAL_WINDOW_SIZE` を 0 にした `GET /v1/nonce`（問 29h-2）。
- **理由:** 答えの本文を送れないので、ハンドラーが終わってもストリームが閉じず、同時に開いた数をクライアントが決められる。
- **却下した案:** 本文を送らない POST。405 で終わり、ストリームが閉じる。
- **却下した案:** `/health`。答えがすぐ終わり、数えるストリームが残るかが速さの競争になる。
- **決定:** ENHANCE_YOUR_CALM（Kestrel が、追い切れない数のストリームに返す）はテストしない（問 29h-1）。
- **理由:** heartbeat の時間に頼り、テストの結果が実時間で決まる。
- **決定:** 製品は上限を設定せず、Kestrel の既定に頼る（問 29h-5）。
- **理由:** 既定が変われば、この行のテストが落ちて知らせる。
