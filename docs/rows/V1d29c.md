# V1d29c（Issue #478）: `elm-service` のイメージを、読み取り専用のルートのファイルシステムで起動して確かめる

## Grill の記録

- 始まり: V1d29（PR #476）の T27 の確かめで、How-to の頁 `docs/guide/how-to/run-the-service-in-a-container.md` の 154 行目が「With a read-only root file system, mount a writable volume on `/tmp` too.」と書くのに、頁の `docker run` も `eng/container/Test-Image.ps1` も `--read-only` で起動せず、この文を試す所がないことが分かった。持ち主の決定（2026-11-22、Issue #348 の最後のコメントの 2）で行にした。
- 測った事実（2026-11-27。Windows 11 と WSL の Ubuntu 22.04.5。イメージは CI の実行 45981950560（PR #476 の head、4a78b61）の artifact `image-oci` の linux/amd64、`elm` は同じ実行の `archives-linux-x64` のもの）:
  - `wslc` 3.0.5 には `--read-only` がない。`wslc run --rm --read-only …` は「オプション名が現在のコマンドに対して認識されませんでした: '--read-only'」で終了コード 1 になる。`wslc run --help` と `wslc create --help` にもない（`--tmpfs` はある）。そのため、`.cursor/rules/testing.mdc` が求める `wslc run` での先の試しはできない。
  - 代わりに、WSL の Ubuntu の root で、読み取り専用のルートを作って動かした。amd64 のマニフェストの層を順にフォルダーへ展開し、`unshare -m --propagation private` の中で、そのフォルダーを bind して `mount -o remount,bind,ro` にした。その前に、UID 1654 のフォルダーを `/data` に、設定と秘密のフォルダーを `/config` に読み取り専用で bind し、`proc` と、`null`、`zero`、`random`、`urandom` だけを持つ tmpfs の `/dev` を載せた。Python の `os.chroot`、`os.chdir("/data")`、`os.setgid(1654)`、`os.setuid(1654)` のあとで `/app/elm-service` を exec した。環境は、イメージの `ELM_LISTEN`（ポートだけ 18091 に変えた）、空の `ASPNETCORE_HTTP_PORTS`、`ELM_PUBLICURLS=https://elm.test/`、`HOME=/home/app`、`PATH=/usr/bin` だけである。ベースのイメージの config の `Env` のほかの変数は渡していない。設定は `Test-Image.ps1` と同じ形（SQLite、`signing.passphraseFile`、秘密はファイル）にした。毎回、root が `/` と `/tmp` に書けないこと（`touch` が失敗する）を確かめてから exec した。
  - `/tmp` に何も載せない場合: `setup` は API キーを出し、終了コード 0 で終わった。起動したサービスは 2 秒で `/health` に 200 で答え、プロセスの UID は 1654 だった。動いているあいだの `backup --config /config/elm-service.json --out /data/backup-1.db` は「backup: /data/backup-1.db, schema version 12」を出した。SIGTERM で `service.stopped` を出し、終了コード 0 で止まった。
  - `/tmp` に書ける tmpfs を載せた場合も、結果は同じだった。
  - コードで読んだこと: `src/` で `Path.GetTempPath` や `/tmp` を使う所は、`ElasticLM.Service` にない。サービスの一時のファイル（`Backup.cs` の 178 行目）は、書き出す先と同じフォルダーに作る。SQLite は、一時のフォルダーを `sqlite3_temp_directory`、`SQLITE_TMPDIR`、`TMPDIR`、`/var/tmp`、`/usr/tmp`、`/tmp`、`.` の順に探し、`osAccess(<フォルダー>, 03)` が通らないもの（書けないもの）を飛ばす（同梱の SQLite 3.54.1 の `unixTempFileDir`、`vendor/sqlite/sqlite3.c` の 46918 行目。読んだだけで、大きな並べ替えのような一時のファイルを使う場面は測っていない）。イメージの作業フォルダーは `/data` である。
  - 試していないもの: Docker そのものの `--read-only`（Docker は `/dev` と `/dev/shm` に書ける tmpfs を別に与え、イメージの config の `Env` をすべて渡す）。PostgreSQL、OIDC、TLS の証明書、利用ログ（`usageLog.directory`）の設定。そのため、設計と頁は「`/data` にだけ書く」を、試した設定（SQLite のデータベースが `/data`、利用ログなし）でのことと書く（独立レビューの C1）。
- 持ち主が決めたこと（2026-11-27、Issue #478 のコメント。3 つとも推奨案）:
  - 問 29c-1: `/tmp` は要らないとする。`Test-Image.ps1` は `--read-only` だけで `setup` と起動を行い、前と同じ確かめ（`setup` のキー、`/health` の 200、UID 1654、`docker stop` の終了コード 0、ログ）をする。頁の 154 行目（英語と日本語）と設計 §20.6 は、`/data` にだけ書くと書く。
  - 問 29c-2: 頁の `docker run` の行は変えず、頁は `Test-Image.ps1` の確かめを指す。
  - 問 29c-3: 手元の測り方（上の名前空間と chroot）をこのファイルに書き、Docker の `--read-only` は PR の CI（`Container image` のジョブ）で初めて確かめることを PR の本文に書く。`.cursor/rules/testing.mdc` の `wslc` の項に、3.0.5 に `--read-only` がないことを足す。
- 実装: `Test-Image.ps1` の `setup` と起動の `docker run` に `--read-only` を足した。`/tmp` には何も載せない。起動したコンテナーの `docker inspect` の `HostConfig.ReadonlyRootfs` が `true` であることも確かめ、オプションが落ちたまま通ることがないようにした。頁（英語と日本語）の 154 行目、`docs/container.md` の `image-test` の文、`.cursor/rules/testing.mdc` の `wslc` の項を直した。
- 手元で走らせたもの: `Test-Image.ps1` は `docker buildx imagetools` と `docker info` を使い、`--read-only` は `wslc` にないので、手元では走らせられない。スクリプトは PowerShell の構文の確かめ（`[System.Management.Automation.Language.Parser]::ParseFile`）だけを通した。Docker の `--read-only` での実行は、PR の CI の `Container image` のジョブ（amd64 と arm64）が初めて確かめる。

## 退けた案

- **決定:** 読み取り専用のルートでは、`/tmp` に何も載せない（問 29c-1）。
- **理由:** `/tmp` を書けないままにして、`setup`、起動、`/health`、バックアップ、SIGTERM での停止がすべて通った。サービスのコードは `/tmp` に書かない。要ると示されていないものを要るように書くと、読み手は理由のないマウントを持つことになる。
- **却下した案 1:** `--tmpfs /tmp` を勧めたまま残し、その形で試す。試していない構成への余裕にはなるが、頁の文が測った結果と合わない。
- **却下した案 2:** `/tmp` なしと `--tmpfs /tmp` の両方を `Test-Image.ps1` で起動する。イメージの試しが長くなるのに、`/tmp` を使わないことはもう 1 つ目で確かめられる。

- **決定:** 頁の `docker run` の行には `--read-only` を足さない（問 29c-2）。
- **理由:** `wslc` 3.0.5 には `--read-only` がなく、足すと、読み手の `wslc run` と、ステップの道具（`eng/docs/Test-GuideSteps.ps1`）の `-ContainerCli wslc` が落ちる。読み取り専用での起動は、`Test-Image.ps1` が CI の Docker で確かめる。
- **却下した案:** 頁の `docker run` に `--read-only` を足し、ステップの道具で流す。頁に `wslc` のための注記が要り、手元で頁を流せなくなる。

- **決定:** 手元では、名前空間と chroot で作った読み取り専用のルートで測り、Docker の `--read-only` は PR の CI で初めて確かめる（問 29c-3）。
- **理由:** `wslc` 3.0.5 では `--read-only` を走らせられない。ルートとほかのフォルダーが書けないことは、名前空間の bind のマウントで作れる（Docker との違いは、上の「試していないもの」と、環境の変数の違い）。
- **却下した案:** WSL のディストリビューションに Docker を入れて測る。開発の機械に、ほかの行が使わない道具を足すことになる。
