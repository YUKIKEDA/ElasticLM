# V1d10（Issue #328）: `release.yml` の `publish` が、`SHA256SUMS` に載っていないパッケージも公開することを直す（V1d の指摘 F16）

## Grill の記録

Issue #328 に記録した。問 10-1 と問 10-2。持ち主の決定はどちらも推奨案 A（2026-11-13）。`release.yml` の `publish` が、`SHA256SUMS` に載っていないパッケージも公開し、`SHA256SUMS` そのものを何とも照らさないことを直す。決めた形は設計（`../design.ja.md`）§20.5 の「公開のジョブの確かめ」、脅威は §5.3 の T22 と T24 にある。

- 調べた事実（Issue #328 の記録）: `publish` は、`SHA256SUMS` のパッケージの行だけを確かめ（`grep … | sha256sum --check --strict`）、フォルダーにある `*.nupkg` をすべて push していた。`gh release edit --draft=false` は、下書きのどの配布物も公開する。`SHA256SUMS` そのものは、何とも照らしていなかった。
- 持ち主が決めたこと:
  - 問 10-1: 下書きの Release の配布物の一覧が、`SHA256SUMS` の行の名前と `SHA256SUMS` そのものに、ちょうど一致しなければ、`publish` を止める。
  - 問 10-2: `SHA256SUMS` を、`checksums` のジョブの出力 `sha256sums` と照らす（V1d7 の問 7-4 の出力を使う）。
  - V1d7（Issue #325）のあとに、別の PR にする。
- 独立レビューのあとに持ち主に聞いて決めたこと（2026-11-13。どちらも推奨案 A。コードは下の形のまま）:
  - 問 10-3: `publish` が取る `image-oci` を、index のダイジェストに加えて、`image` のジョブが出力で渡す tar の SHA-256 と一覧にも照らすか（V1d7 の独立レビューから足した点。Issue #328 の 2 つ目の記録）。作った形: `image-test` と `guide-containers` と同じコマンドで、tar の SHA-256 とフォルダーの中身の一覧を `image` の出力と照らし、index のダイジェストの照らしは push の段に残す。`image-oci` は、ほかの取るジョブと同じく、それだけを入れるフォルダー（`image`）に取る。V1d7 の問 7-1 は、取るジョブがファイルの SHA-256 と照らす形を決め、`image-test` は、V1d7 の設計のレビューのあとで、index のダイジェストに加えてこの照らしを足した。持ち主の決定: 照らす（退けた案: index のダイジェストだけ）。
  - 問 10-4: タグを打たずに、変更をどう確かめるか（§20.7 の表の V1d10 の行の点）。作った形: 確かめのコマンドと同じ文面の段を `checksums` に置いてすべての PR で走らせ、合わない場合は手元の見本のフォルダーで確かめた（下の「こちらが決めたこと」と「手元で確かめたこと」）。`gh release view` と `gh release download` の段は、V1e のタグの実行で初めて走る。持ち主の決定: `gh release` の行は、最初の本番のタグ（V1e）で初めて走ることを受け入れる。確かめはすべて push の前にあるので、外れても何も公開されない（退けた案: PR の中で使い捨ての下書きのリリースを作って確かめる。`contents: write` と外への操作が要る）。
- こちらが決めたこと:
  - 下書きと `image-oci` の確かめを、何かを push する前に置く。V1d10 の前は、パッケージを push したあとで `image-oci` を取っていた。今は、2 つの確かめのあとに、NuGet へのログインと push が来る。
  - 下書きのすべての配布物を取り、問 10-2 のとおり、`SHA256SUMS` の行のすべてのファイルを照らす。フォルダーの中身が同じ名前の一覧とちょうど同じことも確かめる（`attest` と `draft` と同じ確かめ。`gh release download` は、配布物の一覧を取った呼び出しとは別に Release を読むので、一覧とフォルダーの両方を見る）。
  - 確かめのコマンドは、`attest` と `draft` のコマンドに、配布物の一覧の `diff` を 1 行足したものにした。同じ文面の段を `checksums` にも置き、すべての PR で走らせる（V1d7 の「PR で走る場所」の形）。PR では下書きがないので、配布物の一覧には、`draft` が `gh release create` に渡す `assets/*` と同じく、取り直したフォルダーの `*` の名前を書く。そのため PR では、一覧の確かめは、フォルダーの確かめと同じ名前を比べる。一覧が合わないときに落ちることは、下の手元の確かめで見た。
  - 独立レビューの指摘 2 のあとで足した: 最初の確かめから `gh release edit --draft=false` までの数分に、`contents: write` を持つトークン（持ち主、`publish` 自身のトークンとそれを渡された `actions/attest`、ほかの `v*` のタグの実行の `draft` と `publish`）は、配布物を足すか、同じ名前で置き換えられる。そこで、公開の段のすぐ前に、下書きの配布物を `gh release view --json assets` でもう一度読み、名前と `digest`（GitHub の SHA-256）を、確かめた行（`SHA256SUMS` の行と、`SHA256SUMS` そのものの出力の行）と比べる段を足した。`digest` のない配布物があっても止める。PR では、`gh` の代わりに、取り直したフォルダーの `sha256sum` から同じ形の行を書いて、同じ文面の段を `checksums` で走らせる。残る窓（最後の読み取りと公開の間の数秒）は、設計 §20.5 と T24 に、受け入れるものとして書いた。
  - 独立レビューの指摘 3 のあとで決めた: 公開は、下書きの本文、題、プレリリースの印も、そのまま公開する。本文は照らさず、照らさないことを設計 §20.5 に書いた。GitHub が本文を保存して返すときに変えるかは、文書になく、タグの実行でしか測れない。照らして誤って止まれば、タグは消せないので次の版になる。
  - 独立レビューの指摘 5 のあとで足した: ランナーの `gh` は固定していないので、下書きを読む段で `gh --version` をログに書く。設計の `gh` の読み方は、`trunk` のソースを、ランナーの `gh` の代わりに読んだものと書いた。
- 手元で確かめたこと（2026-11-13、Windows 11、Git for Windows の bash 5.3.15 と GNU coreutils 8.32 の `sha256sum`。ワークフローの段から、`checksums` と `publish` で同じ文面であることを確かめて取り出したスクリプトを、見本のフォルダー（2 つの圧縮ファイル、`.nupkg`、`.snupkg`、SBOM、`SHA256SUMS`）で走らせた。PR の代わりの行は、`checksums` の段のスクリプトで書いた）:
  - 下書きの確かめは、合うフォルダーと、一覧の順を変えたものでは通る。一覧に配布物を足したもの、一覧から `.snupkg` を除いたもの、一覧から `SHA256SUMS` を除いたもの、空の一覧、中身を変えたファイル、変えたファイルに合わせて書き直した `SHA256SUMS`、末尾に空の行を足した `SHA256SUMS`、パッケージを足して `SHA256SUMS` と一覧にも足したもの、パッケージを足して一覧にだけ足したもの、パッケージをフォルダーにだけ足したもの、SBOM をフォルダーと一覧の両方から除いたもの、`SHA256SUMS` のないもの、空の出力では落ちる（15 の場合）。
  - 公開の前の確かめは、合う行と、順を変えた行では通る。同じ名前で中身を置き換えた配布物（`digest` だけが違う）、足した配布物、除いた配布物、`digest` のない配布物（`gh` の式が `null` の代わりに書く `none`）、置き換えた `SHA256SUMS` の配布物、配布物のない下書き、手元の `SHA256SUMS` を変えたもの、空の出力では落ちる（10 の場合）。
  - `image-oci` の確かめは、合う tar では通り、中身を変えた tar、足したファイル、名前を変えた tar、空の出力では落ちる（5 の場合）。
  - どの場合も、結果は期待どおりだった。`gh` の式（`.assets[] | (.digest // "none") + "  " + .name`）は、手元の `gh` 2.103.0 で `cli/cli` の v2.104.0 に流すと `sha256:<16 進>  <名前>` の行を書き、v1.0.0 に流すと `none  <名前>` の行を書いた。v2.104.0 の `gh_2.104.0_checksums.txt` の `digest` は、取ったファイルの `sha256sum` と同じだった。`actionlint` 1.7.7 は、`main` と同じ 1 件（`windows-11-arm` のランナーのラベルを知らない）のほかに何も出さなかった。
- タグの実行だけが示すこと: `gh release view` と `gh release download` が、下書きの Release を見つけて、すべての配布物を返すこと（`gh` のソースは読んだ。設計 §20.5 の「公開のジョブの確かめ」）。下書きの配布物が `digest` を持つこと。GitHub が配布物の名前を変えないこと。すべての配布物を取る時間が `publish` の `timeout-minutes`（15 分）に収まること。どれも、`publish` が初めて走る V1e のタグの実行で分かる。はじめの確かめで合わなければ、ジョブは何も push せずに落ちる。公開の前の確かめで合わなければ、Release は公開しないが、NuGet と GHCR への push はもう済んでいる。
- 同じ種類を探した範囲: `release.yml` の `gh release` と `actions/download-artifact` のすべて。`gh release` を使うのは `draft`（`create`）と `publish`（`view`、`download`、`edit`）だけである。`path` を持たない `actions/download-artifact` は `publish` の `image-oci` だけだったので、`image` のフォルダーに取るようにした。
- この行の外で見つけたもの: ない。

## 退けた案

- **決定:** `publish` は、何かを push する前に、下書きの Release の配布物の一覧とすべての配布物を取り、`SHA256SUMS` を `checksums` のジョブの出力 `sha256sums` と、`SHA256SUMS` の行のすべてのファイルを `SHA256SUMS` と照らし、配布物の一覧が `SHA256SUMS` の行の名前と `SHA256SUMS` にちょうど一致しなければ止まる（持ち主の決定、問 10-1 と問 10-2 の推奨案 A。2026-11-13。設計 §5.3 の T22・T24、§20.5 の「公開のジョブの確かめ」）。問 10-3 と問 10-4 は、持ち主の答えを待っている（上の「持ち主に聞いていること」）。
- **理由:** `gh release edit --draft=false` は、下書きのどの配布物も公開し、`publish` はフォルダーの `.nupkg` をすべて push する。そのため、`SHA256SUMS` に載っていない配布物があれば、それも公開された。`checksums` の出力は、V1d7 から `attest` と `draft` が照らしている、`SHA256SUMS` を書いたジョブの値で、`publish` は同じ実行の中でそれを読める。
- **却下した案:**
  - 問 10-1 の (B) `SHA256SUMS` に載っていないパッケージだけを見る（載っていないほかの配布物が、そのまま公開される）。
  - 問 10-2 の (B) `SHA256SUMS` を来歴の証明の検証と照らす。証明は、`attest` のジョブが、同じ実行の artifact の `SHA256SUMS` から作る。そのため、この実行の証明なら、`checksums` の出力と照らすのと同じ値を、証明の検証（`gh attestation verify`）を通して確かめることになる。ただし、検証が結び付けるのは、リポジトリ、署名したワークフロー、ref で、この実行ではない。同じタグのほかの実行や、`workflow_dispatch` の実行が、別の `SHA256SUMS` に証明を付けていれば、それも通る。また、承認のあとのジョブに、ネットワークと Sigstore への依存が増える。
