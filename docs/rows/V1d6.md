# V1d6（Issue #324）: クライアントと `elm` が、答えの本文を全部読み込んだあとで大きさの上限を確かめることを直す

## Grill の記録

- V1d6 の Grill（Issue #324 に記録した。問 6-1〜問 6-6。持ち主の決定はどれも推奨案 A。2026-11-13）: クライアントと `elm` が、答えの本文を全部読み込んだあとで大きさの上限を確かめていたことを直す（V1d の指摘 F07）。却下した案は [design-decisions.md](./design-decisions.md) の「答えの本文を、読みながら上限で止める」。
  - 測った事実（Grill のとき。Windows、SDK 10.0.404、JIT の Release）: `ActivationClient.ActivateAsync` は、256 MiB の答えで約 768 MiB を確保し、終わらない答えは約 2 GiB まで読んで `ELM_NETWORK_ERROR` になった。`Content-Length` が 256 MiB と言っていても、全部読んだ。`elm offline process` も同じだった（子プロセスの最大の作業セットは 346〜2,083 MiB）。`elm server` のコマンドと、サーバーライセンスの状態・読み直しの答えには、上限がなかった。
  - 持ち主が決めたこと:
    - 問 6-1（読み方）: ヘッダーまでを受け取り（`ResponseHeadersRead`）、`Content-Length` を見て、数えながら読む。共通の処理を 1 つにする。
    - 問 6-2（誤り）: 大きすぎる答えは、終わらないものも含めて `ELM_MALFORMED`。`elm` の終了コードは 3。
    - 問 6-3（答えのない要求）: 大きすぎる成功（`2xx`）の答えの `jti` を、答えのない要求の一覧に入れる。リースと有効化の両方。
    - 問 6-4（時間）: 送信から本文の終わりまでを、1 つの 30 秒で打ち切り、クライアントの `TimeProvider` で数える。
    - 問 6-5（`elm server`）: `elm server` とサーバーライセンスのコマンドの答えにも、この行で上限を置く。数字は、正しい答えのいちばん大きいものを測ってから、持ち主にもう一度聞く。
    - 問 6-6（範囲）: 大きさを確かめてから全部読むファイルは、この行に入れず、Issue にする（Issue #386）。`elm admin request` の成功の本文に上限がないことは、設計に「受け入れる」と書く（§16）。
  - こちらが決めたこと（Grill のとき）: `Content-Length` が上限を超えていれば、読まずに断る。大きすぎる答えの `ELM-Nonce` と `Retry-After` は読まない。
  - 実装で決めたこと:
    - 管理 API の答えの上限は 64 MiB で作った。測った大きさと計算は §13.7 の「管理 API の応答の上限」にある。値は `ServerAdminApi.MaxAnswerLength` の 1 か所にある。独立レビューが、`elm` の持つメモリが上限の約 20 倍になることを見つけたので、読み方を直して測り直し、持ち主にもう一度聞いた。持ち主の決定は推奨案 A の 64 MiB（2026-11-13。`elm` が持つメモリは、いちばん多い場合で約 145 MB）。退けた案: 16 MiB（いちばん大きい形のリースでは、§4.2 の目標の 3 倍しか入らない）。256 MiB（`elm` が約 580 MB を持ちうる）。

## 退けた案

- **決定:** クライアント（`LicenseClient`、`ActivationClient`）と `elm`（`elm offline process`、`elm server` のコマンド）は、答えをヘッダーまで受け取り（`ResponseHeadersRead`）、`Content-Length` が上限を超えていれば本文を読まずに断り、そうでなければ数えながら読んで、上限と 1 バイトで止める。処理は `ElasticLM.Client` の 1 つにまとめる（問 6-1）。上限を超えた答えは、終わらない本文も含めて `ELM_MALFORMED` で、`elm` の終了コードは 3 にする（問 6-2）。大きすぎる成功（`2xx`）の答えの要求の `jti` は、リースでも有効化でも、答えのない要求の一覧に入れる（問 6-3）。送信から本文の終わりまでを 1 つの 30 秒で打ち切り、クライアントの `TimeProvider` で数える（問 6-4）。`elm server` のコマンドが読む管理 API の答えにも、この行で上限を置く。値は、正しい答えのいちばん大きいものを測ってから、持ち主にもう一度聞く（問 6-5。実装は 64 MiB で作った）。大きさを確かめてから全部読むファイルは、この行に入れずに Issue #386 にし、`elm admin request` の成功の本文に上限がないことは受け入れる（問 6-6）。Grill のときにこちらが決めたこと: `Content-Length` が上限を超えていれば、読まずに断る。大きすぎる答えの `ELM-Nonce` と `Retry-After` は読まない（持ち主の決定、どれも推奨案 A。2026-11-13。設計 §8.6、§10.4、§12.1、§12.6.2、§12.7.3、§12.8.4、§13.7、§16）。
- **理由:** 測ると、`ActivationClient.ActivateAsync` は、256 MiB の答えで約 768 MiB を確保し、終わらない答えを約 2 GiB まで読んだ。`Content-Length` が 256 MiB と言っていても、全部読んだ。`elm offline process` も同じだった。オンプレミスの最初の接続は、証明書を確かめる前なので、サーバーのアドレスで答えられる相手なら、これをアプリにさせられた（§5.3 の T16）。ヘッダーまでで戻る形なら、状態コードを読んでから断れるので、成功の答えだけを、答えのない要求として数えられる。`ResponseHeadersRead` では、`HttpClient.Timeout` は本文を読む時間を数えないので、30 秒を本文の終わりまで数える処理が要る。
- **却下した案:** 問 6-5 の (B) 16 MiB（いちばん大きい形のリースでは、§4.2 の目標の 3 倍しか入らない）と (C) 256 MiB（`elm` が約 580 MB を持ちうる）。 問 6-1 の (B) `MaxResponseContentBufferSize` を 256 KiB にするだけ（大きすぎる答えの状態コードが読めない）。問 6-2 の (B) 終わらない答えは `ELM_NETWORK_ERROR` のままにする。問 6-3 の (B) 大きすぎる成功の答えの `jti` を、一覧に入れない。問 6-4 の (B) 読み取りごとに、止まっている時間の上限を置く。問 6-5 の (B) `elm server` のコマンドの上限は、行を足して先送りする。問 6-6 の (B) ファイルの読み方も、この行に入れる。
