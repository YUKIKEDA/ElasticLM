### 問 25-4b（問 25-4a の答えを作る前に見つけた。持ち主に問う）

問 25-4a の答えの「強制終了で止まる時刻の行がないときは、止まる前の最後の行の時刻から数える」は、今の借り出しの記録の形では、前のリースを覆わない。借り出しの記録が行を書くのは、借り出し、早期返却、新しいファイル、`key.changed` のときだけで、ふつうのリースの取得と更新では書かない（`BorrowJournal`、`LeaseEngine`）。そのため、最後の行のあとにも、サーバーはリースを出し続けうる。最後の行が 1 時間前で、強制終了の直前に `lease` 10 分のリースを出していれば、「最後の行の時刻 + `lease`」はもう過ぎているのに、そのリースは起動のあと最大 10 分生きている（T8）。

- 案 A（推奨）: 強制終了のとき（止まる時刻の行がないとき）は、起動の時刻から数える。回収の時間の終わりは、記録にある `leaseUntil` と「起動の時刻 + 止まる前のライセンスの `lease`」と「起動の時刻 + 今のライセンスの `lease`」のいちばん遅いものになる。止まる時刻の行があるとき（ふつうの停止）は、「止まった時刻 + 止まる前のライセンスの `lease`」を使い、長く止めたあとの待ちは縮む。良い点: 強制終了でも T8 を守る。記録に書く行は、新しいファイル、`key.changed`、停止のときだけで、リースの要求の道は変わらない。悪い点: 強制終了のあとは、長く止めていても、止まる前のライセンスの `lease` だけ待つ（今と同じ）。
- 案 B: 60 秒ごとのタイマーが、そのあいだにリースを出していれば、`leaseUntil`（今 + `lease` + 余裕）の行を書く。強制終了のときは、最後の行の `leaseUntil` を使う。良い点: 強制終了のあとも、待ちが縮む。悪い点: リースを出しているあいだ、記録に 1 分ごとに署名と書き出しが入り、1 日 1,440 行で 1,000 行の書き写し（V1d16）が毎日起こる。タイマーが遅れたときの余裕の長さを、別に決めて測る必要がある。
- 案 C: リースを出すたびに、`leaseUntil` が進むときだけ記録に書く。良い点: 正確である。悪い点: 取得と更新の道に、署名と書き出しが入る（§4.2 の更新の p99 50 ms）。

推奨は A である。理由: T8 を、強制終了のあとも守り、リースの要求の道と記録の大きさを変えないため。長く止めたあとの待ちが縮まないのは、強制終了のときだけである。問 25-4a の答えは、この問いの答えのあとで作る。この PR の今のコードは、問 25-4 の決め方（今と、記録の最新のファイルの終わりの鍵のライセンスの `lease` の長いほう）のままである。

### 問 25-4 の、前のライセンスの `lease` を記録から読めるか（`origin/main` の 5e026d0 のコードを読んだ）

- 読める。借り出しの記録の各ファイルの最初の行（`chain.start` か `chain.reset`）と、`key.changed` の行は、サーバーライセンスのファイルと公開鍵を持つ（`SignedLog.StartFile`、`SignedLog.ChangeKey`）。`LogVerifier.Verify` は、その行を `ReadKey` で読み、行の時刻（`ts`）の時計の `LicenseVerifier` で、トラストストアで確かめて `ServerIdentity` を作る（`LogVerifier.cs` の `ReadKey`）。`key.changed` のあとの署名の行で、署名に使う鍵をその新しいものに替える（`VerifyFile` の `nextKey`）。ファイルの終わりで署名に使われていた鍵は `LogReport.Files` の最後の `LogFileKey` になるが、V1d25 の前の `LogFileKey` はライセンス ID と鍵の拇印しか持たなかった。
- そのため、`LogFileKey` に、その鍵のサーバーライセンスの `lease`（`VerifiedLicense.LeaseDuration`）を足す（`elm-service` のログでは `null`）。`BorrowJournal.Load` は、最新のファイルが検証に通ったときだけ、それを `PreviousLease` として持つ。
- サーバーの再読み込みは、借り出しの記録に `key.changed` を書けたときだけ新しいライセンスを使う（`SignedLog.ChangeKey` の `takeOnFailure: false`、`ElmServer.ReloadLicense`）。書いた行に署名する前に止まれば、検証は署名のない `key.changed` を採らず、古い鍵がファイルの終わりの鍵になる。どちらでも、終わりの鍵は、止まる前にサーバーが使っていたライセンスと合う。

### 問 25-4a（この行の設計の独立レビューと実装で見つけた。持ち主に問う）

問 25-4 の決め方は、止まっているあいだにライセンスを替えた、1 度の成功した再起動を覆う。次の 3 つの形は覆わない。

1. 動いているあいだに、`lease` の短いライセンスへ読み直した（`elm server reload` か、自動の更新）。前のライセンスで出したリースは、その期限まで生きている（読み直しはリースを残す。`LeaseEngine.ReplaceLicense`）。その期限の前に止めて起動すると、記録の最新のファイルの終わりの鍵は新しいライセンスなので、回収の時間は短いほうになる。
2. 止まっているあいだに替え、起動したあと、長いほうの回収の時間のうちに、もう一度止めて起動した。1 度目の起動は、新しいファイルを今のライセンスで始める（`SignedLog.Open`）ので、2 度目の起動は前のライセンスを知らない。
3. 止まっているあいだに替え、1 度目の起動が失敗した（ポートが使われている、設定の誤り）あと、もう一度起動した。失敗した起動も記録の新しいファイルを始める（§13.1）ので、2 と同じになる（独立レビューの D2）。

どの形でも、回収の時間が終わったあと、前のライセンスのリースのトークンを持つクライアントは、次の更新まで動き続け、その席は別のクライアントに貸せる（T8。回収の時間のあとの回収は、空き席に収まるときだけ受けるので、サーバーの数えが席の数を超えることはない）。

もう 1 つ、問 25-4 の決め方には代償がある（独立レビューの D1）。前のライセンスの `lease` を、サーバーが止まっていた長さによらず使う。止まる前の時刻は記録にない（借り出しの記録の最後の行の `ts` は、借り出しと返却がなければ進まない）。たとえば `lease` が 24 時間（ポリシーの上限）のライセンスを、1 週間止めたあとで 10 分のものに替えると、前のリースはもうないのに、起動から 24 時間、新しいリースを断る。

- 案 A（推奨）: 記録に「この時刻まで生きうるリースの、いちばん長い `lease`」を署名つきで持たせる。たとえば記録の各ファイルの最初の行と `key.changed` の行に `leaseUntil`（その時刻までに出したリースが切れうる最後の時刻）を足し、サーバーが止まるときに、止まった時刻の行を書く。起動は、`leaseUntil` が今より先なら、その残りと今のライセンスの `lease` の長いほうを回収の時間にする。新しいファイルを始めるとき（失敗した起動を含む）は、まだ切れていない `leaseUntil` を引き継ぐ。良い点: 3 つの形を覆い、代償もなくなる（止まっていた長さで縮む）。T8 の性質が、再起動の回数や読み直しのあるなしで変わらない。悪い点: 記録の形（§13.4、§18.1）と `LogVerifier` が変わり、この行より大きい。止まる時刻の行は、強制終了では書かれないので、そのときは止まる前の最後の行の時刻から数える（その時刻より前に止まったことはない）。
- 案 B: 3 つの形と代償を、§5.4 に受け入れるものとして書き、問 25-4 の今の決め方のままにする。問 25-4 で退けた「§5.4 に書いて受け入れる」とは違い、止まっているあいだに替えた 1 度の再起動は、今のとおり覆う。良い点: 記録の形は今のまま。悪い点: 3 つの形では、前のリースの残りのあいだ、席数を超えて使われうる（運用者の操作が起点で、外の攻撃者は起こせない）。代償（長く止めたあとの待ち）も残る。

推奨は A である。理由: §5.3 の T8（席数を超えた利用）の対策を、再起動の回数や読み直しのあるなしで変えず、再起動のあとに新しい利用者が待つ時間を、前のリースが本当に生きうる長さに限るため。この行の実装は、問 25-4 の決定どおり（止まる前のライセンスの `lease`）である。A を選ぶなら、別の行にするか、この行で続けるかも決める。

### こちらが決めたこと

- 決まった一文は「The request proof is not valid.」で、`ElasticLM.Issuing` の `ProofVerifier.Refusal` に置く。両方のサーバーが同じ文を返すためである。答えの文を替えるのは、両方のサーバーの `ProblemAsync`（`ELM_PROOF_INVALID` なら、渡された文を運用のログに書いてから捨てる）で、`ELM_PROOF_INVALID` を返す道が増えても、同じ文になり、ログの行も書く（設計の独立レビューの D8）。`ProofVerifier` の `Invalid` の文は、運用のログの理由として今のまま残す。
- 運用のログの行は `ServerLog.ProofRefused`（イベント 22）と `ServiceLog.ProofRefused`（イベント 23）、`Information`、「A request proof was refused (<経路>): <理由>」。経路は、要求が当たった経路の形（`RouteEndpoint.RoutePattern.RawText` と方法。`POST /v1/leases/{id}/renew` など）で、パスの値を持たない（§18.3）。理由は、検証器の文か、サーバー自身の文（「The proof is not signed by the key the lease is bound to.」など）で、要求の文字を持たない。
- 段は `Information` にした（V1d9a のイベント 21 と同じく、呼び出し元の誤りで、サーバーの故障ではない）。`Debug` にすると、既定の段で理由が残らず、クライアントの組み込みの誤りを運用者が調べられない。行の数は、送信元ごとの頻度の制限で抑えられる。
- 本文を読めない端末の要求の行は、`ServerLog.RequestUnreadable`（イベント 23）と `ServiceLog.DeviceRequestUnreadable`（イベント 24）、`Information`、「A device request (<経路>) could not be read (<状態>); the connection was closed.」。`elm-service` のイベント 21 は「administration call」と言い、操作の名前を持つので、別のイベントにした。
- `key.changed` を書けなかった行は `ServerLog.KeyChangeNotRecorded`（イベント 37、`Error`）、「The borrow record cannot record the new server license; the old license stays.」と例外。`ElmServer.ReloadLicense` の中で書くので、管理の再読み込みと、自動の更新の読み直しの両方で書く。
- 回収の時間は、`LeaseEngine` の作るときに 1 度決める（`LeaseEngineOptions.PreviousLease`）。
- 借り出しの記録の書き込みで、停止で閉じた記録の `ObjectDisposedException` も、イベント 34 に例外ごと書く（`BorrowJournal.Recorded`）。V1d25 の前は、その原因は答えの文にだけあり、答えを決まった文にすると、どこにも残らなくなるためである（設計の独立レビューの D10）。

- 問 25-1a の形: `ElmService.ProblemAsync` に `administrator` を渡し、`POST /v1/admin/offline` の答え（`WriteOfflineAsync`）だけが、`ELM_PROOF_INVALID` の文を替えない。運用のログの行は、どちらの経路でも書く。
- 設計の独立レビューの指摘（PR #470 の bca190c に対して）のうち、コードで直したもの: 自動の更新の読み直しが、停止で閉じた借り出しの記録に当たったとき（`ObjectDisposedException`）も、古いライセンスのままにしてイベント 37 を書く。自動の更新が受け取ったファイルを書けなかったとき（イベント 42 の `write` の段）にも、例外を添える。`ServerLog.RequestUnreadable` を `ServerLog.DeviceRequestUnreadable` にした（`elm-service` の管理 API のイベント 21 の `ServiceLog.RequestUnreadable` と名前が重なっていた）。

## 退けた案

- **決定:** `ELM_PROOF_INVALID` の答えの文を 1 つにし、落ちた検査は運用のログに書く（問 25-1）。
- **理由:** §12.1 は、遠くの呼び出し元に、§19 の分類以上の内部の理由を返さないと決めている。落ちた検査の名前は、証明を作り直す相手に、どの部分が通ったかを教える。運用者は、運用のログで同じ理由を読める。
- **却下した案:** §12.1 に「`detail` は落ちた規則を言ってよい」と書く（Issue #344 の Grill の記録）。§12.1 と `security.mdc` の決まりに例外を足すことになり、`elm-service` のように、インターネットの誰でも届くサーバーの答えから、検査の順と結果を読めるままになる。

- **決定:** 借り出しの記録の書き込みの失敗は「The borrow cannot be recorded.」とだけ返す（問 25-2）。
- **理由:** 原因の例外は、V1d8 から運用のログ（イベント 34）にある。例外の文はデータのフォルダーのパスを持ち、遠くの呼び出し元に返す理由がない。
- **却下した案:** 例外の文を今のまま返す（直す前の形）。パスがクライアントの誤りの文に入る。

- **決定:** `key.changed` を書けなかった原因を、例外ごと運用のログに書き、`admin.sock` の答えは変えない（問 25-3）。
- **理由:** 借り出しと早期返却の書き込みの失敗（イベント 34）と同じく、原因を運用のログで追えるようにする。`admin.sock` は、サーバーと同じ機械で、データのフォルダーに入れる利用者にしか届かない。
- **却下した案:** 答えの文から例外の文を外す。ローカルの管理者が、運用のログを見ずに原因を知る手段がなくなる。Issue #403 の記録は、ほかの選択肢の文を残していない。

- **決定:** 回収の時間を、今のライセンスと、記録にある止まる前のライセンスの `lease` の長いほうにする（問 25-4）。
- **理由:** 止まっているあいだに `lease` の短いライセンスに替えると、前のライセンスのリースが生きているのに、回収の時間が終わって、その席を貸せた（T8）。前のライセンスは、署名を確かめる記録の最新のファイルに、もうある。
- **却下した案:** §5.4 に書いて受け入れる。警告だけを出す（どちらも Issue #344 の Grill の記録）。どちらも、席数を超えた利用（T8）が残る。

- **決定:** 端末の要求の、本文を読めない `BadHttpRequestException`（400、408）は、運用のログに 1 行を書いて接続を切る（問 25-5）。
- **理由:** 呼び出した側が送る本文だけで、スタックつきの `Error` の項目をいくつでも書かせられると、運用者が本物の故障を見落とす（V1d9a の問 9a-5 と同じ）。
- **却下した案:** 今のまま設計に書く（V1d9a の問 9a-5 の退けた案と同じ）。運用のログの `Error` の段が、呼び出した側の誤りで埋まる。

- **決定:** 回収の時間に、記録の `leaseUntil` を使う（問 25-4a の案 A。持ち主の決定 2026-11-22。作るのは問 25-4b の答えのあと）。
- **理由:** 問 25-4 の決め方は、止めているあいだに替えた 1 度の再起動しか覆わず、長く止めたあとも前の `lease` だけ待たせる。
- **却下した案:**
  - 案 A を別の行にする（持ち主の答えにある）。この行の T8 の直しが、覆わない形を残したまま閉じる。
  - 3 つの形と代償を §5.4 に受け入れるものとして書く（問 25-4a の案 B）。運用者の操作の直後の再起動で、席数を超えて使われうる。
  - 記録の最新のファイルのすべての鍵（最初の行と `key.changed` の行の、`LogReport.Files` に入る前の鍵のすべて）の `lease` のいちばん長いものを使う（設計の独立レビューが挙げた軽い形）。読み直しが同じファイルの中にあるときだけ形 1 を覆い、新しいファイルをまたぐと覆わない。形 2 と 3、長く止めたあとの待ちも残る。

- **決定:** 端末の API は `ELM_PROOF_INVALID` を 1 つの決まった文で答え、`POST /v1/admin/offline` だけが理由を返す（問 25-1a）。
- **理由:** §12.1 が理由を絞る相手は認証のない遠くの呼び出し元で、管理 API の呼び出し元はサービスの運用者自身である。
- **却下した案:**
  - どこでも 1 つの文のままにする。管理者が、自分の扱ったオフラインのファイルの断られた理由を、運用のログを探さずに知れない。
  - 設定の誤り（方法と URI の違い）だけ別の文にする。署名より前の確かめの結果が、認証のない相手に分かる。
