## 退けた案

- **決定:** 同時の要求を、（`key_id`, `nonce`）の一意の索引と `ON CONFLICT DO NOTHING` で断る（問 1）。
- **理由:** データベースが、どの書き手にも一意を強制する。両方のエンジンで同じコードになり、`proof_jtis` と `trial_fingerprints` と同じ形である。待ってから 0 行が返ることは、PostgreSQL 18.6 で測った。
- **却下した案:**
  - `pg_advisory_xact_lock` で、インストール鍵のハッシュごとに排他する。守れるのはロックを取る経路だけで、エンジンごとにコードが分かれ、64 ビットのハッシュが衝突すると関係のない鍵どうしが待ち合う。
  - インストール鍵ごとの行を持つ表を作り、`FOR UPDATE` でロックする。表と書き込みが増え、守れるのがロックを取る経路だけという点は上と同じである。

- **決定:** 負けた要求には、順のときと同じ `409` と `ELM_REPLAYED` を返し、書いたものをすべて戻す（問 2）。
- **理由:** 同じ理由で断る要求の答えが、来た順で変わらない。§12.8.4 の「断った要求は `offline_requests` に書かない」にもそろう。
- **却下した案:** `500` や別のコードを返す。同じ理由で断る要求の答えが、来た順で変わってしまう。

- **決定:** 移行 `0013` で、組ごとに `activation_id` の最も小さい 1 行を残して消し、そのあと一意の索引に替える（問 3）。
- **理由:** どのデータベースでも移行が止まらない。消した行の要求ファイルは、渡し直すと `409` になるが、その有効化と、すでに出したトークンはそのまま効く。重複の行は、インストール鍵を持つ人が同じノンスを自分で作ったときにしかできない。
- **却下した案:**
  - 重複があれば移行を止めて起動しないようにし、運用者に手で消してもらう。起動が止まり、手順の文書が要る。
  - 扱いを置かず、`CREATE UNIQUE INDEX` だけにする。重複があると、移行がエラーで止まる。
