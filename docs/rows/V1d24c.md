### 測った事実（`origin/main` の 8c35a87。Windows 11 ビルド 26300、SDK 10.0.404、ランタイム 10.0.15、scratch の Release の `dotnet run`）

- `src/` の読み手を、`File.ReadAll*`、`FileStream`、`File.Open*`、`StreamReader`、`ReadExactly`、`Length` の比べを `rg` で探して一覧にした。
  - 大きさを `FileInfo.Length` で確かめてから全部を読む読み手: `FileClockGuard.ReadState`（`File.ReadAllBytes`、4,096 バイト）、`ActivationStore.Read`（256 KiB。開いたあとの `FileStream.Length` の大きさのバッファーに `ReadExactly` で読み、開いた口では上限を確かめていなかった）、`CliFiles.ReadText`（`File.ReadAllText`）と `CliFiles.ReadBytes`、`ServiceSettings.ReadFile` と `ReadSecret`、`ServerSettings.ReadFile`。
  - 大きさを確かめない読み手: `ElmService.ReadTrust`、`ReadSigningKey`（署名鍵と証明書）、`ElmServer.ReadTrust`（どれも `File.ReadAllText`）、`TlsCertificateFiles.TryLoad`（`LoadPkcs12CollectionFromFile`、`CreateFromPemFile`、`ImportFromPemFile`）。
  - V1d24a のあと `FileReplacement.ReadShared` で読んでいた読み手（`ServerPins`、`InstallationKeyStore`、`LicenseClient.LoadBorrow`、`ProtectedFiles.TryReadSecret`、`ElmServer.TryReadLicense`、`ServerLicenseCommands.RemoveIfKept`）は、開いた口の `FileStream.Length` で上限を確かめ、その長さだけを読むので、大きさは抑えられていた。前の `FileInfo.Length` の確かめは、同じ上限を 2 度確かめていた。`RemoveIfKept` の上限は、V1d24a から保存したファイルの長さで、24c-2 の「64 KiB」は要らなくなっていた。
  - `MachineIdSources.ReadLinuxMachineId`（V1d29e）は、`bufferSize: 0` で 65 バイトまでを読んでいた。
- 確かめてから読むまでのあいだに大きくなるファイル: 100 バイトのファイルの `FileInfo.Length` が 64 KiB の確かめを通ったあとに 512 MiB にすると、`File.ReadAllBytes` は 536,870,912 バイトを読み、513 MiB を確保した（732 ms）。`File.ReadAllText` は 2,053 MiB を確保した（2,805 ms）。`ActivationStore` の形も 513 MiB を確保した。`ReadShared` は、開く前に大きくしたファイルで `null` を返した。
- 本当の競合: 書き手が、開いて `SetLength(100)` して閉じることと、開いて `SetLength(16 MiB)` して閉じることを繰り返し、読み手が 5 秒のあいだ確かめと `File.ReadAllBytes` を繰り返した。確かめを通って 16,777,216 バイトを読んだのは、2 回の実行で 24 回と 15 回だった。同じ競合で `ReadShared` が上限を超えて返したことはない。書き手が開いたままのあいだは、`File.ReadAllBytes`（`FileShare.Read`）は Windows で `IOException` になり、超えた読み取りは 0 回だった。
- `ReadShared` の形で、長さを読んだあとに大きくしたファイルは先頭の 100 バイトだけが返り、縮めたファイルは `EndOfStreamException`（`IOException` の子）になった。
- 上限のない読み手: 512 MiB の `trust.rootKeys` を `File.ReadAllText` で読むと 2,052 MiB を確保した（2,159 ms）。256 MiB の PEM のないファイルを `ImportFromPemFile` で読むと 1,026 MiB を確保した（804 ms）。同じファイルの `LoadPkcs12CollectionFromFile` は、確保なしに 5 ms で `CryptographicException` になった（PKCS#12 の読み手は、BER の SEQUENCE で始まるファイルだけを読む。`X509CertificateLoader.cs` の `ReadAllBytesIfBerSequence`、dotnet/runtime release/10.0）。
- F30: `UTF8.GetBytes(File.ReadAllText(path))` は、`EF BB BF 61` を `61`、`61 FF 62` を `61 EF BF BD 62`、`FF FE 61 00` を `61` にした。
- `ElasticLM.Licensing.csproj` は、`ElasticLM.Issuing`、`ElasticLM.Leasing`、`ElasticLM.Client`（V1d24d が `UnixLeftover` のために足した）、`elm`、`elm-server`、`elm-service`、`elasticlm`、`libelasticlm` に `InternalsVisibleTo` を持っていた。`elm-service` と `ElasticLM.Issuing` は `ElasticLM.Client` を参照しないので、24c-1 の答え（Licensing と Client に 1 つずつ）では、その読み手に届かなかった。

### こちらが決めたこと

- `BoundedFile.Read` は、読んだあとに上限 + 1 バイトのバッファーを 0 で埋める。呼び出し側に渡すのは、読めた長さの写しである。`ProtectedFiles.TryReadSecret` は自分の写しを消し、TLS の PKCS#12 の呼び出し側は読み込んだあとにバイトを 0 で埋める。PEM の文字（TLS の鍵、秘密のファイル）は `BoundedFile.ReadAllText` が文字列にし、読んだバイトは 0 で埋めるが、文字列は .NET では消せない（V1d24c の前の `File.ReadAllText` と同じ）。
- `elm-server` と `elm-service` の PEM と秘密のファイルは、`BoundedFile.ReadAllText` で読む。`File.ReadAllText` は `StreamReader(…, Encoding.UTF8, detectEncodingFromByteOrderMarks: true)` で読み（`File.cs`）、`StreamReader.DetectEncoding` が先頭のバイトから符号化を選ぶ（`StreamReader.cs`、dotnet/runtime release/10.0）。`BoundedFile.ReadAllText` は、同じ順に符号化を選び、`Encoding.GetString` で一度に解く。はじめは `StreamReader` を使ったが、`StreamReader` は自分のバッファーに読んだバイトと文字の写しを持ち、消さないので、PR #520 のレビュー（A2）のあとに改めた。問 Q8 の厳しい UTF-8 は `elm` のファイルの引数だけで、サーバーの読み手の文字は V1d24c の前と同じになる。
- 前の `FileInfo.Length` の確かめは、どの読み手からも外した。上限は `BoundedFile.Read` の 1 か所で確かめる（`.cursor/rules/testing.mdc` の、2 度確かめる上限は変異が生き残る）。ファイルがないときの扱いを分ける読み手（`FileInfo.Exists`）は、前のとおり残した。
- `MachineIdSources.ReadLinuxMachineId` も `BoundedFile.Read(path, 64, FileShare.Read)` で読む（問 Q2 の「1 つの読み手」）。前の形も同じ読み方で、振る舞いは変わらない。
- 新しい誤りの文: 「trust.rootKeys file '<パス>' is larger than 16 KiB.」（両方のサーバー）、「The signing key file '<パス>' is larger than 64 KiB.」、「The certificate file '<パス>' is larger than 16386 bytes.」、「The TLS certificate '<パス>' is larger than 64 KiB.」、「The TLS key '<パス>' is larger than 64 KiB.」、`elm` の「The file '<パス>' is not UTF-8 text.」。前からある文（設定ファイル、秘密のファイル、`elm` の「is larger than <上限> bytes.」と「does not exist.」）は変えない。
- 署名の証明書のファイルの上限は、`Limits.MaxTokenLength`（16 KiB）に CRLF の 2 バイトを足した 16,386 バイトにした。`elm key certify` は LF を書くが、運用者がエディターで保存し直すと CRLF になりうる。16 KiB ちょうどのトークンに UTF-8 の BOM と CRLF が付いたファイル（16,389 バイト）は断る。そのトークンは §8.6 の 1 トークンの上限ちょうどで、ふつうの証明書のトークン（数百バイト）より大きく離れているので、BOM の 3 バイトのために上限を広げなかった。

## 退けた案

- **決定:** 共通の読み手は、`ElasticLM.Licensing` の internal に 1 つだけ置き、ほかのアセンブリは前からある `InternalsVisibleTo` で使う（問 Q2）。
- **理由:** V1d24d が `ElasticLM.Client` への `InternalsVisibleTo` を足したので、24c-1 が退けた理由（Client に新しく見せること）はなくなった。24c-1 の答えのままでは、`ElasticLM.Client` を参照しない `elm-service` と `ElasticLM.Issuing` の読み手に届かない。
- **却下した案:** `ElasticLM.Licensing`、`ElasticLM.Client`、`ElasticLM.Issuing` に 1 つずつ置き、同じテストの表で確かめる（同じコードが 3 つになる）。`ElasticLM.Licensing` に public で置く（公開の API が増え、パッケージの検証にかかる）。24c-1 の、Licensing と Client に 1 つずつ置く形（はじめの答え）。

- **決定:** `ReadShared` のシークできる道も、上限 + 1 バイトまで読む形にする（問 Q3）。
- **理由:** 大きさは前の形でも抑えられていたが、バッファーを `FileStream.Length` から決めていて、`bufferSize` も既定のままで、`.cursor/rules/security.mdc` と合わなかった。道が 1 つに減る。
- **却下した案:** 今のままにし、規則の文を「開いた口の `Length` で上限を確かめてからなら、`Length` で決めてよい」に直す（規則を緩める）。

- **決定:** 読みのあいだに変わったファイルは、読み直さない（問 Q4）。
- **理由:** どの読み手のふるまいも変わらない。書き手と重なった読み取りは、一度だけ誤りになることがある。
- **却下した案:** 上限を超えたり形が悪かったりしたら、1 回だけ読み直す（新しい道とテストが増え、断る理由が見えにくくなる）。

- **決定:** `elm-server` と `elm-service` の `trust.rootKeys` は 1 ファイル 16 KiB、ほかは問 Q5 の数字（問 Q5a）。
- **理由:** 64 KiB のファイルでは、上の測定で `elm-server` の起動が 526〜1,331 ms になり、§4.2 の 1 秒を超えうる。16 KiB では 109〜191 ms だった。ベンダーのルート鍵は、ふつう 1〜3 個（入れ替えのあいだ）である。
- **却下した案:** 64 KiB のままにし、上限ちょうどでは起動が 1 秒を超えうることを §4.2 か §5.4 に受け入れとして書く。バイトの上限は 64 KiB のままにし、`TrustStore.Create` に鍵の数の上限を足す（`ElasticLM.Licensing` の公開 API の振る舞いが変わる）。すべて 1 MiB にする（はじめの Grill で退けた）。`elm` の `--trust` も 16 KiB にそろえる（今は読めているファイルが断られうる。持ち主は 64 KiB のままにした）。

- **決定:** TLS の証明書は、上限つきで読んだバイトと文字から組み立てる（問 Q6）。
- **理由:** パスを受け取る読み込みは、ファイルの全部を読んでから解く（上の測定で、256 MiB の PEM のないファイルに 1,026 MiB を確保した）。
- **却下した案:** 前に `FileInfo` で大きさを確かめるだけにする（確かめてから読む形が残る）。

- **決定:** §5.3 の T16 の攻撃者に A6 と A8 を足す（問 Q7、24c-3）。
- **理由:** ファイルを書けるのは、同じ端末のほかの利用者で、運用者が指すファイルをその者が書ける場所に置いた場合である。
- **却下した案:** T20 に書く。§5.4 に受け入れとして書く。

- **決定:** `ReadText` は厳しい UTF-8 で解き、UTF-8 の BOM は 1 つだけ外す（問 Q8、24c-4）。
- **理由:** 読み手が受け入れるファイルを、文書に書ける。UTF-16 で保存した PEM は、誤りになる（V1d24c の前は読めていた）。
- **却下した案:** UTF-8 の BOM も誤りにする（Windows のメモ帳で保存したファイルも誤りになる）。`ReadBytes` だけを直す（はじめの Grill で退けた）。

- **決定:** 共有の指定は引数にし、今の指定を保つ（問 Q9）。
- **理由:** V1d24d の問 24d-5 の決定（時計の守りは `FileShare.Read`）を崩さず、この行の範囲が大きさの確かめに収まる。
- **却下した案:** どの読み手も `ReadWrite | Delete` にする（24d-5 の決定とぶつかる）。

- **決定:** 直すのは `src/` だけにする（問 Q10）。
- **理由:** `tools/` の道具は、リポジトリの持ち主が自分で渡すファイルを読み、Issue #386 の脅威の外である。
- **却下した案:** `tools/` も同じ読み手で直す。
