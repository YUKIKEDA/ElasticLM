# トークンとファイルの形式

このページには、ElasticLM が読み書きするファイルと署名付きトークンの形式を載せる。対象は、鍵ファイルと鍵 ID、鍵証明書、ライセンストークンとライセンスファイル、リーストークン、オフラインのリクエスト・レスポンス・アクティベーション解除のファイル、サーバーライセンスだ。それぞれについて、ヘッダーとペイロードのメンバーをすべて示す。リクエストのプルーフ（所有証明）のメンバーは[デバイスのプロトコル](device-protocol.md#プルーフ)に、ログの署名のメンバーは[ログ](logs.md#署名に関わる行とチェーン)にある。最後に、クライアントライブラリがデバイスに保存するファイルを挙げる。読者は、検証側やクライアントを自分で書く人、ファイルを手で調べる人、デバイス上のどのファイルをコピーまたは削除してよいかを知る必要がある人だ。これらのファイルの用途については、先に[トラストチェーン](../explanation/trust-chain.md)と[ライセンスファイルと検証](../explanation/license-files-and-verification.md)を読んでおくとよい。[`elm license inspect`](elm-cli.md#elm-license-inspect) は、ライセンスファイルをデコードした中身を表示する。

例は、`elm`、`elm-server`、`elm-service` が書いたファイルから取った。鍵 ID、鍵の座標、トークン ID、アクティベーション ID とライセンス ID、フィンガープリント、ノンス、ライセンスキーは、同じ長さの偽の値に置き換えてある。時刻はそのままだ。署名とトークン全体は `eyJ…` に、PEM ファイルの本体は `…` に縮めた。プログラムは JSON を 1 行で書くが、ここではデコードしたペイロードを読みやすいようにインデントしている。文字列は、プログラムが書いたとおり、`\uXXXX` のエスケープを含めて示す（[ヘッダー](#ヘッダー)を参照）。

## 鍵ファイルと鍵 ID

### 秘密鍵ファイル

`elm key root create` と `elm key signing create` は、ルート鍵または署名鍵の秘密鍵を、`ENCRYPTED PRIVATE KEY` ブロックを 1 つ持つ PEM ファイルに書く。中身は PKCS#8 の ECDSA P-256 の鍵で、パスフレーズで暗号化してある（PBES2。反復回数 600,000 の PBKDF2-HMAC-SHA256 と AES-256-CBC を使う）。

- 新しい鍵のパスフレーズは 12 文字以上にする必要がある。
- 秘密鍵を読むプログラム（`elm` と、署名鍵を読む `elm-service`）は、暗号化した P-256 の鍵しか受け付けない。暗号化していない `PRIVATE KEY` や `EC PRIVATE KEY` のブロック、公開鍵、ほかの曲線の鍵は拒否する。パスフレーズが違う場合も拒否する。

```text
-----BEGIN ENCRYPTED PRIVATE KEY-----
…
-----END ENCRYPTED PRIVATE KEY-----
```

### 公開鍵ファイル

同じコマンドは、公開鍵を、P-256 の鍵の `PUBLIC KEY` ブロック（SubjectPublicKeyInfo）を 1 つ持つ PEM ファイルに書く。ルート公開鍵のファイルは、アプリがトラストストアに組み込むものであり、`--trust`、`trust.rootKeys`、`ELM_TRUST_ROOT_KEYS` で指定するものでもある。

- `ElasticLM.Licensing` のトラストストアは、ルート鍵 1 つにつきブロックを 1 つとり、P-256 の公開鍵でないブロックは拒否する。
- `elm`、`elm-server`、`elm-service` に渡す、信頼するルート鍵のファイルには、`PUBLIC KEY` ブロックを複数続けて入れてよい。

```text
-----BEGIN PUBLIC KEY-----
…
-----END PUBLIC KEY-----
```

### 鍵 ID

鍵 ID（`kid`）は、P-256 の公開鍵の JWK サムプリント（RFC 7638）だ。下の UTF-8 のテキストの SHA-256 を、パディングなしの base64url で書いたもので、テキストには鍵の座標を base64url で入れ、空白は入れない。鍵 ID は 43 文字になる。

```text
{"crv":"P-256","kty":"EC","x":"<x>","y":"<y>"}
```

鍵 ID は、トークンのヘッダーではルート鍵や署名鍵を（`kid`）、証明書では証明された鍵を（`sub`）、インストール鍵に紐付いたトークンではそのインストール鍵を（`cnf.jkt`）指す。[`elm key thumbprint`](elm-cli.md#elm-key-thumbprint) は、公開鍵ファイルの鍵 ID を表示する。

### JSON の中の公開鍵

公開鍵を JSON の中に入れて運ぶとき（鍵証明書、プルーフ、オフラインのリクエストの `jwk` と、`GET /v1/server/license` が返す `key`）は、次のメンバーだけを持つ JWK のオブジェクトにする。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `kty` | 文字列 | はい | `EC`。 |
| `crv` | 文字列 | はい | `P-256`。 |
| `x` | 文字列 | はい | x 座標。32 バイトを base64url にした 43 文字。 |
| `y` | 文字列 | はい | y 座標。32 バイトを base64url にした 43 文字。 |

ほかのメンバーを持つ JWK は拒否する。P-256 曲線の上にない点も拒否する。

## JWS の規則

署名付きのトークンは、どれもコンパクト形式の JWS（RFC 7515）だ。`.` で区切った 3 つの部分からなり、それぞれをパディングなしの base64url で書く。1 つ目がヘッダー、2 つ目がペイロード、3 つ目が署名だ。

```text
eyJ….eyJ….eyJ…
```

- 受け付けるのは正規の形の base64url だけだ。パディング（`=`）、空白、ほかの文字は含められない。
- トークンは 16,384 文字までだ。
- 署名は ES256（P-256 と SHA-256 による ECDSA）で、64 バイトの `r || s` の形を base64url にした 86 文字だ。DER 形式の署名は拒否する。low-S の形は求めない。`s` が大きい署名でも、検証に通れば受け付ける。
- 署名は、受け取ったままの `header.payload` の ASCII のバイト列に対して確かめる。署名を確かめる前に、ペイロードを JSON として読むことはない。例外は、署名を確かめる鍵を示すメンバーで、プルーフと[オフラインのリクエスト](#オフラインのリクエスト-elm-actreqjws)の `jwk`、[オフラインのアクティベーション解除のプルーフ](#オフラインのアクティベーション解除のプルーフ-elm-deactjws)の `act` がこれに当たる。先に読むのはそのメンバーだけだ。

### ヘッダー

ヘッダーは JSON のオブジェクトで、メンバーは次の 3 つだけだ。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `alg` | 文字列 | はい | `ES256`。ほかの値を持つトークンは拒否する。コードはトークンの種類で決まる（表の下を参照）。 |
| `kid` | 文字列 | はい | トークンに署名した鍵の鍵 ID。ヘッダーの確認で求めるのは、空でないことだけだ。そのあと、検証側が知っている鍵を指していなければならず、どの鍵も指さない値は後の段階で失敗する。 |
| `typ` | 文字列 | はい | トークンの種類で、下の表のどれか。検証の処理は、それぞれ 1 つの種類しか受け付けない。 |

ほかのメンバー（`jwk`、`x5c`、`crit` など）を持つヘッダー、メンバーが欠けているか 2 回書かれたヘッダー、値が文字列でないヘッダー、`typ` が違うヘッダーは、ライセンストークン、リーストークン、オフラインのリクエスト、オフラインのアクティベーション解除のプルーフでは `ELM_MALFORMED` になる。`alg` がほかの値のときと、ヘッダーがこうした形のときにどうなるかは、[トークンの種類](#トークンの種類)で決まる。ライセンストークンとリーストークンは、`alg` がほかの値なら `ELM_BAD_SIGNATURE` になる。リクエストのプルーフは、`alg` がほかの値のときも、ヘッダーがこうした形のときも、`ELM_PROOF_INVALID` になる。オフラインのリクエストとオフラインのアクティベーション解除のプルーフは、どちらのときも `ELM_MALFORMED` になる。[鍵証明書](#鍵証明書-elm-certjws)は、どちらのときも読み飛ばす。その結果、署名した鍵の鍵証明書が 1 つも残らないトークンは `ELM_UNTRUSTED_KEY` になる。ログの署名（`elm-log+jws`）は、どちらのときも `ELM_` のコードにならず、[`elm log verify`](logs.md#利用ログの検証) がエラーとして報告する。メンバー名は、大文字と小文字の違いも含めて完全に一致するかで比べる。そのため、トークンは自前の鍵を持ち込めず、ある種類のトークンを別の種類と偽って通すこともできない。

プログラムは、JSON の文字列に含まれる一部の文字を `\uXXXX` のエスケープで書く。対象は `+`、`<`、`>`、`&`、`'`、`"`、`` ` `` と、ASCII 以外のすべての文字だ。そのため、このページの例のとおり、証明書のヘッダーは `"typ":"elm-cert\u002Bjws"` となる。JSON のパーサーはエスケープを元の文字として読むので、読む側は、生のテキストではなく、JSON をデコードした値を比べなければならない。

### トークンの種類

| `typ` | 署名する鍵 | 中身 |
| --- | --- | --- |
| `elm-cert+jws` | ルート鍵 | [鍵証明書](#鍵証明書-elm-certjws) |
| `elm-license+jws` | `license` 用に証明された署名鍵 | [ライセンストークン](#ライセンストークン-elm-licensejws) |
| `elm-lease+jws` | `lease` 用に証明された署名鍵、または `elm-server` のインストール鍵 | [リーストークン](#リーストークン-elm-leasejws) |
| `elm-proof+jws` | デバイスのインストール鍵 | [リクエストのプルーフ](#リクエストのプルーフ-elm-proofjws) |
| `elm-actreq+jws` | デバイスのインストール鍵 | [オフラインのアクティベーションまたはトークンの更新のリクエスト](#オフラインのリクエスト-elm-actreqjws) |
| `elm-deact+jws` | デバイスのインストール鍵 | [オフラインのアクティベーション解除のプルーフ](#オフラインのアクティベーション解除のプルーフ-elm-deactjws) |
| `elm-log+jws` | `log` 用に証明された署名鍵、または `elm-server` のインストール鍵 | 利用ログまたは借用の記録の行に対する署名（[ログ](logs.md#署名に関わる行とチェーン)を参照） |

### ペイロード

ペイロードは UTF-8 の JSON のオブジェクトだ。このページのどのペイロードにも、次の規則が当てはまる。

- 時刻は整数で、1970-01-01T00:00:00Z からの秒数だ。範囲は 0 から 253402300799（9999 年の終わり）まで。
- 期間は整数の秒数で、範囲は 0 から 3162240000（366 日の年で 100 年）まで。
- トークンの表にないメンバーは無視する。表のメンバーが 2 回書かれている、必須のメンバーが欠けている、値の型が違う、値が必須のところに `null` がある、のどれかに当たるトークンは無効になる。
- オブジェクトと配列の入れ子は 8 段までだ。

### サイズの上限

| 対象 | 上限 |
| --- | --- |
| トークン 1 つ | 16,384 文字 |
| ライセンスファイル | 65,536 バイト（64 KiB） |
| ライセンスファイルの `certificates` | 1 から 4 個 |
| ライセンストークンの `feat` | 256 個の機能 |
| 機能 ID（`feat` の `id`） | UTF-8 で 64 バイト |
| ライセンストークンの `fp` | 8 個のフィンガープリント |
| ライセンストークンの `meta` | 32 項目。UTF-8 で、各キーは 64 バイトまで、各値は 1,024 バイトまで |
| JSON の入れ子 | 8 段 |

## 鍵証明書: `elm-cert+jws`

鍵証明書は、ルート鍵が署名鍵に対して、特定の種類のトークンへの署名を一定の期間許すことを示す。[`elm key certify`](elm-cli.md#elm-key-certify) は、鍵証明書をファイルに書く。中身は 1 行のトークンと、それに続く改行だ。証明書のファイルを読むプログラムは、トークンの前後の空白を取り除く。ライセンスファイルには、その署名鍵の証明書が入る。`elm-service` は、クラウドのリーストークンと一緒に証明書を送る。

ヘッダー:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `alg` | 文字列 | はい | `ES256`。 |
| `kid` | 文字列 | はい | 証明書に署名したルート鍵の鍵 ID。 |
| `typ` | 文字列 | はい | `elm-cert+jws`。 |

ペイロード:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `ver` | 整数 | はい | `1`。 |
| `iat` | 整数 | はい | 証明書を作った時刻。 |
| `jti` | 文字列 | はい | トークン ID。`elm` は 128 ビットの乱数を base64url にした 22 文字を書く。 |
| `sub` | 文字列 | はい | 証明された鍵の鍵 ID。`jwk` のサムプリントでなければならない。 |
| `jwk` | オブジェクト | はい | 証明された公開鍵。`kty`（`EC`）、`crv`（`P-256`）、`x`、`y` だけを持つ（[JSON の中の公開鍵](#json-の中の公開鍵)を参照）。 |
| `use` | 文字列の配列 | はい | 鍵が署名してよいもの。`license`、`lease`、`log` のうち 1 つ以上。ほかの値は無視する。 |
| `nbf` | 整数 | はい | 有効期間の開始の時刻。 |
| `exp` | 整数 | はい | 有効期間の終了の時刻。`elm key certify` が作る期間は 1 から 731 日で、既定は 365 日だ。 |

トークンがある証明書のもとで受け入れられるのは、トークンの `iat` が証明書の `nbf` と `exp` のあいだにあるときだ。両端は、検証側が許容する時刻のずれの分だけ広げる。現在時刻を `exp` と比べることはない。

検証側が証明書を使うのは、次のすべてを満たすときだけだ。どれかを満たさない証明書は読み飛ばすだけで、エラーにはしない。そのため、新しい証明書の横に古い証明書を残しておいても害はない。

- ヘッダーの `kid` が、トラストストアにある失効していないルート鍵を指し、その鍵の署名が検証に通る。
- ペイロードが表のすべてのメンバーを範囲内で持ち、`ver` が `1` である。
- `sub` が失効した鍵 ID でなく、`jwk` のサムプリントである。
- `use` が、検証側の必要とする用途を含む。ライセンスファイルなら `license`、クラウドのリーストークンなら `lease`、`elm-service` の利用ログなら `log` だ。

`--use license lease` で作った証明書を、デコードして示す。

```json
{"alg":"ES256","kid":"FAKE-ROOT-KEY-ID-000000000000000000000000R1","typ":"elm-cert\u002Bjws"}
```

```json
{
  "ver": 1,
  "iat": 1793540727,
  "jti": "FAKEjti000000000000001",
  "sub": "FAKE-SIGNING-KEY-ID-000000000000000000000S1",
  "jwk": {
    "kty": "EC",
    "crv": "P-256",
    "x": "FAKE-X-COORDINATE-00000000000000000000000X1",
    "y": "FAKE-Y-COORDINATE-00000000000000000000000Y1"
  },
  "use": [
    "license",
    "lease"
  ],
  "nbf": 1793540726,
  "exp": 1825076726
}
```

## ライセンストークン: `elm-license+jws`

ライセンストークンは、ライセンスそのものを表す。製品、種類、機能、有効期限、デバイスへの紐付けを持つ。トークンは[ライセンスファイル](#ライセンスファイル-elmlic)に入れて運ぶ。検証側がトークンを確かめる順序は[ライセンスファイルと検証](../explanation/license-files-and-verification.md#確かめる順序)にある。

ヘッダー:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `alg` | 文字列 | はい | `ES256`。 |
| `kid` | 文字列 | はい | 署名鍵の鍵 ID。同じファイルにある鍵証明書のどれかが、この鍵を `license` 用に証明していなければならない。 |
| `typ` | 文字列 | はい | `elm-license+jws`。 |

ペイロード:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `ver` | 整数 | はい | `1`。 |
| `iss` | 文字列 | はい | 署名鍵の鍵 ID。ヘッダーの `kid` と等しくなければならない。 |
| `iat` | 整数 | はい | トークンを発行した時刻。ファイルにある鍵証明書のどれかの期間に入っていなければならず、現在時刻に許容する時刻のずれを足した時刻より後であってはならない。 |
| `exp` | 整数 | いいえ | トークンの有効期限の時刻。ないときは、トークンは期限切れにならない。 |
| `jti` | 文字列 | はい | トークン ID で、空でない。発行するプログラムは、128 ビットの乱数を base64url にした 22 文字を書く。 |
| `lic` | 文字列 | はい | ライセンス ID で、空でない。`elm-service` はライセンスの `id` を書き、`elm license issue` は `--license-id` を書く。 |
| `prd` | 文字列 | はい | 製品 ID（製品の `code`）で、空でない。アプリが求める製品 ID と等しくなければならない。 |
| `kind` | 文字列 | はい | `standard`、`trial`、`server` のどれか。 |
| `feat` | オブジェクトの配列 | はい | 機能。0 から 256 個で、メンバーは下に示す。 |
| `cnf` | オブジェクト | `server` のトークンでは必須、ほかでは任意 | トークンを紐付けるインストール鍵。メンバーは `jkt` の 1 つだけで、その鍵 ID が入る。`cnf` があると、トークンはその鍵 ID のインストールでしか検証に通らない（`ELM_WRONG_INSTALLATION`）。 |
| `fp` | 文字列の配列 | いいえ | トークンを紐付けるマシンフィンガープリント。0 から 8 個で、`fpm` の示す方法で比べる。`fp` が空のときやないときは、トークンはどのフィンガープリントにも紐付かず、`fpm` は読まない。 |
| `fpm` | 文字列 | `fp` に要素があるとき | `fp` の比べ方。`any`（1 つが一致すればよい）、`all`（すべてが一致しなければならない）、`ignore`（比べない）のどれか。 |
| `grace` | 整数 | いいえ | `exp` を過ぎてもトークンが有効な長さ（期間）で、この間が猶予期間になる。`trial` のトークンでは、`0` か、ないかのどちらかでなければならない。発行するプログラムは `exp` があるときだけ書き、`exp` がなければ効果はない。 |
| `refresh` | 整数 | いいえ | `exp` のどれだけ前からクライアントがオンラインでのトークンの更新を始めるか（期間）。`elm-service` はポリシーの `refreshWindow` を書く。`elm license issue` は `--refresh-days` があるときだけ書く。 |
| `seq` | 整数 | いいえ | アクティベーションのシーケンス番号。アクティベーションの最初のファイルでは `1` で、新しいファイルのたびに 1 ずつ増える。`elm-service` はアクティベーションのすべてのファイルに書く。`elm license issue` は書かず、マシンに紐付けないライセンスのファイルにも入らない。 |
| `areq` | 文字列 | いいえ | このトークンが応えたリクエストの ID で、1 文字から 64 文字。オンラインのアクティベーション、トークンの更新、トライアルでは[リクエストのプルーフ](#リクエストのプルーフ-elm-proofjws)の `jti`、[オフラインのリクエスト](#オフラインのリクエスト-elm-actreqjws)ではその `nonce` だ。`elm-service` は、アクティベーションのすべてのファイルに書く。レスポンスが失われたあとに送り直したリクエストは以前のファイルを受け取るので、そのファイルは以前のリクエストを指す。`elm license issue` と、紐付けのないライセンスのファイルは書かない。 |
| `act` | 文字列 | いいえ | アクティベーション ID。ハイフンを含む 36 文字の UUID だ。`elm-service` は、アクティベーションのすべてのファイルに書く。`elm license issue` と、紐付けのないライセンスのファイルは書かない。 |
| `lease` | 整数 | `server` のトークンでは必須、ほかでは任意 | リースの時間（秒）。期間で、`server` のトークンでは 1 以上。 |
| `borrow` | 整数 | `server` のトークンでは必須、ほかでは任意 | 借用の最長時間（秒）。期間で、`0` なら借用できない。 |
| `overage` | 整数 | `server` のトークンでは必須、ほかでは任意 | `seats` を超えて貸し出せるシートの数（パーセント）。0 から 1,000。 |
| `clone` | 文字列 | `server` のトークンでは必須、ほかでは任意 | コピーされたアプリのインストールが、コピー元と同じリースを更新したときに `elm-server` がすること。`deny` か `flag`（[再試行とクローン](../explanation/floating-licenses.md#再試行とクローン)）。 |
| `brl` | 整数 | `server` のトークンでは必須、ほかでは任意 | 1 つのインストール鍵、または 1 つのマシンフィンガープリントが、30 日間にできる借用の早期返却の回数。0 から 1,000。 |
| `meta` | オブジェクト | いいえ | ベンダーの値。0 から 32 個のメンバーで、それぞれ文字列。UTF-8 で、キーは 64 バイトまで、値は 1,024 バイトまで。検証側は読まない。 |

`feat` の各要素のメンバー:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `id` | 文字列 | はい | 機能 ID。UTF-8 で 1 から 64 バイトで、文字の種類は問わない。 |
| `ver` | 文字列 | いいえ | ライセンスが対象とする機能のバージョン。空白で区切った 1 から 4 個の比較で、すべてを満たさなければならない。比較は、`>=`、`<=`、`>`、`<`、`=` のどれかに、数字だけからなるバージョン `major.minor` または `major.minor.patch` を続けたもので、各部分は 9 桁まで。patch がなければ 0 とみなす。`ver` がなければ、すべてのバージョンが対象になる。 |
| `seats` | 整数 | `server` のトークンでは必須、ほかでは指定できない | 機能の同時使用シート数で、1 以上。`server` のトークンではすべての機能に必須で、ほかの種類では指定できない。 |
| `exp` | 整数 | いいえ | 機能自身の有効期限の時刻。猶予期間は足さない。 |

`cnf` のメンバー:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `jkt` | 文字列 | はい | インストール鍵の鍵 ID。 |

これらの表の規則に反するトークン（`standard` のトークンに `seats` がある、`lease` のない `server` のトークンなど）は、署名を確かめたあとで `ELM_MALFORMED` になる。サーバーライセンスだけに必要なメンバーは、[サーバーライセンス](#サーバーライセンス)にもう一度挙げる。

検証器は `areq` と `act` の形だけを確かめ、これらのないトークンも検証に通る。アクティベーション、トークンの更新、トライアルのリクエストを送ったクライアントは、これらを自分のリクエストと比べ、別のリクエストに応えたファイルを `ELM_REQUEST_MISMATCH` で拒否する（[`POST /v1/activations`](device-protocol.md#post-v1activations) を参照）。

`elm license issue` が書いたトークンを、デコードして示す。

```json
{"alg":"ES256","kid":"FAKE-SIGNING-KEY-ID-000000000000000000000S1","typ":"elm-license\u002Bjws"}
```

```json
{
  "ver": 1,
  "iss": "FAKE-SIGNING-KEY-ID-000000000000000000000S1",
  "iat": 1793540746,
  "exp": 1830211200,
  "jti": "FAKEjti000000000000002",
  "lic": "LIC-0001",
  "prd": "acme-cad",
  "kind": "standard",
  "feat": [
    {
      "id": "pro",
      "ver": "\u003E=2.0 \u003C3.0"
    },
    {
      "id": "export",
      "exp": 1814313600
    }
  ],
  "grace": 604800,
  "meta": {
    "customer": "Contoso"
  }
}
```

このトークンは `--feature "pro;ver=>=2.0 <3.0" --feature "export;exp=2027-06-30" --expires 2027-12-31 --meta customer=Contoso` で発行した。アクティベーションに対して `elm-service` が発行するトークンには、`cnf`、`refresh`、`seq` も入る。デバイスがフィンガープリントを送り、ポリシーの `fingerprintMatching` が `ignore` でなければ、`fp` と `fpm` も入る。[オフラインのレスポンス](#オフラインのレスポンス-elmresp)の例を参照。`elm license issue` は、`--fingerprint` を渡されると、`--fingerprint-matching ignore` であっても必ず `fp` と `fpm` を書く。

## ライセンスファイル: `.elmlic`

ライセンスファイルは、ライセンストークンと、検証側がそれをルート鍵までたどるための鍵証明書を持ち、ほかには何も要らない。UTF-8 の JSON で、65,536 バイトまで、拡張子は `.elmlic` だ。同じ JSON のオブジェクトが、アクティベーションのレスポンスと `GET /v1/server/license` の `license` メンバーになる。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `format` | 文字列 | はい | `elasticlm-license`。 |
| `version` | 整数 | はい | `1`。 |
| `license` | 文字列 | はい | [ライセンストークン](#ライセンストークン-elm-licensejws)。 |
| `certificates` | 文字列の配列 | はい | トークンに署名した鍵の[鍵証明書](#鍵証明書-elm-certjws)で、1 から 4 個。`null` は含められない。 |

- 外側の JSON には署名がない。中のトークンがそれぞれ署名されているので、外側の JSON を書き換えると、ファイルが検証に失敗することはあっても、通るようになることはない。
- 上限より大きいファイル、このオブジェクトでないファイル、`format` か `version` が違うファイルは `ELM_MALFORMED` になる。ほかのメンバーは無視する。
- `elm license issue` と `elm-service` は、ファイルを 1 行で書き、末尾に改行を付けない。

上のトークンを入れたファイル:

```json
{
  "format": "elasticlm-license",
  "version": 1,
  "license": "eyJ…",
  "certificates": [
    "eyJ…"
  ]
}
```

## リーストークン: `elm-lease+jws`

リーストークンは、ある機能のシートを、期限が切れるまで 1 つのインストール鍵に貸し出す。`elm-server` は自分のインストール鍵で署名する。`elm-service` は署名鍵で署名し、その鍵の証明書を一緒に送る。リーストークンを返すルートは[デバイスのプロトコル](device-protocol.md#elm-server-の-post-v1leases)に、クライアントが確かめることは[フローティングライセンス](../explanation/floating-licenses.md#クライアントがリースごとに確かめること)にある。

ヘッダー:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `alg` | 文字列 | はい | `ES256`。 |
| `kid` | 文字列 | はい | 署名した側の鍵 ID。`elm-server` なら、そのインストール鍵の鍵 ID で、サーバーライセンスの `cnf.jkt` でなければならない。`elm-service` なら、その署名鍵の鍵 ID で、リースと一緒に送る証明書のどれかが、この鍵を `lease` 用に証明していなければならない。 |
| `typ` | 文字列 | はい | `elm-lease+jws`。 |

ペイロード:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `ver` | 整数 | はい | `1`。 |
| `iss` | 文字列 | はい | 署名した側の鍵 ID。ヘッダーの `kid` と等しくなければならない。 |
| `iat` | 整数 | はい | トークンを発行した時刻。現在時刻に許容する時刻のずれを足した時刻より後であってはならない。 |
| `exp` | 整数 | はい | リースが終わる時刻。`iat` より後の時刻。 |
| `jti` | 文字列 | はい | トークン ID で、空でない。発行するプログラムは、128 ビットの乱数を base64url にした 22 文字を書く。 |
| `lse` | 文字列 | はい | リース ID。`A`–`Z`、`a`–`z`、`0`–`9`、`-`、`_` からなる 22 文字。リースのルートは、パスでこの ID を指定する。 |
| `prd` | 文字列 | はい | 製品 ID で、空でない。クライアントの製品 ID と等しくなければならない。 |
| `lic` | 文字列 | はい | ライセンス ID で、空でない。`elm-server` なら、そのサーバーライセンスの `lic` で、それと等しくなければならない。`elm-service` なら、ライセンスの `id`。 |
| `feat` | 文字列 | はい | 機能 ID で、空でない。`elm-server` なら、サーバーライセンスの機能でなければならない。 |
| `n` | 整数 | はい | 貸し出すシートの数で、1 以上。`elm-server` なら、サーバーライセンスにあるその機能の `seats` 以下。 |
| `cnf` | オブジェクト | はい | リースを保持するインストール鍵。メンバーは `jkt` の 1 つだけで、その鍵 ID が入る。これはクライアント自身の鍵 ID でなければならない。 |
| `brw` | 真偽値 | はい | 借用なら `true`、更新していくリースなら `false`。 |
| `srv` | 文字列 | はい | 発行したサーバーの鍵 ID。`iss` と等しくなければならない。 |
| `slic` | 文字列 | `elm-server` が発行したとき | リースを発行したときのサーバーライセンスのトークン ID（`jti`）。クライアントは、これが自分の持っているサーバーライセンスであることを求める。違えば `ELM_LEASE_OUT_OF_BOUNDS` でリースを拒否し、サーバーライセンスを取得し直す。`elm-service` は書かない。 |
| `seq` | 整数 | はい | リースのシーケンス番号。検証側は 0 以上を受け付ける。`elm-server` と `elm-service` は最初のトークンに 1 を書き、リースの更新のたびに 1 ずつ増やすので、どちらも 0 は書かない。 |
| `areq` | 文字列 | はい | このトークンが応えた[リクエストのプルーフ](#リクエストのプルーフ-elm-proofjws)の `jti`。1 文字から 64 文字。レスポンスが失われたか拒否されたあとに送り直したリースの更新には、前のトークンがもう一度返るので、そのトークンは前のリクエストを指す。検証側は長さだけを確かめる。リクエストを送ったクライアントはこの値を比べ、別のリクエストを指すトークンを `ELM_REQUEST_MISMATCH` で拒否する。 |

`cnf` のメンバー:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `jkt` | 文字列 | はい | リースを保持するインストール鍵の鍵 ID。 |

`elm-server` からのリースは、さらにそのサーバーライセンスの範囲に収まっていなければならない。`exp` から `iat` を引いた値はサーバーライセンスの `lease` 以下（`brw` が `true` なら `borrow` 以下）で、`exp` はサーバーライセンスの `exp` に `grace` を足した時刻より後であってはならない。これらのどれかに反するリースは `ELM_LEASE_OUT_OF_BOUNDS` になる。

クライアントは、レスポンスのリースを、自分が頼んだ内容とも比べる。リースの取得と借用では、機能、シート数、借用かどうか、借用なら頼んだ期間より長くないこと、そして `areq` を比べる。リースの更新では、保持しているリースのリース ID、機能、シート数と同じであること、借用でないこと、`seq` が保持している値より大きいこと、そして `areq` を比べる。違っているリースは `ELM_REQUEST_MISMATCH` になる。この比較は[フローティングライセンス](../explanation/floating-licenses.md#クライアントがリースごとに確かめること)で説明している。

`elm-server` が `{"feature":"pro","version":"2.1","count":1}` に対して返したリーストークンを、デコードして示す。

```json
{"alg":"ES256","kid":"FAKE-SERVER-KEY-ID-0000000000000000000000V1","typ":"elm-lease\u002Bjws"}
```

```json
{
  "ver": 1,
  "iss": "FAKE-SERVER-KEY-ID-0000000000000000000000V1",
  "iat": 1793541428,
  "exp": 1793542028,
  "jti": "FAKEjti000000000000005",
  "lse": "FAKElease0000000000001",
  "prd": "acme-cad",
  "lic": "01900000-0000-7000-8000-00000000b001",
  "feat": "pro",
  "n": 1,
  "cnf": {
    "jkt": "FAKE-CLIENT-KEY-ID-0000000000000000000000C1"
  },
  "brw": false,
  "srv": "FAKE-SERVER-KEY-ID-0000000000000000000000V1",
  "slic": "FAKEjti000000000000003",
  "seq": 1,
  "areq": "FAKEjti000000000000006"
}
```

このリースを発行したときのサーバーライセンスは、[オフラインのレスポンス](#オフラインのレスポンス-elmresp)の例にあるものだ。`lic` はそのライセンスの ID、`slic` はその `jti` で、`exp` から `iat` を引いた値はその `lease` の 600 秒になる。

## リクエストのプルーフ: `elm-proof+jws`

プルーフは、デバイスが `elm-service` や `elm-server` へのリクエストごとに `ELM-Proof` ヘッダーで送る、寿命の短いトークンで、インストール鍵で署名する。リクエストのメソッド、URL、本文のハッシュと、サーバーから受け取ったノンスを示すので、リクエストを書き換えることも、もう一度送ることもできない。ヘッダーとクレームは[デバイスのプロトコル](device-protocol.md#プルーフ)に、リクエストに署名する理由は[デバイスとプルーフ](../explanation/devices-and-proofs.md#プルーフ)にある。

## オフラインのリクエスト: `elm-actreq+jws`

オフラインのアクティベーションまたはトークンの更新のリクエストは、拡張子が `.elmreq` のファイルで、`elm-actreq+jws` のトークンを 1 つ、改行なしで持つ。デバイスが `elm-service` に接続できないときに書く。アプリは `CreateActivationRequestAsync` か `CreateRefreshRequestAsync` で書き、`elm-server` は [`elm server activate-request`](elm-cli.md#elm-server-activate-request) と [`elm server refresh-request`](elm-cli.md#elm-server-refresh-request) で書く。誰かがこれを [`elm offline process`](elm-cli.md#elm-offline-process) まで運び、このコマンドがこれを [`POST /v1/offline`](device-protocol.md#post-v1offline) か [`POST /v1/admin/offline`](administration-api.md#post-v1adminoffline) に送る。往復がないので、ファイルにはサーバーのノンスがない。代わりに、自分の `nonce` とデバイスの公開鍵を持つ。

ヘッダー:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `alg` | 文字列 | はい | `ES256`。 |
| `kid` | 文字列 | はい | デバイスのインストール鍵の鍵 ID。ペイロードの `jwk` のサムプリントでなければならない。 |
| `typ` | 文字列 | はい | `elm-actreq+jws`。 |

ペイロード:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `ver` | 整数 | はい | `1`。 |
| `op` | 文字列 | はい | `activate` か `refresh`。 |
| `key` | 文字列 | `activate` のとき | ライセンスキー。 |
| `prd` | 文字列 | `activate` のとき | 製品の `code`。`a`–`z`、`0`–`9`、`-` からなる 1 から 64 文字。 |
| `act` | 文字列 | `refresh` のとき | アクティベーション ID で、UUID。 |
| `seq` | 整数 | `refresh` のとき | デバイスが最後に受け取ったライセンストークンの `seq` で、0 以上。ライブラリはどちらの種類にも書き、アクティベーションのリクエストでは `0` を書く。 |
| `retry` | 文字列の配列 | いいえ | レスポンスがなかったリクエストの `jti`。16 個までで、それぞれ 1 から 64 文字。 |
| `fp` | 文字列の配列 | はい | デバイスのマシンフィンガープリント。0 から 8 個で、それぞれ 16 進数の小文字 32 文字。 |
| `jwk` | オブジェクト | はい | インストール鍵の公開鍵。`kty`（`EC`）、`crv`（`P-256`）、`x`、`y` だけを持つ（[JSON の中の公開鍵](#json-の中の公開鍵)を参照）。 |
| `nonce` | 文字列 | はい | デバイスが作った 128 ビットの乱数を base64url にしたもの。`A`–`Z`、`a`–`z`、`0`–`9`、`-`、`_` からなる 22 文字。レスポンスのライセンストークンが、これを `areq` に入れて返す。 |
| `iat` | 整数 | はい | リクエストを作った時刻。サービスは、自分の時計より 5 分を超えて先の時刻に作られたリクエストを、`ELM_MALFORMED` で拒否する。 |
| `exp` | 整数 | はい | リクエストの有効期限の時刻。ちょうど `iat` + 604800（7 日）。これを過ぎると、サービスは `ELM_REQUEST_EXPIRED` を返す。 |

- 署名を確かめる前に読むクレームは `jwk` だけだ。サービスはこれを読み、そのサムプリントが `kid` であることと、点が曲線の上にあることを確かめてから、これで署名を確かめる。ここで失敗したリクエストは `ELM_PROOF_INVALID` になる。ほかのクレームの不備は、どれも `ELM_MALFORMED` になる。
- リクエストにレスポンスが来るまで、デバイスはクレームを保持し、ファイルを求められるたびに同じペイロードを書く。違うのは署名だけだ。新しいリクエスト（`--renew`、ライブラリでは `renew`）は新しい `nonce` を持ち、前のリクエストを置き換える。前のリクエストのファイルは捨てなければならない。

`elm server activate-request` が書いたリクエストを、デコードして示す。

```json
{"alg":"ES256","kid":"FAKE-SERVER-KEY-ID-0000000000000000000000V1","typ":"elm-actreq\u002Bjws"}
```

```json
{
  "ver": 1,
  "op": "activate",
  "key": "ELM-AAAAA-BBBBB-CCCCC-DDDDD",
  "prd": "acme-cad",
  "seq": 0,
  "retry": [],
  "fp": [
    "fa000000000000000000000000000001",
    "fa000000000000000000000000000002"
  ],
  "jwk": {
    "kty": "EC",
    "crv": "P-256",
    "x": "FAKE-X-COORDINATE-00000000000000000000000X2",
    "y": "FAKE-Y-COORDINATE-00000000000000000000000Y2"
  },
  "nonce": "FAKEnonce0000000000001",
  "iat": 1793540797,
  "exp": 1794145597
}
```

## オフラインのレスポンス: `.elmresp`

レスポンスファイルの拡張子は `.elmresp` だ。中身は、オフラインのリクエストに対するサービスの `200` のレスポンスの本文そのままで、[`POST /v1/activations`](device-protocol.md#post-v1activations) のレスポンスと同じ JSON だ。`elm offline process --out` がこれを書き、デバイスが取り込む（`ImportResponseAsync` か [`elm server import`](elm-cli.md#elm-server-import)）。全体には署名がなく、中のライセンストークンに署名がある。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `activationId` | 文字列 | はい | アクティベーション ID で、UUID。 |
| `license` | オブジェクト | はい | [ライセンスファイル](#ライセンスファイル-elmlic)。そのトークンはリクエストのインストール鍵とフィンガープリントに紐付き、その `areq` はリクエストの `nonce`、`act` はアクティベーション ID だ。 |

デバイスがレスポンスを受け入れるのは、レスポンスが 256 KiB 以下で、UUID の形の `activationId` を持つこの JSON であり、そのライセンスファイルがこのインストールで検証に通り、トークンの `act` が `activationId` と同じで、`areq` が待っているリクエストの `nonce` であるときだけだ。それより大きいレスポンスやこの JSON でないレスポンスは `ELM_MALFORMED` になる。検証に通らないライセンスファイルはその検証のエラーになり、`act` が `activationId` と違うトークンと、`areq` が待っているリクエストの `nonce` でないトークンは `ELM_REQUEST_MISMATCH` になる。デバイスが保存するアクティベーション ID は、署名の対象であるトークンの値だ。

上のリクエストに対するレスポンスを、`elm offline process` が保存したとおりに示す。

```json

      "eyJ…"
    ]
  }
}
```



## オフラインのアクティベーション解除のプルーフ: `elm-deact+jws`

オフラインのアクティベーション解除のプルーフは、拡張子が `.elmdeact` のファイルで、`elm-deact+jws` のトークンを 1 つ、改行なしで持つ。アプリは `CreateDeactivationProofAsync` で書き、`elm-server` は [`elm server deactivate-proof`](elm-cli.md#elm-server-deactivate-proof) で書く。これを書くと、デバイスからアクティベーションとそのライセンスファイルが削除される。`elm offline process` がこれをサービスに送ると、サービスはアクティベーションを解放し、本文のない `204` を返す。レスポンスファイルはない。

ヘッダー:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `alg` | 文字列 | はい | `ES256`。 |
| `kid` | 文字列 | はい | アクティベーションを作ったときのインストール鍵の鍵 ID。 |
| `typ` | 文字列 | はい | `elm-deact+jws`。 |

ペイロード:

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `ver` | 整数 | はい | `1`。 |
| `act` | 文字列 | はい | アクティベーション ID で、UUID。 |
| `seq` | 整数 | はい | デバイスが最後に受け取ったライセンストークンの `seq` で、0 以上。 |
| `retry` | 文字列の配列 | いいえ | レスポンスがなかったリクエストの `jti`。16 個までで、それぞれ 1 から 64 文字。 |
| `iat` | 整数 | はい | プルーフを作った時刻。サービスは、自分の時計より 5 分を超えて先の時刻に作られたプルーフを、`ELM_MALFORMED` で拒否する。 |

- プルーフには `jwk`、`jti`、`exp` がない。サービスはまず `act` を読む（UUID でなければ `ELM_MALFORMED`、その ID のアクティベーションがなければ `ELM_ACTIVATION_NOT_FOUND`）。次に、`kid` がアクティベーションを作ったときの鍵の鍵 ID であることと、その鍵で署名が検証に通ることを確かめる（そうでなければ `ELM_PROOF_INVALID`）。ほかのクレームを読むのは、そのあとだ。
- ユーザーがプルーフを提出したと伝えるまで、デバイスはプルーフを保持し、求められるたびに同じファイルを返す。`ForgetDeactivationProofAsync` か [`elm server forget-proof`](elm-cli.md#elm-server-forget-proof) で、プルーフを捨てる。

`elm server deactivate-proof` が上のアクティベーションに対して書いたプルーフを、デコードして示す。

```json
{"alg":"ES256","kid":"FAKE-SERVER-KEY-ID-0000000000000000000000V1","typ":"elm-deact\u002Bjws"}
```

```json
{
  "ver": 1,
  "act": "01900000-0000-7000-8000-00000000a001",
  "seq": 1,
  "retry": [],
  "iat": 1793541450
}
```

## サーバーライセンス

サーバーライセンスは、`kind` が `server` の[ライセンストークン](#ライセンストークン-elm-licensejws)で、[ライセンスファイル](#ライセンスファイル-elmlic)に入っている。これがあると、1 つの `elm-server` がその機能のシートを貸し出せる。`cnf.jkt` がサーバーのインストール鍵を指し、クライアントは、その鍵が署名したリーストークンを、サーバーライセンスが定める範囲の中でだけ受け入れる。クライアントがサーバーを確かめる方法は[フローティングライセンス](../explanation/floating-licenses.md#サーバーライセンス-クライアントがオンプレミスのサーバーを信頼する仕組み)にある。

種類が `server` のトークンは、すべてのライセンストークンが持つメンバーに加えて、次のメンバーを持たなければならない。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `cnf` | オブジェクト | はい | `jkt`: サーバーのインストール鍵の鍵 ID。 |
| `seats` | 整数 | はい（`feat` のすべての要素で） | 機能の同時使用シート数で、1 以上。 |
| `lease` | 整数 | はい | リースの時間（秒）で、1 以上。 |
| `borrow` | 整数 | はい | 借用の最長時間（秒）。`0` なら借用できない。 |
| `overage` | 整数 | はい | `seats` を超えるシート（パーセント）。0 から 1,000。 |
| `clone` | 文字列 | はい | `deny` か `flag`。コピーされたアプリのインストールが、コピー元と同じリースを更新したときに `elm-server` がすること（[再試行とクローン](../explanation/floating-licenses.md#再試行とクローン)）。 |
| `brl` | 整数 | はい | 30 日間に許す借用の早期返却の回数。0 から 1,000。 |

`fp` と `fpm` は任意だ。`elm-server` はファイルを読むたびに自分のマシンと照らし合わせ、クライアントはこれらを確かめない。`elm-service` は、`licenseKind` が `server` のポリシーからサーバーライセンスを書く。`elm license issue --kind server` は、手作業でサーバーライセンスを書く（[elm コマンドリファレンス](elm-cli.md#elm-license-issue)を参照）。

`elm license issue --kind server --feature "pro;seats=5" --borrow-days 1` が書いたサーバーライセンスを、デコードして示す。`--bind-key` にはサーバーの鍵 ID を、`--fingerprint` にはサーバーのフィンガープリントを渡した。

```json
{"alg":"ES256","kid":"FAKE-SIGNING-KEY-ID-000000000000000000000S1","typ":"elm-license\u002Bjws"}
```

```json
{
  "ver": 1,
  "iss": "FAKE-SIGNING-KEY-ID-000000000000000000000S1",
  "iat": 1793540851,
  "exp": 1830211200,
  "jti": "FAKEjti000000000000004",
  "lic": "SRV-0001",
  "prd": "acme-cad",
  "kind": "server",
  "feat": [
    {
      "id": "pro",
      "seats": 5
    }
  ],
  "cnf": {
    "jkt": "FAKE-SERVER-KEY-ID-0000000000000000000000V1"
  },
  "fp": [
    "fa000000000000000000000000000001"
  ],
  "fpm": "any",
  "grace": 604800,
  "lease": 600,
  "borrow": 86400,
  "overage": 0,
  "clone": "deny",
  "brl": 2
}
```

### サーバーライセンスのファイル

`elm-server` は、設定 `license` が指定する `.elmlic` ファイルからサーバーライセンスを読む（[elm-server の設定](server-configuration.md#最上位の設定)を参照）。このファイルを書くのは、[`elm server activate`](elm-cli.md#elm-server-activate)、[`elm server refresh`](elm-cli.md#elm-server-refresh)、[`elm server import`](elm-cli.md#elm-server-import) と、サーバー自身によるオンラインでのトークンの更新だ。どれも、まず隣に一時ファイルを書き、それで元のファイルを置き換える。そのため、読む側が書きかけのファイルを見ることはない。一時ファイルは `<license path>.tmp` で、その名前に先に何かあれば消してから新しいファイルを作り、置き換えに失敗したときも一時ファイルを消す。Linux と macOS では、書いたファイルを読み書きできるのは所有者だけ（モード `0600`）なので、このファイルを書く `elm server` のコマンドは、サーバーのユーザーで実行する。

### `GET /v1/server/license`

`elm-server` は、[`GET /v1/server/license`](device-protocol.md#get-v1serverlicense) でサーバーライセンスのファイルと自分の公開鍵を返す。クライアントは、ライセンスファイルをルート鍵から検証し、`kind` が `server` であることと、鍵のサムプリントが `cnf.jkt` と等しいことを求める。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `license` | オブジェクト | はい | サーバーライセンスのファイル。`.elmlic` ファイルと同じ JSON。 |
| `key` | オブジェクト | はい | サーバーのインストール鍵の公開鍵。JWK で表し（[JSON の中の公開鍵](#json-の中の公開鍵)を参照）、1,024 バイトまで。その鍵 ID がサーバーライセンスの `cnf.jkt` だ。 |

サーバーライセンスの `jti` は、`ELM-Server-License` ヘッダーの値でもある。`elm-server` は、新しいリーストークンごとにこのヘッダーを送る（[デバイスのプロトコル](device-protocol.md#ヘッダー)を参照）。

## クライアントが保存するファイル

`ElasticLM.Client` と `libelasticlm` は、ファイルをインストール鍵のフォルダーに保存する。既定では、ユーザースコープかマシンスコープにある製品ごとのフォルダーだ（[デバイスとプルーフ](../explanation/devices-and-proofs.md#鍵の保存場所)を参照）。アプリが渡したフォルダーを使うこともある。表には、それぞれのファイルが何か、コピーや削除をしてよいかを示す。ファイルの中の形式は公開のインターフェースではなく、変わることがある。`elm-server` のファイルは、[elm-server の設定](server-configuration.md#データフォルダー)に挙げている。

| ファイルまたはフォルダー | 場所 | 中身 | コピーと削除 |
| --- | --- | --- | --- |
| `installation.key` | インストール鍵のフォルダー | デバイスのインストール鍵で、P-256 の秘密鍵。Windows では、ユーザーまたはマシンの DPAPI で保護する。Linux と macOS では、所有者だけが読めるファイルだ（`0600`。フォルダーは `0700`）。 | コピーしない。別のデバイスにあるコピーは同じデバイスとして振る舞い、両方がオンラインになると、サービスは 2 つをクローンとして扱う。アクティベーション、リース、借用、サーバーのピンがこの鍵に依存している間は削除しない。鍵に紐付いたトークンはこのデバイスで検証に通らなくなり、次のアクティベーションで新しい鍵が作られて、アクティベーションを 1 つ余分に使う。読めない鍵が勝手に置き換えられることはない（`ELM_INSTALLATION_KEY_UNREADABLE`）。 |
| `activation.json` と `activation.lock` | インストール鍵のフォルダー | 保存したアクティベーション。その ID、最後の `seq`、種類、受け取ったライセンスファイル、レスポンスがなかったリクエストの `jti`、待機中のオフラインのリクエスト、まだ提出していないアクティベーション解除のプルーフを持つ。`activation.lock` は、アクティベーションのリクエストを一度に 1 つのプロセスだけが送れるようにする。 | コピーしない。鍵と一緒にコピーすれば、それはクローンになる。削除するのは、アクティベーションを解除したあとか、管理者がアクティベーションを解除したときだけにする。最後の `seq` のないアクティベーションのリクエストは、クローンに見えるからだ。壊れたファイルがあると、`Check` は `ELM_MALFORMED` を返す。`activation.lock` には何も入っておらず、必要になればまた作られる。 |
| `borrows/` | インストール鍵のフォルダーの中のフォルダー | 借用したリースごとに 1 つのファイル `<lease ID>.json`。リーストークンと、それを検証するためのもの（`elm-server` ならサーバーライセンスのファイルとサーバーの鍵、`elm-service` なら証明書）を持つ。ファイルは 1,000 個まで、それぞれ 256 KiB まで。クライアントは、借用の期限が切れたファイルを削除する。 | 別のデバイスにコピーしても使えない。リースがこのインストール鍵を指しているからだ。ファイルを削除すると、再起動のあと、このデバイスでは借用が失われる。一方、そのシートは期限が切れるまでサーバー上で使用中のままになる。 |
| `servers/` | インストール鍵のフォルダーの中のフォルダー | `elm-server` の URL ごとに 1 つのファイル。名前は、正規化したサーバー URL の UTF-8 のバイト列の SHA-256 を 16 進数の小文字 64 文字で表し、拡張子 `.json` を付けたものだ。正規化の形は、プルーフが `htu` で署名するものと同じだ（[デバイスのプロトコル](device-protocol.md#htu-に入れる宛先の-url)を参照）。スキームとホストは小文字、既定のポートはなし、パーセントエンコードは大文字、クエリとフラグメントはなし。たとえば `https://Licenses.Example:443/` は `https://licenses.example/` になる。ファイルは、正規化した URL と、その URL でクライアントが最初に受け入れたライセンス ID とサーバーの鍵 ID を持つ。 | 秘密は含まない。ファイルを削除すると、クライアントはその URL で次に見たサーバーライセンスを受け入れる。`ResetServerPin`（C では `elm_client_reset_server_pin`）と同じ動きだ。壊れたファイルがあると、クライアントはそのサーバーを拒否する。 |
| `clock` | インストール鍵のフォルダー。`ActivationClient` と `LicenseClient` は、アプリが独自の時刻巻き戻し対策を渡さない限りここに置く。`libelasticlm` のアクティベーションとクライアントは常にここに置く。`libelasticlm` の検証側も、インストールを渡したときは、`clock_guard_path` が別のファイルを指定しない限りここに置く | 時刻巻き戻し対策の状態。最後に確認した時刻を、インストール鍵で署名したもの。 | 削除や書き換えをすると、検証中のトークンの `iat` までは時計を戻せるようになる。それより前には戻せない。コピーは別のデバイスの鍵では検証に通らず、そこでは無視される。 |
| `FileClockGuard` の状態 | アプリが `FileClockGuard` に渡すパス。C では `clock_guard_path` に渡すパス | 同じ時刻巻き戻し対策の状態。署名するのは、アプリがインストール鍵を渡したときだけだ。渡さなければ、ファイルに書き込める人なら誰でも状態をリセットできる。 | `clock` と同じ。 |
| `InstallationClockGuard` の状態 | アプリが `InstallationKey` の `CreateClockGuard` に渡すパス | 同じ時刻巻き戻し対策の状態で、インストール鍵で署名する。 | `clock` と同じ。 |
