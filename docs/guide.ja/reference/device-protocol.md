# デバイスのプロトコル

このページには、デバイスが使う HTTP のルートをすべて載せる。SaaS 型のアクティベーションサービス（`elm-service`）のルートは、アクティベーション、トークンの更新、アクティベーション解除、トライアル、オフラインのファイル、クラウドのリースのためのもので、オンプレミスのライセンスサーバー（`elm-server`）のルートはリースのためのものだ。ルートごとに、認証、リクエストの本文、レスポンスとそのヘッダー、エラーコードを示す。読者は、独自のクライアントを書く人と、デバッグのために通信を読む人だ。ほとんどのアプリには要らない。`ElasticLM.Client`（`ActivationClient` と `LicenseClient`）と `libelasticlm` が、アプリの代わりにこれらのリクエストを送るからだ。リクエストに署名する理由は[デバイスとプルーフ](../explanation/devices-and-proofs.md)にあるので、先に読んでおくとよい。各ルートが何をするかは、[アクティベーション](../explanation/activation.md)と[フローティングライセンス](../explanation/floating-licenses.md)で説明している。

## すべてのルートに共通する規則

### 通信

- HTTP で JSON をやりとりする。どのパスも `/v1/` で始まる。
- `elm-service` は `listen` の URL で答える。プルーフ（所有証明）は、その `publicUrls` のどれか 1 つを指す。その既定値が `listen` の URL になるのは、それがループバックアドレスのときだけだ（[elm-service の設定](service-configuration.md#最上位の設定)を参照）。
- `elm-server` は、これらのルートに `listen` のポートでだけ、TLS で答える。ローカルの管理 API のソケットのファイル（サーバーのマシンのプログラムどうしが、ポートの代わりに接続に使うファイル）では、同じパスに本文のない `404` を返す（[elm-server の設定](server-configuration.md#ポート)を参照）。プルーフは、その `publicUrls` のどれか 1 つを指す。その既定値は、`listen` から組み立てた URL だ（[elm-server の設定](server-configuration.md#最上位の設定)を参照）。
- リクエストの本文は 64 KiB までだ。それより大きければ `413` と `ELM_PAYLOAD_TOO_LARGE` が返る。どちらのプログラムも `Content-Type` を確かめない。

クライアントは、`elm-server` の TLS 証明書を、次の 2 つのどちらかを根拠に受け入れる。1 つは、OS がその証明書を検証することだ。管理者が用意した証明書は、これで確かめる。もう 1 つは、証明書の公開鍵が P-256 の鍵で、その[サムプリント](formats.md#鍵-id)がサーバーライセンスの `cnf.jkt` と一致することだ。既定の自己署名証明書の鍵はこれに当たる。クライアントは `cnf.jkt` を、`GET /v1/server/license` が返したサーバーライセンスから、そのライセンスを検証したあとで取り出す。最初の接続では、ライブラリは証明書を記録し、サーバーライセンスを取得して検証してから、初めて比べる。一致しなければ、受け取ったレスポンスを捨てて `ELM_SERVER_PIN_MISMATCH` を返す。TLS を傍受するプロキシを受け入れるのは、OS がその証明書を信頼している場合だけだ。`elm-service` は、OS の信頼だけで確かめる。[TLS](../explanation/floating-licenses.md#tls) を参照。

### ヘッダー

| ヘッダー | 付く場所 | プログラム | 値 |
| --- | --- | --- | --- |
| `ELM-Proof` | リクエスト | 両方 | リクエストのプルーフ（後述）。ヘッダーのフィールドは 1 つだけにする。フィールドが 2 つあるリクエストは `ELM_PROOF_INVALID` になる。 |
| `ELM-Nonce` | レスポンス | 両方 | 次のプルーフに使う新しいノンス。`elm-service` は、デバイス向けのルートのすべてのレスポンスに、エラーも含めて付ける。ただし、`POST /v1/offline` のレスポンスと、送信元ごとのレート制限による `429` には付けない。`elm-server` は、`GET /v1/nonce` と 4 つのリースのルートのすべてのレスポンスに、エラーも含めて付ける。ただし、IP のルールによる `403` と、レート制限による `429` には付けない。 |
| `ELM-Server-License` | レスポンス | `elm-server` | サーバーがいまリースの発行に使っているサーバーライセンスファイルのトークン ID（`jti`）。`POST /v1/leases` と `POST /v1/leases/{id}/renew` の成功のレスポンスに付く。ローカルの管理 API が `licenseToken` として示す値と同じだ（[`GET /admin/v1/status`](administration-api.md#get-adminv1status) を参照）。クライアントが持つコピーのトークン ID と違えば、クライアントは `GET /v1/server/license` をもう一度呼ぶ。 |
| `Retry-After` | レスポンス | 両方 | 待つ秒数。`ELM_RATE_LIMITED` のときは常に `1` だ。`ELM_SERVER_RECOVERING` のときは、リースの再登録の期間の残りを切り上げた値だ。 |

### プルーフ

プルーフは、インストール鍵の持ち主が、このサーバーに宛てて、いまこのリクエストを作ったことを示す。形式は 16,384 文字以下のコンパクト形式の JWS で、ES256 で署名する。署名は、64 バイトの `r || s` の形を base64url にしたものだ。

ヘッダーのメンバーは、次の 3 つだけだ。

| 名前 | 値 |
| --- | --- |
| `alg` | `ES256` |
| `kid` | インストール鍵のサムプリント。公開鍵の RFC 7638 の JWK サムプリント（SHA-256、base64url）だ。 |
| `typ` | `elm-proof+jws` |

ペイロードのクレームは次のとおり。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `ver` | 整数 | はい | `1`。 |
| `iat` | 整数 | はい | プルーフを作った時刻。1970 年からの秒数で、0 から 253402300799 まで。新しさの判定には使わない。新しさはノンスで判定する。 |
| `jti` | 文字列 | はい | 1 から 64 文字で、一度だけ使う（[ノンス](#ノンス)を参照）。ライブラリは 128 ビットの乱数を base64url にして送る。 |
| `htm` | 文字列 | はい | リクエストのメソッド。`POST` のように、送ったとおりに書く。 |
| `htu` | 文字列 | はい | リクエストを送る先の URL を正規化したもの（[`htu` に入れる宛先の URL](#htu-に入れる宛先の-url) を参照）。 |
| `nonce` | 文字列 | はい | このサーバーが発行した、期限の切れていないノンス。このクレームのないプルーフは `ELM_PROOF_INVALID` になる。 |
| `bdy` | 文字列 | はい | 本文のバイト列そのものの SHA-256 を base64url にしたもの。本文がなければ、空文字列のハッシュ `47DEQpj8HBSa-_TImW-5JCeuQeRkm5NMpJWZG3hSuFU` になる。 |
| `jwk` | オブジェクト | 一部のルート | 公開鍵。`kty` は `EC`、`crv` は `P-256` で、座標 `x` と `y`（それぞれ 32 バイト、base64url）を持ち、ほかのメンバーは持たない。サーバーがこれを使うときは、そのサムプリントが `kid` と等しく、点が曲線の上になければならない。 |

未知のクレームは、2 回書かれていても無視する。この表のクレームが 2 回書かれていれば、プルーフは無効になる。

署名を確かめる鍵は次のとおり。

| ルート | 鍵 |
| --- | --- |
| `elm-service`: `POST /v1/activations`、`POST /v1/trials`、`POST /v1/leases`。`elm-server`: `POST /v1/leases`、`POST /v1/leases/reclaim`、借用の `DELETE /v1/leases/{id}` | プルーフの中の `jwk`。 |
| `elm-service`: `POST /v1/activations/{id}/refresh`、`POST /v1/activations/{id}/deactivate` | アクティベーションを作ったときの鍵。 |
| 両方: `POST /v1/leases/{id}/renew`、借用でないリースの `DELETE /v1/leases/{id}` | リースを取得または再登録したときの鍵。 |

サーバーは、署名を確かめる鍵を `kid` で探す。探す順は、起動後に検証した鍵（最大 10,000 個）、アクティベーションやリースに紐付いた鍵、プルーフの中の `jwk` だ。

- サーバーがまだ鍵を知らないとき（最初のアクティベーションや再起動のあとなど）に `jwk` がなければ、`401` と `ELM_PROOF_INVALID` になる。表の 1 行目のルートで `jwk` のないプルーフが通るのは、サーバーがまだその鍵を覚えている間だけだ。そのため、これらのルートでは毎回 `jwk` を送る。
- サーバーが鍵を知っているときに `jwk` があれば、知っている鍵で署名を確かめ、`jwk` は使わない。それでも、文字列のメンバー `kty`、`crv`、`x`、`y` だけを持つオブジェクトでなければならない。そうでなければ、プルーフは `ELM_PROOF_INVALID` になる。
- アクティベーションやリースに紐付いた鍵とは別の鍵で署名したプルーフは、`401` と `ELM_PROOF_INVALID` になる。
- `elm-server` は、再起動のあとに借用の記録から復元した借用の鍵を保持しない。そのため、借用の返却には `jwk` を付ける必要がある。

確認は次の順に行う。

| 確認 | 拒否するときのレスポンス |
| --- | --- |
| ヘッダーが 1 つだけあり、上のヘッダーを持つコンパクト形式の JWS で、署名がその鍵で検証に通る | `401` `ELM_PROOF_INVALID` |
| ペイロードが、上の表のすべてのクレームを範囲内で持つ。クレームが欠けていれば、`nonce` であってもここで失敗する | `401` `ELM_PROOF_INVALID` |
| `htm` と `htu` がリクエストと一致する | `401` `ELM_PROOF_INVALID` |
| `bdy` が受け取った本文と一致する | `401` `ELM_PROOF_INVALID` |
| `nonce` がこのサーバーの発行したもので、期限が切れていない。`nonce` が空か未知の値なら、ここで失敗する | `401` `ELM_NONCE_REQUIRED`。`ELM-Nonce` に新しいノンスが入る |
| `elm-server` のみ: `jti` が以前に使われていない | `401` `ELM_REPLAYED` |
| `elm-server` のみ: 使用済みの `jti` を保存する場所に空きがある（100,000 個） | `503` `ELM_SERVER_BUSY` |
| `elm-service` のみ: プルーフが、アクティベーションやリースに紐付いた鍵で署名されている | `401` `ELM_PROOF_INVALID` |
| `elm-service` のみ: 鍵ごとのレート制限（`rateLimit.clientPerKey`） | `429` `ELM_RATE_LIMITED`。`Retry-After: 1` が付く |
| `elm-service` のみ: `jti` が以前に使われていない | `401` `ELM_REPLAYED` |

`elm-server` には、鍵ごとのレート制限がない。プルーフがリースの鍵で署名されているかは、本文を読んだあとに、ルート自身の確認と一緒に確かめる。

最初のリクエストのようにノンスを持たないクライアントは、`GET /v1/nonce` からノンスを得る（[ノンス](#ノンス)を参照）。プルーフの確認で拒否したレスポンスも、[ヘッダー](#ヘッダー)に挙げたほかのレスポンスと同じく、`ELM-Nonce` に新しいノンスを持つ。

`elm-service` は、鍵ごとのレート制限のあと、本文を解析する前に、`jti` をデータベースに記録する。この時点より後で拒否されたリクエストも、その `jti` を使い切る。`elm-server` は `jti` をメモリに記録する。

ライブラリが作るトークンの更新のプルーフを、デコードして示す（署名は省く）。ライブラリは `typ` の `+` を、例のとおりエスケープ `\u002B` で書く。JSON のパーサーはこれを `+` として読む（[トークンとファイルの形式](formats.md#ヘッダー)を参照）。

```json
{"alg":"ES256","kid":"FAKE-THUMBPRINT-0000000000000000000000000A1","typ":"elm-proof\u002Bjws"}
```

```json
{
  "ver": 1,
  "iat": 1793532548,
  "jti": "FAKEjti000000000000001",
  "htm": "POST",
  "htu": "https://licensing.example.com/v1/activations/01900000-0000-7000-8000-00000000a001/refresh",
  "nonce": "AAAAAGrnIoQfakeNonceFakeNonceFakeNonceFakeNonceFakeNonceFakeNonceFakeNonce1",
  "bdy": "tB6VxD84jVYbFGMm2E46a54xxO8yq5fAR3TDGq2jJGo"
}
```

ここで `bdy` は、本文 `{"seq":1}` のハッシュだ。

### `htu` に入れる宛先の URL

クライアントは `htu` に、リクエストを送る絶対 URL を次の形で入れる。

- スキームとホストは小文字にする。
- ポートは、既定（`https` なら 443、`http` なら 80）でないときだけ書く。
- パスは送ったとおりにする。ただし、`.` と `..` のセグメントを解決し、パーセントエンコードされた非予約文字をデコードし、残ったパーセントエンコードは 16 進数の大文字にする。
- クエリとフラグメントは入れない。

ライブラリは、アプリに渡されたサーバーの URL を取り、末尾に `/` がなければ足し、ルートのパスから先頭の `/` を除いたもの（`v1/activations` など）を後ろにつなげる。サーバーの URL にパスがあれば、そのまま残す。

サーバーは、受け付ける値の一覧を自分で作る。`publicUrls` の各エントリーについて、パスの末尾の `/` を取り除き、リクエストが届いたパスを後ろにつなげ、その結果を同じ方法で正規化する。`htu` は、これらの値のどれかと完全に一致しなければならない。`Host` ヘッダーは使わない。そのため、次のようになる。

- `publicUrls` のエントリーの末尾に `/` があってもなくても、同じ値になる。
- `publicUrls` のエントリーでは、ホストの大文字・小文字や、書き出した既定のポートは問題にならない。エントリーを正規化するからだ。`htu` では、これらがすでに正規化した形になっていなければならない。`htu` が `https://Licensing.example.com:443/v1/activations` のプルーフは `ELM_PROOF_INVALID` になる。
- プログラムをパスのプレフィックスの下で提供するリバースプロキシの後ろでは、プレフィックスは `publicUrls` のエントリーにも `htu` にも含まれる。プログラムは `/v1/` で始まるパスでしかルートを提供しないので、プロキシはプレフィックスを除いてリクエストを転送する。
- クライアントが送った宛先の URL にそのままリクエストを転送するプロキシ（クライアントに設定した HTTP プロキシや透過プロキシなど）なら、`htu` は有効なままだ。サーバーの代わりにクライアントが宛先にするデバッグ用のプロキシ（`https://localhost:8888` など）は、URL を変えてしまう。プルーフにはプロキシの URL が入るので、その URL が `publicUrls` になければ `401` と `ELM_PROOF_INVALID` になる。

例を 2 つ挙げる。

| `publicUrls` のエントリー | リクエスト | `htu` |
| --- | --- | --- |
| `https://licensing.example.com` | `POST https://Licensing.Example.com:443/v1/activations` | `https://licensing.example.com/v1/activations` |
| `https://www.example.com/elm/`。`/elm/v1/…` を `/v1/…` として転送するプロキシの後ろ | `POST https://www.example.com/elm/v1/leases/FAKElease0000000000001/renew` | `https://www.example.com/elm/v1/leases/FAKElease0000000000001/renew` |

### ノンス

- クライアントは、`GET /v1/nonce` から、または前のレスポンスの `ELM-Nonce` ヘッダーからノンスを得る。
- ノンスは、中身を解釈しない文字列として扱う。サーバーが作ってから 300 秒間有効だ。有効な間は複数のプルーフで使ってよいが、プルーフごとに別の `jti` が必要だ。
- `elm-server` は、使用済みの `jti` を、そのノンスの期限が切れるまで保持する。`elm-service` は、リクエストから 360 秒間保持する。これは、どのノンスの有効期間よりも長い。
- `elm-service` のすべてのノード、つまり 1 つのデータベースを共有するインスタンス（[`node`](service-configuration.md#node) を参照）は、1 つのノンスの秘密（`nonce.secretFile`。[elm-service の設定](service-configuration.md#nonce)を参照）を共有する。そのため、どのノードも、ほかのノードが作ったノンスを受け付ける。`elm-server` は起動のたびに新しい秘密を作るので、再起動の前のノンスは `ELM_NONCE_REQUIRED` になる。

### シーケンス番号と `retry`

アクティベーションのライセンストークンとすべてのリーストークンは、シーケンス番号 `seq` を持つ。最初のトークンの `seq` は 1 で、新しいトークンのたびに 1 ずつ増える。アクティベーションやリースを指定するリクエストは、クライアントが最後に受け取ったトークンの `seq` を送る。サーバーはそれを、自分が最後に発行したトークンの `seq` と比べる。

| 送った `seq` | 結果 |
| --- | --- |
| 同じ | 次の `seq` を持つ新しいトークン。 |
| 1 つ小さく、`retry` に最後のトークンを受け取ったリクエストの `jti` が入っている | そのリクエストへのレスポンスが失われた。最後のトークンをもう一度返し、何も変えない。 |
| それ以外。`elm-server` での負の `seq` も含む | クローン。インストールの別のコピーが先に進んだ。`cloneStrategy` が `deny`（ポリシーの値。[ポリシーの設定](../explanation/activation.md#ポリシーの設定)を参照。`elm-server` ではサーバーライセンスの値）なら、レスポンスは `409` と `ELM_CLONE_DETECTED` で、アクティベーションやリースは止まる。`flag` なら、クローンを記録してリクエストの処理を続ける。 |

- `elm-service` は 0 以上の `seq` を受け付け、負の値は `ELM_MALFORMED` になる。`elm-server` は、64 ビットに収まる任意の整数を受け付ける。
- `retry` には、レスポンスのなかったクライアントの以前のリクエストの `jti` を並べる。文字列を最大 16 個までで、それぞれ 1 から 64 文字だ。これより長いリスト、ほかの長さの文字列、`null` の要素は `ELM_MALFORMED` になる。どちらのプログラムも同じ制限を使う。
- レスポンスが失われた最初のアクティベーションは、`seq` を `0` にし、最初のリクエストの `jti` を `retry` に入れて送り直す。レスポンスが失われたトライアルは、最初のリクエストの `jti` を `retry` に入れて送り直す。どちらも、発行済みのファイルを受け取る。
- 止まったアクティベーションは、トークンの更新とアクティベーションをすべて `ELM_CLONE_DETECTED` で拒否する。アクティベーション解除ができるのは、最後のトークンの `seq` を付けたときか、管理者が行うときだけだ。止まったリースは、期限が切れるまでリースの更新と返却を拒否する。

その理由は、[シーケンス番号によるクローン検出](../explanation/activation.md#シーケンス番号によるクローン検出)と[再試行とクローン](../explanation/floating-licenses.md#再試行とクローン)で説明している。

### リクエストの本文

- 本文は 1 つの JSON オブジェクトで、入れ子は 8 段までだ。それ以外は `400` と `ELM_MALFORMED` になる。
- 知らない項目は無視する。そのため、ほかのバージョンのクライアントも動き続ける。
- 同じ項目が 2 回あれば `ELM_MALFORMED` になる。`elm-server` では、これはルートが読む項目だけに当てはまり、知らない項目が 2 回あっても無視する。
- 任意の項目の `null` は、送らなかったものとして扱う。必須の項目の `null` は `ELM_MALFORMED` になる。
- 整数の項目には整数を書く。小数を書くと `ELM_MALFORMED` になる。バイト数で表すサイズは、UTF-8 で数える。

### マシンフィンガープリント

マシンフィンガープリントは、小文字の 16 進数 32 文字だ。それ以外の値は `ELM_MALFORMED` になる。`elm-service` では、同じフィンガープリントが 2 回あっても 1 つと数える。サーバーはこの形しか確かめないので、どんな値も受け付ける。1 台のマシンの 1 つの製品で変わらない値であれば、サーバーの目的には足りる。`elm-service` はトライアルをフィンガープリントで数え、両方のプログラムが借用の早期返却をフィンガープリントで数え、`elm-service` はアクティベーションのフィンガープリントをライセンストークンの `fp` に入れる。そのトークンをライブラリで検証するアプリは、`fp` を、ライブラリが計算したフィンガープリントと比べる。そのため、ライブラリによる確認を受けるクライアントは、同じ値を送らなければならない。[マシンフィンガープリント](../explanation/devices-and-proofs.md#マシンフィンガープリント)を参照。

ライブラリは、読み取れた 16 バイトの OS のマシン ID のそれぞれから、フィンガープリントを 1 つ計算する。

1. 製品のコードを UTF-8 にしたものの SHA-256 から、先頭の 16 バイトを取る。
2. その 16 バイトに対して、マシン ID を鍵にした HMAC-SHA256 を計算し、先頭の 16 バイトを残す。
3. バイト 6 を `(byte 6 & 0x0F) | 0x40` に、バイト 8 を `(byte 8 & 0x3F) | 0x80` にする。
4. 16 バイトを小文字の 16 進数で書く。

マシン ID は、Linux では `/etc/machine-id` が 16 進数 32 文字で持つ 16 バイト、Windows ではレジストリの `MachineGuid` と SMBIOS のシステム UUID（そのままの 16 バイト）、macOS では `IOPlatformUUID` だ。`MachineGuid` と `IOPlatformUUID` は UUID の文字列で、書かれている順に 16 バイトとして読む。ID がない、すべて 0、すべて `0xFF` のいずれかであれば、フィンガープリントは作らない。

### エラーのレスポンス

エラーは、メディアタイプが `application/problem+json` の RFC 9457 の problem だ。`title` と `code` の両方にエラーコードが入る。各コードの意味とすべきことは、[エラーコード](error-codes.md)で説明している。次は `elm-service` の例で、サービスが作っていないノンスを持つプルーフへのレスポンスだ。

```json
{
  "type": "about:blank",
  "title": "ELM_NONCE_REQUIRED",
  "status": 401,
  "detail": "The nonce is missing or expired; get a new one.",
  "code": "ELM_NONCE_REQUIRED"
}
```

`500` と `ELM_INTERNAL_ERROR` は内部の障害だ。`elm-service` では、データベースでエラーが起きたか、ライセンスファイルやリースに署名できなかった。`elm-server` では、借用の記録を書き込めなかった。

### レート制限

- `elm-service` は、デバイス向けのすべてのルートを、何よりも先に送信元のアドレスごとに制限する（`rateLimit.clientPerIp`）。また、プルーフ付きのすべてのリクエストを、プルーフの確認のあと、`jti` を記録する前に、インストール鍵ごとに制限する（`rateLimit.clientPerKey`。[プルーフ](#プルーフ)を参照）。オフラインのファイルは、署名と時刻の確認のあとに、署名した鍵の回数として数える。
- `elm-server` は、まず IP のルール（`allow` と `deny`）を当てはめる。拒否したアドレスには `403` と `ELM_FORBIDDEN` を返す。次に、すべてのルートを送信元のアドレスごとに制限する（`rateLimit.perIp`）。
- 制限を超えたリクエストには、`429` と `ELM_RATE_LIMITED` が `Retry-After: 1` 付きで返る。

制限とその既定値は、[elm-service の設定](service-configuration.md#ratelimit)と[elm-server の設定](server-configuration.md#ratelimit)にある。

## `elm-service` のルート

`elm-service` には、デバイス向けのルートが 9 つある。どのルートも、送信元のアドレスについて `429` と `ELM_RATE_LIMITED` を返すことがある。プルーフ付きのルートは、さらに、前述のプルーフの確認とレート制限のコード、規則に反する本文への `400` と `ELM_MALFORMED`、`413` と `ELM_PAYLOAD_TOO_LARGE`、`500` と `ELM_INTERNAL_ERROR` を返すことがある。以下では、ルートごとにそれ以外のコードを、サービスが確かめる順に挙げる。

以下に出てくるポリシーの設定（`binding`、`floating`、`fingerprintMatching`、`cloneStrategy` など）は、[ポリシーの設定](../explanation/activation.md#ポリシーの設定)に一覧がある。ライセンスはライセンスキーで探す。キーの大文字・小文字と `-` は区別しない。ライセンスキーでない値にも、サービスが知らないキーにも、同じレスポンス、つまり `404` と `ELM_LICENSE_NOT_FOUND` を返す。

### `GET /v1/nonce`

- 認証: なし。
- リクエストの本文: なし。
- 成功: `200`。
- レスポンスヘッダー: `ELM-Nonce`。本文と同じノンスが入る。

```json
{
  "nonce": "AAAAAGrnIoQfakeNonceFakeNonceFakeNonceFakeNonceFakeNonceFakeNonceFakeNonce2"
}
```

エラー: `429` `ELM_RATE_LIMITED`。

### `POST /v1/activations`

インストールをライセンスでアクティベーションする。または、同じインストール鍵でもう一度アクティベーションする。[オンラインでのアクティベーション](../explanation/activation.md#オンラインでのアクティベーション)を参照。

- 認証: `jwk` 付きのプルーフ。
- 成功: 新しいアクティベーションなら `201`。同じインストール鍵がすでにこのライセンスのアクティベーションを持っていれば `200` で、次の `seq` を持つ新しいファイルか、再試行なら最後のファイルをもう一度返す。
- レスポンスヘッダー: `ELM-Nonce`。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `licenseKey` | 文字列 | はい | ライセンスキー。 |
| `product` | 文字列 | はい | 製品のコード。`a-z`、`0-9`、`-` からなる 1 から 64 文字。 |
| `fingerprints` | 文字列の配列 | はい | マシンフィンガープリント（[マシンフィンガープリント](#マシンフィンガープリント)を参照）を 0 から 8 個。ポリシーの `fingerprintMatching` が `any` か `all` でなければ、空でもよい。 |
| `seq` | 整数 | いいえ | 0 以上。最初のアクティベーションでは省く。同じインストール鍵が同じライセンスをもう一度アクティベーションするときは、最後のトークンの `seq` を入れる。最初のアクティベーションを送り直すときは `0` を入れる（[シーケンス番号と `retry`](#シーケンス番号と-retry) を参照）。2 回目のアクティベーションで省くと、クローンと数える。 |
| `retry` | 文字列の配列 | いいえ | レスポンスのなかった以前のリクエストの `jti`（[シーケンス番号と `retry`](#シーケンス番号と-retry) を参照）。 |
| `client` | オブジェクト | いいえ | `{"host": <string>, "user": <string>}`。ホスト名と OS のユーザー名だ。どちらの項目も必須で、255 バイト以下の文字列にする。ポリシーの `clientInfoStrategy` が `hostAndUser` のときだけ保存し、それ以外は無視する。 |
| `app` | 文字列 | いいえ | アプリのバージョン。64 バイト以下。 |

レスポンスには、アクティベーション ID とライセンスファイルが入る。ライセンスファイルは `.elmlic` ファイルと同じ JSON だ（[ライセンスファイル](../explanation/license-files-and-verification.md#ライセンスファイル)を参照）。トークンはアクティベーション ID を持たないので、クライアントは ID をファイルと一緒に保存する。ここでは、トークンと証明書を `eyJ…` に縮めている。

```json
{
  "activationId": "01900000-0000-7000-8000-00000000a001",
  "license": {
    "format": "elasticlm-license",
    "version": 1,
    "license": "eyJ…",
    "certificates": ["eyJ…"]
  }
}
```

| 状態 | コード | 条件 |
| --- | --- | --- |
| `404` | `ELM_LICENSE_NOT_FOUND` | キーがライセンスキーでないか、そのキーを持つライセンスがない。 |
| `400` | `ELM_WRONG_PRODUCT` | ライセンスが `product` とは別の製品のものだ。 |
| `409` | `ELM_CONFLICT` | ポリシーの `binding` が `unbound`（ファイルは管理 API から発行する）か、`floating` が `cloud`（シートはリースで貸し出す）だ。 |
| `400` | `ELM_FINGERPRINT_UNAVAILABLE` | ポリシーの `fingerprintMatching` が `ignore` でなく、`fingerprints` が空だ。 |
| `403` | `ELM_LICENSE_REVOKED`、`ELM_LICENSE_SUSPENDED`、`ELM_EXPIRED` | ライセンスが失効しているか、一時停止中か、期限切れだ。 |
| `409` | `ELM_CLONE_DETECTED` | `cloneStrategy` が `deny` のときに、同じインストール鍵が誤った `seq` でもう一度アクティベーションした。または、そのアクティベーションが止まっている。 |
| `409` | `ELM_ACTIVATION_LIMIT` | 新しいアクティベーションで、ライセンスのアクティベーションがすでに `maxActivations` 件ある。 |

### `POST /v1/activations/{id}/refresh`

アクティベーションの新しいライセンスファイルを得る。`{id}` はアクティベーション ID だ。[トークンの更新](../explanation/activation.md#トークンの更新)を参照。

- 認証: アクティベーションのインストール鍵で署名したプルーフ。`jwk` は要らない。
- 成功: `200`。次の `seq` を持つ新しいファイルか、再試行なら最後のファイルをもう一度返す。
- レスポンスヘッダー: `ELM-Nonce`。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `seq` | 整数 | はい | 0 以上。クライアントが最後に受け取ったトークンの `seq`。 |
| `retry` | 文字列の配列 | いいえ | レスポンスのなかった以前のリクエストの `jti`（[シーケンス番号と `retry`](#シーケンス番号と-retry) を参照）。 |

レスポンスの形は、`POST /v1/activations` のレスポンスと同じだ。

```json
{
  "activationId": "01900000-0000-7000-8000-00000000a001",
  "license": {
    "format": "elasticlm-license",
    "version": 1,
    "license": "eyJ…",
    "certificates": ["eyJ…"]
  }
}
```

| 状態 | コード | 条件 |
| --- | --- | --- |
| `404` | `ELM_ACTIVATION_NOT_FOUND` | その ID のアクティベーションがないか、ID が UUID でない。プルーフを確かめる前に返す。リクエストの処理中にアクティベーションが削除されたときも返す。 |
| `401` | `ELM_PROOF_INVALID` | プルーフが、アクティベーションの鍵とは別の鍵で署名されている。 |
| `403` | `ELM_LICENSE_REVOKED`、`ELM_LICENSE_SUSPENDED`、`ELM_EXPIRED` | ライセンスが失効しているか、一時停止中か、期限切れだ。 |
| `409` | `ELM_CLONE_DETECTED` | `cloneStrategy` が `deny` のときに `seq` が誤っている。または、アクティベーションが止まっている。 |

### `POST /v1/activations/{id}/deactivate`

アクティベーションを削除し、その枠を空ける。`{id}` はアクティベーション ID だ。[アクティベーション解除](../explanation/activation.md#アクティベーション解除)を参照。

- 認証: アクティベーションのインストール鍵で署名したプルーフ。`jwk` は要らない。
- 成功: `204`。本文はない。
- レスポンスヘッダー: `ELM-Nonce`。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `seq` | 整数 | はい | 0 以上。クライアントが最後に受け取ったトークンの `seq`。 |
| `retry` | 文字列の配列 | いいえ | レスポンスのなかった以前のリクエストの `jti`。たとえば、レスポンスが失われたトークンの更新のもの（[シーケンス番号と `retry`](#シーケンス番号と-retry) を参照）。 |

ライセンスの状態は確かめない。失効、一時停止、期限切れのライセンスでも、アクティベーション解除ができる。

| 状態 | コード | 条件 |
| --- | --- | --- |
| `404` | `ELM_ACTIVATION_NOT_FOUND` | その ID のアクティベーションがないか、ID が UUID でない。プルーフを確かめる前に返す。レスポンスが失われたあとに送り直したアクティベーション解除は、このコードを受け取る。 |
| `401` | `ELM_PROOF_INVALID` | プルーフが、アクティベーションの鍵とは別の鍵で署名されている。 |
| `409` | `ELM_CLONE_DETECTED` | アクティベーションが止まっていて、`seq` が最後のトークンの `seq` でない。または、`cloneStrategy` が `deny` のときに `seq` が誤っている。 |
| `409` | `ELM_DEACTIVATION_LIMIT` | ライセンスのアクティベーション解除の回数が、ポリシーの `deactivationLimit` に達している。 |

### `POST /v1/trials`

トライアルを始める。サービスは、製品のトライアルのポリシー、つまり製品が `trialPolicyId` で指定する `trial` のポリシーで、製品のすべての機能を持つライセンスを作り、そのインストールでアクティベーションする。[トライアル](../explanation/activation.md#トライアル)を参照。

- 認証: `jwk` 付きのプルーフ。
- 成功: 新しいトライアルなら `201`。再試行なら `200`。再試行とは、同じインストール鍵で、アクティベーションがまだ `seq` 1 のままで、`retry` にそのアクティベーションを得たリクエストの `jti` が入っている場合だ。再試行は、発行済みのファイルを受け取る。
- レスポンスヘッダー: `ELM-Nonce`。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `product` | 文字列 | はい | 製品のコード。`a-z`、`0-9`、`-` からなる 1 から 64 文字。 |
| `fingerprints` | 文字列の配列 | はい | マシンフィンガープリント（[マシンフィンガープリント](#マシンフィンガープリント)を参照）を 0 から 8 個。`POST /v1/activations` と同じだが、空のリストは `ELM_FINGERPRINT_UNAVAILABLE` になる。トライアルには 1 つ以上必要だ。 |
| `retry` | 文字列の配列 | いいえ | レスポンスのなかった以前のトライアルのリクエストの `jti`（[シーケンス番号と `retry`](#シーケンス番号と-retry) を参照）。 |
| `client` | オブジェクト | いいえ | `POST /v1/activations` と同じ。トライアルのポリシーの `clientInfoStrategy` が `hostAndUser` のときだけ保存する。 |
| `app` | 文字列 | いいえ | アプリのバージョン。64 バイト以下。 |

```json
{
  "activationId": "01900000-0000-7000-8000-00000000a002",
  "license": {
    "format": "elasticlm-license",
    "version": 1,
    "license": "eyJ…",
    "certificates": ["eyJ…"]
  }
}
```

| 状態 | コード | 条件 |
| --- | --- | --- |
| `400` | `ELM_FINGERPRINT_UNAVAILABLE` | `fingerprints` が空だ。 |
| `404` | `ELM_TRIAL_NOT_OFFERED` | そのコードの製品がないか、製品にトライアルのポリシーがない。 |
| `409` | `ELM_TRIAL_USED` | フィンガープリントのどれかで、この製品のトライアルがすでに行われている。 |

### `POST /v1/offline`

オフラインのリクエストファイルを受け取り、レスポンスを返す。ファイルは、アクティベーションかトークンの更新のリクエスト（`.elmreq`、種類は `elm-actreq+jws`）か、アクティベーション解除のプルーフ（`.elmdeact`、種類は `elm-deact+jws`）だ。ファイルは誰が送ってもよい。ファイル自身の署名がファイルを認証する。`elm offline process` は、管理者の資格情報を持っていなければ、ファイルをここに送る。[ファイルの受け渡しによるオフラインのアクティベーション](../explanation/activation.md#ファイルの受け渡しによるオフラインのアクティベーション)を参照。

- 認証: なし。ファイルはインストール鍵で署名されている。アクティベーションかトークンの更新のリクエストは、ファイルが持つ `jwk` で署名され、そのサムプリントは `kid` と一致しなければならない。アクティベーション解除のプルーフは、ファイルが指すアクティベーションの鍵で署名される。
- リクエストの本文: ファイルのテキスト（コンパクト形式の JWS）。前後の空白は取り除く。
- 成功: アクティベーションかトークンの更新のリクエストには、`200` と、`POST /v1/activations` と同じレスポンスを返す。新しいアクティベーションのときも同じだ。この本文をそのまま使ったものが、[`elm offline process`](elm-cli.md#elm-offline-process) が `--out` で書き出し、デバイスが取り込むレスポンスファイル（`.elmresp`）になる。アクティベーション解除のプルーフには、本文のない `204` を返す。
- レスポンスヘッダー: プロトコルのヘッダーは付かない。ファイル自身がノンスを持つので、レスポンスに `ELM-Nonce` はない。

ファイルのヘッダーは、`alg`（値は `ES256`）、`kid`（インストール鍵のサムプリント）、`typ` を持つ。リクエスト、レスポンス、アクティベーション解除のプルーフの形式は、例とともに[トークンとファイルの形式](formats.md#オフラインのリクエスト-elm-actreqjws)にある。サービスがアクティベーションかトークンの更新のリクエストから読むクレームは次のとおり。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `ver` | 整数 | はい | `1`。 |
| `op` | 文字列 | はい | `activate` か `refresh`。 |
| `key` | 文字列 | `activate` のとき | ライセンスキー。 |
| `prd` | 文字列 | `activate` のとき | 製品のコード。 |
| `act` | 文字列 | `refresh` のとき | アクティベーション ID（UUID）。 |
| `seq` | 整数 | `refresh` のとき | 0 以上。オンラインのリクエストと同じ。 |
| `retry` | 文字列の配列 | いいえ | オンラインのリクエストと同じ。 |
| `fp` | 文字列の配列 | はい | マシンフィンガープリントを 0 から 8 個。トークンの更新では保存し直さない。 |
| `nonce` | 文字列 | はい | base64url の 22 文字で、デバイスが作る。 |
| `iat` | 整数 | はい | リクエストを作った時刻。1970 年からの秒数。 |
| `exp` | 整数 | はい | ちょうど `iat` + 604800（7 日）。 |
| `jwk` | オブジェクト | はい | インストール鍵の公開鍵。プルーフと同じ形。 |

アクティベーション解除のプルーフのクレームは、`ver`（`1`）、`act`（アクティベーション ID）、`seq`（必須、0 以上）、`retry`（任意）、`iat` だ。未知のクレームは無視する。同じクレームが 2 回あれば `ELM_MALFORMED` になる。ただし、アクティベーションかトークンの更新のリクエストで `jwk` が 2 回あれば、`ELM_PROOF_INVALID` になる。

- 同じリクエストファイルを送り直すと、前と同じレスポンスを受け取る。ただし、ライセンスが失効、一時停止、期限切れのどれでもなく、アクティベーションがまだあって止まっていない場合に限る。同じインストール鍵と `nonce` を持つ別のリクエストファイルは、`409` と `ELM_REPLAYED` になる。
- シーケンス番号の規則で再試行と判定されたアクティベーションのリクエストは、最後のファイルではなく次のファイルを受け取る。最後のファイルには、別のリクエストのノンスが入っているからだ。
- オフラインのアクティベーションは、`client` も `app` も保存しない。

| 状態 | コード | 条件 |
| --- | --- | --- |
| `413` | `ELM_PAYLOAD_TOO_LARGE` | 本文が 64 KiB より大きい。 |
| `400` | `ELM_MALFORMED` | テキストがどちらの種類のコンパクト形式の JWS でもない。クレームが欠けているか範囲外だ。または、`iat` がサービスの時計より 5 分を超えて先だ。 |
| `400` | `ELM_PROOF_INVALID` | アクティベーションかトークンの更新のリクエストが、サムプリントが `kid` と一致する有効な `jwk` を持たない。または、署名がその `jwk` で検証に通らない。 |
| `404` | `ELM_ACTIVATION_NOT_FOUND` | アクティベーション解除のプルーフが指すアクティベーションがない。`act` を読んだ時点で、署名とほかのクレームより先に確かめる。 |
| `400` | `ELM_PROOF_INVALID` | アクティベーション解除のプルーフが、アクティベーションの鍵で署名されていない。 |
| `400` | `ELM_REQUEST_EXPIRED` | アクティベーションかトークンの更新のリクエストが `exp` を過ぎている。 |
| `429` | `ELM_RATE_LIMITED` | このインストール鍵からのリクエストが多すぎる。 |
| `404`、`400`、`409`、`403` | `POST /v1/activations` のコード | アクティベーションのリクエストで、同じ順に確かめる。 |
| `404` | `ELM_ACTIVATION_NOT_FOUND` | トークンの更新のリクエストが指すアクティベーションがない。 |
| `400` | `ELM_PROOF_INVALID` | トークンの更新のリクエストが、アクティベーションの鍵とは別の鍵で署名されている。 |
| `409` | `ELM_REPLAYED` | 別のリクエストファイルが、このリクエストのインストール鍵と `nonce` を使った。アクティベーションのリクエストでは、ライセンス、その製品、そのポリシーのあとに確かめる。トークンの更新のリクエストでは、アクティベーションが見つかった時点で確かめる。どちらでも、ライセンスの状態より先に確かめる。 |
| `403`、`409` | `POST /v1/activations/{id}/refresh` のコード | トークンの更新のリクエストのとき。 |
| `409` | `POST /v1/activations/{id}/deactivate` のコード | アクティベーション解除のプルーフのとき。 |
| `500` | `ELM_INTERNAL_ERROR` | データベースでエラーが起きたか、ライセンスファイルに署名できなかった。 |

### `POST /v1/leases`

ポリシーの `floating` が `cloud` のライセンスで、機能のシートを貸し出す。本文に `borrow` があれば、借用として貸し出す。借用に専用のルートはない。[SaaS 型のサービスも同じプロトコル](../explanation/floating-licenses.md#saas-型のサービスも同じプロトコル)を参照。

- 認証: `jwk` 付きのプルーフ。
- 成功: `201`。
- レスポンスヘッダー: `ELM-Nonce`。`ELM-Server-License` は付かない。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `licenseKey` | 文字列 | はい | ライセンスキー。 |
| `product` | 文字列 | はい | 製品のコード。`a-z`、`0-9`、`-` からなる 1 から 64 文字。 |
| `feature` | 文字列 | はい | 機能のコード。形は製品のコードと同じ。ライセンスが `seats` 付きで付与していなければならない。 |
| `version` | 文字列 | いいえ | アプリが必要とする機能のバージョン。`major.minor[.patch]` の形で、32 文字以下。ライセンスがその機能に定めるバージョンの範囲内でなければならない。 |
| `count` | 整数 | はい | 取るシートの数。1 から機能の `seats` まで（ポリシーの `overage` はこの上限を上げない）。 |
| `borrow` | 整数 | いいえ | リースを、この秒数の借用にする。1 からポリシーの `borrowLimit` まで。0 未満か 3,162,240,000（100 年）を超える値は `ELM_MALFORMED` になる。 |
| `fingerprints` | 文字列の配列 | いいえ | マシンフィンガープリント（[マシンフィンガープリント](#マシンフィンガープリント)を参照）を 0 から 8 個。借用には 1 つ以上必要だ。 |
| `client` | オブジェクト | いいえ | `POST /v1/activations` と同じ。ポリシーの `clientInfoStrategy` が `hostAndUser` のときだけ保存する。 |
| `app` | 文字列 | いいえ | アプリのバージョン。64 バイト以下。 |

リースの期間は、ポリシーの `leaseDuration`、または `borrow` の期間で、ライセンスと機能の有効期限で打ち切る。レスポンスには、リーストークンと、それを確かめるためのサービスの署名鍵の証明書が入る。ここでは、トークンを `eyJ…` に縮めている。リーストークンは、ペイロードが JSON のコンパクト形式の JWS だ。クライアントが必要とするクレームは、`POST /v1/leases/{id}/renew` と `DELETE /v1/leases/{id}` が指定するリース ID の `lse`、次のリースの更新で送るシーケンス番号の `seq`、リースが終わる時刻の `exp` だ。すべてのクレームは[トークンとファイルの形式](formats.md#リーストークン-elm-leasejws)に、クライアントがトークンを確かめる方法は[クライアントがリースごとに確かめること](../explanation/floating-licenses.md#クライアントがリースごとに確かめること)にある。

```json
{
  "lease": "eyJ…",
  "certificates": ["eyJ…"]
}
```

| 状態 | コード | 条件 |
| --- | --- | --- |
| `404` | `ELM_LICENSE_NOT_FOUND` | キーがライセンスキーでないか、そのキーを持つライセンスがない。 |
| `400` | `ELM_WRONG_PRODUCT` | ライセンスが `product` とは別の製品のものだ。 |
| `409` | `ELM_CONFLICT` | ポリシーの `floating` が `cloud` でない。 |
| `403` | `ELM_LICENSE_REVOKED`、`ELM_LICENSE_SUSPENDED`、`ELM_EXPIRED` | ライセンスが失効しているか、一時停止中か、期限切れだ。 |
| `403` | `ELM_FEATURE_NOT_LICENSED` | ライセンスがその機能を付与していないか、`seats` なしで付与している。 |
| `403` | `ELM_FEATURE_EXPIRED` | 機能が、機能自体の有効期限を過ぎている。 |
| `400` | `ELM_INVALID_ARGUMENT` | `version` が `major.minor[.patch]` の形でない。 |
| `403` | `ELM_FEATURE_VERSION_NOT_LICENSED` | `version` がライセンスの範囲外だ。 |
| `400` | `ELM_INVALID_ARGUMENT` | `count` が 1 から機能の `seats` までの範囲外か、`borrow` が 0 だ。 |
| `403` | `ELM_BORROW_NOT_ALLOWED` | `borrow` がポリシーの `borrowLimit` より長いか、ポリシーに借用の上限がない。 |
| `400` | `ELM_FINGERPRINT_UNAVAILABLE` | フィンガープリントのない借用。 |
| `409` | `ELM_NO_SEATS` | 保持されているシートと `count` の合計が、超過分を含めた機能のシート数を超える。止まったリースと借用も数える。 |
| `403` | `ELM_EXPIRED` | ライセンスか機能の有効期限までに、リースの残りが 1 秒未満になる。 |

### `POST /v1/leases/{id}/renew`

新しい有効期限を持つ新しいリーストークンを得る。`{id}` はリース ID で、base64url の 22 文字だ。トークンの `lse` クレームに当たる。

- 認証: リースのインストール鍵で署名したプルーフ。`jwk` は要らない。
- 成功: `200`。次の `seq` を持つ新しいトークンか、再試行なら最後のトークンをもう一度返す。
- レスポンスヘッダー: `ELM-Nonce`。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `seq` | 整数 | はい | 0 以上。クライアントが最後に受け取ったトークンの `seq`。 |
| `retry` | 文字列の配列 | いいえ | レスポンスのなかった以前のリクエストの `jti`（[シーケンス番号と `retry`](#シーケンス番号と-retry) を参照）。 |

新しいトークンの期間は、その時点のポリシーの `leaseDuration` で、取得のときと同じように打ち切る。

```json
{
  "lease": "eyJ…",
  "certificates": ["eyJ…"]
}
```

| 状態 | コード | 条件 |
| --- | --- | --- |
| `404` | `ELM_UNKNOWN_LEASE` | その ID のリースがない、リースの期限が切れている、または ID がリース ID の形でない。プルーフを確かめる前に返す。リクエストの処理中にリースがなくなったときも返す。クライアントは `elm-service` に対してはリースの再登録をしないので、リースは失われる。 |
| `401` | `ELM_PROOF_INVALID` | プルーフが、リースの鍵とは別の鍵で署名されている。 |
| `409` | `ELM_CLONE_DETECTED` | リースが止まっている。 |
| `400` | `ELM_INVALID_ARGUMENT` | リースが借用だ。借用は期間の終わりまで有効で、更新しない。 |
| `409` | `ELM_CONFLICT` | ポリシーの `floating` がもう `cloud` でない。 |
| `403` | `ELM_LICENSE_REVOKED`、`ELM_LICENSE_SUSPENDED`、`ELM_EXPIRED` | ライセンスが失効しているか、一時停止中か、期限切れだ。 |
| `403` | `ELM_FEATURE_NOT_LICENSED`、`ELM_FEATURE_EXPIRED` | ライセンスがその機能を `seats` 付きで付与しなくなったか、機能の期限が切れた。 |
| `409` | `ELM_NO_SEATS` | このリースを含めて保持されているシートが、いまライセンスが許す数を超える。 |
| `409` | `ELM_CLONE_DETECTED` | `cloneStrategy` が `deny` のときに `seq` が誤っている。リースは期限が切れるまで止まる。 |
| `403` | `ELM_EXPIRED` | ライセンスか機能の有効期限までの残りが 1 秒未満になる。 |

### `DELETE /v1/leases/{id}`

リースを返却する。または、借用を早期返却する。`{id}` はリース ID だ。返却は冪等だ。[返却](../explanation/floating-licenses.md#返却)と[早期返却](../explanation/floating-licenses.md#早期返却)を参照。

- 認証: リースのインストール鍵で署名したプルーフ。`jwk` は要らない。
- リクエストの本文: なし。それでも本文を送った場合、本文は読まないが、プルーフの `bdy` はその本文のハッシュでなければならない。
- 成功: `204`。本文はない。その ID のリースがないときや、リースの期限が切れているときも同じだ（プルーフを確かめる前に返す）。
- レスポンスヘッダー: `ELM-Nonce`。

| 状態 | コード | 条件 |
| --- | --- | --- |
| `401` | `ELM_PROOF_INVALID` | プルーフが、リースの鍵とは別の鍵で署名されている。 |
| `409` | `ELM_CLONE_DETECTED` | リースが止まっている。リースは期限が来た時点で終わる。 |
| `409` | `ELM_RETURN_NOT_ALLOWED` | 借用で、このインストール鍵か借用のフィンガープリントのどれかによる過去 30 日間の早期返却が、ポリシーの `borrowReturnLimit` に達している。または、ライセンスの機能のシート数が借用したときより少ないか、`borrowLimit` が借用したときより短い。 |

## `elm-server` のルート

`elm-server` には、クライアント向けのルートが 6 つある。どのルートも、IP のルールで拒否したアドレスへの `403` と `ELM_FORBIDDEN`、および `429` と `ELM_RATE_LIMITED` を返すことがある。プルーフ付きのルートは、さらに、プルーフの確認のコード（`503` と `ELM_SERVER_BUSY` を含む）、規則に反する本文への `400` と `ELM_MALFORMED`、`413` と `ELM_PAYLOAD_TOO_LARGE` を返すことがある。以下では、ルートごとにそれ以外のコードを、サーバーが確かめる順に挙げる。

`elm-server` は、サーバーライセンスの機能を貸し出す。起動のたびに、サーバーライセンスのリースの期間と同じ長さのリースの再登録の期間を設け、その間は新しいリースを拒否する。この間に、クライアントはまだ保持しているリースを再登録する。すべての機能のシートがふたたび埋まれば、期間は早めに終わる。[再起動とリースの再登録](../explanation/floating-licenses.md#再起動とリースの再登録)を参照。

### `elm-server` の `GET /v1/nonce`

- 認証: なし。
- リクエストの本文: なし。
- 成功: `200`。
- レスポンスヘッダー: `ELM-Nonce`。本文と同じノンスが入る。

```json
{
  "nonce": "AAAAAGrnIoYfakeNonceFakeNonceFakeNonceFakeNonceFakeNonceFakeNonceFakeNonce3"
}
```

エラー: IP のルールとレート制限によるものだけ。

### `GET /v1/server/license`

サーバーライセンスファイルとサーバーの公開鍵を返す。クライアントはこれらで、サーバーとそのリーストークンを確かめる。[サーバーライセンス](../explanation/floating-licenses.md#サーバーライセンス-クライアントがオンプレミスのサーバーを信頼する仕組み)を参照。

- 認証: なし。
- リクエストの本文: なし。
- 成功: `200`。
- レスポンスヘッダー: プロトコルのヘッダーは付かない。

`license` はサーバーライセンスファイルで、`.elmlic` ファイルと同じ JSON だ（[トークンとファイルの形式](formats.md#サーバーライセンス)を参照）。`key` はサーバーのインストール鍵の公開鍵で、`kty`、`crv`、`x`、`y` を持つ JWK だ。そのサムプリントは、サーバーライセンスの `cnf.jkt` と同じ値になる。ここでは、トークンと証明書を `eyJ…` に縮めている。

```json
{
  "license": {
    "format": "elasticlm-license",
    "version": 1,
    "license": "eyJ…",
    "certificates": ["eyJ…"]
  },
  "key": {
    "kty": "EC",
    "crv": "P-256",
    "x": "FAKE-X-COORDINATE-00000000000000000000000X1",
    "y": "FAKE-Y-COORDINATE-00000000000000000000000Y1"
  }
}
```

エラー: IP のルールとレート制限によるものだけ。

### `elm-server` の `POST /v1/leases`

サーバーライセンスの機能のシートを貸し出す。本文に `borrow` があれば、借用として貸し出す。借用に専用のルートはない。[取得](../explanation/floating-licenses.md#取得)と[借用](../explanation/floating-licenses.md#借用)を参照。

- 認証: `jwk` 付きのプルーフ。
- 成功: `201`。
- レスポンスヘッダー: `ELM-Nonce` と `ELM-Server-License`。リースの再登録の期間中に拒否したレスポンスには、`Retry-After` も付く。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `feature` | 文字列 | はい | 機能のコード。UTF-8 で 1 から 64 バイト。この範囲を外れると `400` の `ELM_MALFORMED` になる。サーバーライセンスが付与していなければならない。 |
| `version` | 文字列 | いいえ | アプリが必要とする機能のバージョン。`major.minor[.patch]` の形で、32 文字以下。サーバーライセンスがその機能に定めるバージョンの範囲内でなければならない。 |
| `count` | 整数 | はい | 取るシートの数。1 から、サーバーライセンスにあるその機能のシート数まで。32 ビットに収まらない数は `ELM_MALFORMED` になる。 |
| `borrow` | 整数 | いいえ | リースを、この秒数の借用にする。1 からサーバーライセンスの借用の上限まで。`borrow.maxDuration` のほうが短ければ、そこまで。0 未満か 3,162,240,000（100 年）を超える値は `ELM_MALFORMED` になる。 |
| `fingerprints` | 文字列の配列 | いいえ | マシンフィンガープリント（[マシンフィンガープリント](#マシンフィンガープリント)を参照）を 0 から 8 個。借用には 1 つ以上必要だ。 |
| `client` | オブジェクト | いいえ | `{"host": <string>, "user": <string>}`。どちらも任意で、255 バイト以下。`allow` と `deny` の `host:` と `user:` のエントリーと照らし合わせる（[アクセスルール](server-configuration.md#アクセスルール)を参照）。 |
| `app` | 文字列 | いいえ | アプリのバージョン。64 バイト以下。利用ログに書き込む。 |

`elm-server` は `licenseKey` も `product` も読まない。リースの期間は、サーバーライセンスのリースの期間、または `borrow` の期間で、遅くともサーバーライセンスの有効期限に猶予期間を足した時点で終わる。レスポンスには、サーバーがインストール鍵で署名したリーストークンと、空の `certificates` が入る。ここでは、トークンを `eyJ…` に縮めている。クライアントは、`GET /v1/server/license` から得た鍵でトークンを確かめる。`elm-service` と同じく、クライアントが必要とするクレームは、`POST /v1/leases/{id}/renew` と `DELETE /v1/leases/{id}` が指定するリース ID の `lse`、次のリースの更新で送るシーケンス番号の `seq`、リースが終わる時刻の `exp` だ。すべてのクレームは[トークンとファイルの形式](formats.md#リーストークン-elm-leasejws)にある。

```json
{
  "lease": "eyJ…",
  "certificates": []
}
```

`ELM-Server-License` の例: `ELM-Server-License: FAKElicenseJti00000001`。

| 状態 | コード | 条件 |
| --- | --- | --- |
| `403` | `ELM_FORBIDDEN` | `allow` と `deny` のエントリーが、`client` のホスト名かユーザー名を拒否している。 |
| `403` | `ELM_EXPIRED` | サーバーライセンスの有効期限に猶予期間を足した時点を過ぎている。 |
| `403` | `ELM_FEATURE_NOT_LICENSED` | サーバーライセンスがその機能を付与していない。 |
| `403` | `ELM_FEATURE_EXPIRED` | 機能が、機能自体の有効期限を過ぎている。 |
| `400` | `ELM_INVALID_ARGUMENT` | `version` が `major.minor[.patch]` の形でない。 |
| `403` | `ELM_FEATURE_VERSION_NOT_LICENSED` | `version` がサーバーライセンスの範囲外だ。 |
| `400` | `ELM_INVALID_ARGUMENT` | `count` が 1 から機能のシート数までの範囲外か、`borrow` が 0 だ。 |
| `403` | `ELM_BORROW_NOT_ALLOWED` | `borrow` が許される長さを超えているか、借用が許されていない。 |
| `400` | `ELM_FINGERPRINT_UNAVAILABLE` | フィンガープリントのない借用。 |
| `503` | `ELM_SERVER_RECOVERING` | 起動のあとのリースの再登録の期間が終わっていない。`Retry-After` がその残りを示す。 |
| `409` | `ELM_NO_SEATS` | 保持されているシートと `count` の合計が、超過分を含めた機能のシート数を超える。借用では、そこから `borrow.reserve` で残しておくシートを引いた数を超える。 |
| `403` | `ELM_EXPIRED` | サーバーライセンスの有効期限に猶予期間を足した時点までに、リースの残りが 1 秒未満になる。 |
| `500` | `ELM_INTERNAL_ERROR` | 借用で、借用の記録を書き込めない。 |

リースの再登録の期間中のリクエストへのレスポンスを、`elm-server` が `Retry-After: 15` を付けて送ったとおりに示す。

```json
{
  "type": "about:blank",
  "title": "ELM_SERVER_RECOVERING",
  "status": 503,
  "detail": "The server is reclaiming leases after a restart.",
  "code": "ELM_SERVER_RECOVERING"
}
```

### `POST /v1/leases/reclaim`

クライアントがまだ保持しているリースを再起動したサーバーに渡し、そのシートをサーバーにもう一度数えさせる。クライアントは、リースの更新が `ELM_UNKNOWN_LEASE` を受け取ったときにこれを送る。リースの再登録の期間中も、その後も受け付ける。

- 認証: `jwk` 付きのプルーフ。どのトークンも、その鍵に紐付いていなければならない。
- 成功: `200`。トークンごとに 1 つの結果を、トークンの順に返す。
- レスポンスヘッダー: `ELM-Nonce`。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `leases` | 文字列の配列 | はい | このサーバーが発行したリーストークンを 0 から 64 個。`null` は含めない。 |

各トークンは、クライアントがリースを確かめるのと同じ方法で確かめる。ただし、このサーバーの以前のサーバーライセンスファイルの下で発行されたものでもよい。その場合も、現在のサーバーライセンスのライセンス ID を持ち、そのライセンスの範囲内でなければならない。トークンを受け入れるのは、超過分を含めた空きシートに収まるときだけだ。サーバーがすでに保持しているリースのトークンは、`seq` が同じときだけ同じクライアントと見なす。ほかの `seq` はクローンと数える。再登録したリースは、トークンの `seq` と有効期限を引き継ぎ、クライアントはその `seq` でリースを更新する。

`lease` はリース ID で、トークンを確かめられなかったときは省く。次のレスポンスは、有効なトークン 1 つと、文字列 `not-a-token` に対するものだ。

```json
{
  "results": [
    { "lease": "FAKElease0000000000002", "code": "ELM_OK" },
    { "code": "ELM_MALFORMED" }
  ]
}
```

結果のコードは次のとおり。

| コード | 条件 |
| --- | --- |
| `ELM_OK` | リースをふたたび保持した。または、同じ `seq` ですでに保持していた。または、サーバーライセンスの `clone` が `flag` で、クローンを記録した。 |
| `ELM_MALFORMED` | トークンを読めない。 |
| `ELM_BAD_SIGNATURE` | トークンがこのサーバーの鍵で署名されていない。 |
| `ELM_LEASE_OUT_OF_BOUNDS` | トークンが現在のサーバーライセンスの範囲内にない。ライセンス ID が違う、ライセンスにない機能やシート数を持つ、期間が長すぎる、サーバーライセンスの有効期限と猶予期間を過ぎても続く、のいずれかだ。 |
| `ELM_WRONG_PRODUCT` | 別の製品のトークンだ。 |
| `ELM_WRONG_INSTALLATION` | トークンが、プルーフとは別のインストール鍵に紐付いている。 |
| `ELM_CLOCK_TAMPERED` | トークンの発行時刻が、サーバーの時計より 5 分を超えて先だ。 |
| `ELM_EXPIRED` | トークンの期限が切れている。 |
| `ELM_BORROW_NOT_ALLOWED` | トークンが借用だ。借用は借用の記録から復元する。 |
| `ELM_NO_SEATS` | 空きシートがない。 |
| `ELM_CLONE_DETECTED` | リースが止まっている。または、サーバーライセンスの `clone` が `deny` で、サーバーが別の `seq` でそのリースを保持している。リースは期限が切れるまで止まる。 |

リクエスト自体のエラー: 共通のものだけ（トークンが 64 個を超える本文や、`null` のトークンを含む本文は、`400` と `ELM_MALFORMED` になる）。

### `elm-server` の `POST /v1/leases/{id}/renew`

新しい有効期限を持つ新しいリーストークンを得る。`{id}` はリース ID で、トークンの `lse` クレームに当たる。

- 認証: リースのインストール鍵で署名したプルーフ。`jwk` は要らない。
- 成功: `200`。次の `seq` を持つ新しいトークンか、再試行なら最後のトークンをもう一度返す。
- レスポンスヘッダー: `ELM-Nonce` と `ELM-Server-License`。

| 名前 | 型 | 必須 | 範囲と意味 |
| --- | --- | --- | --- |
| `seq` | 整数 | はい | クライアントが最後に受け取ったトークンの `seq`。64 ビットに収まる任意の整数。負の値も受け付け、クローンと判定する（[シーケンス番号と `retry`](#シーケンス番号と-retry) を参照）。 |
| `retry` | 文字列の配列 | いいえ | レスポンスのなかった以前のリクエストの `jti`（[シーケンス番号と `retry`](#シーケンス番号と-retry) を参照）。 |

新しいトークンの期間はサーバーライセンスのリースの期間で、取得のときと同じように打ち切る。

```json
{
  "lease": "eyJ…",
  "certificates": []
}
```

| 状態 | コード | 条件 |
| --- | --- | --- |
| `404` | `ELM_UNKNOWN_LEASE` | サーバーがそのリースを知らない。サーバーが再起動したか、リースの期限が切れたか、返却された。サーバーにその ID の記録がないときは、プルーフを確かめる前に返す。クライアントはリースを再登録する。 |
| `401` | `ELM_PROOF_INVALID` | プルーフが、リースの鍵とは別の鍵で署名されている。 |
| `409` | `ELM_CLONE_DETECTED` | リースが止まっている。 |
| `400` | `ELM_INVALID_ARGUMENT` | リースが借用だ。借用は期間の終わりまで有効で、更新しない。 |
| `403` | `ELM_EXPIRED` | サーバーライセンスの有効期限に猶予期間を足した時点を過ぎている。 |
| `403` | `ELM_FEATURE_NOT_LICENSED`、`ELM_FEATURE_EXPIRED` | サーバーライセンスがその機能を付与しなくなったか、機能の期限が切れた。 |
| `409` | `ELM_NO_SEATS` | サーバーライセンスが許すシート数が、保持されている数より少なくなった。 |
| `409` | `ELM_CLONE_DETECTED` | サーバーライセンスの `clone` が `deny` のときに `seq` が誤っている。リースは期限が切れるまで止まる。 |
| `403` | `ELM_EXPIRED` | サーバーライセンスの有効期限に猶予期間を足した時点までの残りが 1 秒未満になる。 |

### `elm-server` の `DELETE /v1/leases/{id}`

リースを返却する。または、借用を早期返却する。`{id}` はリース ID だ。返却は冪等だ。[返却](../explanation/floating-licenses.md#返却)と[早期返却](../explanation/floating-licenses.md#早期返却)を参照。

- 認証: リースのインストール鍵で署名したプルーフ。リースなら `jwk` は要らない。借用なら `jwk` を送る。サーバーが鍵なしで借用の記録から借用を復元した可能性があるからだ。
- リクエストの本文: なし。それでも本文を送った場合、本文は読まないが、プルーフの `bdy` はその本文のハッシュでなければならない。
- 成功: `204`。本文はない。サーバーがそのリースを知らないときも同じだ（その ID の記録がないときは、プルーフを確かめる前に返す）。
- レスポンスヘッダー: `ELM-Nonce`。

| 状態 | コード | 条件 |
| --- | --- | --- |
| `401` | `ELM_PROOF_INVALID` | プルーフが、リースの鍵とは別の鍵で署名されている。 |
| `409` | `ELM_CLONE_DETECTED` | リースが止まっている。リースは期限が来た時点で終わる。 |
| `409` | `ELM_RETURN_NOT_ALLOWED` | 借用で、このインストール鍵か借用のフィンガープリントのどれかによる過去 30 日間の早期返却が、サーバーライセンスの上限に達している。サーバーライセンスが借用したときと別のものになったか、機能のシート数が借用したときより少ないか、借用の上限が借用したときより短い。または、返却を借用の記録に書き込めない。 |
