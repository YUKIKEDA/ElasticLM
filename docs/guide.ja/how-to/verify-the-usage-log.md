# 利用ログを検証する

このガイドは、`elm-server` の利用ログが欠けておらず、変えられていないことを確かめる顧客の管理者や監査人に向けている。ログをベンダーに渡す前、監査のとき、サーバーに疑わしい点があったときに使う。サーバーは、リース、借用、返却、管理者の操作をすべて、1 分ごとに数えた拒否の数とともにログに書き込み、自分のインストール鍵で署名する。ログのファイルは[ログ](../reference/logs.md#利用ログ)で説明している。このガイドは、[ライセンスサーバーを動かして .NET のアプリでフローティングライセンスのリースを受ける](../tutorials/use-a-floating-license.md)を終えた状態から始める。そのチュートリアルの `elm-server` が、ログを書き込んでいる。

<!-- steps:after page=docs/guide/tutorials/use-a-floating-license.md -->

## 始める前に

コマンドは、チュートリアルのフォルダーで、その `tools` フォルダーを `PATH` に足した状態で打つ。下の手順では、ログが入っているサーバーのデータフォルダー `server-data` と、ルート公開鍵 `root.pub.pem` を使う。ルート公開鍵は、ログの最初にあるサーバーライセンスを検証するのに使う。

ログを検証するだけなら、サーバーが動いている必要はない。`elm log verify` はファイルを読むだけだ。下のように先に最新の行に署名させるには、サーバーが動いていなければならない。止まっていたら、[サーバーを起動する](../tutorials/use-a-floating-license.md#サーバーを起動する)のとおりに、2 つ目のターミナルでもう一度起動する。

例では、チュートリアルの値を使う。製品 `acme-cad` とデータフォルダー `server-data` だ。自分の値に置き換える。設定の `log.usage` でほかの場所を指定していない限り、ログはデータフォルダーにある。

## 最新の行に署名する

サーバーは、ログにブロックごとに署名する。100 行ごと、60 秒ごと、そして止まるときだ。サーバーに、まだ署名していない行へ署名させる。

<!-- steps:run -->
```shell
elm server seal --data server-data
```

`elm` は何も表示せず、終了コード 0 で終わる。サーバーは同じファイルに書き込み続ける。今の 1 分の拒否の数は、この手順ではなく、その 1 分が終わったときに書き込まれる。この手順を省くと、最新のファイルの最後の行にまだ署名がないことがあり、下の検証ではその行が警告として出る。

## ログを検証する

データフォルダーにある利用ログを検証する。`--product` にはサーバーライセンスの製品を指定し、`--trust` には、ベンダーのサーバーライセンスを確かめるルート公開鍵を指定する。

<!-- steps:run -->
```shell
elm log verify server-data --product acme-cad --trust root.pub.pem
```

`elm` は、古いファイルから順に各ファイルを確かめ、各ファイルから次のファイルへのチェーンも確かめて、次のように表示する。

```text
intact: 1 file(s), 9 event line(s)
```

数は手元のログのものになる。サーバーは、起動するたびと、UTC で日が変わるたびに新しいファイルを始める。終了コード 0 は、ログが欠けておらず変えられていないことを示す。出力に `warning:` の行があっても同じだ。スクリプトのために結果を JSON で受け取るには、次のようにする。

<!-- steps:run -->
```shell
elm log verify server-data --product acme-cad --trust root.pub.pem --json
```

<!-- steps:expect -->
```text
  "intact": true,
```

JSON には、ファイルの数とイベントの行の数を示す `files` と `entries`、問題の一覧 `issues` もある。`issues` の各問題には、`file`、`line`、`severity`、`message` がある。

サーバーは、借用の記録も同じフォルダーに置き、同じ方法で署名している。これは `--stream borrows` で検証する。

<!-- steps:run -->
```shell
elm log verify server-data --product acme-cad --trust root.pub.pem --stream borrows
```

同じ形で `intact:` を表示する。

## 検証の失敗を読む

検証が失敗すると、`elm` は問題ごとに、見つけたファイルと行を添えて 1 行ずつ表示し、そのあと `NOT INTACT:` を表示して、終了コード 1 で終わる。たとえば、署名の前の行を書き換えたあとでは次のようになる。

```text
error: usage-20260115T093000000Z.jsonl:2: The lines before the signature were changed, added, or removed.
NOT INTACT: 1 file(s), 0 event line(s)
```

ほかのエラーには、たとえば、2 つのファイルのあいだのファイルの欠落、別のサーバーの鍵が署名したファイル、検証に通らないサーバーライセンスがある。ファイルの欠落は `The file follows '<name>', not '<previous file>': a file is missing.` と表示する。`<name>` は、そのファイルの最初の行が前のファイルとして名指すファイル（名指していなければ `nothing`）で、`<previous file>` は、その前に渡したファイルだ。名前は合っていても、前のファイルがその名前の別のファイルに置き換えられていれば、`The file follows another file named '<previous file>': that file was replaced or cut.` と表示する。警告では検証は失敗しないが、何を調べればよいかがわかる。最後の署名のあとの行（クラッシュや書き換えで残ることがある）と、`chain.reset` で始め直したチェーン（その理由が付く）だ。すべてのエラーと警告は[利用ログの検証](../reference/logs.md#利用ログの検証)に挙げている。終了コード 2 は、コマンドを実行できなかったことを示す。たとえば、パスがファイルでもフォルダーでもないときだ。

## 書き終えたファイルのコピーを取っておく

最新のファイルが削除されたことや、最後の署名のあとで切り詰められたことは、検証では見つけられない。比べる次のファイルがないからだ。最も古いファイルが削除されたことも見つけられない。検証は、渡された最初のファイルをチェーンの始まりとみなすからだ。最新のファイルより前のファイルは書き終えたもので、次のファイルの最初の行にその最後の署名のハッシュが入っているので、書き換えれば検証でわかる。書き終えたファイルを定期的に、サーバーのマシンから変えられない場所（ファイルを上書きできない共有フォルダーなど）にコピーするか、監査する人に渡す。コピーした先で検証し、あとでサーバーのファイルと比べれば、そのあとで削除されたり変えられたりしたファイルがわかる。最も古いファイルについても同じだ。

これでは、サーバーの root 権限を持つ管理者は防げない。管理者はサーバーの鍵を使って、コピーされる前にログを書き直せる。このことは[セキュリティモデル](../explanation/security-model.md#顧客のライセンスサーバー上)に挙げている。サーバーは、ログのファイルを自分では削除しない。必要なコピーを取ったら、古いファイルを削除する。
