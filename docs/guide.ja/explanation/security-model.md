# 安全性のモデル

このページは、ElasticLM が自分の守りたいものを守るか、自分で何をしなければならないかを判断する必要がある、すべての人に向けたものだ。鍵を持ち `elm-service` を動かすベンダー、クライアントを組み込むアプリの開発者、`elm-server` を動かす顧客の管理者が対象になる。最初に、何を誰から守るかを短く述べ、続いて役割ごとの節を置く。そのあとに、ダウンロードしたものの確かめ方、ElasticLM が守らないものすべて、各役割がすべきことを書く。先に[概要](overview.md)と[信頼の鎖](trust-chain.md)を読んでおくとよい。仕組みの詳細は、ほかの解説のページにある。

## 何を誰から守るか

ライセンスの仕組みを攻撃するのは、主にその仕組みを使う側の人だ。顧客はアプリと本物のライセンスを持ち、自分のマシンを思いどおりに操作できる。その中には、払った分より多くを使いたい人もいる。ElasticLM は、秘密ではなく署名で、次の 3 つを止める。

- 偽造したライセンスや書き換えたライセンス
- 偽造した要求や再送した要求
- 買った数を超える同時利用数

アプリ自体のコードを誰かが書き換えることは、止めようとしない。攻撃者が操作するマシンで動くものは、何であれその攻撃者が書き換えられる。守りは、攻撃者が署名できないものの中にある。

守る価値のあるものは次のとおりだ。

| 守るもの | 攻撃者が手に入れると |
| --- | --- |
| ベンダーのルート鍵と署名鍵 | アプリが受け入れる任意のライセンスやリースを作れる。 |
| ライセンスキー | それで有効化できる。 |
| 端末のインストール鍵 | その端末になりすませる。 |
| `elm-service` の管理者の権限 | ライセンスを発行し、解除し、失効させられる。 |
| 利用ログと監査ログ | 課金や紛争の証拠が失われる。 |
| ElasticLM のリリースのファイルとこのサイト | 偽の `elm-server` やライブラリは、すべての確かめを飛ばせる。偽の `elm` や `elm-service` は、ベンダーの署名鍵を読める。書き換えたページは、読み手を偽のダウンロードに誘導できる。 |

攻撃する者と、その者が持つものは次のとおりだ。

| 攻撃者 | 持っているもの |
| --- | --- |
| 不正な利用者 | アプリ、本物のライセンスファイルかライセンスキー、自分のマシンの管理者権限 |
| ネットワーク上の攻撃者 | 通信を読み、書き換え、再送する力 |
| 顧客の社内の別の人 | ライセンスサーバーに届くネットワーク、またはサーバーマシンへの管理者権限のないログオン |
| インターネット上の外部の者 | `elm-service` とその管理 API に届くネットワーク |
| 退職した、または役割の低いベンダーの管理者、あるいは管理者のマシンのほかのユーザー | 過去の資格情報、低い役割、ローカルのログオン |
| ベンダーの IdP にある別のアプリ、または管理画面と同じホスト名のサイト | 管理者がそのアプリに渡したトークン、または管理者のブラウザーの Cookie |
| サプライチェーンの中にいる者 | 乗っ取ったパッケージ、ビルドの道具、ベースイメージ。プルリクエスト。盗んだ資格情報。ミラーやレジストリ上ですり替えたファイル |

## ベンダーにとって

ベンダーは鍵を持ち、ライセンスを発行し、ふつうは `elm-service` を動かす。

**鍵と発行。** ライセンス、リース、鍵の証明書は、どれも ECDSA P-256(ES256)で署名され、受け取ったバイト列そのものに対して検証される。そのため、書き換えたペイロードは検証に失敗する。検証する側は、アプリのトラストストアにあるルート鍵から鍵の証明書を通してつながる鍵だけを使う。トークンのヘッダーの `alg` は鍵の記録と一致しなければならず、鍵やアルゴリズムを選ぶことはない。そのため、`none` やすり替えたアルゴリズムは断られる。トークンの種類ごとに専用の `typ` があるので、リースはライセンスとしては通らない。ルート鍵はオフラインで保管し、署名鍵を証明するときだけ使う。署名鍵が漏れたときに失効がどこまで届くかは、[信頼の鎖](trust-chain.md)を参照。

**SaaS 型の認証サーバーへの要求。** 状態を変える要求には、どれも端末のインストール鍵で署名した証明がつく。アプリの中に盗める共有の秘密はない。証明にはサーバーのノンスと本文の SHA-256 が入り、各証明 ID はノンスが有効な間(300 秒)に 1 回だけ受け入れられる。そのため、捕まえた要求を再送しても通らない。有効化に関する要求は、その有効化の鍵で署名されていなければならないので、誰もほかの端末の有効化を解除したり更新したりできない。写したマシンは、写しどうしの更新番号がずれたときに見つかる。`cloneStrategy`: `deny` なら、`ELM_CLONE_DETECTED` で止まる。オフラインの応答は、その要求を作った鍵でしか使えない。試用は、製品とマシン指紋ごとに 1 回に限られる。[有効化](activation.md)を参照。

**管理 API。** 人やシステムは、次の 3 つの方法で管理 API を使う。

- **API キー。** 課金システムのような機械のためのものだ。キーは作ったときに 1 度だけ表示され、サービスはそのハッシュだけを保存する。そのため、データベースの写しから使えるキーは得られない。キーにはそれぞれスコープ(使ってよい権限)と有効期限(既定は 90 日、最長 1 年)がある。キーは作った管理者のもので、その管理者のいまの役割が許す以上のことは決してできない。
- **自社の IdP によるサインイン(OIDC)。** 人のためのものだ。`elm admin login` は IdP からアクセストークンを得て、インストール鍵と同じようにユーザー自身の保護されたフォルダーに置き、ログインしたサービスにだけ送る。サービスは、各トークンの署名、発行者、有効期限、オーディエンスを確かめる。トークンは、サービス自身のオーディエンスの値 `oidc.audience` を名指ししていなければならない。`oidc.audience` が IdP での `elm` か管理画面のクライアント ID と同じなら、サービスは起動を拒む。そのため、ID トークンや別のアプリ向けのトークンはここでは使えない。
- **管理画面のセッション。** 管理画面はサービスを通してサインインする。サービスがトークンを持ち、ブラウザーにはセッションの Cookie(`__Host-elm-session`、`HttpOnly`、`Secure`、`SameSite=Lax`)だけを渡す。データベースはそのハッシュだけを持つ。何かを変える要求には独自のヘッダーと一致する `Origin` が要り、コンテンツセキュリティポリシーは厳しく、サインインには PKCE、`state`、`nonce` を使う。サインインの途中の状態は、データベースに保存した鍵で暗号化した Cookie に置く。その鍵は、サービスに渡す 256 ビットの鍵(`ELM_DATAPROTECTION_KEK` か `dataProtection.kekFile`)で暗号化される。セッションは、`session.idleMinutes`(既定は 30)の間使われないと終わり、`session.maxHours`(既定は 12)が過ぎても終わる。

管理者にはそれぞれ役割がある。`owner`(すべて)、`admin`(API キー、管理者、セッション以外のすべて)、`support`(読み取り、解除、リースの強制返却、オフラインの要求)、`viewer`(読み取り)だ。`owner` は管理者を無効にでき、そうするとその管理者の API キーも止まり、セッションも消える。管理操作は監査ログに書かれる。監査ログの行はハッシュで鎖のようにつながっているので、書き換えたり消したりした行は見つかる。行をどれだけ残すかは `audit.retentionDays` で決める。

**資源の上限。** 入力の大きさ、深さ、個数には上限がある。`elm-service` は、端末からの要求を送信元の IP ごと(`rateLimit.clientPerIp`、既定は毎秒 20)とインストール鍵ごと(`rateLimit.clientPerKey`、毎秒 2)に制限する。管理 API への要求は、送信元の IP ごと(`rateLimit.perIp`、毎秒 20)と API キーか管理者ごと(`rateLimit.perKey`、毎秒 10)に制限する。端末と管理の通信は別々の上限を使うので、1 つのアドレスの後ろに多くの端末があっても、管理者が締め出されることはない。`usageLog.directory` を設定すると、サービスはリースと借り出しを署名つきの利用ログにも書く。ファイルの鎖はノードごとに 1 本だ。

## アプリの開発者にとって

アプリの開発者は、トラストストアとクライアントを組み込む。

- **ライセンスは端末でネットワークなしに確かめる。** アプリに組み込んだルート公開鍵で確かめる。偽造したライセンスや書き換えたライセンスは、ネットワークが何を言おうと失敗する。[ライセンスファイルと検証](license-files-and-verification.md)を参照。
- **端末に紐づけたライセンスは、その端末でしか使えない。** ライセンスにはインストール鍵の拇印とマシン指紋が入り、更新にもリースにもその鍵の証明が要る。鍵のファイルは OS が守る(Windows では DPAPI、それ以外ではファイルのモード)。[端末と証明](devices-and-proofs.md)を参照。
- **時計を戻しても得はない。** 時計の守りが信頼できる最新の時刻を記録し、それより前に戻した時計を断る。
- **リースはどれも確かめる。** サーバーが送ってきたからといって信じない。署名、製品と鍵、そしてオンプレミスでは、機能、席数、長さ、終わりの日付がベンダーの署名したサーバーライセンスの範囲内にあることを確かめる。サーバーの鍵を抜き出した顧客でも、サーバーライセンスを超えるリースには署名できない。
- **オンプレミスのサーバーは、自分が誰かを示さなければならない。** クライアントはルート鍵からサーバーライセンスを検証し、`kind: server` を求め、サーバーをピンと照らし合わせ、サーバーライセンスが指す鍵でリースを検証する。既定の自己署名の証明書のときは、接続のたびに TLS の鍵がその鍵であることを確かめる。そのため、サーバーの鍵を持たないネットワーク上の者は、サーバーになりすませない。[フローティングライセンス](floating-licenses.md)を参照。

## 顧客の管理者にとって

顧客の管理者は `elm-server` を動かす。

- **サーバーは、サーバーライセンスを超えて貸せない。** 席はロックの下で数える。再起動のあと、新しいリースは、動いているアプリが自分のリースを回収し終えるまで待つ。借り出しは、署名つきの借り出しの記録から戻る。アプリは、サーバーライセンスの範囲外のリースをすべて断る。
- **ローカルの管理 API は管理者専用だ。** ループバックでだけ待ち受け、定数時間で比べる 256 ビットのトークンを求める。失敗した試みは 1 回ずつ記録せずに 1 分ごとに数えるので、ログをあふれさせることはできない。
- **データのフォルダーはほかのユーザーに閉じている。** Windows では Administrators、SYSTEM、フォルダーを作ったユーザーだけに許し、Linux と macOS ではモードを `0700` にする。ほかのユーザーが先に作ったフォルダーは、サーバーは使わない。
- **利用ログの書き換えは見つかる。** ログはサーバーの鍵でブロックごとに署名され、各ファイルは前のファイルと鎖でつながっている。そのため、書き換えたファイル、欠けたファイル、途中で切ったファイルを `elm log verify` が見つける。
- **大量の要求は制限される。** 要求は送信元の IP ごとに制限される(`rateLimit.perIp`、既定は毎秒 20)。

## ダウンロードしたものを確かめる

GitHub Release からダウンロードしたファイルは、実行したり出荷したりする前に、すべて確かめる。コマンドは [SECURITY.md](https://github.com/YUKIKEDA/ElasticLM/blob/main/SECURITY.md) にある。要約すると次のとおりだ。

```sh
sha256sum --check --ignore-missing SHA256SUMS
gh attestation verify <file> --repo YUKIKEDA/ElasticLM \
  --signer-workflow YUKIKEDA/ElasticLM/.github/workflows/release.yml \
  --source-ref refs/tags/v<version> --deny-self-hosted-runners
```

オプションはすべて残す。`--repo` だけでは、どのワークフローがファイルに署名したかを確かめない。`--source-ref` は、ファイルが意図したバージョンから来たことを確かめる。attestation が示すのは、ElasticLM のリリースのワークフローがそのタグからファイルをビルドしたことだ。コードに欠陥がないという保証にはならない。NuGet のパッケージは nuget.org がもう一度署名し、そのときバイト列が変わる。nuget.org から取ったパッケージは、`SHA256SUMS` と比べずに `dotnet nuget verify` で確かめる。

コンテナイメージ `ghcr.io/yukikeda/elm-service` は、まだ公開していない。それを確かめるコマンドは、イメージを公開する最初のリリースで `SECURITY.md` に足す。公開されたら、`latest` のようなタグではなく、確かめたダイジェストで取得する。タグは別のイメージに付け替えられるからだ。また、信じるのはそのイメージ名だけにし、このリポジトリのものだと名乗るラベルは信じない。

リリースの裏づけは次のとおりだ。

- リリースは、リリースのワークフローだけがビルドする。公開には `release` 環境で持ち主の承認が要り、そこにデプロイできるのは `v*` のタグだけだ。`v*` のタグを作れるのは持ち主だけで、誰もそれを動かしたり消したりできない。フォークからのプルリクエストには秘密が渡らない。
- NuGet への公開では、そのたびに短命の GitHub のトークンを 1 時間有効の API キーと引き換える。そのため、盗める長命の NuGet のキーは存在しない。持ち主の GitHub と nuget.org のアカウントはパスキーを使う。
- 公開した GitHub Release は変更できないので、そのファイルは持ち主でもあとから変えられない。
- ワークフローのアクション、道具のバージョン、Alpine のビルド用イメージ、`elm-service` のベースイメージ(`mcr.microsoft.com/dotnet/runtime-deps:10.0-noble-chiseled`)は、コミットの SHA かダイジェストで固定し、レビューを通したプルリクエストでだけ上げる。npm のパッケージはバージョンとハッシュで固定し、インストールのスクリプトを実行しない。
- このサイトは、持ち主の承認のあと、`v*` のタグからだけ公開し、読み手のデータを送らない。確かめのコマンドは `SECURITY.md` にもあるので、ファイルを確かめるのにこのサイトを信じる必要はない。

## ElasticLM が守らないもの

ここに挙げるものは受け入れている。ElasticLM はこれらを止めない。ほかのページはこれらに一文で触れ、ここにリンクする。

### 利用者のマシンの上

- **書き換えたアプリのバイナリ。** 確かめを飛ばすようにアプリのコードを変えることは、クライアント側のどんなライセンスの仕組みでも防げない。ElasticLM は難読化をしない。
- **オフラインの写し。** 管理者権限を持つ人は、インストール鍵とその状態を別のマシンに写せる。両方の写しがオンラインになれば、サーバーが複製を見つける。オフラインでしか動かない写しは見つからない。
- **失効が端末に届くのは、そのトークンの期限が来たときだけだ。** 失効のリストはない。ライセンスを失効させると新しいトークンとリースは出なくなるが、すでに端末にあるトークンは有効期限に猶予期間を足した日まで使える(既定は 30 日と 7 日)。`tokenLifetime` を短くすると、この幅は狭まる。失効させた署名鍵がアプリに届くのは、アプリの新しいバージョンでだけだ。
- **有効期限のないトークンは失効させられない。** そのようなトークンが出るのは、`elm` で手で発行したときと、期限のないライセンスの `unbound` のライセンスファイルだけだ。`elm` はそれを発行するときに警告する。
- **解除のあとも、ライセンスファイルは使える。** 解除はインストール鍵を消さないので、保存した写しはトークンの有効期限と猶予期間まで使える。これを何回できるかは、ポリシーの `deactivationLimit` で制限する。
- **OS のマシン ID を変えること。** 本当の身元はインストール鍵なので、効果はほとんどない。ただし、マシンごとに試用 1 回という規則はマシン指紋に頼っている。
- **時計の守りの状態を消すこと。** それでも時計はトークンの `iat` より前には戻せないので、実際の限界はトークンの有効期限になる。
- **返したリーストークンを持ち続けること。** トークンは期限まで有効で、通常のリースなら、リースの期間 1 つ分だ。借り出しの早期返却を制限しているのはこのためだ([フローティングライセンス](floating-licenses.md)を参照)。
- **古いオフラインの要求ファイルを新しいものより後に送ること。** 複製として扱われ、`deny` なら、管理者が有効化を解除するまで端末が止まる。古い要求ファイルは捨てる。
- **端末の OS が信頼する TLS 検査のプロキシ。** たとえば会社の検査装置だ。通信を読み、署名のない応答を偽れる。ライセンスやリースは偽れない。エラーは偽れる。偽の `ELM_CLONE_DETECTED` や `ELM_UNKNOWN_LEASE` でリースが失われ、`elm-service` からの偽の `ELM_ACTIVATION_NOT_FOUND` で端末の有効化が消える。被害はネットワークを切られたときと同じで、その顧客自身の端末に限られ、もう一度有効化するかリースを取得すれば元に戻る。プロキシは要求の本文にあるライセンスキーも読めるが、キーだけでは席もトークンも得られない。

### 顧客のライセンスサーバーの上

- **管理者がサーバーの鍵を抜き出す。** 管理者はそのマシンの root 権限を持っている。鍵があれば、席数を超えるリースに署名でき、利用ログを書き換えられる。それでもアプリはサーバーライセンスの範囲内のリースしか受け入れず、サーバーライセンスには期限がある(既定は 30 日)。
- **写したサーバーマシン** は、次のサーバーライセンスの更新のときにしか見つからない。既定では最大 30 日後になる。
- **管理者が借り出した席を空ける。** 借り出しの記録を消す、時計を進める、`--set-aside-broken-records` で起動する、の方法がある。利用ログには痕跡が残り、被害は借り出しの期限で終わる。
- **アプリが `ExpectedServerLicenseId` を設定していないと、最初の接続を信じる。** [フローティングライセンス](floating-licenses.md)を参照。
- **`allow` と `deny` のホスト名とユーザー名は偽れる。** クライアントが申告するからだ。信頼できるのは IP の規則だけだ。
- **最新の利用ログのファイルを消すことや、最後の署名のあとでそのファイルを切ることは、見つけられない。** 比べる次のファイルがないからだ。席の数え方はログに頼らない。

### SaaS 型の認証サーバーとその管理者のまわり

- **データベースに書き込める者** は、監査ログを書き換えてハッシュを計算し直せ、セッションを足せる。データベースと鍵暗号化鍵の両方があれば、途中のサインインを読んだり偽造したりもできる。データベースとそのバックアップは署名鍵と同じように守り、鍵暗号化鍵はデータベースの外に置く。
- **署名鍵とそのパスフレーズを持つ者** は、サービスの利用ログを書き換えられ、ライセンスも偽造できる。
- **有効化を持つ利用者は、監査ログを増やせる。** ただし、それができるのは `cloneStrategy`: `flag` のときだけで、複製の検出を何度も起こすことで増やす。`deny` なら、有効化が止まるときの 1 行だけだ。有効化し直しても行は増える。鍵ごとの上限(毎秒 2)がこれを抑え、ベンダーはその端末の有効化を解除できる。
- **借り出しの権利を持つ利用者は、新しい鍵とマシン指紋で早期返却の表を増やせる。** 行は自分のライセンスに対してだけ数えられ、30 日で消える。
- **IdP での変更は遅れて届く。** 管理者がグループから外れても、サービスには知らされない。古い役割は次のサインインまで残る。その管理者の API キーも、それまでか、OIDC のサインインを設定しているときは、最後のサインインとキーの作成のうち遅いほうから `apiKeys.inactiveAdminDays`(既定は 90)が過ぎるまで使える。アクセストークンは、`elm admin logout` のあとでも期限まで有効で、管理画面のセッションは最長 `session.maxHours` 続く。すぐに止めるには、サービスでその人を無効にする。
- **盗まれたセッションの Cookie は、セッションが終わるまでどの IP からでも使える。** セッションは IP にも端末にも結びつけていない。
- **Cookie はポートを区別しない。** 同じホスト名の別のポートで動くサービスは、管理画面の Cookie を読めて、設定もできる。
- **管理画面からログアウトしても、IdP のセッションは残る。** 共有のマシンでは、ブラウザーを閉じるか、IdP からもログアウトする。
- **間違ったサービスへのサインイン。** `elm admin login --url` が悪意あるサービスを指していると、そのサービスは本物の IdP の情報をそのまま渡し、受け取ったアクセストークンを使える。`elm` はサインインを待つ前にサービスの URL と発行者を表示するので、それを確かめる。
- **デバイスコードのフィッシング。** 攻撃者がデバイスのサインインを始め、本物の確認の URL とコードを管理者に送れる。

### リリースとこのサイト

- **実行ファイルと `libelasticlm` にはコードの署名がない。** Windows SmartScreen が警告することがある。macOS Gatekeeper は、ファイルを確かめたうえで quarantine 属性を外すまで開かない([SECURITY.md](https://github.com/YUKIKEDA/ElasticLM/blob/main/SECURITY.md) を参照)。
- **持ち主の GitHub か nuget.org のアカウントが乗っ取られる。** アカウントを握った者は、タグを付け、承認し、公開し、イメージのタグを付け替え、このサイトを変えられ、attestation は正しく見える。パスキーはこれを難しくし、変更できないリリースは公開済みのファイルを変えさせない。
- **GitHub やそのランナーが侵害される。** リリースと attestation は GitHub に頼っている。
- **attestation が示すのは、どのワークフローがどのコミットをビルドしたかだけだ。** 持ち主がマージした悪いコミットも、正しく attestation される。コードそのものはコードレビューと CI が守る。
- **GHCR のイメージのタグは付け替えられる。** イメージは確かめたダイジェストで取得する。
- **コンテナのベースイメージの脆弱性** は、ElasticLM の次のリリースまで残る。単一のバイナリの `elm-service` を使う人は、OS のライブラリの更新を受けられる。
- **Dependabot は npm の依存について警告しない。** pnpm 12 が書くロックファイルを読めないからだ。代わりに CI の `pnpm audit` が見るので、プルリクエストの間に公開された勧告は次のプルリクエストまで待つ。サイトのビルドの道具にある、レビューした 3 件の勧告は、該当する関数が呼ばれないので受け入れている。
- **このサイトは、持ち主のほかの GitHub Pages のサイトと Web のオリジンを共有している。** それらのどれかの依存が侵害されると、そのサイトを開いた読み手に対して、このサイトのページが変えられるおそれがある。確かめのコマンドを `SECURITY.md` にも置いているのは、これも理由の 1 つだ。

## 各役割がすべきこと

暗号が守りとして働くのは、各役割が自分の分を果たしたときだけだ。

### ベンダー

- ルート鍵はオフラインに置く。`elm` はルート鍵をパスフレーズで暗号化したファイルとして保存する。決してサーバーに置かない。
- `elm-service` には、必要な用途に証明した署名鍵だけを渡す。鍵はファイルとして渡し、パスフレーズは環境変数かファイルで渡す。設定ファイルやイメージには決して入れない。ほかの秘密(ノンスの秘密、データベースの接続文字列、管理画面のクライアントの秘密、鍵暗号化鍵)も同じように、権限を絞って渡す。証明書の切り替えは、[信頼の鎖](trust-chain.md)のとおりに計画する。
- 署名鍵が漏れたら、新しい鍵を証明し、それでライセンスを発行し直す。漏れた鍵の ID を自分のサーバーの `trust.revokedKeyIds` に並べると、サーバーはその鍵を使うのも受け入れるのもやめる。アプリを守れるのは、トラストストアにその ID を並べたアプリのバージョンだけだ。
- ポリシーの値は、受け入れている脅威を踏まえて選ぶ。`tokenLifetime` を短くすると、写しと遅い失効の影響を抑えられる。`leaseDuration` は、停止への耐性と再起動のあとの待ち時間の兼ね合いで決める。`borrowLimit` と `borrowReturnLimit` は借り出しに上限をかける。`cloneStrategy`: `deny` は複製を止める。有効期限のないライセンスは避ける。
- データベースとそのバックアップを守り、鍵暗号化鍵はその外に置く。
- IdP では、管理画面のクライアントに認可コードフローだけを許し、2 つのクライアント ID のどちらとも違う `oidc.audience` を使い、役割のクレームを ID トークンとアクセストークンの両方に入れ、デバイスの承認の画面にクライアントの名前を出す。
- 管理画面には、信頼しないサービスと共有しないホスト名を与える。セッションの設定は管理者が作業できる範囲で短くし、`audit.retentionDays` は記録の保存に求められる期間にする。
- `publicUrls` には端末が使う URL を設定し、デプロイの前にバイナリやイメージを確かめる。

### アプリの開発者

- 組み込むのは、ベンダーのルート公開鍵といまの失効した鍵の ID だけにする。検証の結果にはすべて従い、失敗を警告として扱わない。
- 書き換えたバイナリが自分の製品にとってどれほど問題かを決める。書き換えたバイナリに対しては、どんな確かめも役に立たない。
- オンプレミスのサーバーでは、顧客のサーバーライセンスがわかっているなら `ExpectedServerLicenseId` を設定する。
- `Lost` のリースを扱い、借り出しに頼る前にその `ExpiresAt` を確かめる。
- インストール鍵は、正しいユーザーかマシンだけが読める場所に置く。[端末と証明](devices-and-proofs.md)を参照。
- ベンダーが署名鍵を失効させたら、アプリの新しいバージョンを出す。

### 顧客の管理者

- サーバーマシンを守る。そのマシンの root 権限を持つ人は誰でも、サーバーの鍵を取れる。
- データのフォルダーと管理者トークンは、サービスのアカウントと管理者だけが読めるようにする。`admin.listen` はループバックのままにする(サーバーはそれ以外を断る)。
- 同じ製品のアプリがそのマシンで動くなら、サーバーに専用の `dataDirectory` を与える。
- `allow` と `deny` では IP の規則に頼る。リバースプロキシの後ろでは、IP の規則はプロキシでかけ、`rateLimit.perIp` はその後ろにあるマシンの数に合わせて上げる。
- `--set-aside-broken-records` は、借り出しの記録が壊れた理由を突き止めてから使う。これを使うと、借り出した席が空く。
- サーバーライセンスは期限が来る前に更新し、`elm-server` と `elm` はダウンロードのたびに確かめる。

### すべての人

脆弱性は、公開の Issue ではなく GitHub Security Advisories で報告する。[SECURITY.md](https://github.com/YUKIKEDA/ElasticLM/blob/main/SECURITY.md) にあるとおりだ。報告には、本物の秘密鍵、ライセンストークン、顧客の識別子、マシン ID を入れない。

モデルの線をなぜそこに引いたか(難読化なし、失効のリストなし、待機系のサーバーなし)は、[設計の選択](design-choices.md)にある。
