# セキュリティモデル

このページは、ElasticLM が守りたいものを守ってくれるのか、自分では何をしなければならないのかを判断する必要がある人すべてに向けたものだ。鍵を保持して `elm-service` を運用するベンダー、クライアントを組み込むアプリ開発者、`elm-server` を運用する顧客の管理者を想定している。最初に、何を誰から守るのかを短く説明し、続けて役割ごとの節を置く。そのあとで、ダウンロードしたファイルの検証方法、ElasticLM が防がないものの一覧、各役割がすべきことを説明する。先に[概要](overview.md)と[トラストチェーン](trust-chain.md)を読んでおくと理解しやすい。仕組みの詳細は、ほかの解説ページにある。

## 何を誰から守るか

ライセンスの仕組みを攻撃するのは、たいていその仕組みを使う側の人だ。顧客はアプリと本物のライセンスを持ち、自分のマシンを完全に制御できる。その中には、支払った分より多く使いたいと考える人もいる。ElasticLM は、秘密を隠すことではなく署名によって、次の 3 つを防ぐ。

- ライセンスの偽造や改ざん
- リクエストの偽造や再送
- 購入した数を超える同時使用シート

アプリ自体のコードの改変は、防ごうとしていない。攻撃者が制御するマシンで動くものは、何であれその攻撃者が改変できる。保護の拠り所は、攻撃者には署名を作れないという点にある。

守る価値があるものは次のとおりだ。

| 守るもの | 攻撃者の手に渡ると |
| --- | --- |
| ベンダーのルート鍵と署名鍵 | アプリが受け入れるライセンスやリースを自由に作れる。 |
| ライセンスキー | そのキーでアクティベーションできる。 |
| デバイスのインストール鍵 | そのデバイスになりすませる。 |
| `elm-service` の管理者権限 | ライセンスの発行、アクティベーション解除、失効ができる。 |
| 利用ログと監査ログ | 課金や紛争の証拠が失われる。 |
| ElasticLM のリリースファイルとこのサイト | 偽の `elm-server` やライブラリは、確認をすべて飛ばせる。偽の `elm` や `elm-service` は、ベンダーの署名鍵を読み取れる。改ざんされたページは、読者を偽のダウンロードに誘導できる。 |

攻撃者と、攻撃者が持っているものは次のとおりだ。

| 攻撃者 | 持っているもの |
| --- | --- |
| 不正をはたらくライセンシー（顧客） | アプリ、本物のライセンスファイルまたはライセンスキー、自分のマシンの管理者権限 |
| ネットワーク上の第三者 | 通信を読み取り、改ざんし、再送する能力 |
| 顧客の社内の別の人 | ライセンスサーバーへのネットワークアクセス、またはサーバーマシンへの管理者権限のないログオン |
| インターネット上の部外者 | `elm-service` とその管理 API へのネットワークアクセス |
| ベンダーの元管理者や低いロールの管理者、または管理者のマシンのほかのユーザー | 古い資格情報、低いロール、ローカルのログオン |
| ベンダーの ID プロバイダーに登録された別のアプリ、または管理画面と同じホスト名のサイト | 管理者がそのアプリに渡したトークン、または管理者のブラウザーの Cookie |
| サプライチェーンに関わる者 | 乗っ取ったパッケージ、ビルドツール、ベースイメージ。プルリクエスト。盗んだ資格情報。ミラーやレジストリですり替えたファイル |

## ベンダー向け

ベンダーは鍵を保持し、ライセンスを発行する。`elm-service` も、ふつうはベンダーが運用する。

**鍵と発行。** ライセンス、リース、鍵証明書には、どれも ECDSA P-256（ES256）で署名する。受け取ったバイト列そのものを検証するので、ペイロードを改ざんすると検証に失敗する。検証で使うのは、アプリのトラストストアにあるルート鍵から鍵証明書を介してつながる鍵だけだ。トークンのヘッダーの `alg` は鍵の記録と一致しなければならず、鍵やアルゴリズムの選択には使わない。そのため、`none` やすり替えたアルゴリズムは拒否される。トークンの種類ごとに専用の `typ` があるので、リースをライセンスとして通すことはできない。ルート鍵はオフラインで保管し、署名鍵を証明するときだけ使う。署名鍵が漏れたときに失効がどこまで効くかは、[トラストチェーン](trust-chain.md)を参照。

**SaaS 型のサービスへのリクエスト。** 状態を変えるリクエストには、必ずデバイスのインストール鍵で署名したプルーフ（所有証明）が付く。アプリの中に、盗める共有の秘密はない。プルーフにはサーバーのノンスと本文の SHA-256 が入り、プルーフ ID はノンスの有効期間（300 秒）内に 1 回しか受け付けない。そのため、盗聴したリクエストを再送しても通らない。アクティベーションに関するリクエストは、そのアクティベーションの鍵で署名されていなければならない。そのため、ほかのデバイスのアクティベーション解除やトークンの更新は誰にもできない。コピーされたマシンは、コピーどうしのシーケンス番号が食い違った時点で見つかる。`cloneStrategy`: `deny` なら、`ELM_CLONE_DETECTED` で止まる。オフラインのレスポンスは、そのリクエストを作った鍵でしか使えない。トライアルは、製品とマシンフィンガープリントの組ごとに 1 回に限られる。[アクティベーション](activation.md)を参照。

**管理 API。** 人やシステムは、次の 3 つの方法で管理 API を使う。

- **API キー。** 課金システムのような機械が使う。キーは作成時に一度だけ表示され、サービスはそのハッシュしか保存しない。そのため、データベースのコピーを手に入れても、使えるキーは得られない。キーにはそれぞれスコープ（使ってよい権限）と有効期限（既定は 90 日、最長 1 年）がある。また、キーは作成した管理者に属し、その管理者の現在のロールで許される範囲を超えることはできない。
- **自社の ID プロバイダーでのサインイン（OIDC）。** 人が使う。`elm admin login` は ID プロバイダーからアクセストークンを取得し、インストール鍵と同じようにユーザー自身の保護されたフォルダーに保存する。トークンは、ログインしたサービスにしか送らない。サービスは、トークンごとに署名、発行元、有効期限、オーディエンスを確かめる。トークンのオーディエンスは、サービス自身の値 `oidc.audience` でなければならない。`oidc.audience` が、ID プロバイダーに登録した `elm` や管理画面のクライアント ID と同じなら、サービスは起動しない。そのため、ID トークンや、別のアプリ向けのトークンはここでは使えない。
- **管理画面のセッション。** 管理画面はサービスを経由してサインインする。トークンはサービスが保持し、ブラウザーにはセッション Cookie（`__Host-elm-session`、`HttpOnly`、`Secure`、`SameSite=Lax`）だけを渡す。データベースには、その Cookie のハッシュしか保存しない。変更を伴うリクエストには、独自のヘッダーと、一致する `Origin` が必要だ。コンテンツセキュリティポリシーは厳しく設定しており、サインインでは PKCE、`state`、`nonce` を使う。サインインの途中の状態は、データベースに保存した鍵で暗号化した Cookie に入れる。この鍵は、サービスに渡す 256 ビットの鍵（`ELM_DATAPROTECTION_KEK` または `dataProtection.kekFile`）で暗号化する。セッションは、`session.idleMinutes`（既定は 30）の間使われないと終わる。`session.maxHours`（既定は 12）が過ぎたときも終わる。

管理者にはそれぞれロールがある。`owner`（すべての操作）、`admin`（API キー、管理者、セッション以外のすべての操作）、`support`（参照、アクティベーション解除、リースの強制返却、オフラインのリクエスト）、`viewer`（参照）のいずれかだ。`owner` は管理者を無効にできる。無効にすると、その管理者の API キーも止まり、セッションも削除される。管理操作は監査ログに記録される。監査ログの行はハッシュでつながっているので、改ざんや削除をされた行は見つかる。行を残す期間は `audit.retentionDays` で設定する。

**リソースの上限。** 入力のサイズ、深さ、個数には上限がある。`elm-service` は、デバイスからのリクエストを、送信元の IP ごと（`rateLimit.clientPerIp`、既定は毎秒 20）とインストール鍵ごと（`rateLimit.clientPerKey`、毎秒 2）に制限する。管理 API へのリクエストは、送信元の IP ごと（`rateLimit.perIp`、毎秒 20）と、API キーまたは管理者ごと（`rateLimit.perKey`、毎秒 10）に制限する。デバイスと管理の通信には別々の上限を使うので、1 つのアドレスの後ろに多数のデバイスがあっても、管理者が締め出されることはない。`usageLog.directory` を設定すると、サービスはリースと借用を署名付きの利用ログにも書き込む。利用ログのファイルのチェーンは、ノードごとに 1 本だ。

`elm-service` のすべての設定は、[elm-service の設定](../reference/service-configuration.md)を参照。監査ログの行と利用ログの行は、[ログ](../reference/logs.md)を参照。

## アプリ開発者向け

アプリ開発者は、トラストストアとクライアントをアプリに組み込む。

- **ライセンスはデバイス上で、ネットワークなしで確かめる。** 確認には、アプリに組み込んだルート公開鍵を使う。偽造や改ざんをされたライセンスは、ネットワークから何が返ってきても検証に失敗する。[ライセンスファイルと検証](license-files-and-verification.md)を参照。
- **デバイスに紐付けたライセンスは、そのデバイスでしか使えない。** ライセンスにはインストール鍵のサムプリントとマシンフィンガープリントが入っており、トークンの更新にもリースにも、その鍵のプルーフが必要だ。鍵のファイルは OS が保護する（Windows では DPAPI、それ以外ではファイルのモード）。[デバイスとプルーフ](devices-and-proofs.md)を参照。
- **時計を戻しても効果はない。** 時刻巻き戻し対策が、信頼できる最新の時刻を記録しておき、それより前に戻された時計を拒否する。
- **リースはすべて確かめる。** サーバーから送られてきたというだけでは信用しない。署名、製品と鍵を確かめ、オンプレミスの場合は、機能、シート数、期間、終了日が、ベンダーの署名したサーバーライセンスの範囲内にあることも確かめる。サーバーの鍵を取り出した顧客でも、サーバーライセンスの範囲を超えるリースは作れない。
- **オンプレミスのサーバーは、自分が本物であることを証明しなければならない。** クライアントは、サーバーライセンスをルート鍵から検証し、`kind: server` であることを求め、サーバーをピンと照合し、サーバーライセンスが指す鍵でリースを検証する。既定の自己署名の証明書を使う場合は、接続のたびに TLS の鍵がその鍵であることを確かめる。そのため、サーバーの鍵を持たないネットワーク上の第三者は、サーバーになりすませない。[フローティングライセンス](floating-licenses.md)を参照。

## 顧客の管理者向け

顧客の管理者は `elm-server` を運用する。

- **サーバーは、サーバーライセンスを超えてシートを貸し出せない。** シートはロックをかけて数える。再起動のあとは、動いているアプリがリースの再登録を終えるまで、新しいリースは待たされる。借用は、署名付きの借用の記録から復元する。アプリは、サーバーライセンスの範囲外のリースをすべて拒否する。
- **ローカルの管理 API は管理者しか使えない。** ループバックでしか待ち受けず、256 ビットのトークンを求め、トークンは定数時間で比較する。失敗した試行は 1 回ずつ記録せず、1 分ごとに件数を数える。そのため、失敗を繰り返してログをあふれさせることはできない。
- **データフォルダーには、ほかのユーザーはアクセスできない。** Windows では Administrators、SYSTEM、フォルダーを作ったユーザーにだけアクセスを許す。Linux と macOS ではモードを `0700` にする。ほかのユーザーが先に作ったフォルダーは、サーバーは使わない。
- **利用ログの改ざんは見つかる。** ログはブロックごとにサーバーの鍵で署名され、各ファイルは前のファイルとチェーンでつながっている。そのため、改ざんされたファイル、欠けたファイル、途中で切られたファイルを `elm log verify` で見つけられる。
- **大量のリクエストは制限される。** リクエストは送信元の IP ごとに制限される（`rateLimit.perIp`、既定は毎秒 20）。

`elm-server` のすべての設定は、[elm-server の設定](../reference/server-configuration.md)を参照。利用ログと借用の記録は、[ログ](../reference/logs.md)を参照。

## ダウンロードしたファイルの検証

GitHub Release からダウンロードしたファイルは、実行や配布の前にすべて検証する。コマンドは[SECURITY.md](https://github.com/YUKIKEDA/ElasticLM/blob/main/SECURITY.md)にある。要点は次のとおりだ。

```sh
sha256sum --check --ignore-missing SHA256SUMS   # on macOS: shasum -a 256 --check --ignore-missing SHA256SUMS
gh attestation verify <file> --repo YUKIKEDA/ElasticLM \
  --signer-workflow YUKIKEDA/ElasticLM/.github/workflows/release.yml \
  --source-ref refs/tags/v<version> --deny-self-hosted-runners
```

オプションは省略しないこと。`--repo` だけでは、どのワークフローがファイルに署名したかを確かめない。`--source-ref` を付けると、ファイルが意図したバージョンのものであることを確かめられる。attestation が示すのは、ElasticLM のリリースワークフローがそのタグからファイルをビルドしたことまでで、コードに欠陥がないことは示さない。NuGet パッケージは nuget.org が署名し直すので、バイト列が変わる。nuget.org から取得したパッケージは `SHA256SUMS` と照合せず、`dotnet nuget verify` で検証する。

コンテナイメージ `ghcr.io/yukikeda/elm-service` を push するのは、`v1.0.0` のようなプレリリースでないリリースだけだ。`v1.0.0-rc.1` のようなプレリリースはイメージを push しない。イメージを検証するコマンドは、イメージを初めて push するリリースで `SECURITY.md` に追加する。イメージを取得するときは、`latest` のようなタグではなく、検証したダイジェストを指定すること。タグは別のイメージに付け替えられるからだ。また、信頼するのはそのイメージ名だけにし、このリポジトリのものだと称するラベルは信頼しない。

リリースの信頼性を支えているのは次の点だ。

- リリースをビルドするのは、リリースワークフローだけだ。公開には `release` 環境でのオーナーの承認が必要で、この環境にデプロイできるのは `v*` タグだけだ。`v*` タグを作成できるのはオーナーだけで、誰もそのタグを移動・削除できない。フォークからのプルリクエストにはシークレットを渡さない。
- NuGet への公開では、毎回、有効期間の短い GitHub のトークンを、1 時間有効な API キーと交換する。そのため、盗まれるような長期間有効な NuGet のキーは存在しない。オーナーの GitHub と nuget.org のアカウントはパスキーを使っている。
- 公開済みの GitHub Release はイミュータブルなので、あとからファイルを変更することは、オーナーにもできない。
- ワークフローのアクション、ツールのバージョン、Alpine のビルド用イメージ、`elm-service` のベースイメージ（`mcr.microsoft.com/dotnet/runtime-deps:10.0-noble-chiseled`）は、コミットの SHA かダイジェストで固定している。上げるのは、レビューを通したプルリクエストだけだ。npm パッケージはバージョンとハッシュで固定し、インストールスクリプトは実行しない。
- このサイトは、オーナーの承認を経て `v*` タグからしか公開されず、読者のデータを外部に送らない。検証のコマンドは `SECURITY.md` にも載せているので、ファイルを検証するためにこのサイトを信頼する必要はない。

## ElasticLM が防がないもの

ここに挙げるものは、許容しているリスクだ。ElasticLM はこれらを防がない。ほかのページでは一文で触れ、このページにリンクしている。

### ライセンシーのマシン上

- **アプリのバイナリの改変。** 確認を飛ばすようにアプリのコードを書き換えることは、クライアント側のどんなライセンスの仕組みでも防げない。ElasticLM は難読化をしない。
- **オフラインでのコピー。** 管理者権限を持つ人は、インストール鍵とその状態を別のマシンにコピーできる。両方のコピーがオンラインになれば、サーバーがクローンを見つける。オフラインでしか動かないコピーは見つからない。
- **失効がデバイスに届くのは、トークンの有効期限が切れたときだ。** 失効リストはない。ライセンスを失効させると、新しいトークンやリースは発行されなくなる。しかし、すでにデバイスにあるトークンは、有効期限に猶予期間を足した時点（既定では 30 日と 7 日）まで使える。`tokenLifetime` を短くすれば、この期間は短くなる。失効させた署名鍵がアプリに伝わるのは、アプリの新しいバージョンを出したときだけだ。
- **有効期限のないトークンは失効させられない。** そうしたトークンができるのは、`elm` で手作業で発行したときと、有効期限のないライセンスから作った `unbound` のライセンスファイルだけだ。`elm` は、そうしたトークンを発行するときに警告を出す。
- **アクティベーション解除のあとも、ライセンスファイルは使える。** アクティベーション解除ではインストール鍵を削除しない。そのため、保存しておいたコピーは、トークンの有効期限と猶予期間が過ぎるまで使える。これを何回できるかは、ポリシーの `deactivationLimit` で制限する。
- **OS のマシン ID の変更。** 実際にデバイスを識別するのはインストール鍵なので、ほとんど効果はない。ただし、マシンごとにトライアルは 1 回というルールは、マシンフィンガープリントに依存している。
- **時刻巻き戻し対策の状態の削除。** それでも時計をトークンの `iat` より前には戻せないので、実質的な上限はトークンの有効期限になる。
- **返却したリーストークンを手元に残すこと。** トークンは期限が切れるまで有効で、通常のリースならリースの期間 1 回分だ。借用の早期返却を制限しているのはこのためだ（[フローティングライセンス](floating-licenses.md)を参照）。
- **新しいオフラインのリクエストファイルのあとに、古いものを提出すること。** クローンとして扱われ、`deny` なら、管理者がアクティベーションを解除するまでデバイスが止まる。古いリクエストファイルは捨てること。
- **デバイスの OS が信頼する、TLS の通信を検査するプロキシ。** たとえば企業の検査装置がこれに当たる。このプロキシは通信を読み取り、署名のないレスポンスを偽装できる。ライセンスやリースは偽装できないが、エラーは偽装できる。偽の `ELM_CLONE_DETECTED` や `ELM_UNKNOWN_LEASE` を返されるとリースが失われ、`elm-service` からの偽の `ELM_ACTIVATION_NOT_FOUND` を返されるとローカルのアクティベーションが削除される。被害はその顧客自身のデバイスに限られ、ネットワークを切断されたときと同じく、もう一度アクティベーションするかリースを取得すれば元に戻る。プロキシはリクエストの本文にあるライセンスキーも読み取れるが、キーだけではシートもトークンも得られない。

### 顧客のライセンスサーバー上

- **管理者がサーバーの鍵を取り出す。** 管理者はそのマシンの root 権限を持っている。鍵があれば、シート数を超えるリースに署名でき、利用ログも書き換えられる。それでも、アプリはサーバーライセンスの範囲内のリースしか受け入れない。また、サーバーライセンスには有効期限がある（既定は 30 日）。
- **コピーされたサーバーマシン**は、次のサーバーライセンスの更新のときまで見つからない。既定では最大 30 日後だ。
- **管理者が古いサーバーライセンスのファイルをもう一度読み込ませる。** サーバーは、手作業で読み込ませたファイルを起動するときと同じように確かめるが、置き換える前のファイルとは比べない。`elm license issue` で発行したファイルにはシーケンス番号がないからだ。シートや機能を減らす更新のあとでも、期限が切れていない古いファイルは、前のシートや機能を与え続ける。`elm-service` からオンラインで更新するサーバー（`service.url`）は、古いファイルのライセンス ID が同じなら 1 時間以内に、そうでなければ次の更新のときに、最新のライセンスに戻る。オフラインでアクティベーションしたサーバーは、管理者が次の更新を取り込むまで古いファイルを使い続ける。対策として、手作業で発行するファイルの期限を短くするか、サーバーを `elm-service` でアクティベーションする。[新しいファイルでは取り上げられないもの](../how-to/renew-a-server-license.md#新しいファイルでは取り上げられないもの)を参照。
- **管理者が借用中のシートを空ける。** 方法は、借用の記録を削除する、時計を進める、`--set-aside-broken-records` で起動する、のいずれかだ。利用ログには痕跡が残り、被害は借用の期限が切れた時点で終わる。
- **アプリが `ExpectedServerLicenseId` を設定していないと、最初の接続先を信頼する。** [フローティングライセンス](floating-licenses.md)を参照。
- **`allow` と `deny` に指定するホスト名とユーザー名は偽装できる。** クライアントが自己申告する値だからだ。信頼できるのは IP のルールだけだ。
- **最新の利用ログのファイルを削除したり、最後の署名のあとで切り詰めたりしても、見つけられない。** 比較する次のファイルがないからだ。シートの数え方は、ログに依存しない。

### SaaS 型のサービスとその管理者

- **データベースに書き込める人**は、監査ログを書き換えてハッシュを計算し直せる。セッションを追加することもできる。データベースに加えて鍵暗号化鍵もあれば、進行中のサインインを読み取ったり偽造したりもできる。データベースとそのバックアップは署名鍵と同じように保護し、鍵暗号化鍵はデータベースとは別の場所に置くこと。
- **署名鍵とそのパスフレーズを持つ人**は、サービスの利用ログを書き換えられ、ライセンスも偽造できる。
- **アクティベーションを持つライセンシーは、監査ログを膨らませられる。** ただし、クローン検出を何度も起こして膨らませられるのは `cloneStrategy`: `flag` の場合だけだ。`deny` の場合は、アクティベーションが止まるときの 1 行だけだ。再アクティベーションでも行は増える。鍵ごとの上限（毎秒 2）でこれを抑えられ、ベンダーはそのデバイスのアクティベーションを解除できる。
- **借用の権利を持つライセンシーは、新しい鍵とマシンフィンガープリントを使って、早期返却の記録のテーブルを膨らませられる。** 記録された行はそのライセンシー自身のライセンスにだけ数えられ、30 日後に削除される。
- **ID プロバイダーでの変更は、遅れて反映される。** 管理者がグループから外れても、サービスには通知されない。元のロールは、その管理者が次にサインインするまで残る。その管理者の API キーも、それまでは使える。OIDC のサインインを設定している場合は、最後のサインインとキーの作成のうち遅いほうから `apiKeys.inactiveAdminDays`（既定は 90 日）が過ぎるまで使える。アクセストークンは、`elm admin logout` のあとでも期限が切れるまで有効だ。管理画面のセッションは最長で `session.maxHours` まで続く。すぐに止めるには、サービスでその管理者を無効にする。
- **盗まれたセッション Cookie は、セッションが終わるまで、どの IP からでも使える。** セッションは IP にもデバイスにも紐付けていない。
- **Cookie はポートを区別しない。** 同じホスト名の別のポートで動くサービスは、管理画面の Cookie を読み取ることも、設定することもできる。
- **管理画面からログアウトしても、ID プロバイダーのセッションは残る。** 共用のマシンでは、ブラウザーを閉じるか、ID プロバイダーからもログアウトすること。
- **別のサービスへのサインイン。** `elm admin login --url` で悪意のあるサービスを指定すると、そのサービスは本物の ID プロバイダーの情報をそのまま中継し、受け取ったアクセストークンを悪用できる。`elm` はサインインを待つ前にサービスの URL と発行元を表示するので、それを確認すること。
- **デバイスコードを使ったフィッシング。** 攻撃者がデバイスのサインインを開始し、本物の確認用 URL とコードを管理者に送りつけることができる。

### リリースとこのサイト

- **実行ファイルと `libelasticlm` には、Authenticode の署名も Developer ID の署名もない**（`osx-arm64` のファイルにあるのは、リンカーが付ける ad-hoc の署名だけ）。Windows SmartScreen が警告を出すことがある。macOS Gatekeeper は、ファイルを検証したうえで quarantine 属性を外すまで開かない（[SECURITY.md](https://github.com/YUKIKEDA/ElasticLM/blob/main/SECURITY.md)を参照）。
- **オーナーの GitHub や nuget.org のアカウントが乗っ取られる。** アカウントを手に入れた者は、タグの作成、承認、公開、イメージのタグの付け替え、このサイトの変更ができ、attestation も正しく見える。パスキーによって乗っ取りは難しくなり、イミュータブルなリリースによって公開済みのファイルは変わらない。
- **GitHub やそのランナーが侵害される。** リリースと attestation は GitHub に依存している。
- **attestation が示すのは、どのワークフローがどのコミットをビルドしたかだけだ。** オーナーがマージした問題のあるコミットにも、正しい attestation が付く。コードそのものは、コードレビューと CI で守る。
- **GHCR のイメージのタグは付け替えられる。** イメージは、検証したダイジェストを指定して取得すること。
- **コンテナのベースイメージの脆弱性**は、ElasticLM の次のリリースまで残る。単一バイナリの `elm-service` を使う場合は、OS のライブラリの更新が適用される。
- **Dependabot は npm の依存関係について警告しない。** pnpm 12 が書き出すロックファイルを読めないからだ。代わりに CI の `pnpm audit` で確認している。そのため、プルリクエストとプルリクエストの間に公開されたアドバイザリは、次のプルリクエストまで検出されない。サイトのビルドツールにある 3 件のアドバイザリは、レビューしたうえで、該当する関数が呼ばれないので許容している。
- **このサイトは、オーナーのほかの GitHub Pages のサイトと Web のオリジンを共有している。** そうしたサイトのどれかの依存関係が侵害されると、そのサイトを開いた読者に対して、このサイトのページを書き換えられるおそれがある。検証のコマンドを `SECURITY.md` にも載せている理由の 1 つはこれだ。

## 各役割がすべきこと

暗号による保護が成り立つのは、それぞれの役割が自分の分担を果たしたときだけだ。

### ベンダー

- ルート鍵はオフラインで保管する。`elm` はルート鍵を、パスフレーズで暗号化したファイルとして保存する。決してサーバーに置かないこと。
- `elm-service` には、必要な用途についてだけ証明された署名鍵を渡す。鍵はファイルで渡し、パスフレーズは環境変数かファイルで渡す。設定ファイルやイメージには決して入れない。ほかの秘密の値（ノンス用の秘密の値、データベースの接続文字列、管理画面のクライアントシークレット、鍵暗号化鍵）も、同じ方法で、アクセス権を絞って渡す。鍵証明書の入れ替えは、[トラストチェーン](trust-chain.md)の説明に沿って計画する。
- 署名鍵が漏れたら、新しい署名鍵を証明し、その鍵でライセンスを発行し直す。漏れた鍵の ID を自分のサーバーの `trust.revokedKeyIds` に追加すれば、サーバーはその鍵を使うことも受け入れることもやめる。アプリを守れるのは、トラストストアにその ID を載せた新しいバージョンのアプリだけだ。
- ポリシーの値は、許容しているリスクを踏まえて選ぶ。`tokenLifetime` を短くすれば、コピーや失効の遅れによる影響を抑えられる。`leaseDuration` は、停止にどれだけ耐えられるかと、再起動後の待ち時間とのトレードオフで決める。`borrowLimit` と `borrowReturnLimit` で借用を制限する。`cloneStrategy`: `deny` でクローンを止める。有効期限のないライセンスは避ける。
- データベースとそのバックアップを保護し、鍵暗号化鍵はそれらとは別の場所に置く。
- ID プロバイダーでは、管理画面のクライアントに認可コードフローだけを許可する。`oidc.audience` には、2 つのクライアント ID のどちらとも異なる値を使う。ロールのクレームは、ID トークンとアクセストークンの両方に入れる。デバイスの承認画面には、クライアントの名前を表示する。
- 管理画面のホスト名は、信頼できないサービスと共有しないものにする。セッションの設定は、管理者が作業できる範囲でできるだけ短くする。`audit.retentionDays` は、記録の保存に求められる期間に合わせる。
- `publicUrls` にはデバイスが使う URL を設定する。デプロイの前に、バイナリやイメージを検証する。

### アプリ開発者

- 組み込むのは、ベンダーのルート公開鍵と、現時点で失効している鍵の ID だけにする。検証の結果にはすべて従い、失敗を警告扱いにしない。
- バイナリの改変が自社の製品にとってどれほど問題かを判断する。改変されたバイナリには、どんな確認も通用しない。
- オンプレミスのサーバーを使う場合、顧客のサーバーライセンスが分かっているなら `ExpectedServerLicenseId` を設定する。
- `Lost` になったリースに対処する。借用に頼る前に、その `ExpiresAt` を確かめる。
- インストール鍵は、本来のユーザーかマシンだけが読める場所に置く。[デバイスとプルーフ](devices-and-proofs.md)を参照。
- ベンダーが署名鍵を失効させたら、アプリの新しいバージョンをリリースする。

### 顧客の管理者

- サーバーマシンを保護する。そのマシンの root 権限を持つ人なら誰でも、サーバーの鍵を取り出せる。
- データフォルダーと管理者トークンは、サービスアカウントと管理者だけが読めるようにする。`admin.listen` はループバックのままにする（それ以外のアドレスはサーバーが拒否する）。
- 同じ製品のアプリがそのマシンで動くなら、サーバーに専用の `dataDirectory` を指定する。
- `allow` と `deny` では、IP のルールに頼る。リバースプロキシの後ろでは、IP のルールはプロキシで適用し、`rateLimit.perIp` はプロキシの後ろにあるマシンの数に合わせて引き上げる。
- `--set-aside-broken-records` は、借用の記録が壊れた原因を突き止めてから使う。このオプションを使うと、借用中のシートが空く。
- サーバーライセンスは期限が切れる前に更新する。`elm-server` と `elm` は、ダウンロードするたびに検証する。

### すべての人

脆弱性は公開の Issue には書かず、GitHub Security Advisories で報告する。手順は[SECURITY.md](https://github.com/YUKIKEDA/ElasticLM/blob/main/SECURITY.md)にある。報告には、本物の秘密鍵、ライセンストークン、顧客の識別子、マシン ID を含めないこと。

このモデルの線をここで引いた理由（難読化をしない、失効リストを持たない、待機系のサーバーを置かない）は、[設計上の選択](design-choices.md)にある。
