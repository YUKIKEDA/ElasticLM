# 却下した案

設計（[design.ja.md](./design.ja.md)）で採らなかった案と、その理由を残す。同じ形の案を再び推すときは、ここに書いた理由とどう違うかを示す（`.cursor/rules/consent.mdc`）。

各項目は「決定 / 理由 / 却下した案」の順に書く。

## 形式と方式（D0、Round 4）

2026-10-26 の Grill（Round 4）で決めた。調査の出典は [design.ja.md](./design.ja.md) の各節にある。

### トークン形式

- **決定:** JWS コンパクト形式（ES256）を、ヘッダーを `alg` / `kid` / `typ` に絞った形で使う（§8）。
- **理由:** BCL だけで実装でき、NativeAOT で問題がなく、既存の道具で中身を確かめられる。ML-DSA への道筋が RFC 9964 で標準化されている。約 300 バイトのペイロードでの大きさの差は小さく、ML-DSA の署名（3.3 KB）が入れば形式による差は意味を持たない。
- **却下した案:**
  - COSE_Sign1: `System.Security.Cryptography.Cose` と `System.Formats.Cbor` は BCL の外のパッケージで、アプリに入る部品の依存が増える。
  - PASETO v4.public: Ed25519 が要るが、.NET 10 の BCL にない。承認済みの API（dotnet/runtime#63174）も Windows と macOS では使えない形である。
  - 独自の形式: 約 5% 小さくなるだけで、相互運用性と道具を失う。

### リクエスト認証

- **決定:** インストール鍵で署名した DPoP（RFC 9449）形式の証明に、本文のハッシュを加える（§12.2）。
- **理由:** トークン形式と同じ JWS の処理を使い回せる。本文を守らない DPoP の欠けを、本文のハッシュのクレームで補える。
- **却下した案:**
  - HTTP Message Signatures（RFC 9421）: 署名対象の組み立て（構造化フィールド、RFC 8941）が複雑で、BCL だけで正しく実装する負担が大きい。プロキシとの相互運用が要件にない。
  - 共有秘密（HMAC）: 前身の項を参照。

### 管理画面のログイン

- **決定:** BFF（§15.3）。
- **理由:** RFC 10017 が業務アプリに強く勧める。ブラウザにトークンを置かないため、XSS で盗まれるものがない。
- **却下した案:** ブラウザがアクセストークンを持つ SPA（認可コードと PKCE をブラウザで行い、JwtBearer で検証する）。NativeAOT では確実に動くが、RFC 10017 で最も弱い形とされる。

### SQLite の単一バイナリ化

- **決定:** `vendor/sqlite/` で版とハッシュを固定し、静的ライブラリにビルドして組み込む（§14.2）。
- **理由:** 単一バイナリ（0.1）を守りつつ、出所の分かる SQLite を使える。
- **却下した案:**
  - `SQLitePCLRaw.bundle_e_sqlite3` のまま `e_sqlite3` を横に置く: 単一バイナリを破る。
  - `StaticLink.e_sqlite3`: 所有者が 1 人で、ダウンロードが約 600 件と少なく、供給網を信頼できない。

### 端末の識別子

- **決定:** インストール鍵を識別子とし、OS のマシン ID はアプリごとにハッシュした補助の手がかりにする（§10）。
- **理由:** OS のマシン ID は、一般化しない VM の複製や空でないイメージで重なり、管理者が書き換えられる。生の値を送ると製品をまたいで端末を追跡できてしまう。
- **却下した案:** OS のマシン ID の生の値を識別子にする（前身の設計と 0.7 の当初の書き方）。

### ライセンスファイルの暗号化

- **決定:** 署名だけで、暗号化しない。
- **理由:** 端末への紐づけは署名した `cnf` と `fp` で守れる。復号の鍵はクライアントに置くしかないため、暗号化しても中身を隠す効果はほとんどない。
- **却下した案:** Keygen のように、ライセンスキーとマシン指紋から作る鍵で AES-256-GCM により暗号化する（https://keygen.sh/docs/api/cryptography/ ）。

### 鍵の階層

- **決定:** ルート鍵がオフラインで署名鍵の証明書に署名し、アプリはルート鍵だけを信じる（§7.1）。
- **理由:** 署名鍵の入れ替えと、漏えいからの回復を、アプリの更新なしで行える。
- **却下した案:** 署名鍵の公開鍵をアプリに直接埋め込む（Keygen の方式）。鍵を入れ替えるたびにアプリの更新が要る。

### オンプレミスのサーバーの状態の回復

- **決定:** 再起動の後、回収の時間のあいだ新しい貸出を止め、クライアントの申告で状態を戻す（§13.4）。
- **理由:** データベースを持たない（0.6）まま、再起動で席が二重に貸されることを防げる。FlexNet でネットワークの切断の後に二重に数えられる問題が報告されている。
- **却下した案:** 再起動の直後から新しい貸出を受け付ける。前の貸出と合わせて席数を超える。

## 設計のレビューで決めたこと（D0、Round 5）

2026-10-26 に D0 の設計を独立にレビューし、持ち主が Round 5 で決めた。

### サーバーライセンスの期限

- **決定:** 期限を持たせ（既定 30 日）、サービスから更新させ、更新で複製を検出する（[design.ja.md](./design.ja.md) 0.37）。
- **理由:** 利用者の管理者はサーバーの鍵を取り出せ、サーバーの端末も複製できる。期限と更新がなければ、どちらも永久に検出できない。
- **却下した案:** 期限の長いサーバーライセンスで、鍵の取り出しと複製をすべて受け入れる。

### 再起動での借り出しの扱い

- **決定:** 借り出しだけを署名つきの追記の記録に残す（0.38）。
- **理由:** 借り出した端末は回収を送れないため、記録がなければ再起動のたびに席が増える。
- **却下した案:** 受け入れて、オンプレミスでの借り出しをベンダーが止められるようにする。借り出しという要件（0.21）をオンプレミスで欠くことになる。

### 鍵の証明書の期限の判定

- **決定:** トークンの `iat` の時点で判定し、漏れた鍵はトラストストアの無効の一覧で止める（0.39）。
- **理由:** 現在の時刻で判定すると、期限なしのライセンス（0.17）が証明書の期限（最長 2 年）で使えなくなる。
- **却下した案:** 現在の時刻で判定し、期限なしのライセンスを 2 年以内に発行し直す運用にする。

### 借り出しの早期返却

- **決定:** 認め、回数をポリシーで絞る（0.40）。
- **理由:** 予定より早く戻った利用者が席を返せないと、席が無駄になる。
- **却下した案:** 早期返却を禁止する。返却の前にトークンを写して戻す使い回しは防げるが、正当な返却もできなくなる。

### 複製の検出の方法

- **決定:** 更新番号の巻き戻りだけで検出し、1 つ前の番号の再試行は冪等に扱う（§10.4）。
- **理由:** 応答が届かなかった再試行を複製と誤ると、正当な利用者を止めてしまう。
- **却下した案:** 同じ有効化からの同時の利用で検出する。同じ端末の複数のプロセスが同じインストール鍵を使う正当な場合と区別できない。

### 管理画面の Cookie の `SameSite`

- **決定:** `Lax` と、状態を変える API の独自ヘッダー（§15.3）。
- **理由:** `Strict` では、IdP からの戻りの後の最初の画面で Cookie が送られない。
- **却下した案:** `SameSite=Strict`。

## 前身の実装から引き継がないもの

前身の `_ElasticLM`（2025-06〜08）と `_ElasticLM2`（2025-08）は、どちらも FlexLM 風のフローティングライセンスサーバーだった。2026-10-26 にコードを調べ、次の形を引き継がないと決めた。コードも流用しない。

### 共有の対称鍵（HMAC）によるリクエスト認証

- **決定:** クライアントとサーバーの間で、全クライアントが同じ秘密を持つ方式は使わない。
- **理由:** 秘密が全クライアントのバイナリに入るため、一つのバイナリから取り出せば誰でもリクエストを偽造できる。さらに前身の実装は、クライアントが別に送る「正規化した文字列」の HMAC だけを検証し、その文字列が実際のリクエストの中身と一致するかを見ていなかった。ノンスも時刻もないため、一度盗聴した組で任意の機能・席数を何度でも借りられた。
- **却下した案:** `elasticlm-secrets`（Rust）／`ElasticLM.Secrets`（C#）による埋め込み HMAC 鍵。鍵が無いときに開発用の固定鍵へ黙って切り替える処理を含む。

### 秘密鍵を生成ツールの実行ファイルに埋め込む

- **決定:** 署名用の秘密鍵はリソースや定数として実行ファイルに入れない。運用者が指定する場所（ファイル、環境変数、鍵管理サービス）から読む。
- **理由:** 実行ファイルを持つ人なら誰でもライセンスを作れてしまう。鍵を入れ替えるたびに再ビルドも要る。
- **却下した案:** `EmbeddedKeys/rsa_private_key.der` を `EmbeddedResource` にする構成。

### 署名のために JSON を再シリアライズする

- **決定:** 署名と検証は、運ばれるバイト列そのものに対して行う。
- **理由:** 前身の実装は `integrity` を除いたオブジェクトを再シリアライズし、その結果に署名していた。シリアライザの書式（インデント、日付の表現）が変わると、正しいライセンスが検証に失敗する。RFC 8785 のような正規化も行っていなかった。
- **却下した案:** `JsonCanonicalizer`（匿名型やソース生成コンテキストで再シリアライズする方式）。

### gRPC（HTTP/2 平文）

- **決定:** クライアントとサーバーの通信に gRPC は使わない。HTTPS と JSON にする（[design.ja.md](./design.ja.md) §12）。
- **理由:** 前身の実装は TLS なしの h2c で、待ち受けが localhost に固定され、他の端末から届かなかった。業務エラーを `RpcException` で投げたため、proto の `success` / `error_code` も使われていなかった。gRPC は依存が重く、プロキシや社内ネットワークを通しにくい。
- **却下した案:** `Grpc.AspNetCore` と `Grpc.Net.Client`、サーバーとクライアントへの `license.proto` の重複コピー。

### EF Core を載せる

- **決定:** EF Core のような ORM は使わない。オンプレミスのサーバーは状態をメモリに持ち（0.6）、SaaS 型のサービスは SQL を AuraORM（クエリビルダー）で組み立てて SQLite と PostgreSQL を使う（[design.ja.md](./design.ja.md) §14.2、0.81）。
- **理由:** 前身の実装は EF Core を接続の取得にしか使っておらず、SQL は手書きだった。マイグレーションが消えていて新しい環境では表が作られず、AOT での動作も確かめていなかった。席の貸出は「全セッションを読んでメモリで変え、全行を消して入れ直す」実装で、ロックがなく、同時に借りると席数を超えた。
- **却下した案:** `Microsoft.EntityFrameworkCore.Sqlite` と、コンパイル済みモデル（使われていなかった）。

### 複数言語の構成（Rust のクライアントと鍵 DLL）

- **決定:** すべて C# / .NET で書く。C / C++ から呼ぶネイティブライブラリが要るときは、NativeAOT の共有ライブラリとして .NET から出す。
- **理由:** 前身の実装はサーバーが Rust の DLL を P/Invoke で読み、単一バイナリにできなかった。Rust 側の `elm_get_last_error_message` は NUL で終わらない文字列を返し、呼び出し側の解放も未定義動作だった。
- **却下した案:** `elasticlm-client`（tonic）と `elasticlm-secrets` の Rust クレート。

### .NET 8 を対象にする

- **決定:** 対象は `net10.0` だけにする。
- **理由:** .NET 8 のサポートは 2026-11-10 に終わる。NativeAOT と ASP.NET Core の AOT 対応は .NET 10 のほうが進んでいる。
- **却下した案:** `net8.0` と `net10.0` の両方を対象にする。

### プロセスに 1 つのフローティングライセンス（M3b の Grill）

- **決定:** .NET のクライアントは、C ABI と同じ形の `LicenseClient` と、機能ごとの `Lease` を持つ（[design.ja.md](./design.ja.md) 0.42）。
- **理由:** リースの要求は `feature` と `count` を持つ（§12.7.1）。1 つのアプリが複数の機能を別々に借りられないと、この形を使えない。
- **却下した案:** Cryptlex の `LexFloatClient` の形（`SetHostUrl`、`RequestFloatingLicense`、`DropFloatingLicense`、`uint32` の状態を渡すコールバック。https://github.com/cryptlex/lexfloatclient-go/blob/master/lexfloatclient/LexFloatClient.h ）。

### 複製を見つけたリースを消して席を空ける（M3b の Grill）

- **決定:** `deny` のときは、止めたリースを期限まで残し、更新・回収・返却を断る（0.43, §10.4）。
- **理由:** リースを消すと、もう一方の写しが手元の正しいトークンで回収し直せる。止めたまま残せば、どちらの写しも期限で席を失う。
- **却下した案:** 検出したリースを消して席を空ける。オンプレミスでは常に `deny` にする（ベンダーが `flag` を選んだ意図が届かない）。

### リースを 1 件ずつ回収する（M3b の Grill）

- **決定:** 1 回の要求で 64 件までのトークンを回収し、リースごとの結果を返す（0.44, §13.4）。
- **理由:** 再起動はすべてのリースに同時に影響する。1 件ずつだと、再起動の直後に、リースの数だけ要求と証明の検証がサーバーに集まる。
- **却下した案:** 1 件ずつ回収し、新しいトークンを返す。

### アプリの設定で TLS の方式を選ぶ（M3b の Grill）

- **決定:** OS の検証に通るか、ピンした `cnf.jkt` の鍵であれば受け入れる（0.45, §13.5）。
- **理由:** TLS の方式はサーバーの管理者が決めることで、アプリの開発者は知らない。正しい証明書を持つ別のサーバーにつながっても、リースは `cnf.jkt` の鍵でしか検証に通らない。
- **却下した案:** クライアントの設定で「運用者の証明書」か「自己署名」かを明示させる。

### BCL と ASP.NET Core の頻度の制限器（M3b の Grill）

- **決定:** `TimeProvider` で動く IP ごとのトークンバケットを `elm-server` に持つ（0.46, §13.8）。
- **理由:** `System.Threading.RateLimiting` と `Microsoft.AspNetCore.RateLimiting` は `TimeProvider` を受け取らず（https://github.com/dotnet/runtime/issues/106447 、.NET 10 で未対応）、偽の時計でテストできない。時刻は `TimeProvider` から読む規則（`.cursor/rules/security.mdc`）にも合わない。
- **却下した案:** ASP.NET Core の `AddRateLimiter` と `PartitionedRateLimiter`。

### 1 小さい `seq` をいつでも再試行とみなす（M3b の設計のレビュー）

- **決定:** 1 小さい `seq` に同じトークンを返すのは、再試行が、そのトークンを出した要求の `jti` を名指したときだけにする（[design.ja.md](./design.ja.md) 0.47, §10.4）。
- **理由:** D0 の規則では、タイマーまで複製された 2 つの VM が同じ時刻に更新すると、後の写しはいつも「1 小さい再試行」として同じトークンを受け取り、1 席を分け合っても検出されない。もう一方の写しの要求の `jti` は、その写しの外からは知りようがない。
- **却下した案:** 発行から短い時間（例えば 60 秒）だけ再試行を認める（同じタイマーの写しはその時間内に来る）。限界として受け入れる。

### オンプレミスで早期返却の回数を固定する（M3c の Grill）

- **決定:** サーバーライセンスに必須の `brl` を持たせ、ポリシーの `BorrowReturnLimit` を運ぶ（[design.ja.md](./design.ja.md) 0.48）。
- **理由:** 早期返却を許すかどうかと回数は、ベンダーの決めることである。FlexNet もベンダーが早期返却を禁じられる（FLEXnet Licensing End User Guide v10.8、`lmborrow -return` の節）。
- **却下した案:** オンプレミスでは 2 回に固定する。

### 借り出しの保存をアプリに任せる（M3c の Grill）

- **決定:** `LicenseClient` が借り出しを、確かめに要るサーバーライセンスと公開鍵とともに保存し、オフラインで読み込んで確かめる（0.49）。
- **理由:** 借り出しは、ネットワークのない再起動の後に使えて意味がある。アプリごとに保存と検証を書くと、確かめ方の誤りが起きやすい。FlexNet（Windows はレジストリ、Unix は `$HOME/.flexlmborrow`）も RLM（RLM のディレクトリ）も、クライアントの側で保存して自動で使う。
- **却下した案:** トークンを返すだけにし、保存と再検証をアプリに任せる。

### 管理 API を HTTPS でほかの端末からも使う（M3c の Grill）

- **決定:** ループバックだけの HTTP と管理者トークンにする（0.50）。
- **理由:** §13.7 の要件は同じ端末からの管理で、ほかの端末からの管理は v1 の範囲外である。FlexNet の `lmgrd -local` も管理の操作を同じ端末に限れる。
- **却下した案:** RLM の管理画面（v16 から自己署名の HTTPS とログイン）のように、ほかの端末から HTTPS で管理する。

### 壊れた借り出しの記録を手で消す（M3c の Grill）

- **決定:** `elm-server --set-aside-broken-records` が壊れたファイルを退け、`chain.reset` と利用ログの `records.set_aside` を残して起動する（0.52）。
- **理由:** 何が起きたかが記録に残り、退けたファイルは調べられる形で残る。
- **却下した案:** 管理者が手でファイルを消す。

### すでにある端末の範囲のフォルダーの ACL を張り直す（M3c の設計のレビュー）

- **決定:** 鍵を書く前と読む前にフォルダーと親の所有者と ACL を確かめ、ほかの利用者が読めるか置き換えられるなら止める（[design.ja.md](./design.ja.md) 0.53）。
- **理由:** ほかの利用者が先に作ったフォルダーには、その利用者が置いた管理者トークンや鍵がありうる。ACL を張り直しても、それを信じてしまう。
- **却下した案:** 起動のたびに ACL を自動で張り直す。

### 管理者による借り出しの強制返却を数える（M3c の設計のレビュー）

- **決定:** 管理者は借り出しを返却できない（0.56）。
- **理由:** 管理者がいつでも席を空けられると、早期返却の回数の上限が効かない。借り出しはクライアントの早期返却か期限でだけ終わる。
- **却下した案:** 強制返却を許し、30 日の早期返却の回数に数える。

### 早期返却の回数の抜け道を受け入れる（M3c の設計のレビュー）

- **決定:** インストール鍵ごとと、マシン指紋ごとに数える（0.57）。
- **理由:** インストール鍵は作り直せるため、鍵だけで数えると、同じ端末で鍵を替えて何度でも数え直せる。試用の 1 台 1 回（T11）と同じ手がかりを使う。
- **却下した案:** 抜け道として §5.4 に書いて受け入れる。

### 管理 API の認証の失敗に頻度の制限だけを付ける（M3c の設計のレビュー）

- **決定:** 認証の失敗と `lease.denied` は、1 分ごとに種類ごとの件数を書く（0.58）。
- **理由:** 頻度の制限だけでは、制限の内側の要求で利用ログが増え続ける。件数にまとめれば、行の増え方は要求の数でなく種類の数で決まる。
- **却下した案:** 頻度の制限を足し、失敗は 1 行ずつ書く。

### M4 を 1 行で進める（M4 の Grill）

- **決定:** M4a〜M4d の 4 行に分ける（[design.ja.md](./design.ja.md) 0.61）。
- **理由:** 1 行では 1 つの PR が M3 の 3 つ分の大きさになり、レビューと計測がしにくい。M3 を 3 行に分けた形で、PR ごとのレビューが設計の食い違いを見つけた。
- **却下した案:** M4 を 1 行のまま進める。

### 最初の API キーを環境変数で渡す（M4 の Grill）

- **決定:** `elm-service setup` がホストで最初のキーを作る（0.63）。
- **理由:** 環境変数で渡すと、管理者の秘密がプロセスの環境に残り続ける。
- **却下した案:** 初期の API キーを環境変数で渡し、起動時にハッシュして登録する。

### SQLite のビルド済みの静的ライブラリを置く（M4a の Grill）

- **決定:** アマルガムからビルドのたびに作る（[design.ja.md](./design.ja.md) 0.72）。
- **理由:** ビルド済みのライブラリは、中身を確かめられないバイナリをリポジトリに入れることになる。NativeAOT が同じ C の道具をすでに求めるので、ビルドしても新しい道具は要らない。
- **却下した案:** 各 OS 向けのビルド済みの静的ライブラリをリポジトリに置く。

### SQL を手で書き、`DbConnection` の薄い層で両方のデータベースを扱う（M4a1 のレビュー）

- **決定:** AuraORM で SQL を組み立てる（[design.ja.md](./design.ja.md) 0.81）。
- **理由:** 手書きの SQL は、列の名前や値の型の誤りがテストを流すまで分からず、ID とバイト列の持ち方（SQLite の文字列と PostgreSQL の `uuid` など）を読み書きのたびに手で切り替える必要があった。AuraORM はそれをコンパイルの誤りにし、SQL の形は手書きと同じに保つ。NativeAOT で警告がなく、実行時の依存もない。行のロック（`FOR UPDATE`）は持たないが、自分自身への `UPDATE ... RETURNING` で同じロックを取れる。
- **却下した案:** M4a1 の最初の版の、手書きの SQL と `DbConnection` の上の薄い層。

### 管理 API を JSON:API の形にする（M4a の Grill）

- **決定:** `elm-server` と同じ素の JSON にする（0.73）。
- **理由:** JSON:API は包みが深く、ソース生成の JSON で扱う型が増える。管理 API の呼び出し元（販売システム、CI、`elm`）に、その形の利点は要らない。
- **却下した案:** Keygen と同じ JSON:API の形にする。

### M4a2 を 1 行のまま進める（M4a2 の Grill）

- **決定:** M4a2 と M4a3 に分ける（[design.ja.md](./design.ja.md) 0.82）。
- **理由:** エンドポイントが約 20 本で、M4a1 の約 3 倍になる。M4a1 の PR でもレビューの往復が多かった。
- **却下した案:** 製品・機能・ポリシー・ライセンス・署名鍵の状態・`Unbound` のファイルを 1 行で作る。

### ポリシーの期間を ISO 8601 で書く（M4a2 の Grill）

- **決定:** 期間は秒の整数にする（0.84）。
- **理由:** ISO 8601 の期間（`P30D`）は自前の解析が要り、トークンの期間のクレーム（`grace`、`lease` など）も秒である。
- **却下した案:** `"tokenLifetime": "P30D"` の形。

### `Unbound` のライセンスファイルを `TokenLifetime` で区切る（M4a2 の Grill）

- **決定:** トークンの期限はライセンスの期限と同じにする（0.86）。
- **理由:** `Unbound` にはオンラインの更新がまだなく（M4b）、短い期限は利用者に出し直しの手間を増やすだけである。渡したトークンを期限まで止められないことは §5.4 で受け入れている。
- **却下した案:** ポリシーの `TokenLifetime` を期限にし、期限ごとに出し直す。

### 製品・機能・ポリシーを消す（M4a2 の Grill）

- **決定:** 消す操作を置かない（0.87）。
- **理由:** ライセンスと発行済みのトークンが `code` で参照するので、消すと発行済みのものの意味が変わる。
- **却下した案:** 参照がなければ `DELETE` で消す。

### `PATCH` に版の検査を付ける（M4a2 の Grill）

- **決定:** 付けない。後に書いたほうが勝ち、両方が監査ログに残る（0.87）。
- **理由:** 管理者の数は少なく、同時の変更は監査ログで追える。要るなら管理画面の行（W1）で決める。
- **却下した案:** `ETag` と `If-Match` で、ほかの人の変更を上書きしない。

### 期限のないライセンスには `Unbound` のファイルを出さない（PR #51 のレビュー）

- **決定:** 出す。トークンは期限なしになり、0.17 と §5.4 の「期限なしのトークン」の範囲に足す（[design.ja.md](./design.ja.md) 0.86）。
- **理由:** 無期限の `Unbound` のライセンス（買い切りのオフラインの利用）は、ファイルを出せなければ使い道がない。期限なしのトークンを止められないのは CLI の手動発行と同じで、`elm-service` では出すたびの監査ログの行が記録になる。
- **却下した案:** 期限のないライセンスのファイルの要求を `409` と `ELM_CONFLICT` にする。
