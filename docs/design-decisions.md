# 却下した案

設計（[design.ja.md](./design.ja.md)）で採らなかった案と、その理由を残す。同じ形の案を再び推すときは、ここに書いた理由とどう違うかを示す（`.cursor/rules/consent.mdc`）。

各項目は「決定 / 理由 / 却下した案」の順に書く。

## 形式と方式（D0、Round 4）

2026-10-26 の Grill（Round 4）で決めた。調査の出典は [design.ja.md](./design.ja.md) の各節にある。

### トークン形式

- **決定:** JWS コンパクト形式（ES256）を、ヘッダーを `alg` / `kid` / `typ` に絞った形で使う（§8）。
- **理由:** BCL だけで実装でき、NativeAOT で問題がなく、既存の道具で中身を確かめられる。ML-DSA への道筋が RFC 9964 で標準化されている。約 300 バイトのペイロードでの大きさの差は小さく、ML-DSA の署名（3.3 KB）が入れば形式による差は意味を持たない。
- **却下した案:**
  - COSE_Sign1: `System.Security.Cryptography.Cose` と `System.Formats.Cbor` は BCL の外のパッケージで、アプリに入る部品の依存が増える。
  - PASETO v4.public: Ed25519 が要るが、.NET 10 の BCL にない。承認済みの API（dotnet/runtime#63174）も Windows と macOS では使えない形である。
  - 独自の形式: 約 5% 小さくなるだけで、相互運用性と道具を失う。

### リクエスト認証

- **決定:** インストール鍵で署名した DPoP（RFC 9449）形式の証明に、本文のハッシュを加える（§12.2）。
- **理由:** トークン形式と同じ JWS の処理を使い回せる。本文を守らない DPoP の欠けを、本文のハッシュのクレームで補える。
- **却下した案:**
  - HTTP Message Signatures（RFC 9421）: 署名対象の組み立て（構造化フィールド、RFC 8941）が複雑で、BCL だけで正しく実装する負担が大きい。プロキシとの相互運用が要件にない。
  - 共有秘密（HMAC）: 前身の項を参照。

### 管理画面のログイン

- **決定:** BFF（§15.3）。
- **理由:** RFC 10017 が業務アプリに強く勧める。ブラウザにトークンを置かないため、XSS で盗まれるものがない。
- **却下した案:** ブラウザがアクセストークンを持つ SPA（認可コードと PKCE をブラウザで行い、JwtBearer で検証する）。NativeAOT では確実に動くが、RFC 10017 で最も弱い形とされる。

### SQLite の単一バイナリ化

- **決定:** `vendor/sqlite/` で版とハッシュを固定し、静的ライブラリにビルドして組み込む（§14.2）。
- **理由:** 単一バイナリ（0.1）を守りつつ、出所の分かる SQLite を使える。
- **却下した案:**
  - `SQLitePCLRaw.bundle_e_sqlite3` のまま `e_sqlite3` を横に置く: 単一バイナリを破る。
  - `StaticLink.e_sqlite3`: 所有者が 1 人で、ダウンロードが約 600 件と少なく、供給網を信頼できない。

### 端末の識別子

- **決定:** インストール鍵を識別子とし、OS のマシン ID はアプリごとにハッシュした補助の手がかりにする（§10）。
- **理由:** OS のマシン ID は、一般化しない VM の複製や空でないイメージで重なり、管理者が書き換えられる。生の値を送ると製品をまたいで端末を追跡できてしまう。
- **却下した案:** OS のマシン ID の生の値を識別子にする（前身の設計と 0.7 の当初の書き方）。

### ライセンスファイルの暗号化

- **決定:** 署名だけで、暗号化しない。
- **理由:** 端末への紐づけは署名した `cnf` と `fp` で守れる。復号の鍵はクライアントに置くしかないため、暗号化しても中身を隠す効果はほとんどない。
- **却下した案:** Keygen のように、ライセンスキーとマシン指紋から作る鍵で AES-256-GCM により暗号化する（https://keygen.sh/docs/api/cryptography/ ）。

### 鍵の階層

- **決定:** ルート鍵がオフラインで署名鍵の証明書に署名し、アプリはルート鍵だけを信じる（§7.1）。
- **理由:** 署名鍵の入れ替えと、漏えいからの回復を、アプリの更新なしで行える。
- **却下した案:** 署名鍵の公開鍵をアプリに直接埋め込む（Keygen の方式）。鍵を入れ替えるたびにアプリの更新が要る。

### オンプレミスのサーバーの状態の回復

- **決定:** 再起動の後、回収の時間のあいだ新しい貸出を止め、クライアントの申告で状態を戻す（§13.4）。
- **理由:** データベースを持たない（0.6）まま、再起動で席が二重に貸されることを防げる。FlexNet でネットワークの切断の後に二重に数えられる問題が報告されている。
- **却下した案:** 再起動の直後から新しい貸出を受け付ける。前の貸出と合わせて席数を超える。

## 設計のレビューで決めたこと（D0、Round 5）

2026-10-26 に D0 の設計を独立にレビューし、持ち主が Round 5 で決めた。

### サーバーライセンスの期限

- **決定:** 期限を持たせ（既定 30 日）、サービスから更新させ、更新で複製を検出する（[design.ja.md](./design.ja.md) 0.37）。
- **理由:** 利用者の管理者はサーバーの鍵を取り出せ、サーバーの端末も複製できる。期限と更新がなければ、どちらも永久に検出できない。
- **却下した案:** 期限の長いサーバーライセンスで、鍵の取り出しと複製をすべて受け入れる。

### 再起動での借り出しの扱い

- **決定:** 借り出しだけを署名つきの追記の記録に残す（0.38）。
- **理由:** 借り出した端末は回収を送れないため、記録がなければ再起動のたびに席が増える。
- **却下した案:** 受け入れて、オンプレミスでの借り出しをベンダーが止められるようにする。借り出しという要件（0.21）をオンプレミスで欠くことになる。

### 鍵の証明書の期限の判定

- **決定:** トークンの `iat` の時点で判定し、漏れた鍵はトラストストアの無効の一覧で止める（0.39）。
- **理由:** 現在の時刻で判定すると、期限なしのライセンス（0.17）が証明書の期限（最長 2 年）で使えなくなる。
- **却下した案:** 現在の時刻で判定し、期限なしのライセンスを 2 年以内に発行し直す運用にする。

### 借り出しの早期返却

- **決定:** 認め、回数をポリシーで絞る（0.40）。
- **理由:** 予定より早く戻った利用者が席を返せないと、席が無駄になる。
- **却下した案:** 早期返却を禁止する。返却の前にトークンを写して戻す使い回しは防げるが、正当な返却もできなくなる。

### 複製の検出の方法

- **決定:** 更新番号の巻き戻りだけで検出し、1 つ前の番号の再試行は冪等に扱う（§10.4）。
- **理由:** 応答が届かなかった再試行を複製と誤ると、正当な利用者を止めてしまう。
- **却下した案:** 同じ有効化からの同時の利用で検出する。同じ端末の複数のプロセスが同じインストール鍵を使う正当な場合と区別できない。

### 管理画面の Cookie の `SameSite`

- **決定:** `Lax` と、状態を変える API の独自ヘッダー（§15.3）。
- **理由:** `Strict` では、IdP からの戻りの後の最初の画面で Cookie が送られない。
- **却下した案:** `SameSite=Strict`。

## 前身の実装から引き継がないもの

前身の `_ElasticLM`（2025-06〜08）と `_ElasticLM2`（2025-08）は、どちらも FlexLM 風のフローティングライセンスサーバーだった。2026-10-26 にコードを調べ、次の形を引き継がないと決めた。コードも流用しない。

### 共有の対称鍵（HMAC）によるリクエスト認証

- **決定:** クライアントとサーバーの間で、全クライアントが同じ秘密を持つ方式は使わない。
- **理由:** 秘密が全クライアントのバイナリに入るため、一つのバイナリから取り出せば誰でもリクエストを偽造できる。さらに前身の実装は、クライアントが別に送る「正規化した文字列」の HMAC だけを検証し、その文字列が実際のリクエストの中身と一致するかを見ていなかった。ノンスも時刻もないため、一度盗聴した組で任意の機能・席数を何度でも借りられた。
- **却下した案:** `elasticlm-secrets`（Rust）／`ElasticLM.Secrets`（C#）による埋め込み HMAC 鍵。鍵が無いときに開発用の固定鍵へ黙って切り替える処理を含む。

### 秘密鍵を生成ツールの実行ファイルに埋め込む

- **決定:** 署名用の秘密鍵はリソースや定数として実行ファイルに入れない。運用者が指定する場所（ファイル、環境変数、鍵管理サービス）から読む。
- **理由:** 実行ファイルを持つ人なら誰でもライセンスを作れてしまう。鍵を入れ替えるたびに再ビルドも要る。
- **却下した案:** `EmbeddedKeys/rsa_private_key.der` を `EmbeddedResource` にする構成。

### 署名のために JSON を再シリアライズする

- **決定:** 署名と検証は、運ばれるバイト列そのものに対して行う。
- **理由:** 前身の実装は `integrity` を除いたオブジェクトを再シリアライズし、その結果に署名していた。シリアライザの書式（インデント、日付の表現）が変わると、正しいライセンスが検証に失敗する。RFC 8785 のような正規化も行っていなかった。
- **却下した案:** `JsonCanonicalizer`（匿名型やソース生成コンテキストで再シリアライズする方式）。

### gRPC（HTTP/2 平文）

- **決定:** クライアントとサーバーの通信に gRPC は使わない。HTTPS と JSON にする（[design.ja.md](./design.ja.md) §12）。
- **理由:** 前身の実装は TLS なしの h2c で、待ち受けが localhost に固定され、他の端末から届かなかった。業務エラーを `RpcException` で投げたため、proto の `success` / `error_code` も使われていなかった。gRPC は依存が重く、プロキシや社内ネットワークを通しにくい。
- **却下した案:** `Grpc.AspNetCore` と `Grpc.Net.Client`、サーバーとクライアントへの `license.proto` の重複コピー。

### EF Core を載せる

- **決定:** EF Core のような ORM は使わない。オンプレミスのサーバーは状態をメモリに持ち（0.6）、SaaS 型のサービスは SQL を AuraORM（クエリビルダー）で組み立てて SQLite と PostgreSQL を使う（[design.ja.md](./design.ja.md) §14.2、0.81）。
- **理由:** 前身の実装は EF Core を接続の取得にしか使っておらず、SQL は手書きだった。マイグレーションが消えていて新しい環境では表が作られず、AOT での動作も確かめていなかった。席の貸出は「全セッションを読んでメモリで変え、全行を消して入れ直す」実装で、ロックがなく、同時に借りると席数を超えた。
- **却下した案:** `Microsoft.EntityFrameworkCore.Sqlite` と、コンパイル済みモデル（使われていなかった）。

### 複数言語の構成（Rust のクライアントと鍵 DLL）

- **決定:** すべて C# / .NET で書く。C / C++ から呼ぶネイティブライブラリが要るときは、NativeAOT の共有ライブラリとして .NET から出す。
- **理由:** 前身の実装はサーバーが Rust の DLL を P/Invoke で読み、単一バイナリにできなかった。Rust 側の `elm_get_last_error_message` は NUL で終わらない文字列を返し、呼び出し側の解放も未定義動作だった。
- **却下した案:** `elasticlm-client`（tonic）と `elasticlm-secrets` の Rust クレート。

### .NET 8 を対象にする

- **決定:** 対象は `net10.0` だけにする。
- **理由:** .NET 8 のサポートは 2026-11-10 に終わる。NativeAOT と ASP.NET Core の AOT 対応は .NET 10 のほうが進んでいる。
- **却下した案:** `net8.0` と `net10.0` の両方を対象にする。

### プロセスに 1 つのフローティングライセンス（M3b の Grill）

- **決定:** .NET のクライアントは、C ABI と同じ形の `LicenseClient` と、機能ごとの `Lease` を持つ（[design.ja.md](./design.ja.md) 0.42）。
- **理由:** リースの要求は `feature` と `count` を持つ（§12.7.1）。1 つのアプリが複数の機能を別々に借りられないと、この形を使えない。
- **却下した案:** Cryptlex の `LexFloatClient` の形（`SetHostUrl`、`RequestFloatingLicense`、`DropFloatingLicense`、`uint32` の状態を渡すコールバック。https://github.com/cryptlex/lexfloatclient-go/blob/master/lexfloatclient/LexFloatClient.h ）。

### 複製を見つけたリースを消して席を空ける（M3b の Grill）

- **決定:** `deny` のときは、止めたリースを期限まで残し、更新・回収・返却を断る（0.43, §10.4）。
- **理由:** リースを消すと、もう一方の写しが手元の正しいトークンで回収し直せる。止めたまま残せば、どちらの写しも期限で席を失う。
- **却下した案:** 検出したリースを消して席を空ける。オンプレミスでは常に `deny` にする（ベンダーが `flag` を選んだ意図が届かない）。

### リースを 1 件ずつ回収する（M3b の Grill）

- **決定:** 1 回の要求で 64 件までのトークンを回収し、リースごとの結果を返す（0.44, §13.4）。
- **理由:** 再起動はすべてのリースに同時に影響する。1 件ずつだと、再起動の直後に、リースの数だけ要求と証明の検証がサーバーに集まる。
- **却下した案:** 1 件ずつ回収し、新しいトークンを返す。

### アプリの設定で TLS の方式を選ぶ（M3b の Grill）

- **決定:** OS の検証に通るか、ピンした `cnf.jkt` の鍵であれば受け入れる（0.45, §13.5）。
- **理由:** TLS の方式はサーバーの管理者が決めることで、アプリの開発者は知らない。正しい証明書を持つ別のサーバーにつながっても、リースは `cnf.jkt` の鍵でしか検証に通らない。
- **却下した案:** クライアントの設定で「運用者の証明書」か「自己署名」かを明示させる。

### BCL と ASP.NET Core の頻度の制限器（M3b の Grill）

- **決定:** `TimeProvider` で動く IP ごとのトークンバケットを `elm-server` に持つ（0.46, §13.8）。
- **理由:** `System.Threading.RateLimiting` と `Microsoft.AspNetCore.RateLimiting` は `TimeProvider` を受け取らず（https://github.com/dotnet/runtime/issues/106447 、.NET 10 で未対応）、偽の時計でテストできない。時刻は `TimeProvider` から読む規則（`.cursor/rules/security.mdc`）にも合わない。
- **却下した案:** ASP.NET Core の `AddRateLimiter` と `PartitionedRateLimiter`。

### 1 小さい `seq` をいつでも再試行とみなす（M3b の設計のレビュー）

- **決定:** 1 小さい `seq` に同じトークンを返すのは、再試行が、そのトークンを出した要求の `jti` を名指したときだけにする（[design.ja.md](./design.ja.md) 0.47, §10.4）。
- **理由:** D0 の規則では、タイマーまで複製された 2 つの VM が同じ時刻に更新すると、後の写しはいつも「1 小さい再試行」として同じトークンを受け取り、1 席を分け合っても検出されない。もう一方の写しの要求の `jti` は、その写しの外からは知りようがない。
- **却下した案:** 発行から短い時間（例えば 60 秒）だけ再試行を認める（同じタイマーの写しはその時間内に来る）。限界として受け入れる。

### オンプレミスで早期返却の回数を固定する（M3c の Grill）

- **決定:** サーバーライセンスに必須の `brl` を持たせ、ポリシーの `BorrowReturnLimit` を運ぶ（[design.ja.md](./design.ja.md) 0.48）。
- **理由:** 早期返却を許すかどうかと回数は、ベンダーの決めることである。FlexNet もベンダーが早期返却を禁じられる（FLEXnet Licensing End User Guide v10.8、`lmborrow -return` の節）。
- **却下した案:** オンプレミスでは 2 回に固定する。

### 借り出しの保存をアプリに任せる（M3c の Grill）

- **決定:** `LicenseClient` が借り出しを、確かめに要るサーバーライセンスと公開鍵とともに保存し、オフラインで読み込んで確かめる（0.49）。
- **理由:** 借り出しは、ネットワークのない再起動の後に使えて意味がある。アプリごとに保存と検証を書くと、確かめ方の誤りが起きやすい。FlexNet（Windows はレジストリ、Unix は `$HOME/.flexlmborrow`）も RLM（RLM のディレクトリ）も、クライアントの側で保存して自動で使う。
- **却下した案:** トークンを返すだけにし、保存と再検証をアプリに任せる。

### 管理 API を HTTPS でほかの端末からも使う（M3c の Grill）

- **決定:** ループバックだけの HTTP と管理者トークンにする（0.50）。
- **理由:** §13.7 の要件は同じ端末からの管理で、ほかの端末からの管理は v1 の範囲外である。FlexNet の `lmgrd -local` も管理の操作を同じ端末に限れる。
- **却下した案:** RLM の管理画面（v16 から自己署名の HTTPS とログイン）のように、ほかの端末から HTTPS で管理する。

### 壊れた借り出しの記録を手で消す（M3c の Grill）

- **決定:** `elm-server --set-aside-broken-records` が壊れたファイルを退け、`chain.reset` と利用ログの `records.set_aside` を残して起動する（0.52）。
- **理由:** 何が起きたかが記録に残り、退けたファイルは調べられる形で残る。
- **却下した案:** 管理者が手でファイルを消す。

### すでにある端末の範囲のフォルダーの ACL を張り直す（M3c の設計のレビュー）

- **決定:** 鍵を書く前と読む前にフォルダーと親の所有者と ACL を確かめ、ほかの利用者が読めるか置き換えられるなら止める（[design.ja.md](./design.ja.md) 0.53）。
- **理由:** ほかの利用者が先に作ったフォルダーには、その利用者が置いた管理者トークンや鍵がありうる。ACL を張り直しても、それを信じてしまう。
- **却下した案:** 起動のたびに ACL を自動で張り直す。

### 管理者による借り出しの強制返却を数える（M3c の設計のレビュー）

- **決定:** 管理者は借り出しを返却できない（0.56）。
- **理由:** 管理者がいつでも席を空けられると、早期返却の回数の上限が効かない。借り出しはクライアントの早期返却か期限でだけ終わる。
- **却下した案:** 強制返却を許し、30 日の早期返却の回数に数える。

### 早期返却の回数の抜け道を受け入れる（M3c の設計のレビュー）

- **決定:** インストール鍵ごとと、マシン指紋ごとに数える（0.57）。
- **理由:** インストール鍵は作り直せるため、鍵だけで数えると、同じ端末で鍵を替えて何度でも数え直せる。試用の 1 台 1 回（T11）と同じ手がかりを使う。
- **却下した案:** 抜け道として §5.4 に書いて受け入れる。

### 管理 API の認証の失敗に頻度の制限だけを付ける（M3c の設計のレビュー）

- **決定:** 認証の失敗と `lease.denied` は、1 分ごとに種類ごとの件数を書く（0.58）。
- **理由:** 頻度の制限だけでは、制限の内側の要求で利用ログが増え続ける。件数にまとめれば、行の増え方は要求の数でなく種類の数で決まる。
- **却下した案:** 頻度の制限を足し、失敗は 1 行ずつ書く。

### SQLite のビルド済みの静的ライブラリを置く（M4a の Grill）

- **決定:** アマルガムからビルドのたびに作る（[design.ja.md](./design.ja.md) 0.72）。
- **理由:** ビルド済みのライブラリは、中身を確かめられないバイナリをリポジトリに入れることになる。NativeAOT が同じ C の道具をすでに求めるので、ビルドしても新しい道具は要らない。
- **却下した案:** 各 OS 向けのビルド済みの静的ライブラリをリポジトリに置く。

### SQL を手で書き、`DbConnection` の薄い層で両方のデータベースを扱う（M4a1 のレビュー）

- **決定:** AuraORM で SQL を組み立てる（[design.ja.md](./design.ja.md) 0.81）。
- **理由:** 手書きの SQL は、列の名前や値の型の誤りがテストを流すまで分からず、ID とバイト列の持ち方（SQLite の文字列と PostgreSQL の `uuid` など）を読み書きのたびに手で切り替える必要があった。AuraORM はそれをコンパイルの誤りにし、SQL の形は手書きと同じに保つ。NativeAOT で警告がなく、実行時の依存もない。行のロック（`FOR UPDATE`）は持たないが、自分自身への `UPDATE ... RETURNING` で同じロックを取れる。
- **却下した案:** M4a1 の最初の版の、手書きの SQL と `DbConnection` の上の薄い層。

### 管理 API を JSON:API の形にする（M4a の Grill）

- **決定:** `elm-server` と同じ素の JSON にする（0.73）。
- **理由:** JSON:API は包みが深く、ソース生成の JSON で扱う型が増える。管理 API の呼び出し元（販売システム、CI、`elm`）に、その形の利点は要らない。
- **却下した案:** Keygen と同じ JSON:API の形にする。

### M4a2 を 1 行のまま進める（M4a2 の Grill）

- **決定:** M4a2 と M4a3 に分ける（[design.ja.md](./design.ja.md) 0.82）。
- **理由:** エンドポイントが約 20 本で、M4a1 の約 3 倍になる。M4a1 の PR でもレビューの往復が多かった。
- **却下した案:** 製品・機能・ポリシー・ライセンス・署名鍵の状態・`Unbound` のファイルを 1 行で作る。

### ポリシーの期間を ISO 8601 で書く（M4a2 の Grill）

- **決定:** 期間は秒の整数にする（0.84）。
- **理由:** ISO 8601 の期間（`P30D`）は自前の解析が要り、トークンの期間のクレーム（`grace`、`lease` など）も秒である。
- **却下した案:** `"tokenLifetime": "P30D"` の形。

### `Unbound` のライセンスファイルを `TokenLifetime` で区切る（M4a2 の Grill）

- **決定:** トークンの期限はライセンスの期限と同じにする（0.86）。
- **理由:** `Unbound` にはオンラインの更新がまだなく（M4b1 で入れたのは端末に紐づく有効化だけ）、短い期限は利用者に出し直しの手間を増やすだけである。渡したトークンを期限まで止められないことは §5.4 で受け入れている。
- **却下した案:** ポリシーの `TokenLifetime` を期限にし、期限ごとに出し直す。

### 製品・機能・ポリシーを消す（M4a2 の Grill）

- **決定:** 消す操作を置かない（0.87）。
- **理由:** ライセンスと発行済みのトークンが `code` で参照するので、消すと発行済みのものの意味が変わる。
- **却下した案:** 参照がなければ `DELETE` で消す。

### `PATCH` に版の検査を付ける（M4a2 の Grill）

- **決定:** 付けない。後に書いたほうが勝ち、両方が監査ログに残る（0.87）。
- **理由:** 管理者の数は少なく、同時の変更は監査ログで追える。要るなら管理画面の行（W1）で決める。
- **却下した案:** `ETag` と `If-Match` で、ほかの人の変更を上書きしない。

### 有効化 ID をトークンのクレームにする（M4b の Grill）

- **決定:** 有効化の応答の本文 `{activationId, license}` で渡し、トークンの形式は変えない（[design.ja.md](./design.ja.md) 0.88）。
- **理由:** トークンの形式は M1 で固まり、検証器とオフラインの経路が読む。ID はクライアントが更新と解除のパスに使うだけで、検証には要らない。
- **却下した案:** `elm-license+jws` に `act` クレームを足す。

### `Unbound` のライセンスをオンラインで有効化する（M4b の Grill）

- **決定:** 受け付けない（`409` と `ELM_CONFLICT`、0.88）。`Unbound` は管理 API のファイルだけで配る（0.76）。
- **理由:** インストール鍵に結びつかない有効化は、台数も、`seq` による複製も数えられない。
- **却下した案:** 鍵なしの有効化として受け付け、ファイルを返す。

### 試用のポリシーに機能の一覧を持たせる（M4b の Grill）

- **決定:** 持たせない。試用のライセンスは、その時点の製品の機能をすべて持つ（0.88）。
- **理由:** ポリシーは機能を持たない形で M4a2 に固まった。製品の一部だけを試させたいという要件はまだない。要件が挙がれば、ポリシーに一覧を足せる。
- **却下した案:** 試用のポリシーに `features` を足す。

### 管理者の解除を `DeactivationLimit` に数える（M4b の Grill）

- **決定:** 数えない（0.88）。
- **理由:** 回数の上限は、利用者が解除と有効化を繰り返して台数を回すことを抑えるためのもので、運用の都合で管理者が外すことを縛る理由はない。
- **却下した案:** 端末と管理者の解除を同じ回数に数える。

### `Deny` で止めた有効化を `seq` を問わず解除する（M4b の Grill、M4b1 の設計のレビューで改めた）

- **決定:** 最後に出した `seq` の写しと管理者だけが解除できる（[design.ja.md](./design.ja.md) 0.88、§10.4）。
- **理由:** Grill の Round 2 では「写しのどちらも、もう一方の `seq` を知りようがない」として `seq` を問わない形にしたが、止める原因になった遅れた写しの反対側は最後の `seq` を持っている。`seq` を問わないと、遅れた写しが解除と有効化で枠を取り返し、もう一方を止め返せるので、2 つの写しが 1 台分の枠で新しいトークンを得続ける（レビューの R1）。
- **却下した案:** 止めた有効化は、鍵の証明があれば `seq` を問わず解除できる。

### 待っているオフラインの要求をファイルのまま持つ（M4c2 の Grill の 1 巡目、設計のレビューで改めた）

- **決定:** ライセンスキーを除いた中身とキーの SHA-256 だけを持ち、書き出すたびに渡されたキーで組み立て直して署名し直す（[design.ja.md](./design.ja.md) 0.91、§12.8.5）。
- **理由:** ファイルのまま持つと、ライセンスキーを `activation.json` に平文で置くことになり、「ライセンスキーは保存しない」（§12.6.2）が崩れる。期限の切れた要求も残り続ける。サービスは同じ要求かどうかを署名の対象のハッシュで見る（§12.8.4）ので、署名し直しても同じ要求である（レビューの R6）。
- **却下した案:** 要求ファイル（JWS）をそのまま `activation.json` に持つ。

### 置き換えた要求の `nonce` を次の要求の中にだけ残す（M4c2 の Grill の 1 巡目、設計のレビューで改めた）

- **決定:** その種類の答えのない要求の一覧（`pending` か `retry`）に入れ、新しいファイルを保存するまで残す（§12.8.5）。
- **理由:** 次の要求の中にだけ残すと、2 回作り直したときと、種類の違う要求に置き換えたときに、処理済みの要求の `nonce` が消え、後の要求が複製と判定される（レビューの R1, R2）。
- **却下した案:** 作り直す要求の `retry` に、前の要求の `nonce` だけを足す。

### オフラインの取り込みで時計の守りに `iat` を渡す（M4c2 の設計、レビューで改めた）

- **決定:** 渡さない（§11.4 の手順 4、§12.8.5）。
- **理由:** オフラインの応答は運ぶ間に何日も古くなりうる。渡すと「最後に確認した時刻」が戻り、その分だけ時計を戻せる（レビューの R4）。
- **却下した案:** オンラインと同じに、取り込んだトークンの `iat` で時計の守りを上書きする。

### オフラインの要求の `nonce` を一度だけ受け付ける（D0、M4c の Grill で改めた）

- **決定:** 同じ要求には残した同じ応答を返し、`nonce` が同じで中身の違う要求だけを断る（[design.ja.md](./design.ja.md) 0.90、§12.8.4）。
- **理由:** 運ぶ途中で応答ファイルをなくすことはよくある。一度だけにすると、同じ要求は渡し直せず、新しい更新の要求は「`seq` が 1 小さく `retry` がない」になって複製と判定される。
- **却下した案:** §12.8 のとおり、`nonce` を一意制約で一度だけ受け付ける。

### オフラインの出し直しを §10.4 の再試行の道で返す（M4c の Grill）

- **決定:** 応答を表 `offline_requests` に要求の期限まで残し、同じ要求にはそれを返す（0.90、§12.8.4）。
- **理由:** `nonce` を `LastProof` として覚えて再試行の道で返すと、端末がその後に先へ進んでいるとき、古い要求ファイルを出し直しただけで `seq` が 2 小さくなって複製と判定され、`Deny` なら有効化が止まる。
- **却下した案:** `nonce` を有効化の `LastProof` に入れ、同じ `nonce` の要求を §10.4 の再試行として最後のファイルで答える。

### オフラインの応答を `nonce` ごとに残す（M4c の Grill の 2 巡目、設計のレビューで改めた）

- **決定:** 有効化ごとに 1 行にし、新しく出すたびに置き換える。探すのは（`kid`, `nonce`）の組（0.90、§12.8.4）。
- **理由:** `nonce` ごとに 7 日残すと、有効化を 1 つ持つ人が認証のない入口から新しい `nonce` の更新を送り続けて、7 日で約 120 万行（最大で数十 GB）を残せる。`nonce` だけで探すと、要求ファイルを見た人が同じ `nonce` を自分の要求に使って、持ち主の要求を断らせられる（レビューの R5, R9）。
- **却下した案:** `nonce` を主キーにして、成功した要求ごとに応答を要求の期限まで残す。

### 残した応答を状態を問わずに返す（M4c1 の設計、レビューで改めた）

- **決定:** ライセンスの状態が通り、有効化がまだあって止められていないときだけ返す（§12.8.4）。
- **理由:** 応答をなくした直後にベンダーが失効させても、出し直しで最大 `TokenLifetime` の間使えるトークンを受け取れてしまう（レビューの R8）。
- **却下した案:** 同じ要求には、何も確かめずに残した応答を返す。

### 待っている要求から新しい要求を作らない（M4c の Grill の 1 巡目、設計のレビューで改めた）

- **決定:** 期限（7 日）の切れた待っている要求は捨て、最後の `seq` と、前の要求の `nonce` を入れた `retry` で新しい要求を作る（§12.8.1）。
- **理由:** 期限を過ぎた要求は必ず断られる。`seq` と `retry` のない新しい要求は、既存の有効化に対して複製と判定される（レビューの R6）。
- **却下した案:** 応答を取り込むまで、いつも同じ要求ファイルを書き出す。

### オフラインの応答をライセンスファイル（`.elmlic`）にする（M4c の Grill の 2 巡目、3 巡目で改めた）

- **決定:** 応答はオンラインと同じ発行の応答 `{"activationId", "license"}` で、拡張子は `.elmresp`（0.90、§12.8.4）。
- **理由:** トークンは有効化 ID を持たない（§12.6.1）。アプリは次の更新の要求（`act`）と解除の証明に有効化 ID が要る。
- **却下した案:** 応答をライセンスファイルそのもの（`.elmlic`）にする。

### 解除に `retry` を持たせない（M4b の Grill、M4b1 の設計のレビューで改めた）

- **決定:** 解除も `retry` を読み、応答をなくした更新の後の解除を同じ写しとして受ける（§12.6.1）。
- **理由:** `retry` がないと、更新の応答をなくした正しいクライアントの解除が複製と判定され、`Deny` で止まる（レビューの R6）。
- **却下した案:** 解除の本文を `{seq}` だけにする。

### 解除でインストール鍵を消す（D0、M4b2 の設計のレビューで改めた）

- **決定:** 解除は `activation.json` だけを消し、鍵は残す（[design.ja.md](./design.ja.md) 0.89、§12.6.2）。
- **理由:** 鍵を消しても、端末の利用者は鍵のファイルごと写せるので、残したファイルの写しを止める守りにならない。消すと、同じフォルダーの借り出しが返せなくなって席が期限まで埋まり、サーバーのピンと時計の守りの状態も鍵に結びつかなくなる（レビューの R4）。残した写しは §5.4 で受け入れる。
- **却下した案:** §12.6 のとおり、解除でライセンスファイルとインストール鍵を消す。

### 有効化があるときの別のライセンスの有効化で置き換える（M4b2 の Grill、設計のレビューで改めた）

- **決定:** 試用でない有効化があれば、手元で `ELM_INVALID_STATE` で断る。本文に `product` を足し、サービスが製品の違うキーを有効化の前に断る（0.89、§12.6.1、§12.6.2）。
- **理由:** 置き換えると、前の有効化がサービスに残って台数を使い、手元からは外せない。別の製品のキーは、サービスが有効化を作った後にクライアントが保存できず、台数だけが失われる（レビューの R2）。
- **却下した案:** 保存した `seq` と `retry` を付けて送り、成功したら置き換える（Grill の Round 2 の Q2）。

### インストール鍵の有効化を表全体で 1 つにする（M4b1 の実装）

- **決定:** ライセンスと拇印の組で一意にする（0.88、§12.6.1）。
- **理由:** Grill の Round 2 では「鍵は製品ごとに作るので、同じ鍵が 2 つのライセンスを持つことはない」として表全体で一意にすると答えたが、同じ製品の試用の後に買ったライセンスを有効化する流れで、同じ鍵が 2 つ目のライセンスを持つ。表全体で一意にすると、その有効化を断ることになる。
- **却下した案:** 拇印を表全体で一意にする。

### 期限のないライセンスには `Unbound` のファイルを出さない（PR #51 のレビュー）

- **決定:** 出す。トークンは期限なしになり、0.17 と §5.4 の「期限なしのトークン」の範囲に足す（[design.ja.md](./design.ja.md) 0.86）。
- **理由:** 無期限の `Unbound` のライセンス（買い切りのオフラインの利用）は、ファイルを出せなければ使い道がない。期限なしのトークンを止められないのは CLI の手動発行と同じで、`elm-service` では出すたびの監査ログの行が記録になる。
- **却下した案:** 期限のないライセンスのファイルの要求を `409` と `ELM_CONFLICT` にする。

### 管理画面を Preact 以外で作る（W0、Issue #94）

- **決定:** Preact 11 と TypeScript、Vite 8（Preact 用のプリセットなし）（[design.ja.md](./design.ja.md) 0.96、§15.2、[ADR 0001](./adr/0001-admin-ui-preact-pnpm.md)）。
- **理由:** 同じ試作で比べ、持ち主の希望（依存が少なく、小さく、書きやすい）に一番合った。入るパッケージは 56 個（フレームワークなしより 1 個多い）、brotli で 6,771 バイト、型は `tsc` だけで確かめられる。
- **却下した案:**
  - Svelte 5: 実行時の依存はないが、大きさが 2 倍（14,840 バイト）。リリースが 12 か月で 96 回と多く、テンプレートの型の確かめに `svelte-check` が要る。
  - Vue 3: 一番大きく（24,720 バイト）、`vue` が実行時の依存にコンパイラーの一式（25 個）を持つ。3.6 が RC。
  - SolidJS: 小さい（7,264 バイト）が、2.0 が RC で、選ぶとすぐに大きな版の移行が来る。テストに設定の追加が要った。
  - フレームワークなし: 一番小さい（1,744 バイト）が、M5 の多くの画面で状態と描き直しの仕組みを自分で作って保守することになる。
  - Preact と `@preact/preset-vite`: Babel が入り、パッケージが 124 個になる。得られるのは状態を保ったままのホットリロードだけ。
  - React、Blazor WebAssembly、htmx（W0 の Grill で、測らずに比べる前に外した）: React は Preact と同じ書き方なので、比べるのは Preact で足りる。Blazor WebAssembly は .NET のランタイムをブラウザに送る形で、0.20 が Blazor を採らないと決めている。htmx はサーバーが HTML を作る形で、§15.2 の静的な SPA と形が違う。

- **理由:** 持ち主の問いから、選んだ Preact の試作で比べた。入るパッケージも `dist` も同じで、入れる時間は 1.0–1.2 秒（npm は 8.1–9.5 秒）。依存のビルドスクリプトを既定で走らせず、公開から 1 日たたない版を入れない。

### Linux の glibc の配布物を `ubuntu-latest` で作る（F1 の設計のレビュー、Issue #149）

- **決定:** `linux-x64` と `linux-arm64` は glibc 2.28 の `almalinux:8` のコンテナで作り、glibc 2.28 以降で動くようにする（持ち主の決定。[design.ja.md](./design.ja.md) 0.109、§4.1、§20.5）。
- **理由:** NativeAOT の実行ファイルは、作った機械と同じか新しい glibc でしか動かない。`ubuntu-latest`（glibc 2.39）で作ると、RHEL 8 と 9、Debian 11 と 12、Ubuntu 22.04 では `elm-server` も `libelasticlm` も動かない。オンプレミスのサーバーは、企業の古めの Linux で動かされる。
- **却下した案:** `ubuntu-latest` のまま作る（glibc 2.39 以降）。`ubuntu-22.04` のランナーで作る（glibc 2.35 以降。RHEL 8 と 9、Debian 11 と 12 で動かない）。

### `almalinux:8` の中でランナーの PowerShell を使う（F1 の試し、Issue #149）

- **決定:** `almalinux:8` の中では PowerShell を使わない。SQLite の Linux と macOS のビルドは POSIX の `vendor/sqlite/build.sh` にし、コンテナの中の発行は `eng/release/publish-rid.sh` で行い、警告はランナーでログから数える（持ち主の決定。[design.ja.md](./design.ja.md) §20.5）。
- **理由:** arm64 のランナーの PowerShell は glibc 2.33 を要り、glibc 2.28 の中では起動しなかった（x64 は動いた）。SQLite のビルドは MSBuild から PowerShell で呼ばれていたので、PowerShell がないとビルドできない。
- **却下した案:** ランナーの PowerShell を読み取りだけでつなぐ（F1 の設計のレビューのあとの §20.5 の形）。`linux-arm64` だけ `ubuntu-22.04-arm` で作り、glibc の下限を 2.35 に上げる。

- **決定:** コンテナのレジストリの経路の脅威（T26、T27 と受け入れる脅威）は、F2 の前に別の設計の PR で脅威モデルに足す（[design.ja.md](./design.ja.md) 0.110、§5）。
- **理由:** 脅威モデルの変更は、それを守る実装より先に入れる。0.108 で、この脅威は F2 で足すと決めてあった。
- **却下した案:** F2 の PR で、脅威とイメージの仕組みを一緒に書く。

### `elm-service` のイメージでベースの `ASPNETCORE_HTTP_PORTS` を引き継ぐ（F2 の設計のレビュー、Issue #157）

- **決定:** Dockerfile でベースの `ASPNETCORE_HTTP_PORTS` を空にする（持ち主の決定。[design.ja.md](./design.ja.md) 0.111、§20.6）。ほかのベースの環境変数はそのままにする。
- **理由:** `elm-service` は `listen` だけで待ち受けるので、ASP.NET Core に別の待ち受けを知らせない。引き継いだままだと、起動のログに待ち受けの上書きの知らせが出るおそれがあった。F2 の試しと手元の `wslc` で、知らせが出ないことを確かめた。
- **却下した案:** ベースの環境変数を引き継いだままにし、設計の文だけを「イメージが足すのは `ELM_LISTEN` だけ」に直す。

### GHCR へのログインに `docker/login-action` を使う（F2 の設計のレビュー、Issue #157）

- **決定:** 公開のジョブは `docker login` の run の段で GHCR にログインし、第三者のアクションを足さない（持ち主の決定。[design.ja.md](./design.ja.md) 0.111、§20.6、§5.3 の T25）。
- **理由:** 公開のジョブは、いちばん強い権限（`contents: write`、`id-token: write`、`packages: write`、`attestations: write`）を持つ。skopeo と `actions/attest` の `push-to-registry` は、どちらも `docker login` が書く `~/.docker/config.json` を読むので、アクションは要らない。0.110 の T25 が名指ししていた `docker/login-action` は外した。
- **却下した案:** `docker/login-action` を SHA で固定して使う。

### V1 を 1 行のまま進める（V1 の Grill、Issue #173）

- **決定:** V1 を V1a（端から端までのテスト）、V1b（参照機での計測）、V1c（文書とサンプル）、V1d（安全性の見直し）、V1e（v1 の公開）の 5 行に分け、この順に進める（持ち主の決定。[design.ja.md](./design.ja.md) 0.112、§22）。

- **却下した案:** V1 を 1 つの Issue と PR で進める。

### 公開するバイナリに、テストのための時計の入口を作る（V1a の Grill、Issue #178）

- **決定:** 公開する `elm-server`・`elm-service`・`elm`・`libelasticlm` に、時計を差し替える入口（環境変数や設定）を作らない。端から端までのテストは短い期間と本当の時計で待ち、日の単位の流れは偽の時計を使うプロセスの中のテストに任せる（持ち主の決定。[design.ja.md](./design.ja.md) 0.113、§20.7）。
- **理由:** 時計を進められる入口は、利用者の端末でも期限・猶予・リースの時間をずらす道になる（§11 の時計の守りを外から外せる）。テストのためだけに公開する面を増やさない。
- **却下した案:** テストのときだけ読む時計の環境変数を足し、端から端までのテストでも時計を進める。

### 端から端までのテストを `./build.ps1` で流す（V1a の Grill、Issue #178）

- **決定:** `./build.ps1` は `tests/ElasticLM.E2E` をビルドするだけで流さない。CI の `aot` ジョブと `tests/ElasticLM.E2E/run.ps1 -Publish` が流す（持ち主の決定。[design.ja.md](./design.ja.md) 0.113）。
- **理由:** 端から端までのテストには NativeAOT の公開が要り、1 つの OS で数分かかる。毎回のゲートに入れると、コードを変えるたびの確かめが遅くなる。
- **却下した案:** `./build.ps1` で公開と E2E も流す。

### 端から端までのテストを `release.yml` の 7 つの RID で流す（V1a の Grill、Issue #178）

- **決定:** E2E は PR ごとに CI の `aot` ジョブの 3 つの OS で流し、`release.yml` の 7 つの RID では流さない（持ち主の決定。[design.ja.md](./design.ja.md) 0.113）。
- **理由:** 流れの正しさは RID によらない。RID に固有の問題（ローダー、glibc、ICU、マシン ID）は、7 つの RID で動くいまのスモークと C のテストが見つける。
- **却下した案:** `release.yml` の各 RID のビルドのジョブでも E2E を流す。

### 参照機での計測を PR ごとに動かす（V1b の Grill、Issue #182）

- **決定:** §4.2 の計測は、`workflow_dispatch` と計測に触れる PR で動くワークフロー `measure.yml` で行い、PR ごとの CI では動かさない（持ち主の決定。[design.ja.md](./design.ja.md) 0.114、§20.7）。
- **理由:** リース 10,000 件の計測だけで、起動のあとの回収の 10 分を含めて 20 分かかる。PR ごとに流すと、すべての PR の確かめが遅くなる。§4.2 に関わる PR は、その PR で手で動かす。
- **却下した案:** `ci.yml` の `aot` ジョブで、PR ごとに計測する。

### リースの負荷を `LicenseClient` で作る（V1b の設計のレビュー、Issue #182）

- **決定:** 計測の道具は、`ElasticLM.Client` の公開の部品（`InstallationKeyStore`、`ProofBuilder`）で要求を自分で作って送り、返ったリースのトークンを時間を測る範囲の外で `LeaseVerifier` で確かめる（持ち主の決定。[design.ja.md](./design.ja.md) 0.114、§20.7）。
- **理由:** `LicenseClient` はリースの更新を自分の中で行い、1 件ごとの時間を外に出さない。目標の「更新の p99」を測るには、1 件ごとの時間が要る。
- **却下した案:** Grill の Q4 のとおり、100 個の `LicenseClient` を動かす。

### メモリの目標を cgroup の `memory.peak` で比べる（V1b の設計のレビュー、Issue #182）

- **決定:** 「メモリ 200 MB 以下」は、プロセスの `VmHWM` を 200,000,000 バイトと比べる。cgroup の `memory.peak` は記録だけにする（持ち主の決定。[design.ja.md](./design.ja.md) 0.114、§20.7）。
- **理由:** `memory.peak` は、サーバーが更新のたびに書く利用ログのページキャッシュも数える。プロセスが持つメモリの目標とは違うものを含む。
- **却下した案:** cgroup の `memory.peak` を目標と比べる。

### 有効化の p99 の外れを、SQLite の `synchronous` か目標で直す（V1b の PR、Issue #182）

- **決定:** 製品も §4.2 の目標も変えない。遅い有効化とディスクの書き出しの時刻を計測に記録し、`report` の目標との比べ方はそのままにする（持ち主の決定。[design.ja.md](./design.ja.md) 0.115、§4.2、§20.7）。
- **理由:** p99 が外れた 2 つのジョブでも p50 は速いままで、記録を足して測り直すと、遅い有効化はディスクの書き出しが止まった時刻に重なった。ディスクの速いランナーでは p99 が 5〜7 ms なので、目標を緩める理由は弱い。`synchronous=NORMAL` にすると、電源が落ちたとき、応答したあとの有効化が戻りうる（https://www.sqlite.org/pragma.html#pragma_synchronous ）。端末が受け取った `seq` をサービスが失えば、複製の検出（§10.4）の前提が崩れる。
- **却下した案:** SQLite を `synchronous=NORMAL` にする。目標を p99 500 ms 以下などに緩める。

### PR でのサイトの確かめを `ci.yml` で行う（V1c の設計のレビュー、Issue #186）

### npm の依存の更新を手でだけ行う（V1c1 の Grill、Issue #190）

- **決定:** Dependabot の `npm` を `website/` と `web/admin/` に `cooldown` 付きで足し、脆弱性は CI の `pnpm audit` で確かめる（持ち主の決定。[design.ja.md](./design.ja.md) §20.7 の V1c1 の形、§5.4）。
- **理由:** pnpm 12 の lock では Dependabot の脆弱性の警告が出ないので、警告に頼れない。版の更新の PR は出せるので、更新を人の記憶に頼らずに済む。
- **却下した案:** Dependabot を足さず、依存の更新は行の作業のときに手で行う。

### タグの実行でも `pnpm audit` で落とす（V1c1 の設計のレビュー、Issue #190）

- **決定:** `release.yml` の `site` は、PR と `workflow_dispatch` の実行でだけ `pnpm audit` を流し、タグの実行では流さない（持ち主の決定。[design.ja.md](./design.ja.md) §20.7 の V1c1 の形、T28）。
- **理由:** タグのコミットは変えられず、受け入れる勧告はそのコミットの `pnpm-workspace.yaml` に書くので、マージのあとに公表された勧告はそのタグの `site` をずっと落とす。そのタグのサイトが出なくなるだけで、前のサイトは残り、読み手の守りは増えない。タグの lock はマージの前の PR で audit を通っている。
- **却下した案:** タグでも流して落とし、そのタグの文書が次の版まで出ないことを受け入れる。タグでは流すが、落とさずに警告にとどめる。

### 管理 API の API キーの渡し方（V1c3b の Grill の Q3、Issue #217）

- **却下した案:** 本文をファイルに書き、`curl` で管理 API に送る。
- **却下した案:** `elm admin request` に、キーのファイルを読む `--api-key-file` のオプションを足す。

### ノンスの秘密の作り方（V1c3b の Grill の Q4、Issue #217）

- **決定:** `elm` に、ランダムな秘密のファイルを作る小さなコマンドを足す（例: `elm secret create --out nonce.secret`）。形は V1c3d の Grill で決める（持ち主の決定。[design.ja.md](./design.ja.md) §20.7 の V1c3 の形の「V1c3b の Grill」と V1c3d の行）。

- **却下した案:** 頁に、例として決まったノンスの秘密を載せる。
- **却下した案:** シェルごとのコマンドで乱数のファイルを作る手順を、コードブロックの外の文で示す。

### `elm-server` の起動直後の待ちの長さ（V1c3b の Grill の Q5、Issue #217）

### Tutorials を公開まではソースから作る形で書く（V1c3e の Grill の方針、Issue #219）

- **決定:** 利用者の文書を、リリースした製品として書く。読み手が実際に打つとおりに、実行ファイルは GitHub の Releases の成果物から、パッケージは nuget.org から入れる形にし、CI では手順を流す仕組みが頁の外でジョブの成果物とローカルのフィードに置き換える。V1c3 の Grill の Q2（「始める前に」にソースから作る手順を書き、V1e で書き換える）、V1c3 の設計のレビューの R2 と R4（頁の `dotnet publish`、`dotnet pack`、`nuget.config`）、V1c3b の Grill の Q2（`elm-service` をソースから作る）を改める。新しい行 V1c3e を V1c3d の前に置く（持ち主の指摘と決定。[design.ja.md](./design.ja.md) §20.7 の V1c3 の形の「V1c3e の Grill」）。

- **改めた:** V1c3e の記録の途中の持ち主の決定 P1 で、頁は読み手が今手に入れられるものを書くとし、試しの期間は GitHub のプレリリースの圧縮ファイルと `.nupkg` から入れる形にした。V1c3 の設計のレビューの R4（頁の `nuget.config`）は、`feed` を `packages` にして残る。nuget.org の形への切り替えは V1e の 1 つの PR（P3）。ソースから作る手順を頁に書かないことは変わらない（下の「試しの期間の頁を nuget.org の形で書く」）。

### 成果物の名前から版を外す（V1c3e の Grill の Q2、Issue #219）

- **決定:** 頁は、GitHub の Releases の頁の最新のリリースから、自分の OS の `elm-<版>-<RID>` の圧縮ファイルを取り、展開して PATH に足すと本文で書く。展開のコマンドはシェルと OS で違うので手順のブロックにせず、確かめ方は `SECURITY.md` の節へのリンクで示す。CI では独立の行の `steps:prebuilt` の印で、ジョブが作った実行ファイルに置き換える。成果物の名前は今の `<名前>-<版>-<RID>` のまま（持ち主の決定。[design.ja.md](./design.ja.md) §20.7 の V1c3 の形の「V1c3e の Grill」）。
- **理由:** 版を外せば `/releases/latest/download/<名前>` の決まった URL で最新を取れるが、取ったファイルの名前から版が分からなくなり、`SHA256SUMS` と証明の確かめで、どの版のファイルかを名前で見られなくなる。また、GitHub の `latest` はプレリリースを除くので、`1.0.0-rc.1` のあいだは指す先がない。展開とコマンドがシェルごとに違う以上、決まった URL があっても頁は手順のブロックにできない。
- **却下した案:** 成果物の名前から版を外し、`/releases/latest/download/` の決まった URL で最新を取れるようにする。
- **改めた:** 持ち主の決定 P1 で、頁が指すのは「Pre-release」の印が付いたうちの最も新しいリリースになり、頁は GitHub の「Latest」がプレリリースを指さないことも書く（下の「試しの期間の頁を nuget.org の形で書く」）。成果物の名前と、決まった URL を使わないことは変わらない。

### 頁で版を `--version` に固定する（V1c3e の Grill の Q3、Issue #219）

- **決定:** 頁は `--version` を書かずに `dotnet add app package ElasticLM.Client` とし、最新を入れる。頁から `dotnet pack` と `nuget.config` の手順を外す。CI では、`aot` ジョブが `ElasticLM.Licensing` と `ElasticLM.Client` を pack してスクリプトに `-Feed` で渡し、スクリプトが頁の外で、`ElasticLM.*` をそのフィードに割り当てる `nuget.config` を作業フォルダーに置く（持ち主の決定。[design.ja.md](./design.ja.md) §20.7 の V1c3 の形の「V1c3e の Grill」）。
- **理由:** 版を頁に書けば、版を上げるたびにすべての頁を直すことになり、直し忘れれば CI の復元が落ちる。`--version` がなければ、読み手は公開した最新を入れ、CI では割り当てたフィードにある版（ジョブが今 pack した版）だけが選ばれるので、頁は版によらない。
- **却下した案:** 頁に `--version <版>` を書き、公開のたびに頁を直す。
- **改めた:** 持ち主の決定 P1 で、試しの期間の頁は `nuget.config`（`ElasticLM.*` を作業フォルダーの `packages` だけに割り当てる）を自分で書き、`dotnet add app package <パッケージ> --prerelease` と打つ形にした。スクリプトが頁の外で `nuget.config` を書く形はやめ、ジョブがプレリリースの版で pack したパッケージを、スクリプトが `steps:prebuilt name=packages` の印のところで `packages` に写す（下の「試しの期間の頁を nuget.org の形で書く」）。`--version` を書かないことは変わらない。

### NuGet のパッケージを GitHub Packages に置く（V1c3e の記録の途中の持ち主の決定 D1、Issue #219）

- **決定:** パッケージは、公開でも nuget.org に置く（持ち主の決定。[design.ja.md](./design.ja.md) §20.5 の「V1e で変えること」、§20.7 の V1c3 の形の「V1c3e の Grill」）。
- **理由:** GitHub Packages の NuGet の登録所は、公開のパッケージを入れるのにも personal access token（classic）を求める（「You need an access token to publish, install, and delete private, internal, and public packages.」。https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-nuget-registry ）。利用者のすべての開発者とその CI が、範囲の広い classic のトークンを持つことになる。nuget.org は、トークンなしで入れられ、`dotnet` の既定の源でもある。
- **却下した案:** NuGet のパッケージを GitHub Packages に置く。

### rc のパッケージを nuget.org に、rc のイメージを GHCR に push する（V1c3e の記録の途中の持ち主の決定 D2、Issue #219）

- **決定:** V1e から、rc のタグ（`v1.0.0-rc.N`）は、すべてのファイル（実行ファイルと `libelasticlm`、`.nupkg` と `.snupkg`、`SHA256SUMS`、来歴の証明など）を付けた GitHub のプレリリースだけを出し、nuget.org にもコンテナのレジストリにも push しない。`release.yml` の `publish` は、プレリリースの後ろのない版のタグだけで動く。rc を試す人は、プレリリースの `.nupkg` を置いたフォルダーをローカルのフィードにして入れ、その手順は `docs/releasing.md` に書く。`release.yml` と `docs/releasing.md` の変更は V1e で行う（持ち主の決定。[design.ja.md](./design.ja.md) §20.5 の「V1e で変えること」、§20.7 の V1e の行）。
- **理由:** nuget.org と GHCR に置いた版は取り消せない（nuget.org はパッケージを消せず、隠すだけで、隠した版も版を指せば入れられる。https://learn.microsoft.com/en-us/nuget/nuget-org/policies/deleting-packages 。GHCR の package を public にする操作も取り消せない。[design.ja.md](./design.ja.md) T26）。rc を nuget.org に置くと、プレリリースの版だけがあるあいだ、頁の `--version` のない `dotnet add package` が何をするかが .NET の文書に書かれていない状態に頼ることになる。rc を GitHub のプレリリースに限れば、公開の前の試しを、取り消せない場所を使わずにでき、nuget.org の最初の版は正式版になる。ローカルのフォルダーのフィードなら、試す人にトークンも要らない。
- **却下した案:** 今の `release.yml` のとおり、rc のパッケージも nuget.org に、rc のイメージも GHCR に push する。

### ID の接頭辞の予約を V1e で行う（V1c3e の記録の途中の持ち主の決定 D3、Issue #219）

- **決定:** nuget.org の ID の接頭辞 `ElasticLM.` を、持ち主が V1c3e の PR のマージの前に予約し、予約が受けられてからその PR をマージする。V1e の行から接頭辞の予約を外す（持ち主の決定。[design.ja.md](./design.ja.md) §20.5 の持ち主の作業、§20.7 の V1c3 の形の「V1c3e の Grill」）。
- **理由:** V1c3e で、頁から `nuget.config`（`ElasticLM.*` をローカルのフィードだけに割り当てていた）が外れ、頁は `--version` のない `dotnet add package ElasticLM.Client` を書く。`main` の頁は公開の前から GitHub で読めるので、予約がなければ、だれかが同じ名前のパッケージを nuget.org に置いたとき、頁のとおり打った読み手がそれを入れる。予約した接頭辞に合う ID のパッケージは、予約した持ち主のほかから送られれば nuget.org が断る（https://learn.microsoft.com/en-us/nuget/nuget-org/id-prefix-reservation ）。
- **却下した案:** 接頭辞の予約は V1e で行い、それまでのこの道を、README の Status の 1 行のほかに守りのない受け入れたリスクとする。
- **改めた:** 持ち主はこの決定を改め、V1c3e では予約しないとした（下の「ID の接頭辞を今予約し、V1c3e の PR のマージの条件にする」）。前提だった「頁から `nuget.config` が外れる」も、P1 で頁が `nuget.config` を持つ形に戻ったので成り立たない。

### 試しの期間の頁を nuget.org の形で書く（V1c3e の記録の途中の持ち主の決定 P1、Issue #219）

- **決定:** 利用者の文書は、読み手が今実際に手に入れられるものを書く。試しの期間（V1e の rc のプレリリースによる試しの公開のあと、正式版を出すかの判断まで）は GitHub のプレリリースなので、頁は、実行ファイルを「Pre-release」の印が付いたうちの最も新しいリリースの圧縮ファイルから入れ（GitHub の「Latest」はプレリリースを指さないと頁に書く）、パッケージはそのプレリリースの `.nupkg` を作業フォルダーの `packages` に置き、頁の `nuget.config`（`<clear/>`、相対の `packages` と nuget.org、`packageSourceMapping` で `ElasticLM.*` を `packages` だけに）と `dotnet add app package <パッケージ> --prerelease`（`--version` なし）で入れる。CI は、`steps:prebuilt name=elm` などで実行ファイルを、`steps:prebuilt name=packages` で `packages` の中身を、ジョブが作ったもの（パッケージは `-p:VersionSuffix=ci.<実行の番号>` で pack したプレリリースの版）に置き換え、頁の `nuget.config` のブロックと `dotnet add` の行は書いてあるとおりに流す（持ち主の決定。[design.ja.md](./design.ja.md) §20.7 の V1c3 の形の「V1c3e の Grill」）。
- **理由:** D2 で、正式版を出すまで nuget.org に `ElasticLM.*` は置かれない。頁を nuget.org の形で書くと、試しの期間の読み手が頁のとおり打っても入らず、持ち主の試しも頁と違う手順になる。プレリリースの形なら、頁の手順そのものが試しの期間に動き、CI も頁の `nuget.config` と `--prerelease` の行を書いてあるとおりに流せる。頁の割り当ては、`ElasticLM.*` を `packages` からだけ取らせるので、同じ名前のパッケージが nuget.org に置かれても入らない（SDK 10.0.402 で、より高い版を割り当てのない源に置いて試すと、`dotnet add` はその版を選び、復元は NU1102 で落ち、その版は入らなかった）。
- **却下した案:** 記録の途中の V1c3e の Q3 のとおり、頁を今から nuget.org の形（`nuget.config` も `--prerelease` もない `dotnet add package`）で書き、CI ではスクリプトが頁の外で `nuget.config` を書いてジョブのフィードに割り当てる。

### 入手の手順を 1 つの頁にまとめる（V1c3e の記録の途中の持ち主の決定 P2、Issue #219）

- **決定:** 実行ファイルとパッケージの入手の手順は、各 Tutorial の「始める前に」に置く（持ち主の決定。[design.ja.md](./design.ja.md) §20.7 の V1c3 の形の「V1c3e の Grill」）。
- **理由:** Tutorial ごとに要るもの（Tutorial 1 は `elm` と `ElasticLM.Licensing`、Tutorial 3 は加えて `elm-server` と `ElasticLM.Client`）が違い、各 Tutorial は独立にする（V1c3b の Grill の Q7）。手順を流す仕組みは頁ごとに作業フォルダーを作るので、別の頁に置いた手順は流れない。
- **却下した案:** 入手の手順を 1 つの頁にまとめ、各 Tutorial からリンクする。

### 利用者の文書の nuget.org の形への切り替えを正式版の公開のあとにする（V1c3e の記録の途中の持ち主の決定 P3、Issue #219）

- **決定:** 頁を nuget.org の形（`packages` のダウンロード、`nuget.config`、`--prerelease` のない形）に切り替えるのは、V1e で正式版のタグの前に 1 つの PR で行い、CI が頁を流して確かめる。ID の接頭辞 `ElasticLM.` を予約するか、先に公開して名前を取るかは、そのとき V1e で決める（持ち主の決定。[design.ja.md](./design.ja.md) §20.5 の持ち主の作業、§20.7 の V1e の行と「V1c3e の Grill」）。
- **理由:** 切り替えを 1 つの PR に収めれば、試しの期間の頁は一度も書き直さずに済み、切り替えの差分も 1 か所で読める。正式版のタグの前に CI で流せば、公開する版のサイトに確かめていない手順が載らない。
- **却下した案:** 正式版の公開のあとに頁を切り替える（公開したサイトが、しばらくプレリリースの形のまま残る）。

### ID の接頭辞を今予約し、V1c3e の PR のマージの条件にする（D3 を改めた持ち主の決定、Issue #219）

- **決定:** V1c3e では nuget.org の ID の接頭辞 `ElasticLM.` を予約しない。予約するか、先に公開して名前を取るかは、V1e で頁を nuget.org の形に切り替える PR の前に決める（P3）。`docs/releasing.md` の「V1e の前に予約するかを決める」は変えない（持ち主の決定。[design.ja.md](./design.ja.md) §20.5 の持ち主の作業、§20.7 の V1c3 の形の「V1c3e の Grill」の D3）。
- **理由:** 持ち主の言葉で「リリースできるかも分からないのに予約するのは気が引ける」。試しの期間に同じ名前のパッケージが nuget.org に置かれる道は、P1 の頁の `nuget.config` の割り当てが塞ぐ（置かれても、頁の `dotnet add` の行が落ちるだけで、その版は入らない）。V1e の切り替えで頁から割り当てが外れるとこの道が戻るので、その時点で V1e が決める。
- **却下した案:** 記録の途中の D3 のとおり、V1c3e の PR のマージの前に接頭辞を予約し、予約が受けられたことをマージの条件にする。
